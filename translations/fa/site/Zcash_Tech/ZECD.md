# zecd — سرور کیف‌پول با اولویت محافظت‌شده

zecd یک سرور کیف‌پول با اولویت محافظت‌شده برای Zcash است که بر پایه [librustzcash](https://github.com/zcash/librustzcash) ساخته شده و از طریق گویش JSON-RPC در Bitcoin Core در دسترس قرار می‌گیرد. این سرور به توسعه‌دهندگان و یکپارچه‌کنندگان پرداخت، یک API آشنا و سازگار با بیت‌کوین برای تعامل با Zcash ارائه می‌دهد — و در عین حال Orchard (خصوصی‌ترین استخر) را پیش‌فرض قرار می‌دهد. zecd که توسط [zec.rocks](https://zec.rocks) توسعه یافته است، برای جایگزینی قابلیت‌های کیف‌پول `zcashd` در استقرارهای مدرن و cloud-native طراحی شده است.

**نسخه فعلی:** 0.5.0-rc3 (13 ژوئیه 2026) — با پشتیبانی از Ironwood (NU6.3). از طریق `cargo install zecd` نصب کنید یا از ایمیج رسمی Docker استفاده کنید.

---

## خلاصه

- zecd یک **دیمن (سرور) کیف‌پول** است — نه یک فول‌نود. مدیریت کلیدها، اسکن، تولید اثبات و RPC را بدون استفاده از پروتکل P2P Zcash انجام می‌دهد.
- از **گویش JSON-RPC در Bitcoin Core** استفاده می‌کند: همان نام متدها، ساختار فیلدها، احراز هویت و کدهای خطا — بسیاری از کلاینت‌های RPC بیت‌کوین بدون هیچ تغییری با Zcash کار می‌کنند.
- **آدرس‌های Orchard (محافظت‌شده) پیش‌فرض هستند**؛ پشتیبانی از آدرس‌های شفاف (t-address) و Sapling نیازمند فعال‌سازی صریح برای هر کیف‌پول است.
- به یک **فول‌نود [Zebra](Zebra_Full_Node.md) خودمیزبان** از طریق JSON-RPC محلی متصل می‌شود — نیازی به lightwalletd نیست.
- **بدون حالت در طراحی**: کل کیف‌پول تنها از روی عبارت بازیابی قابل بازیابی است و همین ویژگی، پوشه داده را دورریختنی می‌کند.
- **جایگزین مستقیم zcashd نیست**: تنها زیرمجموعه‌ای از متدهای RPC Zcash را پیاده‌سازی می‌کند و تفاوت‌های طراحی عمدی برای حریم خصوصی و ایمنی دارد.
- کارمزدها از **ZIP-317** پیروی می‌کنند (محاسبه قطعی کارمزد)؛ کارمزدهای تعیین‌شده توسط کاربر رد می‌شوند.
- از **یادداشت‌های محافظت‌شده (ZIP-302)** از طریق رابط آشنای RPC بیت‌کوین پشتیبانی می‌کند.

## zecd چه مشکلی را حل می‌کند؟

`zcashd` نود و کیف‌پول اصلی و یکپارچه Zcash بود — که در سال 2016 از کدبیس C++ بیت‌کوین فورک شد. با گذشت زمان، این موضوع اصطکاک ایجاد کرد: نگهداری کد دشوار است، کیف‌پول به‌شدت به نود وابسته است و آدرس‌های شفاف به‌عنوان گزینه‌های درجه‌یک در کنار آدرس‌های محافظت‌شده ارائه می‌شوند.

zecd مسئولیت کیف‌پول را از اجماع جدا می‌کند. این یک **لایه کیف‌پول اختصاصی** است که میان برنامه‌ها و یک فول‌نود Zebra قرار می‌گیرد و موارد زیر را فراهم می‌کند:

- یک پیاده‌سازی تمیز و مدرن Rust بر پایه librustzcash (همان کتابخانه‌ای که Zodl و Zingo را به کار می‌اندازد)
- طراحی با حریم خصوصی به‌صورت پیش‌فرض (آدرس‌های Orchard، مگر اینکه به‌گونه‌ای دیگر پیکربندی شود)
- یک رابط RPC سازگار با بیت‌کوین که نیاز به یادگیری ابزارهای مختص Zcash را از بین می‌برد
- معماری بدون حالت و قابل بازیابی از seed، مناسب برای استقرارهای کانتینری و ابری

## معماری

zecd در یک مدل سه‌لایه عمل می‌کند:

```
Your app / Bitcoin RPC client
        ↓  JSON-RPC
       zecd
   (keys, scanning, proving, RPC)
        ↓  JSON-RPC (local only)
       Zebra
   (full node — consensus, mempool, chain data)
```

zecd **منحصراً از طریق JSON-RPC محلی** با Zebra ارتباط برقرار می‌کند — بدون شبکه نظیربه‌نظیر، بدون ایندکسرهای شخص ثالث و بدون lightwalletd. اتصال Zebra عمداً فقط محلی است: zecd از ارسال اطلاعات احراز هویت به میزبانی که به‌صورت سراسری قابل مسیریابی است خودداری می‌کند، مگر اینکه به‌صراحت برای یک تونل امن خارج از باند (مثلاً WireGuard یا SSH) پیکربندی شده باشد.

## ویژگی‌های کلیدی

### اولویت با محافظت‌شده، Orchard به‌صورت پیش‌فرض

zecd از آدرس‌های یکپارچه Orchard به‌عنوان نوع آدرس پیش‌فرض استفاده می‌کند. استخرهای Sapling و شفاف (t-address) نیازمند پیکربندی صریح برای هر کیف‌پول هستند. این طراحی خطر ارسال‌های شفاف تصادفی را کاهش می‌دهد — دامی رایج برای حریم خصوصی در ابزارهای قدیمی‌تر Zcash.

سیاست حریم خصوصی برای هر فراخوانی یا به‌صورت سراسری در `[spend] privacy_policy` قابل پیکربندی است:

| سیاست | رفتار |
|--------|----------|
| `AllowRevealedRecipients` (پیش‌فرض) | ارسال به گیرندگان شفاف را مجاز می‌کند؛ مبلغ و گیرنده را on-chain آشکار می‌کند |
| `AllowRevealedAmounts` | ارسال‌های بین‌استخری (Sapling↔Orchard) را مجاز می‌کند اما گیرندگان شفاف را رد می‌کند |
| `FullPrivacy` | فقط ارسال‌های کاملاً محافظت‌شده درون یک استخر؛ گیرندگان شفاف و ارسال‌های بین‌استخری را رد می‌کند |
| `AllowFullyTransparent` | ارسال‌های t→t را که از UTXOهای شفاف تأمین می‌شوند نیز مجاز می‌کند |

### سازگاری با RPC در Bitcoin Core

zecd گویش JSON-RPC در Bitcoin Core را با انطباق در موارد زیر پیاده‌سازی می‌کند:

- نام متدها (مثلاً `getblockchaininfo`، `getbalance`، `getnewaddress`، `listtransactions`، `sendtoaddress`، `sendmany`)
- نام و نوع فیلدها در پاسخ‌ها
- ساختار پاکت JSON-RPC 1.0
- احراز هویت Basic، ورودی‌های `rpcauth` و احراز هویت با فایل cookie
- کدهای خطا و نگاشت وضعیت HTTP (HTTP 500 همراه با بدنه خطا، معناشناسی 401)

این یعنی بسیاری از کتابخانه‌های پرداخت بیت‌کوین، یکپارچه‌سازی‌های صرافی‌ها و ابزارهای پایش موجود می‌توانند با تغییرات اندک یا بدون هیچ تغییری در کد، از طریق zecd با Zcash تعامل کنند.

مجموعه آزمون انطباق (بیش از 140 بررسی) روی هر PR در برابر یک دیمن regtest زنده اجرا می‌شود و روی testnet عمومی نیز اعتبارسنجی شده است.

### یادداشت‌های محافظت‌شده (ZIP-302)

zecd قابلیت یادداشت محافظت‌شده Zcash را از طریق رابط آشنای RPC بیت‌کوین در دسترس قرار می‌دهد — چیزی که در ابزارهای استاندارد بیت‌کوین وجود ندارد:

- `sendtoaddress` یک یادداشت hex اختیاری را به‌عنوان یک پارامتر اضافی در انتها می‌پذیرد (حداکثر 512 بایت؛ برای گیرندگان شفاف رد می‌شود)
- ورودی‌های تاریخچه تراکنش در `listtransactions` و `gettransaction`، هنگامی که یک خروجی دارای یادداشت باشد، شامل فیلدهای `memo` (hex) و `memoStr` (متن رمزگشایی‌شده) هستند
- ارسال‌های با مبلغ صفر به یک گیرنده محافظت‌شده برای کاربردهای فقط-یادداشت پشتیبانی می‌شوند (الگوی «memo-only-send» در `z_sendmany`)

این ویژگی، zecd را برای برنامه‌هایی که به پیام‌رسانی خصوصی و on-chain در کنار پرداخت‌ها نیاز دارند مناسب می‌سازد.

### بدون حالت در طراحی

zecd **هیچ حالت off-chainای را که بازیابی صرفاً از seed نتواند بازسازی کند، ذخیره نمی‌کند**. پایگاه داده کیف‌پول (`data.sqlite`) به‌طور کامل از عبارت بازیابی قابل استخراج است — وجوه محافظت‌شده بدون قید و شرط بازیابی می‌شوند؛ وجوه شفاف تا gap limit پیکربندی‌شده بازیابی می‌شوند.

برای بازیابی یک کیف‌پول از seed:

```sh
zecd init --restore --birthday <block-height>
```

این ویژگی پوشه داده را **دورریختنی** می‌کند: کانتینری بدون volume پایدار که در هر بار راه‌اندازی از seed بازسازی می‌شود، هیچ چیز حیاتی را از دست نمی‌دهد. اپراتورها مسئول پیگیری آدرس‌هایی هستند که در اختیار دیگران قرار می‌دهند — zecd تنها زمانی آدرس‌ها را به خاطر می‌سپارد که وجوهی را on-chain دریافت کرده باشند.

برچسب‌ها عمداً وجود ندارند. از آنجا که برچسب‌ها هیچ منبع on-chain ندارند و نمی‌توان آن‌ها را از seed بازسازی کرد، zecd به‌سادگی از آن‌ها پشتیبانی نمی‌کند. فراخوانی متدهای برچسب، خطای `method-not-found` (`-32601`) را برمی‌گرداند.

### بدون وابستگی به lightwalletd

zecd بلوک‌های فشرده، وضعیت درخت و دید mempool را مستقیماً از JSON-RPC Zebra به دست می‌آورد. هیچ lightwalletd برای راه‌اندازی یا نگهداری وجود ندارد — و این پیچیدگی عملیاتی را برای استقرارهای خودمیزبان کاهش می‌دهد.

### استقرارهای cloud-native و کانتینری

معماری بدون حالت zecd برای محیط‌های Docker و Kubernetes طراحی شده است:

- استک کامل Compose Docker (`zebra → zecd`) در مخزن موجود است
- اندپوینت سلامت روی پورت `9233` با readiness probeهای قابل پیکربندی (`synced` یا `connected`)
- گزینه لاگ‌گیری ساختاریافته JSON برای پایپ‌لاین‌های تجمیع لاگ
- کارمزدهای قطعی ZIP-317 — بدون اوراکل کارمزد یا پیکربندی دستی کارمزد
- `bootstrap_from_keys` (به‌طور پیش‌فرض فعال): یک پوشه داده خالی در کنار `keys.toml`، کیف‌پول را هنگام راه‌اندازی به‌طور خودکار بازسازی می‌کند — با mount کردن یک Secret و شروع با یک PVC خالی، استقرار را انجام دهید

## مدل‌های نگهداری کلید

zecd از سه مدل نگهداری کلید پشتیبانی می‌کند که برای الزامات استقرار و امنیتی مختلف مناسب هستند:

### 1. رمزنگاری‌نشده (پیش‌فرض — باز شدن خودکار قفل)

عبارت بازیابی موجود در `keys.toml` با یک **فایل هویت age** (`identity.txt`) رمزنگاری می‌شود. با `auto_unlock = true` پیش‌فرض، seed هنگام راه‌اندازی در حافظه رمزگشایی می‌شود تا ارسال‌ها بدون نظارت انجام شوند و نیازی به فراخوانی `walletpassphrase` نباشد.

مناسب برای: پردازشگرهای پرداخت خودکار، کیف‌پول‌های داغ صرافی‌ها، محیط‌های توسعه‌دهندگان.

```sh
zecd init --datadir ./data --wallet default --account-name primary
```

> در mainnet، `identity.txt` را **خارج از** پوشه داده ذخیره کنید — هر کسی که هر دو فایل را بخواند، اختیار خرج کردن وجوه را دارد.

### 2. رمزنگاری‌شده (حفاظت‌شده با عبارت عبور)

عبارت بازیابی به‌جای یک فایل هویت، با یک عبارت عبور (age scrypt) رمزنگاری می‌شود. کیف‌پول در حالت قفل شروع به کار می‌کند؛ `walletpassphrase "<pass>" <timeout>` آن را برای مدت زمان مشخص‌شده باز می‌کند و پس از پایان زمان، به‌طور خودکار دوباره قفل می‌کند — مطابق با رفتار کیف‌پول رمزنگاری‌شده در Bitcoin Core.

مناسب برای: کیف‌پول‌های داغی که در آن‌ها اختیار خرج بدون نظارت لازم نیست؛ گردش‌کارهای تعاملی اپراتور.

```sh
zecd init --datadir ./data --encrypt
# later: walletpassphrase "my-passphrase" 300
```

### 3. فقط-مشاهده (UFVK — بدون کلید خرج)

با یک Full Viewing Key یکپارچه (UFVK) که از کیف‌پول دیگری صادر شده است، مقداردهی اولیه می‌شود. می‌تواند وجوه را دریافت کند، اسکن کند و موجودی‌ها را گزارش دهد — اما نمی‌تواند تراکنش‌ها را امضا کند. برای پایش، صدور فاکتور یا نودهای حسابرسی که از کیف‌پول امضاکننده جدا هستند، ایده‌آل است.

```sh
# On the signing wallet's host:
zecd export-ufvk

# On the watch-only host:
zecd init --datadir ./data-watch --ufvk "uview1..." --birthday <height>
```

## پشتیبان‌گیری و بازیابی

وجوه **تنها از روی عبارت بازیابی** قابل بازیابی هستند. همه چیز دیگر صرفاً کش است.

| مورد | مکان | از چه چیزی محافظت می‌کند | پشتیبان‌گیری؟ |
|----------|----------|-----------------|----------|
| **عبارت بازیابی 24 کلمه‌ای** | یک بار هنگام `zecd init` نمایش داده می‌شود | وجوه — از دست دادن آن = از دست رفتن دائمی | **بله — آفلاین (کاغذ/HSM)** |
| `keys.toml` | `<wallet dir>/keys.toml` | seed رمزنگاری‌شده + birthday + شبکه | **بله — به‌عنوان یک Secret** |
| `identity.txt` | `[keys] age_identity` | `keys.toml` را رمزگشایی می‌کند (اختیار خرج) | **بله — جدا از `keys.toml`** |
| ارتفاع birthday | داخل `keys.toml` | بازیابی را سریع می‌کند (هر ارتفاعی پیش از اولین تراکنش) | همراه با عبارت بازیابی ثبت کنید |
| `data.sqlite` | `<wallet dir>/data.sqlite` | کش کیف‌پول — هنگام بازیابی از seed بازسازی می‌شود | خیر — دورریختنی |
| `blocks/` | `<wallet dir>/blocks/` | کش بلوک‌های فشرده | خیر — هرگز منتقل نکنید؛ ممکن است حجم زیادی پیدا کند |
| `.cookie` | `<datadir>/.cookie` | cookie موقت RPC | خیر — هنگام راه‌اندازی دوباره تولید می‌شود |

> **پوشه داده باید روی همان میزبان و به‌صورت محلی باشد.** قفل تک‌نمونه‌ای zecd (`<datadir>/.lock`) یک قفل مشورتی سیستم‌عامل است — میان میزبان‌ها عمل نمی‌کند. هرگز یک پوشه داده را به‌صورت خواندنی-نوشتنی میان چند ماشین به اشتراک نگذارید (NFS، `ReadWriteMany` در Kubernetes) — دو نمونه zecd پایگاه داده کیف‌پول را خراب می‌کنند. در Kubernetes از volumeهای `ReadWriteOnce` استفاده کنید.

## فهرست مجاز متدهای RPC

برای استقرارهایی که نشت اطلاعات احراز هویت در آن‌ها فاجعه‌بار خواهد بود، zecd از محدود کردن سطح RPC به زیرمجموعه‌ای انتخاب‌شده از متدها پشتیبانی می‌کند:

```toml
[rpc]
allowed_methods = ["getblockchaininfo", "getbalance", "getnewaddress", "listtransactions"]
```

هر متدی که در فهرست نباشد، `-32601` (HTTP 404) را برمی‌گرداند — که از متدی که اصلاً وجود ندارد قابل تشخیص نیست؛ بنابراین یک سرور محدودشده هیچ اطلاعاتی درباره آنچه غیرفعال کرده است افشا نمی‌کند. یک صادرکننده فاکتور فقط-دریافت می‌تواند `sendtoaddress`، `sendmany` و `stop` را غیرفعال کند تا دامنه آسیب ناشی از یک کلاینت به خطر افتاده را به حداقل برساند.

## تفاوت‌های کلیدی با RPC در Bitcoin Core

توسعه‌دهندگانی که از ابزارهای بیت‌کوین یا zcashd مهاجرت می‌کنند، باید از این تفاوت‌های عمدی آگاه باشند:

| رفتار | Bitcoin Core | zecd |
|----------|-------------|------|
| قالب آدرس | `1...` / `bc1...` | `u1...` (آدرس یکپارچه Orchard) — توسط کلاینت‌هایی که رشته را تجزیه می‌کنند، به‌عنوان آدرس بیت‌کوین قابل تجزیه نیست |
| برچسب‌ها | ذخیره‌ساز کامل برچسب | پیاده‌سازی نشده — `setlabel`، `listlabels` و غیره `-32601` را برمی‌گردانند |
| کارمزدها | قابل تنظیم توسط کاربر؛ بازار کارمزد | فقط ZIP-317 قطعی؛ `settxfee`، `fee_rate` و `subtractfeefromamount` با `-8` رد می‌شوند |
| یادداشت‌ها | پشتیبانی نمی‌شود | `sendtoaddress` یادداشت hex را می‌پذیرد؛ تاریخچه دارای فیلدهای `memo` + `memoStr` است |
| تأییدها برای خرج | 1 | 3 (باقی‌مانده تراکنش‌های خودتان) / 10 (شخص ثالث) — قابل پیکربندی از طریق `trusted_confirmations` / `untrusted_confirmations` |
| `listsinceblock` هنگام reorg | تا نقطه فورک به عقب برمی‌گردد | اگر cursor بر اثر reorg حذف شود، `-5` (Block not found) را برمی‌گرداند — با یک فراخوانی بدون پارامتر، مبنا را دوباره تنظیم کنید |
| گیرندگان تکراری در `sendmany` | خطا | تجزیه‌گر JSON پیش از آنکه zecd آن‌ها را ببیند، موارد تکراری را ادغام می‌کند (آخرین مورد اعمال می‌شود) — یک آدرس را دو بار فهرست نکنید |
| موجودی در طول همگام‌سازی اولیه | مسدود می‌شود یا warm-up | موجودی جزئی ارائه می‌دهد — خودکارسازی را مشروط به `GET /readyz` کنید (تا زمان همگام‌سازی کامل و تخلیه backlog بهبود، 503 برمی‌گرداند) |
| `minconf 0` در `getbalance` | موجودی 0-conf | به‌صورت 1 ارائه می‌شود — یک note محافظت‌شده هرگز پیش از استخراج قابل خرج نیست |

## شروع سریع

**پیش‌نیازها:** Zebra که به‌صورت محلی با `rpc.listen_addr = 127.0.0.1:18234` (testnet) در حال اجرا باشد.

از crates.io نصب کنید (0.4.3+):

```sh
cargo install zecd
```

یا از سورس بسازید:

```sh
git clone https://github.com/zecrocks/zecd && cd zecd
cargo build --release
```

```sh
# 1. Initialize a testnet wallet (generates a 24-word mnemonic and an account)
zecd --datadir ./data --testnet init --wallet default --account-name primary

# 2. Start the daemon (syncs in background, serves JSON-RPC on port 18232)
zecd --datadir ./data --testnet \
    --rpcuser zec --rpcpassword secret --rpcbind 127.0.0.1 --rpcport 18232
```

**تعامل از طریق curl:**

```sh
curl -s --user zec:secret --data-binary \
  '{"jsonrpc":"1.0","id":"1","method":"getblockchaininfo","params":[]}' \
  -H 'content-type: text/plain;' http://127.0.0.1:18232/
```

**تعامل از طریق Python (با استفاده از یک کتابخانه RPC بیت‌کوین):**

```python
from bitcoinrpc.authproxy import AuthServiceProxy
rpc = AuthServiceProxy("http://zec:secret@127.0.0.1:18232")
print(rpc.getblockchaininfo())
addr = rpc.getnewaddress()          # returns a u1... Orchard Unified Address
print(rpc.getbalance())
print(rpc.listtransactions("*", 20))

# Send with a shielded memo
rpc.sendtoaddress(addr, 0.001, "", "", False, "48656c6c6f205a6563617368")  # hex memo
```

**بازیابی از seed:**

```sh
zecd --datadir ./data init --restore --birthday 2500000
# paste your 24-word mnemonic when prompted
```

## zecd در برابر zcashd در برابر Zaino

| | zcashd | Zaino | zecd |
|--|--------|-------|------|
| نقش | فول‌نود + کیف‌پول | ایندکسر (جایگزین lightwalletd) | فقط سرور کیف‌پول |
| زبان | C++ | Rust | Rust |
| وضعیت | منسوخ | فعال | فعال (v0.5.0-rc3، ژوئیه 2026) |
| استخر پیش‌فرض | شفاف | N/A | Orchard (محافظت‌شده) |
| گویش RPC | مختص zcashd | gRPC (lightwalletd) | Bitcoin Core JSON-RPC |
| نیاز به فول‌نود | بله (خودش) | Zebra یا zcashd | Zebra |
| بازیابی بدون حالت | خیر | N/A | بله (فقط از seed) |
| یادداشت‌های محافظت‌شده | بله (`z_sendmany`) | N/A | بله (رابط RPC بیت‌کوین) |
| فقط-مشاهده (UFVK) | بله | بله | بله |
| Cloud-native | خیر | جزئی | بله |
| نصب | ساخت/باینری | ساخت | `cargo install zecd` |
