# Zinder نمایه‌ساز

Zinder یک نمایه‌ساز Zcash خودمیزبان است که با Rust نوشته شده و توسط Zcash Foundation منتشر شده است. این ابزار زنجیره را فقط یک‌بار از یک نود کامل Zebra یا Zakura می‌خواند، یک نمای سازگار از آن ذخیره می‌کند و هم‌زمان آن را در اختیار چندین کیف‌پول، برنامه و کاوشگر قرار می‌دهد. کیف‌پول‌های سبک موجود می‌توانند از طریق یک آداپتور سازگار با lightwalletd به آن دسترسی پیدا کنند.

> **Zinder آلفا است.** README آن می‌گوید API بومی، سطح سازگاری lightwalletd، چیدمان‌های ذخیره‌سازی و توپولوژی استقرار تغییر خواهند کرد و انتشار نسخه برچسب‌خورده تضمین‌کننده پایداری نیست. نسخه‌های دقیق را ثابت نگه دارید و انتظار ارتقاهای ناسازگار را داشته باشید.

## خلاصه

* **Zebra** یا **Zakura** زنجیره را اعتبارسنجی می‌کند. **Zinder** آنچه را نود در اختیار دارد نمایه‌سازی می‌کند و به کلاینت‌ها ارائه می‌دهد.
* دو راه برای اتصال وجود دارد: API gRPC بومی Zinder یعنی `WalletQuery`، و آداپتوری جداگانه که با پروتکل lightwalletd یعنی `CompactTxStreamer` کار می‌کند؛ بنابراین کیف‌پول‌های ساخته‌شده برای lightwalletd می‌توانند بدون تغییر کد به آن متصل شوند.
* هر خواندن به یک وضعیت زنجیره (یک «دوره») متصل است؛ بنابراین یک دسته همگام‌سازی هرگز داده‌های دو سر زنجیره رقیب را با هم ترکیب نمی‌کند. کلیدها و اسکن محافظت‌شده در کیف‌پول باقی می‌مانند.
* این سامانه برای یک اپراتور ساخته شده است که یک نود را اجرا می‌کند و به چندین مصرف‌کننده سرویس می‌دهد. نقاط پایانی عمومی را پشت TLS، احراز هویت و محدودیت نرخِ تحت کنترل خودتان قرار دهید.
* انتشار نسخه‌ها سریع است (از 0.7.0 تا 0.12.0 بین 10 و 14 نوامبر 2026) و چند نسخه نیز تغییرات ناسازگار داشته‌اند. پیش از هر ارتقا، گزارش تغییرات را بخوانید.

## Zinder چه جایگاهی دارد؟

کیف‌پول‌های سبک هرگز مستقیماً با فول‌نود ارتباط برقرار نمی‌کنند. آن‌ها برای بلوک‌های فشرده، وضعیت درخت و داده‌های تراکنش از یک نمایه‌ساز درخواست می‌فرستند (به [نودهای Lightwallet](/zcash-tech/lightwallet-nodes) مراجعه کنید). اکنون در اکوسیستم Zcash چند نمایه‌ساز وجود دارد که این کار را انجام می‌دهند:

| نمایه‌ساز | زبان | نگه‌دارنده | ارتباط با | توضیحات |
|:--|:--|:--|:--|:--|
| lightwalletd | Go | ECC / کامیونیتی Zcash | Zebra یا zcashd | سرور اصلی کیف‌پول سبک |
| [Zaino](/zcash-tech/zaino) | Rust | Zingo Labs | Zebra یا zcashd | نمایه‌ساز اختیاری در پشته Z3 |
| [Ztreamer](https://github.com/zcashlabs/ztreamer) | Rust | zcashlabs | نود Zakura تعبیه‌شده | به معیارسنجی [Zaino در برابر Ztreamer](/zcash-tech/indexer-benchmark-zaino-vs-ztreamer) مراجعه کنید |
| **Zinder** | Rust | Zcash Foundation | Zebra 7.0.0 یا Zakura 1.8.6 (نود آرشیوی) | آلفا. API بومی به‌همراه آداپتور lightwalletd و خواندن اختیاری برای کاوشگر |

مستندات Zinder درباره زمان مناسب استفاده از آن صریح است: این ابزار زمانی بهترین انتخاب است که دسترسی به زنجیره باید پس از پایان اجرای یک فرایند کیف‌پول ادامه یابد، به چند مصرف‌کننده مستقل سرویس بدهد یا از کد هر کیف‌پول جدا بماند. برای یک کیف‌پول واحد با اتصال تنگاتنگ، نمایه‌ساز تعبیه‌شده می‌تواند ساده‌تر باشد و مصرف‌کننده‌ای که فقط به داده‌های موجود در نود نیاز دارد می‌تواند مستقیماً از RPC Zebra استفاده کند.

## ساختار آن

Zinder کارها را میان فرایندهای جداگانه تقسیم می‌کند که هرکدام یک وظیفه دارند:

| زمان اجرا | نقش |
|:--|:--|
| `zinder-ingest` | تنها نویسنده در ذخیره‌ساز canonical زنجیره (RocksDB). نود را دنبال می‌کند، بازسازمان‌دهی‌ها را مدیریت می‌کند و وضعیت زنده مم‌پول را نگه می‌دارد |
| `zinder-projector` | تنها نویسنده در ذخیره‌ساز کیف‌پول. نمای زنجیره متناسب با کیف‌پول را می‌سازد و دنبال می‌کند |
| `zinder-query` | API بومی gRPC `WalletQuery` را ارائه می‌دهد |
| `zinder-compat-lightwalletd` | API `CompactTxStreamer` lightwalletd را بر پایه همان داده‌ها ارائه می‌دهد |

یک لایه اختیاری برای کاوشگر (`zinder-explorer` به‌همراه `ExplorerQuery`) خلاصه بلوک‌ها، جزئیات تراکنش‌ها، نماهای مم‌پول و جست‌وجو را ارائه می‌دهد؛ آداپتوری اختیاری نیز APIهای REST و WebSocket کاوشگر CipherScan را ارائه می‌کند. هیچ‌کدام بخشی از ایمیج‌های انتشار نیستند.

هر زمان اجرا `/healthz`، `/readyz` و `/metrics` را ارائه می‌دهد. خوانشگرها فقط زمانی وضعیت آماده را گزارش می‌کنند که نسخه‌هایشان از ذخیره‌ساز زنجیره و ذخیره‌ساز کیف‌پول دقیقاً به یک وضعیت زنجیره اشاره کنند.

## روش‌های اتصال

* **کیف‌پول‌های سبک موجود** یکپارچه‌سازی lightwalletd خود را حفظ می‌کنند و آن را به `zinder-compat-lightwalletd` متصل می‌کنند. مستندات Zinder سازگاری پروتکل را از پشتیبانی جدا می‌داند: یک کیف‌پول فقط پس از آن پشتیبانی‌شده محسوب می‌شود که نسخه فعلی آن گواهی آزمون سرتاسری را بگذراند. نسخه 0.10.0 فیلد نسخه پروتکل `GetLightdInfo` را اصلاح کرد تا Zingo بتواند همگام‌سازی کند.
* **کلاینت‌های بومی** برای خواندن‌های متصل به وضعیت مشخص، بلوک‌های فشرده، جریان رویدادهای زنجیره و مم‌پول و نتایج انتشار با علت‌های ردِ دارای نوع مشخص، `zinder-query` را فراخوانی می‌کنند.
* **برنامه‌های Rust** از crate `zinder-client` استفاده می‌کنند؛ یک SDK با اولویت اتصال از راه دور که بدون پیوند دادن پشته ذخیره‌سازی به `zinder-query` متصل می‌شود.
* **کاوشگرها و بک‌اندها** خواندن‌های کیف‌پول را با لایه اختیاری `ExplorerQuery` ترکیب می‌کنند.

## اجرای آن

راهنمای شروع سریع بالادستی ابتدا نودی را با پشته [Z3](/zcash-tech/z3-stack) راه‌اندازی می‌کند و سپس از checkout Zinder با Docker Compose، Zinder را اجرا می‌کند:

```bash
# In the Z3 checkout
Z3_NETWORK=testnet docker compose up -d

# In the Zinder checkout
docker compose --env-file deploy/.env.testnet \
  -f deploy/docker-compose.yml up -d --build
```

فایل‌های env برای Mainnet و یک نود Zakura (`deploy/.env.zakura-mainnet`، `deploy/.env.zakura-testnet`) در کنار آن قرار دارند. از نسخه 0.11.0، فایل Compose دیگر Z3 را به‌طور پیش‌فرض فرض نمی‌کند: فایل env باید شبکه، volume کوکی و نشانی RPC نود را مشخص کند.

درگاه‌های پیش‌فرض میزبان (در Testnet عدد 10000 به آن‌ها اضافه می‌شود):

| سرویس | Mainnet | Testnet |
|:--|:--|:--|
| gRPC بومی `WalletQuery` | 9102 | 19102 |
| gRPC سازگار با lightwalletd | 9067 | 19067 |
| آمادگی: دریافت / پروژکتور / پرس‌وجو / سازگاری | 9105 / 9110 / 9106 / 9107 | 19105 / 19110 / 19106 / 19107 |

هر دو درگاه کیف‌پول به loopback متصل می‌شوند. با دستور زیر آن‌ها را بررسی کنید:

```bash
grpcurl -plaintext -d '{}' 127.0.0.1:19102 zinder.v1.wallet.WalletQuery/ServerInfo
grpcurl -plaintext -d '{}' 127.0.0.1:19067 cash.z.wallet.sdk.rpc.CompactTxStreamer/GetLightdInfo
```

روش‌های دیگر استقرار:

* **ایمیج‌های انتشار** در `ghcr.io/zcashfoundation/`: چهار زمان اجرا، به‌علاوه `zinder-wallet-serving` (دریافت، پروژکتور و پرس‌وجوی بومی در یک کانتینر برای میزبان‌هایی که می‌توانند یک volume را به یک کانتینر متصل کنند؛ بدون آداپتور lightwalletd) و `zinder-canonical-runtime` (فقط دریافت).
* **باینری‌های Linux** برای x86-64 (به پردازنده x86-64-v3 نیاز دارد) و AArch64، با glibc نسخه 2.34 یا جدیدتر. Debian 12 خط پایه گواهی‌شده است. هر نسخه یک SBOM و گواهی منشأ امضاشده SLSA ارائه می‌کند.

### نود باید چه چیزی فراهم کند؟

* یک **نود آرشیوی**. از نسخه 0.11.0، `zinder-ingest` از راه‌اندازی در برابر نود هرس‌شده خودداری می‌کند.
* Zebra **7.0.0** یا Zakura **1.8.6**. مسیرهای انتشار این دو نسخه نود را گواهی می‌کنند.
* برای ایمیج `zinder-wallet-serving`، **نقطه پایانی gRPC نمایه‌ساز** نود (`ZINDER_NODE__INDEXER_GRPC_ADDR`، Zebra یعنی `indexer_listen_addr`، درگاه 8155 در Mainnet). نمایه‌ساز Zakura در نشانی‌ای غیر از loopback به TLS دوسویه نیاز دارد؛ Zinder از نسخه 0.11.0 از آن پشتیبانی می‌کند.

### منابع موردنیاز برای Mainnet

بر اساس راهنمای اجرای سرویس کیف‌پول:

* دست‌کم **8 گیگابایت حافظه**. اوج مصرف اندازه‌گیری‌شده: حدود 2.6 GiB برای دریافت، حدود 2.7 GiB برای پروژکتور هنگام ساخت و تا حدود 1.4 GiB برای پرس‌وجو.
* هنگام ساخت ذخیره‌ساز کیف‌پول Mainnet، حدود **130 گیگابایت فضای خالی** روی volume نگه دارید.
* یک ساخت اندازه‌گیری‌شده Mainnet از پیدایش، حدود **چهار ساعت** برای ذخیره‌ساز زنجیره (با حدود 310 گیگابایت فضای موقت) و **بیش از دو ساعت** برای ذخیره‌ساز کیف‌پول زمان برد. مهلت‌های ساخت ارائه‌شده فقط برای Testnet کافی‌اند: آن‌ها را برای Mainnet دست‌کم به 24 ساعت و 12 ساعت افزایش دهید، وگرنه ساخت دوباره آغاز می‌شود و هرگز به پایان نمی‌رسد.

## اشتباهات رایج

**رفتار با آن مانند نرم‌افزار آماده تولید.** پروژه خود را آلفا می‌نامد. به گفته خود پروژه، اجرای Compose محلیِ بدون خطا «به‌تنهایی گواهی تولید نیست».

**اتصال آن به نود هرس‌شده.** فرایند دریافت هنگام راه‌اندازی خارج می‌شود. از نود آرشیوی Zebra یا Zakura استفاده کنید.

**در معرض اینترنت قرار دادن مستقیم درگاه‌های gRPC.** هر دو درگاه کیف‌پول به دلیلی به loopback متصل می‌شوند. پیش از باز کردن آن‌ها به اینترنت، TLS، احراز هویت، محدودیت نرخ و سهمیه‌ها را پشت پروکسی‌ای قرار دهید که خودتان کنترل می‌کنید.

**ارتقای زمان‌های اجرا یکی‌یکی.** چند نسخه، بازنگری پروتکل بومی یا قالب ذخیره‌ساز را تغییر می‌دهند. سرویس‌های Zinder را با هم ارتقا دهید و کلاینت‌های بومی را نیز در همان مرحله به‌روزرسانی کنید.

**فرض اینکه کیف‌پول به‌خاطر پشتیبانی از پروتکل، پشتیبانی می‌شود.** آداپتور lightwalletd با پروتکل کار می‌کند، اما Zinder تنها پس از گواهی سرتاسری نسخه فعلی کیف‌پول، آن را پشتیبانی‌شده اعلام می‌کند.
