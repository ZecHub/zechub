# راستی‌آزمایی نسخه‌های منتشرشده‌ی Zcash

## خلاصه

- دانلود یک فایل اجرایی Zcash با دریافت همان فایلی که پروژه منتشر کرده یکی نیست. راستی‌آزمایی روشی است که با آن تفاوت این دو را تشخیص می‌دهید.
- یک checksum ثابت می‌کند که فایل سالم به دست شما رسیده است. یک **امضای دیجیتال** ثابت می‌کند چه کسی آن را تولید کرده است. شما به هر دو نیاز دارید و checksum به‌تنهایی چیز زیادی را ثابت نمی‌کند.
- Zebra یک فایل `SHA256SUMS` به همراه یک بسته‌ی **Sigstore** منتشر می‌کند که نسخه‌ی منتشرشده را به یک workflow مشخص در GitHub Actions، یک tag و یک commit گره می‌زند؛ بدون اینکه نیازی به مدیریت کلید باشد.
- Zallet امضاهای دیجیتال جداشده‌ی **GPG** (`.asc`) را در کنار SLSA provenance و یک SBOM منتشر می‌کند.
- کلید امضای Zcash در سال 2026 از Electric Coin Company به Zcash Open Development Lab (ZODL) تغییر کرد. اگر نسخه‌های قدیمی‌تر را راستی‌آزمایی کرده‌اید، به کلید جدید نیاز دارید؛ و بیانیه‌ی انتقال با هر دو کلید امضا شده است، بنابراین می‌توانید خودِ این تغییر کلید را هم راستی‌آزمایی کنید.
- `gpg` **زیرکلیدی** را گزارش می‌کند که فایل را امضا کرده است، نه کلید اصلی‌ای که در اطلاعیه‌ها نام برده می‌شود. اثر انگشتی که اشتباه به نظر می‌رسد معمولاً یک زیرکلید است، نه یک حمله.
- اگر راستی‌آزمایی ناموفق بود، فایل اجرایی را اجرا نکنید.

*راستی‌آزمایی‌شده با Zebra `v6.3.0` و Zallet `v0.1.0-beta.2` در تاریخ 2026-08-18.*

## چرا این موضوع برای Zcash اهمیت بیشتری دارد

یک فایل اجرایی دست‌کاری‌شده‌ی کیف‌پول می‌تواند کلید خرج‌کننده یا کلید مشاهده را به بیرون نشت دهد. برخلاف یک رمز عبور لورفته، این از دست رفتن دائمی است: نه امکان بازگشت وجود دارد، نه برگشت وجه و نه میز پشتیبانی. تراکنش‌های محافظت‌شده از آنچه *on-chain* رخ می‌دهد محافظت می‌کنند؛ اما وقتی نرم‌افزاری که اجرا می‌کنید پیش از رسیدن به دست شما جایگزین شده باشد، هیچ محافظتی ارائه نمی‌دهند.

این یکی از معدود مسیرهای حمله است که در آن تضمین‌های حریم خصوصی پروتکل اساساً موضوعیتی ندارند. راستی‌آزمایی لایه‌ای است که این مسیر را پوشش می‌دهد.

## مدل تهدید: راستی‌آزمایی چه چیزی را شناسایی می‌کند و چه چیزی را نه

**شناسایی می‌کند:**

- یک mirror دست‌کاری‌شده یا فایل تغییریافته‌ای که از جایی غیر از صفحه‌ی انتشار پروژه ارائه می‌شود.
- مبادله‌ی فایل در یک حمله‌ی مرد میانی هنگام دانلود.
- یک CDN نفوذشده یا یک میزبان توزیع ربوده‌شده.
- خرابی تصادفی فایل در حین انتقال.

**شناسایی نمی‌کند:**

- نگه‌دارنده‌ای که کد مخرب را امضا می‌کند. امضای دیجیتال به‌درستی تأیید می‌شود؛ این امضا منشأ را ثابت می‌کند، نه نیت را.
- یک میزبان build نفوذشده که یک فایل امضاشده اما مخرب تولید می‌کند. Buildهای تکرارپذیر و گواهی‌های provenance برای محدود کردن همین مورد وجود دارند.
- کلیدی که آن را از همان منبع نفوذشده‌ی فایل اجرایی گرفته‌اید. اگر مهاجم هم فایل و هم کلیدی را که با آن فایل را بررسی می‌کنید در اختیار داشته باشد، راستی‌آزمایی چیزی به شما نمی‌گوید.

این نکته‌ی آخر همان چیزی است که بیشتر راهنماها از آن می‌گذرند. **اینکه کلید را از کجا می‌گیرید به اندازه‌ی اجرای دستور اهمیت دارد.**

## بخش 1 — Zebra: checksumها و Sigstore

Zebra برای هر نسخه این فایل‌ها را منتشر می‌کند:

| فایل | کاربرد |
|---|---|
| `zebrad-<version>-<arch>.tar.gz` | آرشیو فایل اجرایی |
| `zebrad-<version>-<arch>.tar.gz.sha256` | checksum هر فایل |
| `SHA256SUMS` | checksumهای همه‌ی معماری‌ها |
| `SHA256SUMS.sigstore.json` | بسته‌ی Sigstore که `SHA256SUMS` را امضا می‌کند |

### گام 1 — دانلود

```bash
BASE=https://github.com/ZcashFoundation/zebra/releases/download/v6.3.0
curl -sLO $BASE/zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz
curl -sLO $BASE/SHA256SUMS
curl -sLO $BASE/SHA256SUMS.sigstore.json
```

### گام 2 — بررسی checksum

```bash
sha256sum -c --ignore-missing SHA256SUMS
```

خروجی واقعی:

```
zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz: OK
```

`--ignore-missing` در اینجا لازم است، چون `SHA256SUMS` همه‌ی معماری‌ها را پوشش می‌دهد و شما فقط یکی را دانلود کرده‌اید. بدون آن، `sha256sum` آرشیو aarch64 را که وجود ندارد به‌عنوان خطا گزارش می‌کند و ممکن است نتیجه‌ی موفق را ناموفق تفسیر کنید.

نسخه‌ی مخصوص هر فایل هم کار می‌کند:

```bash
sha256sum -c zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz.sha256
```

```
zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz: OK
```

**این گام به‌تنهایی کافی نیست.** شما checksum را از همان جایی دانلود کرده‌اید که فایل اجرایی را. هر کسی که بتواند یکی را جایگزین کند، می‌تواند دیگری را هم جایگزین کند. Checksum یکپارچگی را ثابت می‌کند؛ گام بعدی منشأ را ثابت می‌کند.

### گام 2b — همین بررسی روی Windows

PowerShell حالت راستی‌آزمایی `-c` ندارد، بنابراین مقایسه را به‌صورت دستی انجام می‌دهید:

```powershell
Get-FileHash .\zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz -Algorithm SHA256 | Format-List
```

خروجی واقعی:

```
Algorithm : SHA256
Hash      : 86326F5324F4E59CC2008C15F94407CC8D5FEACF75D64942164BB5F08ECA8C5E
Path      : \\wsl$\Ubuntu\home\briefking\verify\zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz
```

آن را با نتیجه‌ی Linux که پیش‌تر در این صفحه آمد مقایسه کنید:

```
86326f5324f4e59cc2008c15f94407cc8d5feacf75d64942164bb5f08eca8c5e
86326F5324F4E59CC2008C15F94407CC8D5FEACF75D64942164BB5F08ECA8C5E
```

**مقادیر یکسان هستند.** در هگزادسیمال بزرگی و کوچکی حروف معنایی ندارد و این رایج‌ترین هشدار نادرست روی Windows است.

دو دام دیگر مخصوص Windows:

- **هیچ exit code برای بررسی وجود ندارد.** روی Linux، `sha256sum -c` در صورت خطا مقدار 1 برمی‌گرداند و یک اسکریپت می‌تواند بر اساس آن عمل کند. `Get-FileHash` فقط یک hash چاپ می‌کند؛ مقایسه با شماست و اشتباه کردن در آن با یک نگاه سرسری هم با شما.
- **خواندن 64 کاراکتر هگزادسیمال با چشم قابل اعتماد نیست.** اجازه دهید shell این کار را انجام دهد:

```powershell
$expected = "86326f5324f4e59cc2008c15f94407cc8d5feacf75d64942164bb5f08eca8c5e"
$actual = (Get-FileHash .\zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz -Algorithm SHA256).Hash.ToLower()
if ($actual -eq $expected) { "OK" } else { "MISMATCH" }
```

> **روی macOS:** روند کار همین است، اما userland در BSD به‌جای `sha256sum` ابزار `shasum` را ارائه می‌کند؛ از `shasum -a 256 -c --ignore-missing SHA256SUMS` استفاده کنید. نویسنده‌ی این صفحه دستگاه macOS در اختیار نداشت، بنابراین این دستور بر اساس ابزارهای Apple مستند شده و اجرا نشده است. اگر روی macOS راستی‌آزمایی می‌کنید، لطفاً یک PR باز کنید و آن را تأیید یا اصلاح کنید.

### گام 3 — راستی‌آزمایی بسته‌ی Sigstore

Sigstore کلیدهای امضای بلندمدت را با گواهی‌های کوتاه‌مدتی جایگزین می‌کند که به یک هویت CI متصل‌اند و در یک لاگ شفافیت عمومی ثبت می‌شوند. هیچ‌کس کلید انتشاری در اختیار ندارد که بتوان آن را دزدید.

مسیر ساده از `cosign` استفاده می‌کند:

```bash
cosign verify-blob \
  --bundle SHA256SUMS.sigstore.json \
  --certificate-identity-regexp '^https://github\.com/ZcashFoundation/zebra/' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  SHA256SUMS
```

دو flag مربوط به `--certificate-*` اصل ماجرا هستند. **بدون آن‌ها فقط تأیید می‌کنید که کسی، در جایی، فایل را امضا کرده است.** با آن‌ها تأیید می‌کنید که فایل توسط یک workflow در مخزن Zebra امضا شده و صادرکننده‌ی OIDC مربوط به GitHub آن را احراز هویت کرده است.

> ⚠️ **نسخه اهمیت دارد.** Buildهای قدیمی‌تر cosign نمی‌توانند قالب فعلی بسته‌ی Sigstore را بخوانند. اجرای دستور بالا با cosign `v2.4.1` این نتیجه را می‌دهد:
>
> ```
> Error: bundle does not contain cert for verification, please provide public key
> ```
>
> بسته *واقعاً* یک گواهی دارد؛ این گواهی زیر `verificationMaterial.certificate.rawBytes` قرار دارد که نسخه‌های قدیمی‌تر به دنبال آن نمی‌گردند. این محدودیت کلاینت است، نه یک نسخه‌ی خراب. اگر با آن مواجه شدید، به‌جای اینکه نتیجه بگیرید دانلود مشکل دارد، cosign را به‌روزرسانی کنید. Cosign بسته‌بندی‌شده در توزیع‌ها اغلب از نسخه‌ی upstream بسیار عقب‌تر است.

دو گام بعدی نشان می‌دهند که چگونه همین بسته را به‌صورت دستی راستی‌آزمایی کنید؛ فهمیدن این کار در هر حال ارزشمند است و وقتی build شما از cosign همکاری نمی‌کند، یک جایگزین عملی است.

### گام 4 — بخوانید گواهی واقعاً چه ادعایی دارد

می‌توانید بسته را بدون `cosign` بررسی کنید؛ این کار برای فهمیدن اینکه به چه چیزی اعتماد می‌کنید مفید است. گواهی را استخراج کنید:

```bash
python3 -c "
import json,base64
d=json.load(open('SHA256SUMS.sigstore.json'))
open('cert.der','wb').write(base64.b64decode(d['verificationMaterial']['certificate']['rawBytes']))"

openssl x509 -in cert.der -inform DER -noout -issuer -ext subjectAltName
```

خروجی واقعی برای Zebra v6.3.0:

```
issuer=O = sigstore.dev, CN = sigstore-intermediate
X509v3 Subject Alternative Name: critical
    URI:https://github.com/ZcashFoundation/zebra/.github/workflows/zfnd-release-binaries.yml@refs/tags/v6.3.0
```

Subject Alternative Name همان هویت است. این فیلد مخزن، فایل دقیق workflow و tag را نام می‌برد. Sigstore فراداده‌های بیشتری از build را در افزونه‌های سفارشی جاسازی می‌کند:

| فیلد | مقدار برای v6.3.0 |
|---|---|
| OIDC issuer | `https://token.actions.githubusercontent.com` |
| Source repository | `https://github.com/ZcashFoundation/zebra` |
| Build commit | `f5c5277fe41eba9c74f37098738f93f35dd70d60` |
| Ref | `refs/tags/v6.3.0` |
| Runner environment | `github-hosted` |
| Workflow run | `.../actions/runs/31424510487/attempts/1` |
| Repository visibility | `public` |

تک‌تک این موارد قابل بررسی هستند. Hash مربوط به commit باید با tag در مخزن مطابقت داشته باشد؛ اجرای workflow باید وجود داشته باشد و عمومی باشد.

### گام 5 — راستی‌آزمایی رمزنگارانه‌ی امضای دیجیتال

می‌توانید امضای دیجیتال را مستقیماً با OpenSSL تأیید کنید:

```bash
python3 -c "
import json,base64
d=json.load(open('SHA256SUMS.sigstore.json'))
open('sig.bin','wb').write(base64.b64decode(d['messageSignature']['signature']))"

openssl x509 -in cert.der -inform DER -pubkey -noout > pub.pem
openssl dgst -sha256 -verify pub.pem -signature sig.bin SHA256SUMS
```

خروجی واقعی:

```
Verified OK
```

بسته همچنین digestی را که امضا کرده ثبت می‌کند. تأیید کنید که با فایل محلی شما مطابقت دارد:

```
bundle digest : 3eb5de0634f637e793d0411b6c7108802a36e1219f9151803ecc6108fd0f59f6
local  digest : 3eb5de0634f637e793d0411b6c7108802a36e1219f9151803ecc6108fd0f59f6
```

### گام 6 — ورودی لاگ شفافیت

بسته یک ورودی Rekor دارد که ثابت می‌کند امضای دیجیتال در یک لاگ عمومی و فقط‌افزودنی منتشر شده است:

| فیلد | مقدار |
|---|---|
| Rekor log index | `2412071838` |
| Entry type | `hashedrekord v0.0.1` |
| Integrated at | 2026-08-10 19:43:09 UTC |

همین است که سوءاستفاده‌ی بی‌صدا از کلید را قابل تشخیص می‌کند. امضایی که هرگز در لاگ ظاهر نشده یا در زمانی نامعقول ظاهر شده، نشانه‌ای است که باید بر اساس آن اقدام کرد. زمان ثبت را با اطلاعیه‌ی انتشار مقایسه کنید.

> **نکته درباره‌ی مسیر OpenSSL:** این روش امضای دیجیتال را با کلید عمومی گواهی تأیید می‌کند، اما به‌تنهایی زنجیره‌ی گواهی را تا ریشه‌ی Sigstore اعتبارسنجی نمی‌کند و اثبات شمول ورودی لاگ را هم بررسی نمی‌کند. `cosign verify-blob` هر سه کار را انجام می‌دهد. از OpenSSL برای فهمیدن سازوکار استفاده کنید؛ از `cosign` به‌عنوان بررسی واقعی خود استفاده کنید.

## بخش 2 — Zallet: امضاهای دیجیتال GPG

Zallet مجموعه‌ی متفاوتی از فایل‌ها را منتشر می‌کند:

| فایل | کاربرد |
|---|---|
| `zallet-<version>-<platform>.tar.gz` | آرشیو فایل اجرایی |
| `.tar.gz.asc` | امضای دیجیتال جداشده‌ی GPG |
| `.tar.gz.intoto.jsonl` | گواهی SLSA provenance |
| `.tar.gz.provenance.json` | فراداده‌ی provenance |
| `.tar.gz.sbom.spdx` | فهرست اجزای نرم‌افزار |

### گام 1 — پیش از جست‌وجوی کلید امضا، آن را شناسایی کنید

راستی‌آزمایی را *ابتدا* و بدون وارد کردن هیچ کلیدی اجرا کنید:

```bash
gpg --verify zallet-v0.1.0-beta.2-linux-amd64.tar.gz.asc \
             zallet-v0.1.0-beta.2-linux-amd64.tar.gz
```

خروجی واقعی:

```
gpg: Signature made Tue Jul 28 19:18:44 2026 WAT
gpg:                using RSA key 1FE99324758F296718B457067F4BBBBA23F0617F
gpg:                issuer "sysadmin@zodl.com"
gpg: Can't check signature: No public key
```

این یک خطا نیست. این خروجی به شما می‌گوید که یک امضای دیجیتال وجود دارد و دقیقاً نام می‌برد که به کدام کلید نیاز دارید، **پیش از** آنکه جست‌وجو را آغاز کنید. اثر انگشت و صادرکننده را یادداشت کنید، سپس کلید را از منبعی مستقل از دانلود به دست آورید.

> `gpg` زمان‌ها را در منطقه‌ی زمانی محلی شما نمایش می‌دهد. خروجی بالا `WAT` (UTC+1) را نشان می‌دهد؛ همین امضا در جای دیگر به صورت `18:18:44 UTC` خوانده می‌شود. لحظه یکی است. تفاوت منطقه‌ی زمانی را عدم تطابق تلقی نکنید.

### گام 2 — وارد کردن کلید و راستی‌آزمایی

```bash
curl -sL https://apt.z.cash/zodl.asc -o zodl.asc
gpg --import zodl.asc
gpg --verify zallet-v0.1.0-beta.2-linux-amd64.tar.gz.asc \
             zallet-v0.1.0-beta.2-linux-amd64.tar.gz
```

خروجی واقعی:

```
gpg: Signature made Tue Jul 28 19:18:44 2026 WAT
gpg:                using RSA key 1FE99324758F296718B457067F4BBBBA23F0617F
gpg:                issuer "sysadmin@zodl.com"
gpg: Good signature from "Zcash Open Development Lab (ZODL) (Dallas, Texas) <sysadmin@zodl.com>" [unknown]
gpg: WARNING: The key's User ID is not certified with a trusted signature!
gpg:          There is no indication that the signature belongs to the owner.
Primary key fingerprint: 0338 34DD 49DE CF9D BB99  34BC 6C93 CA8E 58E2 6AB1
     Subkey fingerprint: 1FE9 9324 758F 2967 18B4  5706 7F4B BBBA 23F0 617F
```

`Good signature` همان چیزی است که می‌خواستید. دو چیز در این خروجی افراد را سردرگم می‌کند و هر دو عادی هستند.

### چرا اثر انگشت با اطلاعیه مطابقت ندارد

بیانیه‌ی انتقال کلید ZODL اثر انگشت `0338 34DD 49DE CF9D BB99 34BC 6C93 CA8E 58E2 6AB1` را نام می‌برد. اما `gpg --verify` مقدار `1FE9 9324 …  23F0 617F` را گزارش کرد. این به نظر عدم تطابق می‌آید، اما نیست.

`gpg` **زیرکلیدی** را گزارش می‌کند که امضا را ایجاد کرده است. اطلاعیه **کلید اصلی** را نام می‌برد. این رابطه را خودتان تأیید کنید:

```bash
gpg --list-keys --with-subkey-fingerprints sysadmin@zodl.com
```

خروجی واقعی:

```
pub   rsa4096 2026-03-23 [SCEA]
      033834DD49DECF9DBB9934BC6C93CA8E58E26AB1
uid           [ unknown] Zcash Open Development Lab (ZODL) (Dallas, Texas) <sysadmin@zodl.com>
sub   rsa4096 2026-03-23 [SEA]
      1FE99324758F296718B457067F4BBBBA23F0617F
```

خط `sub` زیرکلید امضاکننده است؛ خط `pub` کلید اصلی است. یک هویت، یک بسته‌ی کلید. به همین دلیل خروجی راستی‌آزمایی **هر دو** اثر انگشت را چاپ می‌کند؛ کلید *اصلی* را با هر اطلاعیه‌ی منتشرشده مقایسه کنید و خط زیرکلید را نشانه‌ای بدانید از اینکه کدام بخش کلید کار را انجام داده است.

تقسیم کلیدها به این شکل عمدی است: یک زیرکلید امضا را می‌توان بدون کنار گذاشتن هویت اصلی و اعتماد انباشته‌ی آن تعویض یا باطل کرد.

### هشدار `[unknown]` به چه معناست

```
gpg: WARNING: The key's User ID is not certified with a trusted signature!
```

این **مشکلی** در امضای دیجیتال نیست. امضای دیجیتال از نظر رمزنگاری معتبر است؛ همان چیزی که `Good signature` بیان می‌کند. هشدار چیز دیگری می‌گوید: شما به GnuPG محلی خود نگفته‌اید که باور دارید این کلید متعلق به کسی است که ادعا می‌کند.

GnuPG دو پرسش را از هم جدا می‌کند:

1. **آیا این کلید این فایل را امضا کرده است؟** — پاسخ آن را `Good signature` می‌دهد. رمزنگارانه، بدون قضاوت انسانی.
2. **آیا این کلید متعلق به ZODL است؟** — رمزنگاری اصلاً به آن پاسخ نمی‌دهد. شما این را با بررسی اثر انگشت در برابر یک منبع مستقل ثابت می‌کنید.

این هشدار را تقریباً در هر راستی‌آزمایی خواهید دید، مگر اینکه کلید را به‌صراحت به‌صورت محلی امضا کنید. آن را خطا تلقی نکنید. **اما** نبودِ `Good signature` را خطا تلقی کنید.

### گام 3 — راستی‌آزمایی خودِ انتقال کلید

امضای نسخه‌های Zcash در سال 2026 از Electric Coin Company به Zcash Open Development Lab منتقل شد؛ پس از آنکه ZODL در ژانویه‌ی 2026 توسط تیم سابق مهندسی و محصول ECC تشکیل شد.

| | کلید قدیمی | کلید جدید |
|---|---|---|
| اثر انگشت | `B1C9 095E AA18 48DB B54D 9DDA 1D05 FDC6 6B37 2CFE` | `0338 34DD 49DE CF9D BB99 34BC 6C93 CA8E 58E2 6AB1` |
| UID | Zcash Master Signing Key (ECC) `<sysadmin@z.cash>` | Zcash Open Development Lab (ZODL) `<sysadmin@zodl.com>` |
| نوع | RSA 3072 بیتی، ایجادشده در 2023-06-19 | RSA 4096 بیتی، ایجادشده در 2026-03-23، انقضا در 2028-03-22 |
| محل انتشار | `https://apt.z.cash/zcash.asc` | `https://apt.z.cash/zodl.asc` |

جدول زمانی منتشرشده: کلید جدید در 2026-03-23 تولید شد، در 2026-03-27 اعلام شد، امضای انحصاری با آن از 2026-04-23 آغاز شد و ابطال کلید قدیمی ECC برای 2026-06-23 برنامه‌ریزی شد.

یک اطلاعیه‌ی تغییر کلید در یک وب‌سایت فقط به اندازه‌ی خود آن وب‌سایت قابل اعتماد است. سازوکار درست، بیانیه‌ای است که **با هر دو کلید clear-sign شده باشد**، تا کلید قدیمی ضامن کلید جدید شود. ZODL دقیقاً همین را منتشر می‌کند:

```bash
curl -sL https://zodl.com/security/key-transition.txt.asc -o key-transition.txt.asc
curl -sL https://apt.z.cash/zcash.asc -o zcash.asc
gpg --import zcash.asc
gpg --verify key-transition.txt.asc
```

خروجی واقعی (خلاصه‌شده؛ دو امضای دیجیتال روی یک سند):

```
gpg: Signature made Fri Mar 27 01:11:14 2026 WAT
gpg:                using RSA key B1C9095EAA1848DBB54D9DDA1D05FDC66B372CFE
gpg:                issuer "sysadmin@z.cash"
gpg: Good signature from "Zcash Master Signing Key (Electric Coin Company) <sysadmin@z.cash>" [unknown]
Primary key fingerprint: B1C9 095E AA18 48DB B54D  9DDA 1D05 FDC6 6B37 2CFE

gpg: Signature made Fri Mar 27 01:11:14 2026 WAT
gpg:                using RSA key 1FE99324758F296718B457067F4BBBBA23F0617F
gpg:                issuer "sysadmin@zodl.com"
gpg: Good signature from "Zcash Open Development Lab (ZODL) (Dallas, Texas) <sysadmin@zodl.com>" [unknown]
Primary key fingerprint: 0338 34DD 49DE CF9D BB99  34BC 6C93 CA8E 58E2 6AB1
     Subkey fingerprint: 1FE9 9324 758F 2967 18B4  5706 7F4B BBBA 23F0 617F
```

دو نتیجه‌ی `Good signature` روی یک سند، از کلید قدیمی و کلید جدید. اگر برای نسخه‌های قبلی به کلید ECC اعتماد داشتید، این اعتماد اکنون به کلید ZODL منتقل می‌شود، بدون اینکه لازم باشد به `zodl.com`، `apt.z.cash` یا یک پست انجمن اعتماد کنید. این همان ویژگی‌ای است که هر بار پروژه‌ای کلیدهایش را تعویض می‌کند باید به دنبالش باشید؛ و نبودِ آن ارزش پرسیدن دارد.

### کلید را از کجا بگیرید و از کجا نه

از بهترین به بدترین:

1. **بیانیه‌ای که با کلید قبلی امضا شده باشد**، مانند بالا. قوی‌ترین گزینه پس از تعویض کلید.
2. **منبعی مستقل از دانلود.** فایل اجرایی از GitHub آمده است؛ کلید از `apt.z.cash` آمده است. مهاجم به هر دو نیاز دارد.
3. **یک keyserver، با بررسی متقابل در برابر یک اثر انگشت منتشرشده.** در بیشتر keyserverها هر کسی می‌تواند کلیدی با ادعای هر هویتی بارگذاری کند. مقایسه‌ی اثر انگشت است که این روش را امن می‌کند، نه keyserver.
4. **همان صفحه‌ای که فایل اجرایی در آن است.** تقریباً هیچ اطمینانی نمی‌دهد. هر کسی که بتواند یکی را جایگزین کند، می‌تواند دیگری را هم جایگزین کند.

همیشه اثر انگشت **کامل** را با کلید **اصلی** مقایسه کنید. شناسه‌های کوتاه کلید به‌سادگی قابل تصادم هستند و در حملات واقعی از آن‌ها استفاده شده است.

## بخش 3 — یک راستی‌آزمایی ناموفق

راستی‌آزمایی تنها زمانی مفید است که بدانید شکست چه شکلی دارد. در اینجا یک نمونه‌ی واقعی آمده است که با افزودن یک بایت null به انتهای یک آرشیو معتبر ایجاد شده است:

```bash
cp zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz tampered.tar.gz
sha256sum tampered.tar.gz > tampered.sha256
printf '\x00' >> tampered.tar.gz
sha256sum -c tampered.sha256
```

خروجی واقعی:

```
tampered.tar.gz: FAILED
sha256sum: WARNING: 1 computed checksum did NOT match
```

Exit code: `1`.

دو digest را کنار هم بگذارید:

```bash
sha256sum zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz tampered.tar.gz
```

```
86326f5324f4e59cc2008c15f94407cc8d5feacf75d64942164bb5f08eca8c5e  zebrad-6.3.0-x86_64-unknown-linux-gnu.tar.gz
8d4e2e22adcb014e006fafc71a974f987ba11297587f593cf89eb9bb1feff0b5  tampered.tar.gz
```

یک بایت به انتهای فایلی با حجم 66,992,676 بایت افزوده شده است. دو hash هیچ وجه مشترکی ندارند؛ نه پیشوندی، نه الگویی. هیچ تطابق جزئی و هیچ «تقریباً کافی» وجود ندارد: checksum یا دقیقاً مطابقت دارد یا فایل همان فایلی نیست که می‌خواستید.

### وقتی این اتفاق افتاد چه کنید

1. **فایل اجرایی را اجرا نکنید.** آن را استخراج نکنید و روی آن `chmod +x` اجرا نکنید.
2. **دوباره از صفحه‌ی رسمی انتشار تلاش کنید.** بیشتر خطاها ناشی از دانلودهای ناقص هستند.
3. **اگر بار دوم هم ناموفق بود، مسیر شبکه را تغییر دهید.** اتصالی دیگر یا یک VPN. خطایی که در شبکه‌های مختلف همراه شما می‌آید با خطایی که این‌طور نیست تفاوت دارد.
4. **مطمئن شوید که فایل checksum درست را برای نسخه‌ی درست در اختیار دارید.** مقایسه‌ی v6.3.0 با checksumهای v6.2.3 به‌درستی ناموفق خواهد بود.
5. **اگر همچنان ناموفق بود، آن را گزارش کنید.** در مخزن پروژه یک issue باز کنید، یا برای هر چیزی که گمان می‌کنید عمدی است از راه ارتباطی امنیتی در `SECURITY.md` استفاده کنید. برای کانال‌های افشا، صفحه‌ی [Zcash امنیت اکوسیستم](/zcash-community/zcash-ecosystem-security) را ببینید.
6. **فایل را نگه دارید.** یک فایل اجرایی دست‌کاری‌شده مدرک است. پیش از گزارش دادن آن را حذف نکنید.

شکست امضای دیجیتال جدی‌تر از شکست checksum است. عدم تطابق checksum معمولاً ناشی از خرابی فایل است؛ اما فایلی معتبر با امضای نامعتبر چیزی نیست که تصادفی رخ دهد.

## بخش 5 — کیف‌پول‌های موبایل و سخت‌افزاری

وقتی از دانلود مستقیم فاصله می‌گیرید، راستی‌آزمایی به شکل متفاوتی کار می‌کند.

**فروشگاه‌های اپلیکیشن.** شما نمی‌توانید امضای دیجیتال را خودتان بررسی کنید. فروشگاه بسته را امضا می‌کند و شما به بازبینی فروشگاه و یکپارچگی حساب توسعه‌دهنده اعتماد می‌کنید. آنچه *می‌توانید* راستی‌آزمایی کنید این است که اپلیکیشن درست را در اختیار دارید: نام ناشر و شناسه‌ی بسته را با سایت رسمی پروژه مقایسه کنید، نه با نتایج جست‌وجو. اپلیکیشن‌های جعلی رایج هستند و فهرست‌شدن در فروشگاه دلیلی بر اصالت نیست.

**فایل‌های APK مستقل Android.** این فایل‌ها *قابل* راستی‌آزمایی هستند. ZODL فایل‌های اجرایی مستقل Android را با امضای GPG از طریق GitHub Releases منتشر می‌کند، بنابراین روند بخش 2 در مورد آن‌ها صدق می‌کند. اگر زنجیره‌ای قابل بررسی می‌خواهید، این مسیر را ترجیح دهید.

**کیف‌پول‌های سخت‌افزاری.** دستگاه خودش اصالت firmware خود را گواهی می‌کند، بنابراین لنگر اعتماد سخت‌افزار است، نه فایلی روی دستگاه شما. برای روند راستی‌آزمایی دستگاه، [Keystone Zashi](/guides/keystone-zashi) را ببینید. مستقیماً از سازنده خرید کنید؛ دست‌کاری در زنجیره‌ی تأمین بین کارخانه و خریدار رخ می‌دهد.
