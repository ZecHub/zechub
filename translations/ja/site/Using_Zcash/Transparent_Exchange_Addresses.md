# Zcash TEXアドレスとは？

## TL;DR

* TEXアドレスは、異なる形式で表記された透明なZcashアドレスです。`tex1`で始まり、[ZIP 320](https://zips.z.cash/zip-0320)で定義されています。
* ウォレットに伝えることは1つだけです。このアドレスには透明な資金のみで支払ってください。
* 残高がシールドされている場合、対応ウォレットが2段階の処理を行います。金額を一時的な透明アドレスへ移動してから、TEXアドレスへ送信します。
* 2023年、BinanceはZcashコミュニティに対し、シールドされた入金を拒否して返金する方法を求めました。TEXアドレスはその答えであり、BinanceはZecHubの[カストディアル取引所](/using-zcash/custodial-exchanges)リストでTEX入金を受け付けている取引所です。
* 送信側での対応も広がっています。CoinbaseではユーザーがZECをTEXアドレスへ送信でき、ウォレット用ツールキットにもZIP 320のサポートが追加されています。
* TEXアドレスへの支払いは、他の透明な支払いと同様にブロックチェーン上で公開されます。シールドされた残高の残りは非公開のままです。

## 基本的な説明

Zcash TEXアドレスは、特別な種類の受取アドレスです。TEXは「Transparent Exchange」の略です。単一のp2pkh透明アドレスをBech32mで再エンコードしたもので、TEXアドレスは`tex1`で始まり、Unified Addressとは別の種類です。

TEXアドレスは、対応ウォレットにTransparent-Only（T -> T）トランザクションを作成するよう伝えます。 

仕組みは次のとおりです。対応ウォレットがTEXアドレスを検出すると、それをデコードして含まれる透明な受信者を取得します。次にウォレットは、トランザクションに必要な資金をシールドプールから、ユーザーが管理する別の一時的な透明アドレスへ送信します（Z -> T）。その後、TEXアドレスからデコードした透明な受信者へ資金を送信します（T -> T）。  

TEXアドレスの技術提案はZcash [ZIP 320](https://zips.z.cash/zip-0320)で概説されており、透明アドレスからの資金受取専用のアドレスタイプを定義しています。

### TEXアドレスはどの程度利用されていますか？

普及はまだ部分的ですが、もはや単一の取引所だけに限られてはいません。区別すべき2つの役割があります。

* **TEX入金アドレスの発行。** Binanceは、当サイトの[カストディアル取引所](/using-zcash/custodial-exchanges)リストにある、入金用にTEXアドレスを発行する取引所です。これにより、資金は透明な送信元から到着します（[ZIP 320、背景](https://zips.z.cash/zip-0320#background)）。ZIP 320では、支払いの送信元アドレスを知る必要がない限り、他の取引所がTEXアドレスを発行することは想定していません。
* **TEXアドレスへの送信。** 成長しているのはこちらです。2024年10月、CoinbaseはCoinbase.comのユーザーがZcashをTEXアドレスへ送信できると発表しました（[Coinbase Assetsの発表](https://x.com/CoinbaseAssets/status/1844428577921507416)）。ウォレット用ツールキットにもZIP 320のサポートが追加されています。KeepKeyはファームウェア7.15でTEXトランザクションの署名機能を追加し（[keepkey/hdwallet #75](https://github.com/keepkey/hdwallet/pull/75)）、XChainJSの`zcash-js`ライブラリは有効な`tex1`受信者を拒否した後に修正されました（詳細は後述）。

したがって、TEXアドレスは普遍的ではありませんが、Binanceだけに存在すると考えるべきではなくなっています。

### TEXアドレスが必要になる場合

#### 透明アドレスへ直接送信できないウォレットを使って、透明アドレスに資金を送る場合はTEXアドレスが必要です。

一部のウォレットでは透明アドレスに直接送信できず、受取人がTEX相当のアドレスを提供していないこともあります。そのため、透明アドレスをTEXアドレスへ変換する必要が生じる場合があります。これは[zip-320](https://zips.z.cash/zip-0320#reference-implementation)で示されているリファレンス実装を実行することで、手動で行えます。

#### 資金が透明な送信元から来ることを要求する中央集権型取引所へ送金する場合はTEXアドレスが必要です。

[Binance](https://www.binance.com/)が、TEXアドレスが存在する理由です。2023年11月、同社はZcashコミュニティに対し、シールドアドレスからの入金を拒否して入金者へ返金する方法がなければ、ZECが上場廃止となる可能性があると伝えました（[ZIP 320、背景](https://zips.z.cash/zip-0320#background)）。ZIP 320では、支払いの送信元アドレスを知る必要がない限り、他の取引所がTEXアドレスを発行することは想定していません。Binanceは、当サイトの[カストディアル取引所](/using-zcash/custodial-exchanges)リストにある、TEXアドレス宛の入金を受け付ける取引所です。
TEXアドレスは、対応ウォレットに対して、そのアドレスへ送るすべての資金を透明にし、シールドされた価値をそのアドレスへ送信しないよう伝えます。
Binanceのような取引所が送信された価値を拒否した場合、その価値を送信元アドレスへ返すために必要な手段を備えています。また、Binanceのような組織が政府その他の当局による法律や規制に従う助けにもなります。

### TEXアドレスに対応しているウォレットは？

最新の一覧は、当サイトの[ウォレット](/using-zcash/wallets)ページで確認できます。TEX Addressフィルターを使用してください。

## 図解 / たとえ話

シールドされた残高を、自宅にある施錠された金庫の中のお金だと考えてください。外部の人には、中にいくら入っているか見えません。

Binanceのような取引所は、カウンターに「透明な封筒に入れた支払いのみ受け付けます。そうすれば係員が資金の送信元を確認し、必要に応じて返金できます」と書かれた札を掲げています。TEXアドレスはその札です。

ウォレットがその札を見ると、金庫から金額を取り出し、返送先アドレスが記された透明な封筒（一時的な透明アドレス）に入れて、カウンターへ運びます。金庫は施錠されたままであり、他に何が入っているかは誰にも分かりません。

## 詳細

### TEXアドレスの構成

`t1`で始まる通常の透明アドレスには、Base58Checkで表記された20バイトのキーハッシュが含まれます。TEXアドレスには同じ20バイトが含まれ、`tex`というプレフィックス（テストネットでは`textest`）を用いてBech32mで再エンコードされます。両者の変換は数行のコードで可能であり、ZIP 320はそのリファレンス実装で示しています。

この単純な設計はBinanceからの要件でした。変換は取引所のフロントエンドコード上で、Base58CheckとBech32mのライブラリだけを使って実行できなければなりませんでした。ZIP 320の初期ドラフトではこの仕組みをUnified Addressに組み込んでいましたが、この理由によりそのバージョンは取り下げられました。

TEXアドレスはUnified Address形式からBech32mエンコーディングを借用していますが、その構造のほとんどは保持していません。Bech32mやZcashアドレスの検証方法に不慣れな場合は、[Unified Address](/using-zcash/unified-addresses)ページで[ZIP 316](https://zips.z.cash/zip-0316)の基本を確認できます。TEXアドレスはUnified Addressと比べて、具体的に4つの違いがあります。

| | Unified Address（ZIP 316） | TEXアドレス（ZIP 320） |
|---|---|---|
| 含まれるもの | 複数の受信者をまとめたもの | 単一のP2PKH透明受信者 |
| 人間可読プレフィックス（HRP） | `u`（メインネット） | `tex`（テストネットでは`textest`） |
| F4Jumble難読化 | あり | なし |
| 各受信者のタイプコード | あり | なし |

要するに、TEXアドレスは可能な限り単純なBech32mラッパーです。透明なキーハッシュ1つ、`tex`プレフィックス、そしてそれ以外は何もありません。

### ウォレットおよび統合者向けの処理ルール

この部分は実装で誤りが生じているため、明確に説明する価値があります。TEXアドレスを検出した際、ウォレットまたは統合者は**シールドプールからTEX宛先へ直接送金してはなりません。** ZIP 320では、TEX支払いのすべての入力を透明にすることが求められているため、支払いは次の2段階で構築されます。

1. **デシールド。** シールドプールから、ウォレットが所有する、新しく生成されたユーザー管理下の一時的な透明アドレスへ金額を移動します（Z -> T）。
2. **透明から透明への送信。** その一時的な出力を使い、TEXアドレス内でデコードされたP2PKH受信者へ送金します（T -> T）。

これを安全にするいくつかのルールは、すべてZIP 320に基づいています。

* 一時的なアドレスはシードフレーズから導出する必要があります。そうすれば取引所が資金を返金した場合でも、ウォレットはその資金を見つけて使用できます。
* 別々の支払いを互いに関連付けられないよう、毎回新しい一時的アドレスを使用する必要があります。
* 2番目のトランザクションでは透明な入力のみを使用する必要があります。これにより取引所には、明確な透明から透明への入金として表示されます。

変換と2段階のフローは、[ZIP 320のリファレンス実装](https://zips.z.cash/zip-0320#reference-implementation)で示されています。これは現実に起きた最近の問題です。2026年10月、XChainJSの`zcash-js`ライブラリは、有効な`tex1`受信者を「Invalid 'to' address」エラーで拒否しました。これはバリデーターがBase58Checkの`t1`形式しか受け付けなかったためで、ZECアドレスを公開するサービスへの`tex1`入金が妨げられました（[issue #1782](https://github.com/xchainjs/xchainjs-lib/issues/1782)）。この問題は、バリデーターがZIP 320のエンコーディングを受け入れるようにすることで修正されました（[PR #1783](https://github.com/xchainjs/xchainjs-lib/pull/1783)）。

### TEX送金で明らかになること

TEX支払いは透明な支払いであるため公開されますが、観察者に見えるものと見えないものを正確に理解することが重要です。

チェーン上で**見える**もの:

* 一時的な透明アドレス。デシールド段階の出力および最終送信の入力として現れるためです。
* 両方の金額。Z -> T段階でシールドプールから出た価値と、T -> T段階で送られた価値です。
* 取引所の透明な受信者。TEXアドレスにエンコードされているP2PKHアドレスです。

**隠される**もの:

* シールドされた残高の残り、および支払いにどの特定のシールドノートが使われたか。デシールド段階では、何らかの価値がプールから一時的アドレスへ移動したことは分かりますが、プール内のどこから来たかは分かりません。

したがって観察者は、一時的アドレスを取引所への支払いに関連付けることができ（同じ資金が透明から透明へ移動するため）、それがシールドされた出金から補充されたことも確認できます。しかし、他のシールド資金や活動とは結び付けられません。実際には、チェーン上でその支払いを「TEX」送金として示すものはありません。ZIP 320が指摘するように、コンセンサスルールは変わらず、ルール全体がウォレット内に存在するため、TEXアドレスへの支払いは対応する`t1`アドレスへの支払いと区別できません。

![On-chain footprint of a TEX send: funds leave the shielded pool to an ephemeral transparent address, then go transparent-to-transparent to the exchange; the ephemeral address, both amounts and the exchange address are visible, while the rest of the shielded balance stays hidden](/content-images/tex-onchain-footprint.webp)

### ブロックチェーンに表示されるもの

TEXルールはウォレット内にあります。ノードはこれを検証しないため、コンセンサスルールは変わりません。チェーン上では、TEXアドレスへの支払いは対応する`t1`アドレスへの支払いと同じように見えます。金額、一時的アドレス、取引所のアドレスは、他の透明なトランザクションと同様に公開されます。
