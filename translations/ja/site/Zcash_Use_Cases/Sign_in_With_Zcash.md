# <img src="/content-images/icons8-lock-2f8e221321.svg" width="24" height="24" alt="lock icon"/> Zcashでサインイン

<span className="inline-flex items-center gap-[6px]"><span className="inline-block w-[12px] h-[12px] bg-green-500 rounded-full"></span>中級 - 7分</span>

## 要約

- パスワードの代わりに、Zcashアドレスを自分が管理していることを示してログインします
- 現在は、**チャレンジへの署名**、または**メモ内のコードを含むシールドされた支払い**という2つの設計が使われています
- シールドされたアドレスは残高と履歴を隠すため、管理していることを示しても財務情報は公開されません
- このパターンはまだ初期段階です。承認済みの標準はなく、実装間の相互運用性もありません

<br/>

## <img src="/content-images/user-svgrepo-com-21adf62b7c.svg" width="24" height="24" className="inline-block align-middle mr-1 p-[2px]" alt="user icon"/> これは誰向けですか？

- 個人データを収集せずにパスワードレスログインを実現したい開発者
- すべてのサイトにメールアドレスを渡したくないユーザー
- 財務履歴をアカウントに紐付けずにログインしたいすべての人

<br/>

## <img src="/content-images/warning-error-svgrepo-com-b7ea8a50da.svg" width="24" height="24" className="inline-block align-middle mr-1 p-[2px]" alt="warning icon"/> 問題

ほとんどのログイン方法では、何らかの情報が漏洩します。

- **パスワードとメール**は、本人のアイデンティティに紐付くアカウントを作成し、どちらも漏洩データに含まれることになります
- **ソーシャルサインイン**では、アイデンティティプロバイダーに、どのサービスへいつログインしたかが伝わります
- **公開型チェーンでのウォレットサインイン**は、見た目以上に問題があります。ウォレットを接続すると、サイトに残高全体とトランザクション履歴が恒久的に渡る可能性があります

通常は、利便性と情報開示の間で選択することになります。

<br/>

## <img src="/content-images/celebration-spark-svgrepo-com-bc98dec7c1.svg" width="24" height="24" className="inline-block align-middle mr-1 p-[2px]" alt="spark icon"/> なぜZcashなのですか？

Zcashは、*管理していることを示すこと*と*財務情報を明かすこと*を分けます。

- **シールドされたアドレス（Shielded addresses）**は残高とトランザクション履歴を非公開に保つため、保有していることを示しても、何を保有しているかは分かりません
- **暗号化されたメモ（Encrypted memos）**は、トランザクション内に1回限りのログインコードを非公開で含められます
- **ビューイングキー（Viewing keys）**は選択的開示を可能にするため、アプリには必要な情報だけを読み取るアクセス権として与えられ、それ以上は渡りません

<br/>

## <img src="/content-images/ladder-svgrepo-com-7232bf46ed.svg" width="24" height="24" className="inline-block align-middle mr-1 p-[2px]" alt="step icon"/> 仕組み

2つのアプローチが登場しています。どちらも、アプリが安定した識別子を保持し、パスワードを必要としない形で終わります。

### アプローチ1: チャレンジに署名する

1. アプリがランダムな1回限りのチャレンジを生成します
2. ウォレットが、アドレスに対応するキーでそのチャレンジに署名します
3. アプリが署名を検証し、ログインさせます

何もブロードキャストされないため、手数料はかからず、ブロックを待つ必要もありません。関連する仕様は[ZIP 304、Saplingアドレス署名](https://zips.z.cash/zip-0304)です。これはまだドラフトであるため、メッセージ署名に対するウォレットの対応状況は異なります。

### アプローチ2: シールドされた支払いで示す

1. アプリが1回限りのコードを生成し、支払いリクエストを表示します
2. メモにそのコードを含めた少額のシールドされたトランザクションを送信します
3. アプリがメモを監視し、コードを照合してログインさせます

これは、現在すでにメモに対応しているウォレットで動作し、そのようなウォレットは大半を占めます。トレードオフは、ネットワーク手数料がかかり、承認を待つ必要があることです。

### アドレスを非公開に保つ

アプリは、ユーザーを認識するためにアドレスを保存する必要はありません。一部の実装では、アドレスをアプリケーション固有の値とともにハッシュ化するため、同じユーザーでも各サイトには異なる安定した識別子として見えます。これにより、サイト同士が情報を照合してアカウントを紐付けることを防げます。

## <img src="/content-images/icons8-toolbox-9bebbb1619.svg" width="24" height="24" className="inline-block align-middle mr-1 p-[2px]" alt="toolbox icon"/> トレードオフ

これを構築の基盤としたり、依存したりする前に理解しておくべき点です。

| | 署名付きチャレンジ | シールドされた支払い |
|---|---|---|
| コスト | 無料 | ログインごとにネットワーク手数料 |
| 速度 | 即時 | 承認を待機 |
| ウォレット対応 | 限定的、ZIP 304はドラフト | 幅広い対応、必要なのはメモのみ |
| チェーン上の記録を残す | いいえ | はい、トランザクションが存在します |

共通する制限事項:

- **デフォルトではアカウント復旧がありません。** アプリが復旧経路を設計しない限り、キーを失うとアカウントも失われます
- **アドレスの再利用は追跡につながります。** 多くのサイトで同じアドレスを使うと追跡の問題が再現されるため、アプリ固有の識別子が重要です
- **承認済みの標準がありません。** プロジェクトごとに独自の方式があるため、あるプロジェクト向けに構築されたログインは別のプロジェクトでは機能しません
- **それ自体で匿名性を提供するものではありません。** アプリから財務情報を隠せますが、ログイン後に行うことはアプリにプロファイリングされ得ます

<br/>

## <img src="/content-images/icons8-cancel-7f786be3c1.svg" width="24" height="24" className="inline-block align-middle mr-1 p-[2px]" alt="cancel icon"/> 避けるべきよくある間違い

- チャレンジコードを再利用すること。すべてのコードは1回限りとし、すぐに期限切れにする必要があります。そうしないと、取得されたコードが再利用される可能性があります
- ログインのために意味のある金額を送るようユーザーに求めること。支払いは所有を示すためのものであるため、金額はごく少額にすべきです
- アプリケーション固有の識別子で同じ目的を果たせるのに、生のアドレスを保存すること
- メッセージ署名がどこでも機能すると考えること。ユーザーが実際に使っているウォレットを確認してください
- 後になってメモを秘密情報として扱うこと。メモは送信者が行動したことを示すものであり、パスワードではありません

## <img src="/content-images/checked-checkbox-svgrepo-com-7ea19022da.svg" width="28" height="28" className="inline-block align-middle mr-1 p-[2px]" alt="done icon"/> これを探求するプロジェクト

これらは、[ZecHub Hackathon 3.0](https://zechub.wiki/hackathon)の**Zcashログイン**トラック向けに構築されました。完成品ではなく実験であり、同じアイデアをいかに異なる方法で構築できるかを示しています。

- **ZecAuth** - Zcash向けのウォレット接続プロトコルで、他の場所でWalletConnectが行うことと同様の理念に基づいています。アプリは、サインイン、支払いリクエスト、ビューイングアクセスなど、要求する機能とチャレンジを含むQRコードまたは`zecauth://`リンクを表示します。トランザクション、手数料、チェーンとのやり取りはありません。コードとともに文書化されたプロトコル仕様を提供しています
- **ZShield** - シールドされたアドレスをW3C DIDおよびOpenID Connectアイデンティティへ変換します。ブラウザーがキーペアを生成し、サーバーがZIP 304形式のインターフェースを通じてノンスを発行し、ウォレットがそれに署名して、サーバーがJWTを返します。結果はOIDC互換であるため、既存のアプリは個別の統合なしに利用できます
- **ZecPass** - 署名付きメモを通じて所有を示し、アプリがユーザーのアドレスをまったく知ることがないよう構築されています。安定した識別子として使うアプリケーションスコープのハッシュを導出し、チャレンジを1回限りかつ時間制限付きに保ち、Node検証ライブラリを備えたすぐに導入できるReactボタンを提供しています
- **Portal** - メモ内の1回限りのコードを含むシールドされたトランザクションを送信してログインし、メインネットで稼働しています。同じフローは、有料コンテンツのロック解除や、リンクを通じた送金・受け取りにも再利用されます
- **ZcashMe** - シールドされた支払いをアイデンティティの根拠として用い、ラップトップでのサインインにブラウザー拡張機能を必要としないよう、デスクトップとモバイルの隔たりに焦点を当てています
- **ZBooks** - Zcashでのサインインを製品そのものではなく再利用可能な認証プリミティブとして扱う会計・支払いツールで、Unified Full Viewing Keyを通じてトレジャリーデータを読み取ります
