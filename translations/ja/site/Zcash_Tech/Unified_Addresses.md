# Unified Address (ZIP-316) の検証

*これは学習ガイドであり、パッケージ化されたデコーダーやコピー＆ペースト用の決済ライブラリではありません。Unified Address がどのように構成されているかを説明し、保守されているライブラリが内部で何を行っているのかを理解できるようにします。実際の資金を扱うものについては、[ZIP-316 仕様](https://zips.z.cash/zip-0316)および以下でリンクされている公式実装に従ってください。*

---

## 全体像

Unified Address（UA）は、**Transparent**、**Sapling**、**Orchard**、またはそれらの組み合わせという、複数の受信者タイプを含む単一のアドレス文字列です。支払い側のウォレットは、対応している中で最適な受信者プールを自動的に選択します。

UA は、ラベル付きのカードを何枚か収めた封印済みの封筒だと考えてください。各カードは、あなたに届く異なる方法を表します。アドレスを確認するには、アプリケーションは以下を行う必要があります。

1. **封筒を開く：** テキスト文字列をデコードする。
2. **中身の並びを戻す：** 保護用のスクランブル（**F4Jumble**）を解除する。
3. **各カードを読む：** 個々の受信者を抽出する。
4. **プロトコル規則を適用する：** typecode の範囲に従ってエントリを無視または拒否する。

---

## 「Bech32m をデコードするだけ」では不十分な理由

UA は Bech32m テキストエンコーディングを使用しますが、Bech32m をデコードするだけでは利用可能な受信者は判明しません。

ZIP-316 は、エンコード前に意図的に **F4Jumble** を使用してペイロードをスクランブルします。F4Jumble は、アドレス内のたった1文字を変更した場合でも、デコード結果全体が変化することを保証します。これにより、攻撃者がアドレスの接頭辞と接尾辞を有効に見せたまま、途中のバイトを入れ替えるアドレス可鍛性攻撃を防止します。

> **重要な規則：** 可鍛性保護は、アプリケーションが完全なデコードおよび検証パイプラインを実行する場合にのみ機能します。部分的なデコードは、安全性を取り除きながらすべてのリスクを残します。

---

## デコードパイプラインの手順

### ステップ1：Bech32m をデコードし、ネットワークを確認する
- **人間可読部分（HRP）：** `u` はメインネットを、`utest` はテストネットを識別します。*（メインネットの UA は `u1` で始まり、`1` は Bech32 の区切り文字です。）*
- **長さの制限：** 標準の Bech32m では90文字の制限が適用されます。UA は通常この制限を超えるため、デコーダーでは標準の長さチェックを無効にする必要があります。
- 5ビットの Bech32m ワードを、標準の8ビットバイトに戻します。

### ステップ2：F4Jumble を逆変換する
F4Jumble は BLAKE2b 上に構築された4ラウンドの Feistel ネットワークです。

- **左半分の長さ：** `min(64, floor(length / 2))` バイトです。64バイトという上限は BLAKE2b の最大出力サイズに対応します。右半分には残りのペイロードが含まれます。
- **ハッシュ関数：** 固定のパーソナライゼーションラベル（`UA_F4Jumble_G` および `UA_F4Jumble_H`）を使用して G と H を交互に適用します。
- **ラウンド順序：** 順方向のエンコードは G(0) → H(0) → G(1) → H(1) の順に実行されます。逆変換（スクランブル解除）は H(1) → G(1) → H(0) → G(0) の順に実行されます。
- **範囲チェック：** ZIP-316 のペイロードサイズ制限の範囲外にある入力は拒否します。

### ステップ3：パディングを削除し、HRP を検証する
スクランブル前に、エンコーダーは HRP を含みゼロで埋められた16バイトを追加します。

- スクランブル解除後、末尾の16バイトを削除します。
- 埋め込まれた HRP が想定するネットワーク（`u` または `utest`）と一致することを確認します。これにより、テストネットのアドレスが誤ってメインネットで受け入れられることを防ぎます。

### ステップ4：受信者を抽出する
残りのペイロードは `(typecode, length, content)` エントリで構成され、typecode と長さはコンパクトサイズ整数（小さい値では1バイト）として格納されます。既知の受信者 typecode は以下のとおりです。

| Typecode | 受信者タイプ       | コンテンツ長 |
| :------- | :------------------ | :------------- |
| `0x00`   | Transparent (P2PKH) | 20バイト       |
| `0x01`   | Transparent (P2SH)  | 20バイト       |
| `0x02`   | Sapling             | 43バイト       |
| `0x03`   | Orchard             | 43バイト       |

これらに加えて、ZIP-316 は将来の互換性のためにさらに2つの範囲を予約しています。

- **`0xC0`–`0xDF`（MUST-understand ではないメタデータ）：** この範囲で認識できないメタデータ項目は、コンシューマーが無視しなければなりません。
- **`0xE0` および `0xE1`（割り当て済みの MUST-understand 有効期限メタデータ）：** 現行の ZIP-316 レジストリでは、これらはアドレス有効期限のブロック高および時刻に割り当てられています。コンシューマーはこれらの項目を理解するか、アドレスを拒否しなければなりません。
- **`0xE2`–`0xFC`（未割り当ての MUST-understand メタデータ）：** この範囲で認識できない項目に遭遇した場合、コンシューマーはアドレスを拒否しなければなりません。

既知の受信者タイプについては、エンコードされた長さがそのタイプに指定されたコンテンツ長と一致することを検証します。メタデータ項目については、エンコードされたコンパクトサイズの長さを使用してコンテンツ長を決定します。切り詰められたエントリまたは末尾に残るバイトは拒否します。

**優先する受信者順序。** アドレスの解析に成功したら、ウォレットまたは決済ツールは次の順序で最適な受信者を選ぶべきです。Orchard、次に Sapling、その次に transparent です。

## 必須の ZIP-316 拒否規則

**デコードに成功しても、アドレスが有効になるわけではありません。** 公式の Zcash ウォレットは、以下の規則に違反するアドレスを厳格に拒否します。決済の失敗を防ぐため、Web ツールも同様に拒否しなければなりません。

- **シールドされた受信者の欠如：** アドレスには少なくとも1つの Sapling または Orchard 受信者が**必ず**含まれていなければなりません。transparent 受信者のみを持つ UA は、ZIP-316 では無効です。
- **重複する typecode：** 各受信者タイプは最大1回しか出現できません。
- **未ソートの typecode：** 受信者は typecode の厳密な昇順で出現しなければなりません。
- **競合する transparent 受信者：** UA は P2PKH または P2SH のいずれかを含められますが、**両方を含めることはできません**。
- **不正なエントリまたはパディング：** ネットワークプレフィックスの不一致、切り詰められたペイロード、または長さの不一致は、即時に拒否しなければなりません。
- **認識されない typecode：** コンシューマーは、MUST-understand メタデータ範囲（`0xE0`–`0xFC`）内の項目を除き、認識できない項目を無視しなければなりません。この範囲の項目は、認識できない場合に拒否しなければなりません。現行のレジストリでは、`0xE0` と `0xE1` は割り当て済みの有効期限タイプであり、`0xE2`–`0xFC` は未割り当てです。これとは別に、Sapling または Orchard 受信者の要件を含む、上記の必須有効性規則を満たさないアドレスはすべて拒否します。

## 開発者向けベストプラクティス

- **生の文字列ではなく、解析済みの受信者を比較してください。** 等価性を確認する前に、まずアドレスをデコードします。
- **資金を扱うものには、保守されているライブラリを使用してください。** カスタムの JavaScript デコーダーをデプロイするのではなく、`zcash_address` などの公式 Rust クレートを WebAssembly にコンパイルしてください。
- **手書きのパーサーには注意してください。** 学習のために作成する場合は、学習プロジェクトとして扱い、何かを任せる前に以下の公式ベクターに対してテストしてください。

## 用語集

| 用語 | 意味 |
| :----------------------- | :-------------------------------------------------------------------- |
| **Unified Address (UA)** | 複数の受信者プールを束ねた単一のアドレス文字列。 |
| **受信者** | 特定の決済先タイプ（transparent、Sapling、または Orchard）。 |
| **Bech32m** | UA 文字列に使用されるテキストエンコーディング方式。 |
| **HRP** | 人間可読部分、またはネットワークプレフィックス（`u` または `utest`）。 |
| **F4Jumble** | アドレスの完全性を保証する、可逆的な難読化アルゴリズム。 |
| **Typecode** | ペイロード内の受信者タイプを定義する各エントリの番号。 |
| **可鍛性** | 検出されずにアドレスのバイトを不正に変更できる性質。 |
