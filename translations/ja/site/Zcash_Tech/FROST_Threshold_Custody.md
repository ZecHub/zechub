# FROSTとシールドされたZECのためのしきい値カストディ

> FROSTプロトコルの暗号学的な詳細については、[FROST技術ページ](FROST.md)をご覧ください。

FROSTのしきい値カストディはZcashの議論で繰り返し話題になっており、ZecHub Hackathon 2026では最も人気のあるトラックでした。しかし、この概念は必ずしも平易な言葉で説明されていません。このページでは、その意味、実際に必要となる場面、トレードオフ、そして現在これをサポートしているツールについて説明します。

---

## 要約

- **FROST**により、キーホルダーのグループは、誰も完全な秘密鍵を保持せずに、シールドされたZcashアドレスを共同で管理できます。
- **t-of-n**しきい値とは、支出にはt人の共同署名が必要であり、t-1人以下では単独で資金を動かせないことを意味します。
- トランザクション（transaction）は他のシールドされたトランザクションと同じように見えます。しきい値署名が使用されたことを示すオンチェーン（on-chain）の痕跡はありません。
- これは公開型（transparent）マルチシグとは根本的に異なります。公開型マルチシグはオンチェーンで公開され、Zcashは長年サポートしてきましたが、FROSTはシールドされたプール（pool）内で機能します。
- DAO、取引所（exchange）、カストディサービス、共同貯蓄、チームのトレジャリー（treasury）など、鍵に関する単一障害点を許容できないあらゆる場面で役立ちます。

---

## FROSTとは、平易な言葉で言うと何ですか？

3人のビジネスパートナーが、それぞれ鍵の一部を持っていると想像してください。共同ウォレット（wallet）から支出するには、3人のうち任意の2人が同意して共同署名する必要があります。結果として得られるトランザクションは、通常の個人送金とまったく同じに見えます。ブロックチェーン（blockchain）上から複数人が関与したことを見分けることはできません。

FROST（**Flexible Round-Optimized Schnorr Threshold Signatures**）は、シールドされたZcashでこれを可能にする暗号プロトコルです。これはChelsea Komlo（University of Waterloo / Zcash Foundation）とIan Goldbergによって作られました。

主な特性は以下のとおりです。

- **しきい値**：t-of-nの署名者だけが参加すればよいです（例：2-of-3、3-of-5）。
- **シールドされた**：Orchardプライバシー（privacy）プール内で機能し、金額、送信者、受信者は非公開のままです。
- **識別不能**：最終的な署名（signature）は、他のZcashシールドされたトランザクションと同じように見えます。
- **ノンカストディアル（custodial）**：コーディネーターを含め、単一の当事者が完全な鍵を保持することはありません。

---

## しきい値カストディはいつ使うべきですか？

しきい値カストディは、**鍵1つまたは人物1人を失っても、資金を失うことになってはならない**場合に適しています。

| 状況 | しきい値カストディが役立つ理由 |
|-----------|----------------------------|
| **DAOまたはチームのトレジャリー** | 単一の管理者が一方的に資金を引き出すことはできず、コンセンサス（consensus）が必要です。 |
| **取引所またはカストディアン** | セキュリティゾーンや従業員に鍵のリスクを分散できます。 |
| **個人のコールドストレージ（信頼できる家族と）** | 自分と家族2人による2-of-3です。死亡またはアクセス喪失が起きても、資金は失われません。 |
| **エスクロー** | 購入者、販売者、仲裁者がそれぞれシェアを保持し、2人が同意した時点で資金が解放されます。 |
| **高額な助成金（grant）の支払い** | ZCG方式では、支払い前に複数の独立した署名者が必要です。 |
| **developerの鍵管理** | 内部脅威を防止します。単一のエンジニアがプロトコル資金を引き出すことはできません。 |

個人で単独管理するウォレット、小額資金、または追加の調整負担がリスク低減を上回る状況では、しきい値カストディはおそらく**必要ありません**。

---

## 公開型マルチシグとどう異なりますか？

Zcashは長年、公開型マルチシグをサポートしてきました。これはtアドレスからの支出に複数の鍵を必要とする仕組みです。しかし、公開型マルチシグには大きなプライバシーコストがあります。**マルチシグの構造、すべての公開鍵、すべての署名者がブロックチェーン上で可視化されます**。

FROSTは、シールドされたプール内で動作することでこれを解決します。

| | 公開型マルチシグ | FROSTしきい値（シールドされた） |
|--|---------------------|--------------------------|
| プール | 公開型（公開） | Orchard（シールドされた） |
| 署名者はオンチェーンで可視 | はい — すべての公開鍵が公開されます | いいえ — 単一署名者による支出と識別できません |
| 金額は可視 | はい | いいえ |
| 必要な調整 | オンチェーンスクリプト | オフチェーンでの通信ラウンド |
| プライバシー | なし | 完全なシールドされたプライバシー |

## トレードオフと制限事項

FROSTは強力ですが、使用前に理解すべき現実的なトレードオフがあります。

### 調整のオーバーヘッド
署名ラウンドを完了するには、署名者が同時に、またはほぼ同時にオンラインである必要があります。t人の署名者が異なるタイムゾーンにいたり、接続が不安定だったりする場合、支出には単独ウォレットでは不要な調整が必要です。

### 定足数が利用できない場合は署名できません
十分な数のキーホルダーが利用できない場合（病気、旅行中、応答なしなど）、資金は一時的に支出不能になります。しきい値とシェア数は慎重に選んでください。2-of-3は2-of-2よりも回復力があります。

### 鍵生成セレモニー
FROSTの設定には、n人の参加者全員が同時にオンラインになる分散鍵生成（DKG）セレモニーが必要です。これは一度きりのイベントですが、慎重に実施しなければなりません。DKG中に参加者が侵害されると、セキュリティが損なわれます。

### ツール群はまだ成熟段階です
シールドされたFROSTZcashは比較的新しいものです。IETF標準（draft-irtf-cfrg-frost）は成熟していますが、ウォレット統合は限定的です。標準的な単一鍵ウォレットと比べると、いくつかの粗い部分があることを想定してください。

### 復旧の複雑さ
シャードを失っても世界の終わりではありません（それがしきい値の目的です）。ただし、復旧計画は事前に文書化しておく必要があります。バックアップを保持するのは誰ですか？2つのシャードを同時に失った場合、何が起こりますか？

## FROST上のZcashで構築しているのは誰ですか？

### Zcash Foundation — frost.zfnd.org
Zcash Foundationは、動作するFROST実装とデモサイトを提供しています。これはテストと開発に使用されるリファレンス実装です。

### Ywallet FROSTデモ
Ywalletには初期のFROSTデモ統合があり、[Ywallet FROSTデモガイド](/guides/Ywallet_FROST_Demo)で説明されています。Ywalletは現在メンテナンスされておらず、Ironwood向けに更新されることもないため、このガイドは現在実行するものではなく背景情報としてお読みください。同じdeveloperによるZkoolは維持されている後継であり、機能の1つとしてFROSTマルチシグを挙げています。

### ZecHub Hackathon 2026 — FROSTトラックのプロジェクト

FROSTトラックは、ZecHub Hackathon 2026で最も競争が激しいトラックでした。注目すべきプロジェクトは以下のとおりです。

- **ZecVault** — メインネット上で決済される2-of-3シールドされたエスクロー（FROSTしきい値）
- **Steward** — 復旧を重視したUXを備えた、シールドされたZcashのしきい値カストディ

### Coinbase
Coinbaseは、Bitcoin向けのしきい値署名システムのために、本番環境用のFROST実装を構築しました。これは前処理段階を削除し、アグリゲーターの役割をすべての参加者に分散する変更を加えたものです。その経験は、本番規模におけるFROSTのセキュリティモデルを裏付けています。

## 署名セッションの仕組み（簡略版）

1. **セットアップ（1回のみ）：** n人の参加者全員が分散鍵生成（DKG）セレモニーを実行します。各参加者は秘密シャードを受け取り、共有公開鍵が導出されます。完全な秘密鍵を知る当事者はいません。

2. **署名者の調整：** 支出が必要になったとき、コーディネーター（署名者の1人でも構いません）が、署名する意思のあるt人の参加者からcommitmentを集めます。

3. **ラウンド1：** 参加する各署名者はノンスを生成し、commitment（公開情報であり、機密ではありません）をブロードキャストします。

4. **ラウンド2：** 参加する各署名者は、自身の秘密シャードを使って部分署名を計算し、それをブロードキャストします。

5. **集約：** コーディネーターはt個の部分署名を1つの最終Schnorr署名に結合します。これはオンチェーンでは単一当事者の署名と識別できません。

6. **ブロードキャスト：** トランザクションは通常どおりZcashネットワークにブロードキャストされます。

いずれかの署名者が不正な部分署名を送信した場合、プロトコルはその署名者を特定して中止します（その署名者は以降のセッションから除外されます）。調整はオフチェーンで行われ、ブロックチェーンが見るのは最終トランザクションだけです。

## しきい値パラメータの選び方

| 構成 | 回復力 | リスク |
|-------|-----------|------|
| 1-of-1 | 回復力なし — 単一障害点 | 鍵の喪失 = 永久的な喪失 |
| 2-of-2 | 両方の署名者が必要 — 耐障害性なし | 1人が利用不能 = 資金凍結 |
| 2-of-3 | 1つのシャードを失うか利用不能でもよい | 3-of-5より低いセキュリティマージン |
| 3-of-5 | 2つのシャードを失ってもよく、強力なセキュリティ | 調整のオーバーヘッドが大きい |
| 3-of-7 | 機関レベルで、2件の障害に耐えられる | 調整コストが高い |

ほとんどのチームにとって実用的な出発点は、**2-of-3**（回復力があり、調整が最小限）または**3-of-5**（機関向けで、より高いセキュリティ）です。
