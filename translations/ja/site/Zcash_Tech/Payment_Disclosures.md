# シールドされた支払いのproofと支払い開示

## 要約

- トランザクションIDはトランザクションを識別しますが、シールドされた受取人、金額、またはメモを明らかにしません。
- 支払い開示は、送信者が自身のウォレット（Wallet）履歴の残りを公開せずに、1件の支払いに関する選択した詳細を証明できるように設計されています。
- ビューイングキー（viewing key）は、アドレスまたはアカウントへの継続的な読み取りアクセスを付与します。継続的な監査には使用できますが、1件の支払いに関する異議申し立てには使用しません。
- 支払い開示では、商品の配送を証明したり、それだけで人物を特定したり、支払いを取り消したり、確認チェックに代わったりすることはできません。
- [ZIP 311](https://zips.z.cash/zip-0311)は依然として**ドラフト**です。現行の本文では、Orchardのサポート、公開型入力のサポート、エンコーディング、バージョニング、ユーザーインターフェースのルールが未完成です。

## トランザクションIDだけでは不十分な理由

誰でも公開型Zcash支払いの公開詳細を確認できます。ブロックエクスプローラーでは、そのアドレス、金額、確認ステータスを表示できます。

シールドされた支払いは異なる仕組みで動作します。チェーン（chain）はトランザクションがZcashのルールに従ったことを証明しますが、シールドされた送信者、受取人、金額、またはメモを公開しません。トランザクションIDを共有すれば、トランザクションがマイニングされたことは示せますが、その中にどのプライベートな支払いが含まれていたかを加盟店や第三者に証明することはできません。

これは実務上の問題を生みます。顧客は加盟店との紛争を解決する必要があるかもしれず、取引所（exchange）は出金を処理したことを証明する必要があるかもしれず、寄付者は1件の寄付を証明したいかもしれません。完全なビューイングキーを共有すると、これらのいずれのケースでも必要以上の情報が明らかになります。

[ZIP 311: Zcash支払い開示](https://zips.z.cash/zip-0311)は、より限定的な答えを提案しています。すなわち、1件のトランザクションから選択した情報を開示して認証することです。

![A transaction ID proves that a transaction exists but does not reveal shielded payment details. A ZIP 311 payment disclosure would let a verifier authenticate only the selected recipient, amount, memo, and optional sender details against the mined transaction.](/content-images/payment-disclosure-proof-flow-208c033e06.webp)

## 支払い開示の仕組み

基本的な流れは次のとおりです。

1. インタラクティブなproofが適切な場合、検証者は送信者に一意のチャレンジまたは参照情報を提供します。
2. 送信者は、開示するトランザクションおよびシールドされた出力を1件または複数件選択します。
3. 互換性のあるウォレットソフトウェアが、そのトランザクションおよび、任意でチャレンジに紐付いた支払い開示を作成します。
4. 送信者は検証者に開示を渡します。
5. 検証者は信頼できるZcashノード（node）から実際のトランザクションを取得し、それがマイニングされたことを確認し、開示を照合して検証します。
6. 有効な結果は、その開示に含まれる主張だけを確認します。

ZIPのSapling設計では、送信cipherキーを使用して、選択した各出力を復元します。これにより、出力の受取人、金額、およびメモを明らかにできます。また、少なくとも1つのトランザクション入力に対する支出権限のproofも必要です。そのため、トランザクションを単に見た人が、自分が送信したかのように有効な開示を作成することはできません。

Saplingの支払い開示では、送信者アドレスを明らかにする必要はありません。支出権限は多数の多様化アドレスを制御できるため、支出の制御を証明しても、1つのアドレスが自動的に特定されるわけではありません。ZIP 311には、proofを既知の送信者アドレスに結び付ける必要がある場合のために、任意のアドレスproofが含まれています。

## 支払い開示とビューイングキーの比較

| 方法 | 最適な用途 | 明らかになる情報 | 継続的なアクセス | 支払いに暗号学的に紐付いているか |
| --- | --- | --- | --- | --- |
| Transaction ID | トランザクションがマイニングされたことの確認 | 公開トランザクションデータと確認情報 | いいえ | はい。ただし、シールドされた支払いの詳細は隠されたままです |
| Screenshot or receipt | 非公式な記録管理 | 送信者が表示を選択したすべての情報 | いいえ | いいえ。画像は編集できます |
| Payment disclosure | 1件の支払いに関する選択した詳細の証明 | 選択したトランザクション出力と、含まれる送信者またはチャレンジproof | いいえ。ただし、共有されたproofはコピーできます | はい |
| Incoming Viewing Key | アカウントが受け取った支払いの監視 | キーが対象とする受信アクティビティ | はい | 一致する受信支払いを復号します |
| Full Viewing Key | アカウントの会計または監査 | キーが対象とする受信および送信アクティビティ、金額、メモ、残高 | はい | 一致するアカウントアクティビティを復号します |

質問に答えるために必要な最小限の開示を使用してください。1件の支払いに関する加盟店との紛争では、通常、アカウント内のすべての支払いへのアクセスは正当化されません。完全な報告期間を確認しなければならない会計担当者には、代わりにビューイングキーが必要になる場合があります。

いずれの方法でも支出権限は付与されません。支払いのproofとして、シードフレーズ（seed phrase）、支出鍵（spending key）、秘密鍵、またはウォレットバックアップを決して共有しないでください。

![A transaction record is available today but provides no new third-party proof. A payment disclosure would prove selected details of one payment. A viewing key provides broader, ongoing visibility.](/content-images/payment-disclosure-scope-0585cdc075.webp)

## 現在利用できるものは何ですか？

現在、ZIP 311の支払い開示の作成または検証を実装しているウォレットは、ここでは特定されていません。ZIPは引き続きドラフトであり、そのリファレンス実装は「TBD」と記載されています。以下の保守されているツール（tools）は、送信者、受取人、または認可された監査担当者が、現在利用可能な記録を確認する際に役立ちます。

| アプリ | 現在役立つ用途 | 重要な制限 |
| --- | --- | --- |
| [Zkool](https://github.com/hhanh00/zkool2) | 詳細なトランザクションメタデータ、金額、プール（pool）の入力と出力、メモの表示。UnifiedまたはSaplingビューイングキーを閲覧専用アカウントへインポートすること | ZIP 311の開示作成または検証を提供すると公表していません |
| [Zingo PC](https://github.com/zingolabs/zingo-pc) | シールドされたトランザクション履歴とメモの確認。Unified Full Viewing Keyを読み取り専用モードでインポートすること | ウォレット記録または読み取り専用アカウントは、選択的に範囲を限定した支払い開示ではありません |
| [Zallet](https://zcash.github.io/zallet/) | `z_viewtransaction`、`z_exportviewingkey`、`z_importviewingkey`を使用するオペレーターのワークフロー | ベータソフトウェアです。ビューイングキーおよびトランザクションRPCは、ZIP 311のproofではなく、より広範な情報またはローカルの記録を対象とします |

まず、支払いを送信または受信したウォレットを使用してください。トランザクション詳細、メモ、トランザクションID、確認情報を確認し、その後、相手方に自身の記録とそれらの詳細を比較するよう依頼してください。証拠を作成するためだけに新しいウォレットをインストールしてシードフレーズを入力しないでください。監査担当者が継続的な可視性を必要とする場合は、互換性のある閲覧専用アカウントを検討し、共有する前にビューイングキーの範囲を理解してください。

これらのアプリは、記録を確認するための実用的な代替手段であり、標準化された支払い開示が利用可能である証拠ではありません。スクリーンショットは記録の比較に役立つ場合がありますが、編集可能であり、暗号学的proofではありません。

## 支払い開示が適用される場面

### 加盟店との紛争

顧客は、特定の金額が加盟店のシールドされたアドレスに送られたことを証明できます。このproofは、商品が配送されたこと、返金義務があること、または提示した人物が特定の法的身元を持つことを立証しません。これらの問題は引き続き注文記録と当事者間の合意に依存します。

### シールドされた出金

ZIP 311では、シールドされた出金を対象ユースケース（use case）として挙げています。取引所は、これらの詳細をオンチェーン（on-chain）で公開せずに、受取人と金額を証明します。公開型入力のproofは未完成のままであるため、これはまだ完全に標準化されたワークフローではありません。顧客はトランザクションの確認ステータスも独自に確認しなければなりません。

### 寄付

寄付者またはキャンペーンは、無関係な支払いをプライベートに保ちながら、特定の寄付を証明できます。開示を公開すると、その選択した詳細はコピーを受け取るすべての人に公開されるため、公開proofが不要な場合は、プライベートな検証チャネルの方が安全です。

### 会計

会計担当者が1件のトランザクションの証拠を必要とする場合は、支払い開示を使用してください。会計担当者が多数のトランザクションまたは完全な報告期間への継続的なアクセスを必要とする場合は、最も範囲の狭い適切なビューイングキーを使用してください。

## プライバシーを守るワークフロー

ZIP 311は、まだ完成し、広く展開可能なウォレット標準ではありません。互換性のある送信者および検証者ツールが利用可能になったら、次のチェックリストを使用してください。

1. **まず互換性を確認してください。** 両方のツールが同じ開示形式と、その支払いで使用されたシールドされたプールをサポートしていなければなりません。
2. **通常の問題を先に解決してください。** プライベートな詳細を明らかにする前に、ウォレットの同期、トランザクションID、確認数、有効期限ステータス、受取人の記録を確認してください。
3. **チャレンジを要求してください。** 紛争の場合、検証者は新しい注文番号またはランダムなチャレンジを提供し、開示がその要求に紐付くようにする必要があります。
4. **必要な出力だけを選択してください。** 同じトランザクションに含まれる無関係な出力を含めないでください。
5. **公開されるすべての項目をプレビューしてください。** エクスポート前に、受取人、金額、メモ、送信者アドレスproof、チャレンジを確認してください。
6. **プライベートなチャネルで共有してください。** 開示は秘密の支出鍵ではありませんが、受け取った人は、そこに明らかになった情報を保持または再配布する可能性があります。
7. **チェーンに対して検証してください。** 検証者は信頼できるノードから正確なトランザクションを取得し、それが意図したネットワークおよびブロックに含まれることを確認してから、開示を検証しなければなりません。
8. **追加の秘密ではなく結果を記録してください。** 紛争、出金、寄付、または会計処理で必要とされるものだけを保持してください。

ウォレットが開示を生成できない場合、そのより広範で永続的な範囲を理解せずに完全なビューイングキーで代用しないでください。受取人が自身のウォレット記録から支払いを確認できるか、より機微性の低い記録を受け入れられるかを尋ねてください。

## 有効な開示では証明できないこと

検証が成功しても、次のことは証明されません。

- トランザクションが検証者のリスクポリシーに必要な数の確認を得ていること
- チェーン再編成によって最近のトランザクションが削除されないこと
- 商品またはサービスが提供されたこと
- 返金またはチャージバックが必要であること
- 適切なアドレスproofが含まれていない限り、送信者が特定のアドレスを制御していること
- 開示を提示した人物が主張する現実世界の身元を持つこと
- 未開示の出力、他のトランザクション、またはウォレットの残高が特定の値を持つこと
- 共有後も開示がプライベートに保たれること

検証者は、チェーンへの包含と確認ステータスを別途確認しなければなりません。ZIP 311の検証手順は、呼び出し元がすでにマイニングされたトランザクションとそのブロック高を取得していることを前提としています。

## 現在の制限事項

ZIP 311は、現行のウォレットに動作する**支払いを証明**ボタンがあるという約束ではなく、提案された標準として扱ってください。

このドラフトは現在、Saplingの支出と出力を規定していますが、Orchard、公開型入力、開示エンコーディング、バージョニング、およびウォレットが異なる有効性レベルをどのように表示すべきかについては、未完成の項目が残っています。リファレンス実装も「TBD」と記載されています。本文のとおり、OrchardまたはIronwood支払いの支払い開示は定義されていません。

トランザクションがその出力用の送信ビューイングキーなしで意図的に作成された場合、送信者は出力を開示できないこともあります。ZIP 311は、新しい復元経路を作るのではなく、そのプライバシー上の選択を維持します。

古い文書では、`zcashd`における実験的な`z_getpaymentdisclosure`および`z_validatepaymentdisclosure`コマンドについて説明しています。これらのコマンドは、**Sprout JoinSplit出力のみ**をサポートしており、ZIP 311のSapling設計をサポートしていたわけではなく、非推奨となりました。`zcashd`は2026年7月に最終的なサポート終了停止に達しました。そのレガシーな手順を現在の資金に対する指示として使用しないでください。

これらの不足は、その考え方が役に立たないことを意味するものではありません。プライバシーモデルとユースケースを、一般ユーザー向けに準備できているソフトウェアから慎重なガイドが分ける必要がある理由を説明しています。

## FAQ

### トランザクションIDだけでシールドされた支払いを証明できますか？

いいえ。IDはトランザクションとその確認ステータスを識別できますが、シールドされた受取人、金額、メモは公開されません。

### 支払い開示はビューイングキーと同じですか？

いいえ。開示は、1件のトランザクションに関する選択した詳細に範囲が限定されます。ビューイングキーは、アドレスまたはアカウントに一致するアクティビティを時間の経過とともに明らかにできます。

### 受取人は送信者のproofを作成できますか？

ZIP 311の設計ではできません。有効な開示は、少なくとも1つの入力に対する支出権限を証明しなければなりません。受取人は自身のウォレット記録を使用して支払いを確認できますが、それは別の主張です。

### 共有後に開示を取り消すことはできますか？

いいえ。ビューイングキーのように将来のアカウントアクセスを付与するものではありませんが、明らかになったデータとproofはコピーできます。あらゆるプライベートな金融記録と同じように慎重に共有してください。

### 検証によってZECが移動またはロックされますか？

いいえ。開示の作成または検証によって、資金が支出、返金、凍結、または取消されることはありません。

### ウォレットに開示機能がない場合、現在は何を使用すべきですか？

まず、受取人のウォレット記録、トランザクションIDと確認ステータス、暗号化されたメモ内の請求書参照情報、または相互に受け入れられる別の領収書を使用してください。そのより広い範囲が真に必要であり理解されている場合にのみ、ビューイングキーを使用してください。
