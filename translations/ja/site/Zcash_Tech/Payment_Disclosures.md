# シールドされた支払い証明と支払い開示

## 要約

- トランザクションIDはトランザクションを識別しますが、シールドされた受取人、金額、メモは明らかにしません。
- 支払い開示は、送信者がウォレット履歴の残りを公開せずに、1件の支払いに関する選択された詳細を証明できるように設計されています。
- 閲覧キーは、アドレスまたはアカウントへの継続的な読み取りアクセスを許可します。継続的な監査には使用できますが、1件の支払いに関する紛争には使用しません。
- 支払い開示では、商品の配送を証明したり、それ単独で人物を特定したり、支払いを取り消したり、確認チェックの代替としたりすることはできません。
- [ZIP 311](https://zips.z.cash/zip-0311) は依然として**ドラフト**です。現在の文面では、Orchardのサポート、透明入力のサポート、エンコーディング、バージョニング、ユーザーインターフェースのルールが未完成のままです。

## トランザクションIDだけでは不十分な理由

誰でも透明なZcash支払いの公開詳細を確認できます。ブロックエクスプローラーでは、アドレス、金額、確認状況を表示できます。

シールドされた支払いは異なります。チェーンはトランザクションがZcashのルールに従ったことを証明しますが、シールドされた送信者、受取人、金額、メモは公開しません。トランザクションIDを共有すれば、トランザクションが採掘されたことは示せますが、その中に含まれるどのプライベートな支払いかを加盟店や第三者に証明することはできません。

これは実務上の問題を生みます。顧客は加盟店との紛争を解決する必要があるかもしれず、取引所は出金を処理したことを証明する必要があるかもしれず、寄付者は1件の寄付を証明したいかもしれません。完全な閲覧キーを共有すると、こうしたいずれのケースでも必要な情報を大きく超えて公開してしまいます。

[ZIP 311: Zcash支払い開示](https://zips.z.cash/zip-0311)は、より限定的な解決策を提案しています。すなわち、1件のトランザクションから選択した情報を開示し、認証することです。

![A transaction ID proves that a transaction exists but does not reveal shielded payment details. A ZIP 311 payment disclosure would let a verifier authenticate only the selected recipient, amount, memo, and optional sender details against the mined transaction.](https://raw.githubusercontent.com/ZecHub/zechub/main/site/Zcash_Tech/assets/payment-disclosure-proof-flow.png)

## 支払い開示の仕組み

基本的な流れは次のとおりです。

1. インタラクティブな証明が適切な場合、検証者は送信者に一意のチャレンジまたは参照情報を渡します。
2. 送信者は、開示するトランザクションおよびシールドされた出力を1つ以上選択します。
3. 対応するウォレットソフトウェアが、そのトランザクションと、任意でチャレンジに紐付けられた支払い開示を作成します。
4. 送信者は検証者に開示を渡します。
5. 検証者は、信頼できるZcashノードから実際のトランザクションを取得し、それが採掘済みであることを確認してから、開示を照合して検証します。
6. 有効な結果は、その開示に含まれる主張のみを確認します。

ZIPのSapling設計では、送信側暗号鍵を使用して、選択した各出力を復元します。これにより、出力の受取人、金額、メモを明らかにできます。また、少なくとも1つのトランザクション入力に対する支出権限の証明も必要とします。そのため、単にトランザクションを見ただけの人が、自分が送ったかのように有効な開示を作成することはできません。

Saplingの支払い開示では、送信者アドレスを公開する必要はありません。支出権限は多数の多様化アドレスを制御できるため、支出の制御を証明しても、1つのアドレスが自動的に特定されるわけではありません。ZIP 311には、証明を既知の送信者アドレスに結び付ける必要がある場合のために、任意のアドレス証明が含まれています。

## 支払い開示と閲覧キーのどちらを使うべきですか？

| 方法 | 最適な用途 | 明らかになる情報 | 継続的なアクセス？ | 支払いと暗号学的に結び付いている？ |
| --- | --- | --- | --- | --- |
| トランザクションID | トランザクションが採掘されたことの確認 | 公開トランザクションデータと確認情報 | いいえ | はい。ただし、シールドされた支払いの詳細は非公開のままです |
| スクリーンショットまたは領収書 | 非公式な記録管理 | 送信者が表示することを選んだ情報 | いいえ | いいえ。画像は編集できます |
| 支払い開示 | 1件の支払いについて選択した詳細を証明すること | 選択したトランザクション出力、および含まれている送信者またはチャレンジの証明 | いいえ。ただし、共有された証明はコピーできます | はい |
| Incoming Viewing Key | アカウントが受け取った支払いの監視 | キーの対象となる受信アクティビティ | はい | 一致する受信支払いを復号します |
| Full Viewing Key | アカウントの会計または監査 | キーの対象となる受信・送信アクティビティ、金額、メモ、残高 | はい | 一致するアカウントアクティビティを復号します |

質問に答えるために必要な最小限の開示を使用してください。1件の支払いに関する加盟店との紛争は、通常、アカウント内のすべての支払いへのアクセスを正当化しません。会計担当者が報告期間全体を確認する必要がある場合は、代わりに閲覧キーが必要になることがあります。

いずれの方法も、支出の権限を与えるものではありません。支払いの証明として、シードフレーズ、支出キー、秘密鍵、またはウォレットのバックアップを決して共有しないでください。

![A transaction record is available today but provides no new third-party proof. A payment disclosure would prove selected details of one payment. A viewing key provides broader, ongoing visibility.](https://raw.githubusercontent.com/ZecHub/zechub/main/site/Zcash_Tech/assets/payment-disclosure-scope.png)

## 今日利用できるものは？

現在、ZIP 311の支払い開示の作成または検証を実装しているウォレットは、ここでは確認されていません。ZIPはドラフトのままであり、参照実装は「TBD」と記載されています。以下の保守されているツールは、今日利用可能な記録を送信者、受取人、または認可された監査者が確認する際に役立ちます。

| アプリ | 現在役立つ用途 | 重要な制限 |
| --- | --- | --- |
| [Zkool](https://github.com/hhanh00/zkool2) | 詳細なトランザクションメタデータ、金額、プールの入力と出力、メモの表示。UnifiedまたはSapling閲覧キーを閲覧専用アカウントにインポートすること | ZIP 311の開示作成または検証を提供しているとは案内していません |
| [Zingo PC](https://github.com/zingolabs/zingo-pc) | シールドされたトランザクション履歴とメモの確認。Unified Full Viewing Keyを読み取り専用モードでインポートすること | ウォレット記録や読み取り専用アカウントは、選択的に範囲を限定した支払い開示ではありません |
| [Zallet](https://zcash.github.io/zallet/) | `z_viewtransaction`、`z_exportviewingkey`、`z_importviewingkey`を使用する運用者向けワークフロー | ベータソフトウェア。その閲覧キーおよびトランザクションRPCは、ZIP 311の証明ではなく、より広範な情報またはローカル記録です |

まず、支払いを送信または受信したウォレットを使用してください。トランザクションの詳細、メモ、トランザクションID、確認状況を確認し、次に相手方に自身の記録とそれらの詳細を比較するよう依頼してください。証拠を作成するためだけに、新しいウォレットをインストールしてシードフレーズを入力しないでください。監査者に継続的な可視性が必要な場合は、互換性のある閲覧専用アカウントを検討し、共有前に閲覧キーの範囲を理解してください。

これらのアプリは記録を確認するための実用的な代替手段であり、標準化された支払い開示が利用できることの証明ではありません。スクリーンショットは記録の比較に役立ちますが、編集可能であり、暗号学的な証明ではありません。

## 支払い開示の適用先

### 加盟店との紛争

顧客は、特定の金額が加盟店のシールドされたアドレスへ送られたことを証明できます。この証明は、商品が配送されたこと、返金義務があること、または提示者が特定の法的身元を持つことを確立するものではありません。これらの問題は依然として注文記録と当事者間の合意に依存します。

### シールドされた出金

ZIP 311では、シールドされた出金を対象ユースケースとして挙げています。取引所は、これらの詳細をチェーン上で公開せずに、受取人と金額を証明できます。透明入力の証明は依然として未完成であるため、これはまだ完全に標準化されたワークフローではありません。顧客はトランザクションの確認状況も独自に確認する必要があります。

### 寄付

寄付者またはキャンペーンは、無関係な支払いを非公開にしたまま、特定の寄付を証明できます。開示を公開すると、選択した詳細はコピーを受け取るすべての人に公開されるため、公開証明が不要な場合はプライベートな検証チャネルのほうが安全です。

### 会計

会計担当者が1件のトランザクションの証拠を必要とする場合は、支払い開示を使用してください。会計担当者が多数のトランザクションまたは報告期間全体への継続的なアクセスを必要とする場合は、最も範囲の狭い適切な閲覧キーを使用してください。

## プライバシーに配慮したワークフロー

ZIP 311は、まだ完成済みで広く展開可能なウォレット標準ではありません。互換性のある送信者用および検証者用ツールが利用可能になったら、次のチェックリストを使用してください。

1. **まず互換性を確認します。** 両方のツールが、同じ開示形式と支払いで使用されたシールドプールをサポートしている必要があります。
2. **まず通常の問題を解決します。** プライベートな詳細を公開する前に、ウォレットの同期、トランザクションID、確認数、有効期限の状況、受取人の記録を確認してください。
3. **チャレンジを要求します。** 紛争の場合、検証者は開示をその要求に紐付けるため、新しい注文番号またはランダムなチャレンジを提供する必要があります。
4. **必要な出力だけを選択します。** 同一トランザクションの無関係な出力を含めないでください。
5. **公開されるすべてのフィールドをプレビューします。** エクスポート前に、受取人、金額、メモ、送信者アドレス証明、チャレンジを確認してください。
6. **プライベートなチャネルで共有します。** 開示は秘密の支出キーではありませんが、受け取った人は、それが明らかにする情報を保持または再配布できます。
7. **チェーンに照らして検証します。** 検証者は、信頼できるノードから正確なトランザクションを取得し、意図したネットワークおよびブロックに含まれていることを確認してから、開示を検証する必要があります。
8. **追加の秘密ではなく結果を記録します。** 紛争、出金、寄付、または会計プロセスで必要となるものだけを保持してください。

ウォレットが開示を生成できない場合、そのより広範かつ恒久的な範囲を理解せずに完全な閲覧キーで代用しないでください。受取人が自身のウォレット記録から支払いを確認できるか、あるいはより機微性の低い記録を受け入れられるかを尋ねてください。

## 有効な開示で証明できないこと

検証が成功しても、次のことは証明されません。

- トランザクションが検証者のリスクポリシーに十分な確認数を持つこと
- チェーン再編成によって最近のトランザクションが削除されないこと
- 商品またはサービスが提供されたこと
- 返金またはチャージバックが必要であること
- 適切なアドレス証明が含まれていない限り、送信者が特定のアドレスを制御していること
- 開示を提示する人物が主張する現実世界の身元を持つこと
- 開示されていない出力、他のトランザクション、またはウォレット残高に特定の値があること
- 共有後も開示がプライベートであり続けること

検証者は、チェーンへの含有と確認状況を別途確認する必要があります。ZIP 311の検証手順は、呼び出し元が採掘済みトランザクションとそのブロック高をすでに取得していることを前提としています。

## 現在の制限

ZIP 311は、現在のウォレットに動作する**支払いを証明**ボタンがあるという約束ではなく、提案された標準として扱ってください。

このドラフトは現在、Saplingの支出と出力を規定していますが、Orchard、透明入力、開示のエンコーディング、バージョニング、ウォレットが異なる有効性レベルを表示する方法については、未完成の項目が残っています。参照実装も「TBD」と記載されています。文面どおりでは、OrchardまたはIronwoodの支払いに対する支払い開示を定義していません。

トランザクションがその出力に対する送信閲覧キーなしで意図的に作成された場合、送信者も出力を開示できないことがあります。ZIP 311は、新たな復元経路を作るのではなく、そのプライバシー上の選択を維持します。

古い文書では、`zcashd`における実験的な`z_getpaymentdisclosure`および`z_validatepaymentdisclosure`コマンドについて説明しています。これらのコマンドは**Sprout JoinSplit出力のみ**をサポートしており、ZIP 311のSapling設計ではなく、すでに非推奨となっています。`zcashd`は2026年7月に最終的なサポート終了停止に達しました。現在の資金に対する手順として、このレガシーな説明を使用しないでください。

これらの不足が、この考え方を無用にするわけではありません。慎重なガイドが、プライバシーモデルとユースケースを、一般のユーザーが利用できる状態にあるソフトウェアから分けなければならない理由を説明しています。

## よくある質問

### トランザクションIDだけでシールドされた支払いを証明できますか？

いいえ。IDはトランザクションとその確認状況を識別できますが、シールドされた受取人、金額、メモは公開されません。

### 支払い開示は閲覧キーと同じですか？

いいえ。開示の範囲は、1件のトランザクションに関する選択された詳細に限定されます。閲覧キーは、時間の経過とともにアドレスまたはアカウントに一致するアクティビティを明らかにできます。

### 受取人は送信者の証明を作成できますか？

ZIP 311の設計ではできません。有効な開示は、少なくとも1つの入力に対する支出権限を証明しなければなりません。受取人は自身のウォレット記録を使用して支払いを確認できますが、それは別の主張です。

### 共有後に開示を取り消すことはできますか？

いいえ。閲覧キーのように将来のアカウントアクセスを許可するものではありませんが、公開されたデータと証明はコピーできます。プライベートな金融記録と同じくらい慎重に共有してください。

### 検証によってZECが移動またはロックされますか？

いいえ。開示の作成または検証によって、資金が支出、返金、凍結、または取り消されることはありません。

### ウォレットに開示機能がない場合、現在は何を使うべきですか？

受取人のウォレット記録、トランザクションIDと確認状況、暗号化されたメモ内の請求書参照、または双方が受け入れた別の領収書から始めてください。より広い範囲が本当に必要で理解されている場合にのみ、閲覧キーを使用してください。
