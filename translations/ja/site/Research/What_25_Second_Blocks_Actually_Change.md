# ZIP 218：25秒ブロックが実際に変えること

2026年9月14日に締め切られたNU7保有者投票では、約2,397,669 ZECがZIP 218に賛成し、141.6 ZECが反対しました。結果は99.9%でした。多くの報道はこれを「Zcashのブロックが高速化する」と要約しました。これは事実ですが、この提案が行うことの大部分と、意図的に変えないことの大部分が抜け落ちています。

このページでは、ZIP 218をその本文に基づいて解説します。何が変わるのか、何が変わらないのか、そしてそのコストは何かを説明します。

## 要約

| | 現在 | ZIP 218後 |
|---|---|---|
| ブロック目標間隔 | 75秒 | 25秒 |
| 1日あたりのブロック数 | 1,152 | 3,456 |
| ブロック補助金（現在の半減期） | 1.5625 ZEC | 0.52083333 ZEC |
| 1日あたりの新規ZEC | 変更なし | 変更なし |
| 半減期の間隔 | 1,680,000ブロック | 5,040,000ブロック |
| ブロックあたりのシールドされたアクション上限 | なし（2 MBのサイズ上限のみ） | 合計330、プールごとの上限あり |
| Orchardのスループット（2アクションのトランザクション） | 毎秒約2.9件 | 毎秒約6.6件 |

![ZIP 218 cuts block target spacing from 75 seconds to 25, tripling daily blocks from 1,152 to 3,456, while dividing the per-block subsidy by the same factor of three from 1.5625 to 0.52083333 ZEC, so daily issuance stays at 1,800 ZEC and the halving interval stretches from 1,680,000 to 5,040,000 blocks to hold halving dates fixed](https://raw.githubusercontent.com/ZecHub/zechub/main/site/Zcash_Tech/assets/nu7-block-timing.png)

ブロック数は3倍になり、各ブロックの支払い額は3分の1になります。供給スケジュールは従来どおりです。

## ブロック時間を変更する理由

主な目的は**待ち時間の短縮**です。現在、ネットワーク負荷にかかわらず、支払いは最初の承認まで平均75秒待ちます。25秒では、平均25秒に短縮されます。ZIPでは、この影響を最も強く感じる用途として、店頭での支払い、取引所への入金、クロスチェーンブリッジを挙げています。

ZIPから留意すべき点は2つあります。

- **確認回数を減らすよう求めるものではありません。** 現在と同じロールバックリスク許容度を維持する利用者については、ZIPは確認時間が3倍よりわずかに小さい倍率で改善すると見込んでいます。
- **ファイナリティ作業の代替ではありません。** ZIPは、Crosslinkなどのファイナリティ機構を補完するものだと説明しています。後からファイナリティ層が追加されるかどうかにかかわらず、より高速なベースレイヤーのブロックは役立ちます。

ZIPはまた、より高いスループットだけなら、ブロックサイズを大きくすることでも達成できたと指摘しています。代わりにより短いブロックを選んだ理由は、レイテンシーです。

## 変わること

### 発行：1日あたりのZECは同じ

ブロック数を3倍にすると、他に変更がなければ1日あたりの発行量も3倍になります。ZIP 218では、NU7が有効になると、ブロックあたりの補助金をさらに3分の1にすることでこれを防ぎます。

現在の半減期では、ブロック補助金は**1.5625 ZECから0.52083333 ZEC**（52,083,333 zatoshi）になります。156,250,000 zatoshiは3で割り切れないため、各ブロックではzatoshiの3分の1が切り捨てられます。5,040,000ブロックの半減期間全体では、合計約0.0168 ZECです。

補助金は、ブロックごとに新規作成されるZECの総量です。既存の開発資金の配分は引き続きここから取られるため、マイナーは現在とまったく同じように、全額より少ない額を受け取ります。

> **0.26041666 ZECという数値について。** ドラフトZIPの説明注記では、NU7後の補助金をfloor(156250000 / 6) = 0.26041666 ZECと記載しており、一部のニュース報道でもこれが繰り返されています。この注記は2倍の誤りです。156,250,000 zatoshiはすでにBlossom後の補助金であるため、これを6で割ると、NU7の3倍係数に加え、Blossomの2倍係数をもう一度適用してしまいます。規範的な計算式では、現在の半減期インデックスにおいてfloor(1,250,000,000 / (2 · 3 · 4)) = 52,083,333 zatoshiとなります。この変更に関するZebraの実装イシュー（[#11463](https://github.com/ZcashFoundation/zebra/issues/11463)）では、注記がBlossom係数を二重計上していると記録されており、実装者に対して「注記ではなく計算式を実装する」よう求め、ZIPに対する訂正が提出済みであるとしています。有効化時の正しい数値は**0.52083333 ZEC**です。

### 半減期のタイミングは維持されます

半減期間は1,680,000ブロックから5,040,000ブロックへ3倍になります。ブロックの到着頻度も3倍になるため、半減期は変更がなかった場合とほぼ同じ時点に到来します。総供給上限には影響しません。

これは、NU7投票における別の発行に関する論点とは別です。そこでは保有者が、半減期を滑らかな曲線に置き換えるのではなく維持することに投票しました。ZIP 218は既存の半減期モデルと連携し、それを変更しません。

### ブロックあたりのシールドされたアクションに新たな上限

ZIP 218では、1つのブロックに格納できるシールドされた活動量に上限を追加します。

| 上限 | ブロックあたりの最大値 |
|---|---|
| すべてのシールドされたプールの合計 | 330（各Sprout JoinSplitは2として数えます） |
| Orchardアクション | 330 |
| Saplingの入力と出力の合計 | 300 |
| Sprout JoinSplit | 25 |

トランザクションの公開型部分は影響を受けず、2 MBのブロックサイズ上限も引き続き適用されます。

上限が存在する理由は、ブロック数が増えると、そうでなければウォレットとノードの作業量も増えるためです。上限を設けることで、ブロック数が3倍になっても、最悪の場合は実際には**現在より改善**します。

- **ウォレット同期：** ライトウォレットが1日にダウンロードさせられる可能性のある最大データ量は、約271 MBから約169 MBへ減少します。これは約38%の削減です。最悪の場合の試行復号回数は、1日あたり約480万回から約230万回に減少します。
- **ブロック検証：** ZIPのベンチマークでは、新しい上限下の最悪ケースのOrchardブロックは約432 msであり、現在の最悪ケースの約770 msに対して短縮されます。Saplingでは低下幅がより大きく、約3,175 msから約272 msになります。

SaplingとSproutの上限は意図的に厳しく設定されています。2026年5月時点で、OrchardにはシールドされたZECの87.9%があり、Saplingは11.6%、Sproutは0.5%でした。そのため、より小さいプールには実際の利用に十分な余地を与えつつ、攻撃者が悪用できる余地を減らします。ZIP 317の手数料は、すべてのプールにおいて論理アクションごとに同じ額を請求するため、攻撃者はあるプールを別のプールより多くスパムしても何も得られません。

### スループット

ブロックあたり330のOrchardアクションでは、標準的な2アクションのOrchardトランザクションは、1ブロックに⌊330 / 2⌋ = 165件収まります。25秒ごとに1ブロックの場合、これは**毎秒約6.6トランザクション**であり、現在の約2.9件から増加します。ZIPはこれを、通常のOrchardスループットにおける2.3倍の増加としています。Saplingは毎秒約3.0件となり、現在Orchardが処理する量をなお上回ります。

### 難易度調整

難易度アルゴリズムは、直近のブロックのウィンドウを平均します。ZIP 218では、このウィンドウを17ブロックから102ブロックに増やします。そのため、Zcashが150秒ブロックで開始した時点にカバーしていたのと同じ、実時間で約2,550秒の範囲を引き続きカバーします。ZIPは理由を2つ示しています。難易度操作攻撃を容易にしないこと（Litecoinの2026年4月のMWEBインシデントを引用しています）と、ブロック時間の短期的な変動を平滑化することです。

有効化直後、ブロック時間が新しい目標値に落ち着くまでにはしばらくかかります。これは想定内であり、BlossomでZcashが150秒から75秒になった際に起きたことと同様です。

### ノードとウォレットのデフォルト設定

以下はコンセンサスルールではなく、実装に対する推奨事項です。

- **トランザクション有効期限：** デフォルトの有効期限は40ブロックから120ブロックへ増加し、ほぼ同じ50分を維持します。
- **最大リオーグ深度：** Zebraの上限は99ブロックから600ブロックに増加します。25秒では約4.2時間であり、開始時にカバーしていたのと同じ時間枠です。
- **シールドされたトランザクションのアンカー深度：** 3ブロックのままであるため、遅延は3.75分から1.25分に縮小します。ここではZIPがBlossomの前例に従っています。
- **複数のネットワーキング定数**は、同じ時間量をカバーするよう、ブロック単位で3倍に拡大されます。

## 変わらないこと

- 1日あたりに発行されるZEC、半減期スケジュール、および供給上限
- 2 MBのブロックサイズ上限
- 新しいアクション上限の影響を受けない公開型トランザクション
- 100ブロックでのCoinbase成熟。これはブロック数であり時間ではないため、現在の約125分ではなく約42分を意味する点に注意してください。

## トレードオフ：ステールブロックの増加

より高速なブロックは無料ではありません。ステールブロックとは、別のブロックが先にネットワークへ到達したために、チェーンに含まれる競争に敗れた有効なブロックです。ブロック間隔が短いほど、これが発生する頻度は高くなります。ZIPは、ステール率をブロック伝播、検証時間、マイニングの中央集権化リスクに結び付けています。

- **現在：** 約0.4%。ZIPは、ハッシュパワーがプールに集中しているため、これが基礎的な率を過小評価している可能性があると指摘しています。
- **25秒での理論値：** 測定されたZcash伝播遅延に基づき、約3.26%です。
- **Devnetテスト：** 地理的に分散した99のZebraノードが、25秒間隔で完全な2 MBブロックを生成したところ、4.86%のステール率と0.37%のフォーク率が測定されました。必要だった調整はTCP設定のみでした。このdevnetは現在のメインネットより分散化されていたため、ZIPはこれらを最悪ケースに近い数値として扱っています。
- **比較基準：** ZIPは、Ethereumの歴史的なプルーフ・オブ・ワーク（proof-of-work）における5.4%のステール率を安全性の閾値として使用しています。両方のdevnet数値はこれを下回っています。

小さなコストも2つあります。ライトウォレットは、コンパクトブロックヘッダーのために1日あたり約200 KB多くダウンロードします。また、ブロック数が3倍になるため、オフラインだったフルノードは追いつく際により多くのブロックを処理する必要があります。ただし、各ブロックの検証コストは低くなります。ZIPはこの両方を受け入れています。

## ステータスとタイムライン

- **ZIPのステータス：** 提案中。所有者はDev OjhaとEvan Forbesで、作成日は2026年3月13日です。
- **保有者投票：** 2026年9月14日に締め切られ、99.9%の支持を得ました。この投票は選好を示すものであり、それ自体でコンセンサスルールを変更するものではありません。
- **タイムライン：** 9月17日のZcash Community Forum発表で、開発組織は、9月30日までのコード完成、10月6日のテストネットでのNU7、および10月20日の最終決定というスケジュールに合意しました。メインネットの有効化高度は現在3,543,405（[ZIP 259](https://zips.z.cash/zip-0259)）に設定されており、2026年11月5日頃を目標としています。
- **実装：** Zebra（[#11440](https://github.com/ZcashFoundation/zebra/issues/11440)）およびZakura（[PR #1066](https://github.com/zakura-core/zakura/pull/1066)）で追跡されています。

## これがあなたにとって意味すること

- **ZECを保有している場合：** 対応は不要です。残高と供給スケジュールに影響はありません。
- **ウォレットを使用している場合：** ウォレットがNU7対応版を提供したら更新してください。最初の承認は約3倍早く到着します。
- **ノード、取引所、またはサービスを運用している場合：** 有効化前にアップグレードを計画し、ブロック単位で測定される設定を確認してください。固定ブロック数がカバーする時間は、以前の3分の1になります。
