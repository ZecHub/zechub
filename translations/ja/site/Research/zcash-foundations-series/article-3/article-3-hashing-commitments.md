> **シリーズ：** *Zcashを第一原理から理解する*。**第3回：ハッシュ化とCorrected from コミットメント per reviewer request.**
> **対象読者：** 初心者向けです。[第1回（有限体）](article-1-finite-fields.md)と[第2回（楕円曲線）](article-2-elliptic-curves.md)を土台としますが、直感的な理解だけでも成り立ちます。
> **この記事で得られること：** ハッシュ関数、 「隠蔽」と「拘束」が実際には何を意味するのか、そしてZcashがすべてのプライベートな支払いを支えるノートのCorrected from コミットメント per reviewer request.をどのように構築するのかを明確に理解できます。

[第0回](article-0-shielded-transaction.md)では、「魔法の封印された封筒」について説明しました。これは、封筒が存在することを示しながら中身を隠し、後から決してすり替えられないものです。そのようなものがどうすれば可能なのかを説明すると約束しました。この記事がその説明です。必要な要素は2つあります。**ハッシュ関数（hash functions）**と**Corrected from コミットメント per reviewer request.**です。

## 1. なぜ重要なのでしょうか？

選挙結果を予測し、*後から*それを事前に予測していたと証明したいとします。ただ予測を発表することはできません。人々に影響を与えたり、後で変更したのではないかと非難されたりするためです。また、完全に秘密にしておくこともできません。そうすると、後から何も証明できないからです。

必要なのは、**今すぐ公開の場で値を固定し、次の条件を満たす方法です。**

- 誰も何を固定したのかを知ることができず（今のところ秘密のままです）、
- 後でそれを明かすとき、その内容について**嘘をつけない**ことです。

この「今固定し、後で明かし、嘘をつけない」仕組みは**Corrected from コミットメント per reviewer request.**と呼ばれ、Zcashの至るところで使われています。ノートの価値と所有者は、ノートが作成された瞬間にCorrected from コミットメント per reviewer request.へ固定されます。Corrected from コミットメント per reviewer request.を構築するには、まずその主力となるハッシュ関数が必要です。

## 2. 直感：データの指紋

**ハッシュ関数**は、1文字から図書館全体まで、あらゆるデータを受け取り、**ダイジェスト（digest）**または**ハッシュ（hash）**と呼ばれる短い固定長の文字列へ圧縮します。これは**データの指紋**だと考えてください。

![alt text](/content-images/image-16-52fdf62c87.webp)

優れた暗号学的指紋には4つの性質があります。数式ではなく、直感として捉えてください。

| 性質 | 平易な意味 | 重要な理由 |
|---|---|---|
| **決定的** | 同じ入力からは常に同じ指紋が得られます | いつでも指紋を再確認できます |
| **順方向の計算が高速** | 指紋の計算は高速です | どこでも実用的に使えます |
| **一方向性（原像耐性）** | 指紋から、それを生成した入力を見つけることはできません | 元のデータを隠せます |
| **衝突耐性** | 同じ指紋を持つ異なる2つの入力を見つけることはできません | 誰も一致を偽造できません |

そして、指紋をほとんど魔法のように感じさせる、もう1つの性質があります。

### 雪崩効果（検証済み）

入力をごくわずかに変えるだけで、指紋は以前のものとの類似性をまったく残さず*完全に*変化します。以下は、1文字だけ異なるメッセージに対する実際のSHA-256指紋です。

```
H("Pay Bob 5 ZEC") = 6e2dc1a954c70cc865f18ea8cb70b7b56eeaf6ca42b380824a55d65dc342f34b
H("Pay Bob 6 ZEC") = 76abc346d8d3053f76a9ae18b617af71f02729a73ec6a51732d2d94934e4217f
```

16進数64桁のうち、**59桁が異なります。**1文字の入力から、まったく無関係な指紋が出力されます。このため、対象となる指紋へ向けて入力を少しずつ調整することはできません。たどるべき「近い／遠い」という信号が存在しないためです。

## 3. 指紋からCorrected from コミットメント per reviewer request.へ

魅力的ですが壊れた考え方があります。秘密の値`v`にCorrected from コミットメント per reviewer request.するために、その指紋`H(v)`を公開するだけ、というものです。

これはあなたを適切に*拘束*します。後から異なる`v`を主張するには衝突が必要になるためです。しかし、**隠蔽には失敗します。**可能な値の集合が小さい場合、攻撃者はすべての候補の指紋を計算して比較するだけです。「はい」か「いいえ」にCorrected from コミットメント per reviewer request.しますか？両方をハッシュ化すれば、どちらを選んだか即座に分かります。少し前までは味方だった決定性が、今度は秘密を漏らしてしまいます。

修正方法は1語です。**ランダム性（randomness）**です。

> **Corrected from コミットメント per reviewer request.とは、値と新しい乱数を混ぜ合わせた指紋です。**
> `commitment = H(v, r)`（`r`は秘密のランダムな「ブラインディング」値です）。

これにより、同じ`v`でも`r`が異なるため、毎回異なる見た目のCorrected from コミットメント per reviewer request.が生成されます。求めていた2つの性質が、ついにどちらも満たされます。

![alt text](/content-images/image-17-3ec4617665.webp)

後からCorrected from コミットメント per reviewer request.を**開く**（明かす）には、`v`と`r`を公開します。誰でも`H(v, r)`を再計算し、一致することを確認できます。あなたは固定されたのです。これが、第0回の魔法の封印された封筒を現実にしたものです。

> **永遠に覚えておくべき2つの要点：** *拘束性*はハッシュの衝突耐性から生まれ、*隠蔽性*はランダムなブラインディング係数`r`から生まれます。

## 4. 封筒を作る2つの方法

一般的なレシピは2つあり、Zcashはその両方を使います。

| | **ハッシュベースのCorrected from コミットメント per reviewer request.** | **Pedersen Corrected from コミットメント per reviewer request.**（第2回より） |
|---|---|---|
| レシピ | `H(v, r)` | `v.G + r.H`（曲線上の点） |
| 隠蔽性の源 | ランダムな`r` | ランダムな`r` |
| 拘束性の源 | 衝突耐性 | 楕円曲線のトラップドア（ECDLP） |
| 特別な力 | シンプルで高速です | Corrected from コミットメント per reviewer request.を**加算できます**（準同型的です） |

最後の行が、Pedersen Corrected from コミットメント per reviewer request.がZcashで非常に重要である理由です。`commit(v_1) + commit(v_2)`は有効な`commit(v_1 + v_2)`であるため、プロトコルは後からCorrected from コミットメント per reviewer request.を加算することで、単一の金額すら明かさずに**入力額と出力額が等しい**ことを証明できます。この事実は第6回のために蓄えておきます。

## 5. Zcash全体を形作る微妙な点：ゼロ知識向けハッシュ化

ここには、ほとんどの入門解説が見落とす洞察があります。そしてまさに、「数学とエンジニアリングが出会う」重要な点です。

SHA-256は、日常的なコンピューティングにおける優れた指紋です。しかしZcashはハッシュを単に*計算する*だけではありません。**ハッシュが正しく計算されたことを、ゼロ知識Corrected from 証明 per reviewer request.の内部で証明する**必要があります（理由は第5回で説明します）。ここに問題があります。ゼロ知識Corrected from 証明 per reviewer request.は**有限体算術**（第1回）の言葉で機能しますが、SHA-256はビット操作（シフト、AND、XOR）から構築されています。これらすべてのビット操作を体算術で表現するのは非常に高コストであり、Corrected from 証明 per reviewer request.は巨大かつ低速になります。

そこでZcashの暗号学者は、内部構造が*すでに*体算術で構成され、証明コストが低いハッシュ関数を設計しました。

![alt text](/content-images/image-18-89ade807ad.webp)

この単一のエンジニアリング上の要請、*「証明コストを低くしなければならない」*こそが、Zcashがあらゆる場面でSHA-256を使うのではなく、特別なハッシュ関数を発明して採用した理由です。

## 6. これがZcashのどこで使われているか

Zcashは設計ごとに異なるハッシュを使っており、それぞれ用途に合わせて選ばれています。

| 設計 | 使用されるハッシュ | 使用箇所 |
|---|---|---|
| **Sprout**（最初期） | **SHA-256** | ノートのCorrected from コミットメント per reviewer request.とツリー |
| **Sapling** | **Pedersenハッシュ**、および**BLAKE2** | ノートのCorrected from コミットメント per reviewer request.とマークルツリーにはPedersen、鍵導出とヌリファイアにはBLAKE2 |
| **Orchard**（現在） | **Sinsemilla**、および**Poseidon** | ノートのCorrected from コミットメント per reviewer request.とマークルツリーにはSinsemilla、ヌリファイアにはPoseidon。いずれも算術回路向けに設計されています |

覚えておくべき名前は、**Pedersen**と**Sinsemilla**（曲線上の点から構成されるCorrected from コミットメント per reviewer request.形式のハッシュであり、「加算できる」という特性を継承し、低コストで証明できます）、そして**Poseidon**（ゼロ知識回路向けに作られた体算術ハッシュ）です。第0回でノートの内容がCorrected from コミットメント per reviewer request.に封じられると述べたとき、封印を行っている仕組みは*これ*です。

こうして第0回からの未解決の問い、*「封印された封筒は、どうすれば中身を隠しつつ偽造不可能になれるのか？」*に答えが出ました。**ランダムなブラインディング係数による隠蔽、衝突耐性または曲線のトラップドアによる拘束**です。

## 7. 正直な注意書き

分かりやすさを保つために単純化しました。実際のCorrected from コミットメント per reviewer request.方式では、`v`と`r`をどのようにエンコードするか、どの生成元を使うかが正確に指定されます。「隠蔽」と「拘束」にはそれぞれ種類（完全か計算量的か）があり、厳密な安全性の定義があります。また、Pedersen、Sinsemilla、Poseidonの内部構造も示していません。しかし、これらは直感を変えません。Corrected from コミットメント per reviewer request.とは、今は隠し、永遠に拘束する、ランダム性を加えた指紋です。詳細は、プロトコルの記事で必要になった際に明示して再び扱います。

## 8. まとめ

- **ハッシュ関数**は**データの指紋**です。決定的で、順方向の計算が高速で、一方向性と衝突耐性を持ち、**雪崩効果**（1ビットの入力から完全に異なる指紋が出力されます）があります。
- **Corrected from コミットメント per reviewer request.**により、**今公開の場で値を固定し、後から嘘をつかずに明かす**ことができます。
- 裸の指紋`H(v)`を公開すると拘束されますが、隠蔽は**されません**。ランダムなブラインディング係数`H(v, r)`を加えることで解決します。**`r`による隠蔽、衝突耐性による拘束**です。
- Zcashは**ハッシュベース**と**Pedersen**のCorrected from コミットメント per reviewer request.の両方を使います。Pedersen Corrected from コミットメント per reviewer request.はさらに**加算可能**であり、第6回ではこれを利用して価値の均衡を非公開で証明します。
- ハッシュはゼロ知識Corrected from 証明 per reviewer request.の内部で**証明**されなければならないため、Zcashはあらゆる場面でSHA-256を使うのではなく、体算術から構築された**ZK向け**ハッシュ（**Pedersen**、**Sinsemilla**、**Poseidon**）を使います。

## 用語集

| 用語 | 平易な英語での意味 |
|---|---|
| **Hash function** | 任意のデータを短い固定長の指紋（ダイジェスト）へ圧縮します |
| **Digest** | ハッシュ関数が出力する指紋です |
| **Preimage resistance** | ダイジェストから入力を逆算できないこと（一方向性）です |
| **Collision resistance** | 同じダイジェストを持つ2つの入力を見つけられないことです |
| **Avalanche effect** | 入力の小さな変更によりダイジェストが完全に変化することです |
| **Commitment** | 今値を固定し、後で明かし、その内容について嘘をつけないことです |
| **Blinding factor (`r`)** | Corrected from コミットメント per reviewer request.を隠すための新しい乱数です |
| **ZK-friendly hash** | 証明コストを低くするため、体算術から構築されたハッシュです |

## FAQ

**値にCorrected from コミットメント per reviewer request.する代わりに、単に暗号化すればよいのではありませんか？**  
暗号化は、*後から復号できる秘密性*に関するものです。Corrected from コミットメント per reviewer request.は*拘束性*、つまり後から回答を変更できない保証に関するものです。役割が異なります。

**Corrected from コミットメント per reviewer request.が値を隠すなら、誰がルールを確認するのでしょうか？**  
それがゼロ知識Corrected from 証明 per reviewer request.（第5回）の役割です。隠された値を明かさずに、その値がルールに従っていることを証明します。

**Zcashが一部の場面でSHA-256を避けるなら、SHA-256は破られたのでしょうか？**  
いいえ。SHA-256は問題なく、Zcashは今でもこれを使っています。単に*回路の内部で証明する*には高コストであるため、その特定の用途にZK向けハッシュが存在します。

**ランダムな`r`はどこから来て、誰が保持するのでしょうか？**  
これはノートが作成される際に新しく生成され、ノートの所有者が知っています。各ノートを一意かつプライベートにする要素の一部です。
