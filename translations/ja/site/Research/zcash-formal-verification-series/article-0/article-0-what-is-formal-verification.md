# 形式検証とは？

### プログラムが正しいことを、ただ願うのではなく証明する方法

> **シリーズ：** *形式検証シリーズ* · **全3回中 第1回**
> **対象読者：** 完全な初心者。数学、プログラミング、暗号技術の知識は前提としません。
> **この記事を読み終える頃には：** ソフトウェアが正しいことを*証明する*とはどういう意味か、それがテストと根本的にどう異なるか、機械検証済みの証明とは何か、そしてそのような証明が約束できることの正確な（そして誠実な）限界を明確に理解できます。

ほとんどのソフトウェアは、*テスト*されているから信頼されています。多くの入力で実行し、その振る舞いを確認するのです。形式検証は、さらに大胆な問いを投げかけます。誰も試そうと思いつかなかった入力も含め、**あらゆる**可能な入力に対して、システムが期待どおりに動作することを数学的な確実性をもって*証明*できるでしょうか？この記事では、その考え方を基礎から築いていきます。まずは直感から。必要になるまで記号は使いません。

---

## 1. なぜ気にかけるべきなのでしょうか？

これは実話であり、このシリーズが存在する理由でもあります。

2022年、プライバシー重視の暗号通貨Zcashは、Orchardという新しいシールドプールを導入し、金額を隠したまま取引できるようにしました。4年間、完璧に動作し、専門家による監査も繰り返し通過していました。ところが2026年5月、基礎となる数学を注意深く考察したセキュリティ研究者が（AIツールの助けも借りて）、システムの数学にある一箇所の**制約不足**を発見しました。その一つの欠落により、攻撃者は*無制限*の偽造通貨を作れた可能性があり、金額は隠されているため、誰にも起きていることは見えなかったでしょう。この欠陥はずっと存在していたのです。

テストによって発見されたのではありません。すべてのテストは4年間通過していました。発見したのは、*数学について推論した*人でした。そしてチームは修正した際、単にパッチを当てて終わりにはしませんでした。置き換えたものにこの種類の欠陥がまったく含まれ得ないことを示す、2,700個を超える個別の定理からなる**機械検証済みの数学的証明**を書いたのです。

それが形式検証であり、得られるものは「多くのケースを試してうまく動いた」ではなく、「すべてのケースで成り立つことを証明した」です。一つでも見落としたケースが壊滅的な結果を招くシステム（通貨、航空機、医療機器、暗号技術）では、この違いがすべてです。

テストの盲点は、数十年前に計算機科学者エドガー・ダイクストラが名付けたもので、今も真実です。

> **テストはバグの*存在*を示せますが、その*不在*を示すことは決してできません。**

テストが通ったなら、その入力に対してシステムが動作することだけが分かります。試していない入力については何も分かりません。そして危険なバグは、ほとんど常に誰も試していないケースにあります。

## 2. 直感：扉を確認することと、建物を証明すること

あなたが千の扉がある建物を任され、夜にはすべての扉が施錠されていることを保証する役目だと想像してください。

- **テストのアプローチ：** 建物を回り、扉の一部を試します。50枚、100枚、500枚と試す。試した扉はすべて施錠されているので、確信は強まります。しかし、すべてを試したわけではなく、施錠されていない一枚は見逃した扉かもしれません。
- **形式検証のアプローチ：** *施錠システムそのもの*を調べ、「ロック」ボタンを押せば必ずすべての扉が施錠されることを、その設計から証明します。これなら個々の扉を試す必要はまったくありません。仕組み上不可能であるため、*どの扉も施錠されずに残ることはあり得ない*と示したのです。

違いは、**現実をサンプリングすること**と、**設計の性質を証明すること**の間にあります。テストはサンプリングします。形式検証は証明します。それが全体の考え方であり、ほかのすべてはそれを厳密に行うための仕組みです。

## 3. あらゆる形式検証を支える3本の柱

どれほど高度な形式検証であっても、正確に3つの要素から成り立っています。これらを明確に押さえれば、残りは詳細です。

| 柱 | 平易な意味 | 建物のたとえ |
|---|---|---|
| **仕様** | 「正しい」とは何を*意味するか*を正確に記述したもの | 「夜にはすべての扉が施錠されなければならない」 |
| **システム** | 実際に確認される対象（プログラム、回路、プロトコル） | 建物とその施錠機構 |
| **証明** | システムが常に仕様を満たすことを示す厳密な論証 | 「ロック」を押すと全扉が施錠されることの論理的な実証 |

そして、もう一つ静かな要素が、全体を信頼できるものにします。

- **機械チェッカー。** 証明は人間が書いて目視で確認するだけではありません。プログラム（**証明支援系**、または**定理証明器**とも呼ばれます）に渡され、*論理上の一歩一歩すべて*が検査されます。人間は曖昧に済ませたり、微妙な誤りを犯したりすることがありますが、機械は厳密に導かれないステップを受け入れません。これが、結果を**機械検証済み**と呼ぶ理由です。

![alt text](image-3.png)

名前を耳にする証明支援系には、**Lean**、**Rocq**（旧Coq）、**Isabelle**があります。これらは実質的に、非常に厳格な論理検査エンジンです。冒頭の話に出たZcashの証明は、**Lean**で書かれました。特筆すべきことに、現代のAIモデルは人間の指導のもと、これらの証明を*書く*支援にもますます使われており、以前は何年もかかった作業を数週間に短縮しています。機械はなおもすべてのステップを検査するため、速度向上によって確実性が損なわれることはありません。

## 4. 証明とは実際に何か

「証明」という言葉は威圧的に感じられるかもしれません。そこで、具体的に確認可能な例でその正体を明らかにしましょう。暗号技術ではなく、学校で習う算数だけです。

**主張：** すべての自然数`n`について、和`0 + 1 + 2 + ... + n`は`n(n+1)/2`に等しい。

これを*テスト*することはできます。`n = 5`なら`0+1+2+3+4+5 = 15`となり、`5 × 6 / 2 = 15`です。✓ 一致しています。`n = 10`も試してみましょう。和は`55`で、式からは`10 × 11 / 2 = 55`となります。✓（これらは計算・確認済みであり、実際にこの主張は直接確認すると0から999までのすべての`n`で成り立ちます。）

しかし、たとえ千個の値をテストしても、「**すべての**自然数」に到達することはできません。無限にあるからです。**証明**は、**帰納法**と呼ばれる手法を用い、有限の論証によってその無限の隔たりを埋めます。

1. **基底ケース：** `n = 0`では、和は単に`0`であり、式からは`0 × 1 / 2 = 0`となります。一致します。✓
2. **帰納ステップ：** ある数`k`について、式が成り立つと*仮定*します。次の数`k+1`を加えます。`k+1`までの和は`(sum up to k) + (k+1) = k(k+1)/2 + (k+1)`です。一行の代数計算でこれを`(k+1)(k+2)/2`に変形でき、これは`k`の代わりに`k+1`を入れた式そのものです。✓

最初（0）で成り立ち、各ステップが次の数へと成り立つことを引き継ぐため、一つの有限な論証によって、永遠に**すべての**自然数で成り立ちます。それが証明です。証明支援系もまさにこの推論を行いますが、「一行の代数計算」を含む各ステップが、それまでの内容から本当に導かれることを機械的に検証します。

> 身につけるべき飛躍はこれです。証明は「無限に多くのケース」を**有限で検証可能な論証**へ変換します。これはテストが構造上持ち得ない超能力です。

## 5. バグは実際にはどこにあるのか

形式検証が強力なのは、そもそもバグが*どこから*生じるかについて、明確な洞察を与えるからでもあります。ルールを検査するシステムのあらゆる欠陥は、次の3つの場所のいずれかにたどり着きます。

| バグの発生源 | 意味 | 証明によって排除できるか？ |
|---|---|---|
| **仕様** | 数学またはルール自体が間違っている（条件の欠落、不適切な定義） | **はい**。直接的に可能で、ここが形式検証の主戦場です |
| **実装** | 正しい仕様をコードが忠実に実行できていない | 部分的には可能。こうした失敗はしばしば検出可能な痕跡を残します |
| **破られた仮定** | システム全体が依存する何かが、誤りだと判明する | いいえ。仮定は還元不可能な基礎です |

この分類は見た目以上に重要で、第2回と第3回はこれを軸に展開します。最も深く、最も危険で、永久に隠れうるバグは、**仕様**に存在しがちです。つまり、システムが何をすべきかという数学的記述です。そして仕様こそ、機械検証済みの証明が直接、すべてのケースを一度に検査できる対象です。だからこそ本格的な形式検証の取り組みは、まずそこを目指します。

## 6. この分野で最も重要な注意点

形式検証は強力ですが、その約束は正確なものであり、それを誤解すると人は道を誤ります。したがって、慎重に述べましょう。

> **証明が保証するのは、*明記された仮定*のもとで、*システム*が*仕様*を満たすことだけです。それ以上ではありません。**

ここから4つの帰結が導かれ、どれも重要です。

- **仕様が間違っていれば、証明は無価値です。** 「すべての扉が施錠される」と証明しても、本当の要件が「すべての*窓*が施錠される」だったなら、完全に間違ったことを証明しただけです。検証は、*指定したもの*を構築したかを確認するものであり、正しいものを指定したかを確認するものではありません。
- **定義が微妙に誤って記述されていれば、保証の範囲は静かに狭まります。** 「残高」の定義がわずかに間違っていることについての証明は、すべての検査に通りながらも、あなたが考えるより少ないことしか確立しないかもしれません。だからこそ、検証の中核となる定義は短く、標準的で、人間が公開レビューできるものでなければなりません。
- **仮定が破れれば、保証は失われます。** 証明は仮定（「鍵のハードウェアが物理的に壊れていない」）の上に成り立ちます。現実において仮定が偽なら、結論は成り立たない可能性があります。
- **「バグが決してない」という意味ではありません。** 「これらの仮定のもと、この仕様が排除する種類のバグはない」という意味です。より限定的で、より誠実で、はるかに有用な主張です。

形式検証を弱めるどころか、この正確さこそがその強みです。何が得られるのかを*正確に*教えてくれます。第3回で見るように、Zcashチームが範囲と仮定を明確に述べること（「これらの名前付き仮定のもと、供給の健全性を証明したのであり、プライバシーは証明していない」）は、その誠実さの模範です。

## 7. 誠実な免責事項

読みやすくするために単純化しました。実際の仕様は英語の文ではなく正確な形式言語で書かれます。形式検証には、異なる問題に適した複数の*スタイル*（対話型定理証明、モデル検査、SMTベースの手法）があります。また、AIの支援があっても、これらの証明を書くことは熟練と労力を要する作業です。証明支援系が内部で論理をどのように表現するかも省略しました。これらのどれも、明記された仮定のもとで、仕様、システム、そして両者が一致することを示す機械検証済みの証明という核心を変えるものではありません。必要に応じて詳細に戻ります。

## 8. まとめ

- **テスト**は特定の入力をサンプリングし、バグが存在することは示せますが、バグが存在しないことは示せません。危険なバグは、誰もサンプリングしないケースに隠れています。
- **形式検証**は、**あらゆる**可能なケースで性質が成り立つことを、有限で検証可能な論証によって証明します。
- あらゆる検証には、**仕様**（正しいとは何か）、**システム**（検査する対象）、両者が一致することを示す**証明**という3本の柱に加え、すべてのステップを機械検査する（**Lean**のような）**証明支援系**があります。
- **証明**（たとえば**帰納法**によるもの）は、無限に多くのケースを一つの有限な論証に集約します。
- バグは**仕様**、**実装**、または**破られた仮定**に存在します。形式検証は仕様を直接対象にし、最も深く隠れたバグはそこに存在しがちです。
- 保証は正確です。システムが**仕様**を満たすのは、**明記された仮定**のもとに限られます。誤った仕様、誤って記述された定義、または破られた仮定は保証を無効にし、決して「バグがまったくない」ことを意味しません。

## 用語集

| 用語 | 平易な意味 |
|---|---|
| **形式検証** | システムがすべてのケースで仕様を満たすことを、数学的に証明すること |
| **仕様** | 「正しい振る舞い」とは何を意味するかを正確に記述したもの |
| **システム** | 検査される実際のプログラム、回路、またはプロトコル |
| **証明** | すべてのケースにおける主張を確立する、有限な論理ステップの連鎖 |
| **証明支援系 / 定理証明器** | 証明の各ステップを検査するソフトウェア（Lean、Rocq、Isabelle） |
| **機械検証済み** | 人間が読むだけでなく、コンピュータにより一歩ずつ検証されていること |
| **帰納法** | 最初で真であり、各ステップが次のものへ真であることを引き継ぐ証明手法 |
| **仮定** | 証明が依存する条件。偽であれば保証は成り立たない場合がある |

## FAQ

**形式検証はテストに取って代わりますか？**
いいえ。両者は補完し合います。テストは実用上の問題や誤った仮定を低コストで発見し、検証はテストでは決してサンプリングされないかもしれないバグのクラス全体を排除します。

**これほど強力なら、なぜすべてを形式検証しないのですか？**
費用がかかり、専門的なスキルを必要とするからです。ただし、AI支援によりそのコストは下がりつつあります。まれなバグが壊滅的な結果を招くシステムのために使われ、そのような場面こそコストに見合います。

**形式検証されたシステムでも失敗することはありますか？**
はい。仕様が間違っていた場合、定義が誤って記述されていた場合、仮定が成り立たなかった場合、または失敗が仕様の対象外にある場合です。証明がカバーするのは、主張している範囲だけです。

**機械検証済みの証明は、人間による証明より信頼できますか？**
大規模で複雑な証明については、一般にそうです。機械は微妙な欠落を見落としたり、曖昧な説明を受け入れたりしません。ただし、与えられた仕様と定義は依然として信頼します。

**AIが証明を書くのを支援するなら、なぜ信頼できるのですか？**
証明支援系がすべてのステップを機械的に検査するからです。AIはステップを提案し、機械がそれを検証します。誤ったステップは単に拒否されるため、AIは保証を弱めることなく作業を高速化します。
