# 形式検証（Formal Verification）とは？

### プログラムが正しいことを、ただ期待するのではなく証明する方法

> **シリーズ：** *形式検証シリーズ* · **全3部の第1部**
> **対象読者：** 完全な初心者向けです。数学、プログラミング、暗号技術の知識は前提としません。
> **この記事を読み終える頃には：** ソフトウェアが正しいことを*証明する*とは何を意味するのか、なぜそれがテストとは根本的に異なるのか、マシンチェックされたプルーフとは何か、そしてそのようなプルーフが保証できることの正確で正直な限界を明確に理解できます。

ほとんどのソフトウェアは、*テスト*（Testing）されているため信頼されています。多くの入力で実行し、その振る舞いを観察するのです。形式検証は、より大胆な問いを投げかけます。誰も試そうと思いつかなかったものも含め、考えられる**すべて**の入力に対して、システムが本来行うべきことを行うと、数学的な確実性をもって*証明*できるでしょうか。この記事では、この考え方を基礎から構築します。まず直感を扱い、必要になるまで記号は使いません。

## 1. なぜ気にかけるべきなのでしょうか？

これは実話であり、このシリーズが存在する理由です。

2022年、プライバシー重視の暗号資産 Zcash は、Orchard という新たなシールドされたプールを公開し、金額を隠した取引を可能にしました。4年間にわたり完璧に機能し、専門家による監査も繰り返し通過しました。ところが2026年5月、基礎となる数学について慎重に推論したセキュリティ研究者が、AIツールの助けも借りて、システムの数学にある1か所の**制約不足**を発見しました。このたった1つの抜け穴により、攻撃者は*無制限*の偽造通貨を作成できた可能性があり、金額は隠されているため、誰にもそれが起きたことは見えなかったでしょう。この欠陥は当初からずっと存在していました。

これはテストでは発見されませんでした。4年間、すべてのテストは通過していました。発見したのは、*数学について推論した*人物です。そしてチームは修正時に、単にパッチを当てて先へ進んだのではありません。置き換え後の仕組みにこの種の欠陥がまったく含まれないことを示す、2,700を超える個別の定理からなる**マシンチェックされた数学的プルーフ**を書きました。

これが形式検証であり、得られるものです。「多数のケースを試して動いた」ではなく、「あらゆるケースで成り立つと証明した」です。1つの見落としが壊滅的な結果につながるシステム、たとえば貨幣、航空機、医療機器、暗号技術では、この違いがすべてです。

テストの盲点は、数十年前に計算機科学者のエドガー・ダイクストラが名付けたものであり、今でも真実です。

> **テストはバグの*存在*を示せますが、その*不在*を示すことは決してできません。**

テストが通過した場合、分かるのはシステムが*その入力で*動作するということです。試していない入力については何も分かりません。そして危険なバグは、ほとんどの場合、誰も試さなかったケースにあります。

## 2. 直感：扉を確認することと、建物を証明すること

1,000枚の扉がある建物を管理しており、夜間にすべての扉が施錠されていることを保証する仕事を任されていると想像してください。

- **テストによる方法：** 建物を回り、扉の一部を試します。50枚、100枚、500枚と試すでしょう。試した扉がすべて施錠されていれば、確信は強まります。しかし、すべてを試したわけではなく、施錠されていない1枚は、飛ばした扉かもしれません。
- **形式検証による方法：** *施錠システムそのもの*を調べ、「施錠」ボタンを押せば必ずすべての扉が施錠されることを、その設計から証明します。これで、個々の扉を試す必要はまったくありません。仕組み上不可能であるため、*どの扉も施錠されずに残ることはあり得ない*と示したのです。

違いは、**現実をサンプリングすること**と、**設計の性質を証明すること**の間にあります。テストはサンプリングします。形式検証は証明します。それが全体の考え方であり、ほかのすべてはそれを厳密に行うための仕組みです。

## 3. あらゆる形式検証を支える3本の柱

どれほど高度な形式検証でも、構成要素はちょうど3つです。これらを明確に把握すれば、残りは詳細です。

| 柱 | 平易な意味 | 建物のたとえ |
|---|---|---|
| **仕様（Specification）** | 「正しい」が何を*意味するかを正確に述べたもの | 「すべての扉は夜間に施錠されなければならない」 |
| **システム（System）** | 実際に確認される対象（プログラム、回路、プロトコル） | 建物とその施錠機構 |
| **プルーフ（Proof）** | システムが常に仕様を満たすことを示す厳密な論証 | 「施錠」を押すとすべての扉が施錠されることの論理的な実証 |

そして、より控えめな4つ目の要素が、全体を信頼できるものにします。

- **マシンチェッカー。** プルーフは人間が書いて目視確認されるだけではありません。*すべての論理的なステップ*を確認するプログラム、すなわち**プルーフアシスタント（proof assistant）**、または**定理プローバー（theorem prover）**に与えられます。人間は曖昧な説明をしたり、微妙な誤りを犯したりできますが、マシンは厳密に導かれないステップを受け入れません。これが、結果を**マシンチェックされた**ものと呼ぶ理由です。

![alt text](image-3.png)

名前を耳にするかもしれないプルーフアシスタントには、**Lean**、**Rocq**（旧Coq）、**Isabelle**があります。実質的には、非常に厳格な論理チェックエンジンです。冒頭の物語における Zcash のプルーフは、**Lean** で書かれました。特に注目すべきことに、現代のAIモデルは、人間の指導のもとでこれらのプルーフを*書く*支援にますます使われており、かつて数年を要した作業を数週間へと短縮しています。それでもマシンが各ステップを確認するため、速度向上によって確実性が失われることはありません。

## 4. プルーフとは実際に何か

「プルーフ」という言葉は威圧的に感じられるかもしれません。そこで、具体的かつ確認可能な例で分かりやすく説明します。暗号技術ではなく、学校で学ぶ算数だけです。

**主張：** すべての整数 `n` について、和 `0 + 1 + 2 + ... + n` は `n(n+1)/2` に等しくなります。

これを*テスト*できます。`n = 5` では `0+1+2+3+4+5 = 15` となり、`5 × 6 / 2 = 15` です。✓ 一致します。`n = 10` も試してみましょう。和は `55` であり、式からは `10 × 11 / 2 = 55` になります。✓（これらは計算して確認できます。実際、この主張は直接確認すると、0から999までのすべての `n` について成り立ちます。）

しかし、1,000個の値をテストしても、「**すべての**整数」に到達することはできません。整数は無限にあります。**プルーフ**は、**数学的帰納法（induction）**という手法を用いて、有限の論証でこの無限の隔たりを埋めます。

1. **Base ケース：** `n = 0` では、和は単に `0` であり、式は `0 × 1 / 2 = 0` になります。一致します。✓
2. **帰納ステップ：** ある数 `k` について式が成り立つと*仮定*します。ここで次の数 `k+1` を加えます。`k+1` までの和は `(sum up to k) + (k+1) = k(k+1)/2 + (k+1)` です。1行の代数計算により、これは `(k+1)(k+2)/2` に整理でき、`k` の代わりに `k+1` を置いた式と正確に一致します。✓

最初の値である0で成り立ち、各ステップで次の数へ引き継がれるため、有限の1つの論証によって、永遠に**すべての**整数で成り立ちます。これがプルーフです。プルーフアシスタントはまさにこの推論を行いますが、「代数計算の1行」も含め、すべてのステップが前の内容から本当に導かれることを機械的に確認します。

> 理解すべき飛躍はこれです。プルーフは「無限に多いケース」を**有限で確認可能な論証**へ変えます。これが、テストには構造的に欠けている強みです。

## 5. バグは実際にはどこに存在するのか

形式検証が強力である理由の一部は、そもそもバグが*どこから*生じるのかについて明確な理解をもたらすことです。ルールを確認するシステムにおけるあらゆる欠陥は、次の3つの場所のいずれかにたどり着きます。

| バグの発生源 | 意味 | プルーフで排除できるか？ |
|---|---|---|
| **仕様** | 数学またはルールそのものが誤っていること（条件の欠落、不適切な定義） | **はい**。直接的に可能であり、ここが形式検証の主戦場です |
| **実装（Implementation）** | 正しい仕様をコードが忠実に実行できていないこと | 部分的には可能です。このような失敗は多くの場合、検出可能な痕跡を残します |
| **破綻した仮定** | システム全体が依存する何かが、誤りだと判明すること | いいえ。仮定はこれ以上還元できない基盤です |

この分類は見た目以上に重要であり、第2部と第3部はこれを軸に展開します。最も深刻で危険な、永遠に隠れ続ける可能性があるバグは、**仕様**に存在しがちです。すなわち、システムが何をすべきかという数学的な記述です。そして、仕様こそがマシンチェックされたプルーフで直接調べられる対象であり、すべてのケースを一度に扱えます。これが、本格的な形式検証の取り組みがまずそこを目指す理由です。

## 6. この分野で最も重要な注意点

形式検証は強力ですが、その保証は正確なものであり、誤解すると人を誤った方向へ導きます。したがって、慎重に述べましょう。

> **プルーフが保証するのは、*システム*が、明示された*仮定*のもとで、*仕様*を満たすことだけです。それ以上ではありません。**

ここから4つの帰結が導かれ、どれも重要です。

- **仕様が誤っていれば、プルーフには価値がありません。** 「すべての扉が施錠される」とプルーフしても、実際の要件が「すべての*窓*が施錠される」だったなら、完全に間違ったものをプルーフしたことになります。検証は、*指定したもの*を構築したことを確認するのであって、正しいものを指定したことまでは確認しません。
- **定義が微妙に誤って記述されると、保証は気付かないうちに狭まります。** 「残高」のわずかに誤った定義に関するプルーフは、すべてのチェックを通過しながら、考えているより少ないことしか確立していないかもしれません。だからこそ、検証の中核にある定義は、短く、標準的で、人間が公開してレビューできるものでなければなりません。
- **仮定が成り立たなければ、保証は失われます。** プルーフは仮定に基づいています（「鍵のハードウェアが物理的に壊れていない」など）。現実で仮定が偽であれば、結論は成り立たない可能性があります。
- **「バグが一切ない」という意味ではありません。** 「これらの仮定のもと、この仕様が排除する種類のバグは存在しない」という意味です。より限定的で、より正直であり、はるかに有用な主張です。

形式検証を弱めるどころか、この正確さこそが強みです。得られるものを*正確に*教えてくれます。第3部で見るように、Zcash チームがその範囲と仮定を明確に述べていること、すなわち「これらの名前付き仮定のもとで供給の健全性をプルーフしたのであり、プライバシーについてはプルーフしていない」という姿勢は、この正直さの模範です。

## 7. 正直な免責事項

読みやすくするために単純化しました。実際の仕様は英語の文章ではなく、正確な形式言語で記述されます。また、異なる問題に適した形式検証には、対話型定理プルーフ、モデル検査、SMTベースの手法など、複数の*スタイル*があります。AIの支援があっても、これらのプルーフを書くことは、今なお専門的な技能と努力を要する作業です。また、プルーフアシスタントが内部で論理をどのように表現するかも省略しました。これらのいずれも、明示された仮定のもとで、仕様、システム、そして両者が一致することを示すマシンチェックされたプルーフという核心を変えるものではありません。必要に応じて詳細に戻ります。

## 8. まとめ

- **テスト**は特定の入力をサンプリングし、バグが存在することは示せますが、バグが存在しないことは示せません。危険なバグは、誰もサンプリングしないケースに潜んでいます。
- **形式検証**は、有限で確認可能な論証により、**あらゆる**可能なケースで性質が成り立つことをプルーフします。
- あらゆる検証には3本の柱があります。**仕様**（正しさの意味）、**システム**（確認対象）、それらが一致することを示す**プルーフ**です。さらに、各ステップをマシンチェックする**プルーフアシスタント**（**Lean** など）があります。
- **プルーフ**は、たとえば**数学的帰納法**により、無限に多いケースを1つの有限な論証にまとめます。
- バグは**仕様**、**実装**、または**破綻した仮定**に存在します。形式検証は仕様を直接対象にします。そこは最も深く、最も隠れやすいバグが存在しがちな場所です。
- 保証は正確です。システムが**仕様**を、**明示された仮定**のもとで満たすということです。誤った仕様、誤記された定義、または破綻した仮定があれば保証は無効となり、決して「バグが一切ない」という意味にはなりません。

## 用語集

| 用語 | 平易な英語での意味 |
|---|---|
| **Formal verification** | システムがすべてのケースで仕様を満たすことを、数学的にプルーフすること |
| **Specification** | 「正しい振る舞い」が何を意味するかを正確に述べたもの |
| **System** | 確認対象となる実際のプログラム、回路、またはプロトコル |
| **Proof** | すべてのケースで主張を確立する、有限の論理的ステップの連鎖 |
| **Proof assistant / theorem prover** | プルーフの各ステップを確認するソフトウェア（Lean、Rocq、Isabelle） |
| **Machine-checked** | 人間が読むだけではなく、コンピューターがステップごとに確認したもの |
| **Induction** | 最初に真であり、各ステップが次のステップへ真を引き継ぐプルーフ手法 |
| **Assumption** | プルーフが依存する条件。偽であれば保証が成り立たない可能性があります |

## FAQ

**形式検証はテストに取って代わりますか？**  
いいえ。両者は補完し合います。テストは実務上の問題や誤った仮定を低コストで発見し、検証はテストでは決してサンプリングされないかもしれないバグのクラス全体を排除します。

**それほど強力なら、なぜすべてを形式検証しないのですか？**  
費用がかかり、専門的な技能を必要とするためです。ただし、AI支援によりそのコストは下がりつつあります。まれなバグが壊滅的な結果をもたらすシステムのために使われ、そのような場面こそコストに見合います。

**形式検証されたシステムでも失敗することはありますか？**  
はい。仕様が誤っていた場合、定義が誤記されていた場合、仮定が成り立たなかった場合、または失敗が指定された範囲の外にある場合です。プルーフが対象とするのは、主張している範囲だけです。

**マシンチェックされたプルーフは、人間によるものより信頼できますか？**  
大規模で複雑なプルーフについては、一般にそうです。マシンは微妙な抜け穴を見落としたり、曖昧な説明を受け入れたりしません。ただし、与えられた仕様と定義は依然として信頼します。

**AIがプルーフを書く支援をするなら、なぜ信頼できるのですか？**  
プルーフアシスタントが各ステップを機械的に確認するからです。AIはステップを提案し、マシンがそれを検証します。誤ったステップは単に拒否されるため、AIは保証を弱めることなく作業を高速化します。
