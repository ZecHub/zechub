# ZecHub ハッカソン・ビルダー向けガイド

## 要約

- コードを書く前に、なぜ作るのかを理解してください。複雑さより有用性が重要です
- シンプルに保ってください。未完成の大きなアイデアより、うまく仕上げた小さなアイデアの方が優れています
- Zcashのインフラストラクチャ・スタックを早めに学んでください。ここが最も難しい部分です
- アプリが資金を移動する場合、メインネットで動作しなければなりません。テストネットで構築し、その後メインネットで実証してください
- ドキュメントと明確なデモは、製品そのものより重要になることがあります
- 受賞はスタートラインです。評判を築き、コミュニティでの扉を開きます

<br/>

## 対象者

- ZecHubまたはZcashのハッカソンに初めて参加するビルダー
- Zcashに初めて触れる、他のエコシステムのCorrected from 開発者 per reviewer request.
- ハッカソンのプロジェクトを長く続くものにしたいすべての人

<br/>

## なぜ作るのかから始めましょう

エディタを開く前に、どの問題を解決しようとしているのか、そしてなぜ誰かがそれを気にかけるのかを理解してください。良いテストはシンプルです。作ろうとしているものが存在しなかった場合、誰かはそれを惜しむでしょうか。自分自身が使いたいものを作ってください。プライバシー（privacy）はZcashが存在する理由です。そのため、作ろうとしている相手にとってプライバシーがなぜ重要なのかを理解し、それをプロジェクト全体の形づくりに活かしてください。

<br/>

## まずスタックを学びましょう

他のチェーンから来たビルダーにとって最も一般的な驚きは、コーディングではなくZcashインフラストラクチャの学習曲線です。アプリを設計する前に、構成要素がどのように組み合わさるかを理解する時間を取ってください。しばしば「Z to the third」と呼ばれる中核スタック、すなわちzebrad、ライトサーバー、そしてウォレット（wallet）から始めましょう。続いて、Corrected from 開発者 per reviewer request.ツール（tools）にも慣れてください。

1. [zechub.wiki/developers](https://zechub.wiki/developers)にあるウィキのCorrected from 開発者 per reviewer request.ページを読んでください。ここが推奨される最初の訪問先です
2. zingolibとzingo-cliを調べてください。これらの呼び出しは、各トラックにおけるプロジェクトの必要事項の大半をカバーします
3. より低レベルの構築要素として、librustzcashとZODLリファレンス・ウォレットを確認してください
4. FROSTプロジェクトでは、Zcash Foundationのfrostdとcrates.ioのfrost-coreを使用してください。定義を理解する助けとしてAIも活用できますが、FROSTを安全に使用するには、依然として相応の努力と時間が必要です

<br/>

## メインネットの意味を理解しましょう

いくつかのトラックでは、アプリがZcashメインネットと相互作用する必要があります。実際には、これはあなたのプロジェクト、またはAIエージェントを含むその利用者が、メインネット上で実際の資金を送受信すること、あるいはそれを可能にするツールを構築・改善することを意味します。アプリがトランザクション（transaction）を作成する場合は、提出物でメインネット上のトランザクションを実演しなければなりません。

開発中はテストネットで構築してください。メインネットでの活動には実際のZECがかかり、時間とともにさらに高額になるため、反復作業にはテストネットが推奨されます。最終的な実証のためにメインネットへ切り替えてください。フローを設計する際には、1つの詳細を念頭に置いてください。資金がシールドされた（shielded）アドレス（address）に到着すると、ウォレットはそれらをスキャンして見つけなければ支出できず、そのスキャンには少し時間がかかります。受取資金がすぐに使えると想定するのではなく、この短い待ち時間をアプリに組み込んでください。

<br/>

## シンプルに保ちましょう

シンプルで適切に実行されたアイデアは、複雑なアイデアを何度も上回ってきました。現実の問題を解決し、理解しやすかったために、同じイベントでより技術的に野心的なプロジェクトを基本的なコンセプトが上回る場面を、審査員は見てきました。完了できると思う量より少なく引き受けてください。細部の見落とし、過大なスコープ、調査の省略は、ビルダーが賞を逃す原因となる失敗です。中核コンセプトから最初のコマンドまで、プロジェクトを理解しやすく、実行しやすいものにしてください。

<br/>

## 最初の30秒で印象をつかみましょう

レビュー担当者はすぐに強い印象を形成するため、ソリューションの新規性と並んで、プレゼンテーション、テーマ、ビジュアルには大きな重みがあります。ドキュメントと明確なデモは後回しにするものではありません。誰もあなたが作ったものを理解できなければ成功できないため、アイデアを伝えることは、ときにアイデアそのものより重要です。審査では通常、技術的な深さ、ユーザー体験、独創性、実用性がバランスよく評価され、強力なドキュメントはそのすべてを高めます。

<br/>

## より難しく参加者の少ないトラックを見てみましょう

混雑の少ない競争を望む場合、難しいトラックは挑戦する人が少ないため、応募数も少ないことがよくあります。Accountingトラックは、オンチェーン（on-chain）トランザクション作業を避けたい初心者にとって良い選択肢です。FROSTは強力で十分に活用されておらず、プロジェクトの確かな基盤になります。コミュニティは何を作るべきかを規定していないため、ゼロから始めるのではなく、エコシステムにすでにある有能なツールの上に構築することは賢明です。

<br/>

## ハッカソン後

受賞は道の終わりではありません。受賞はポートフォリオと評判を築き、コミュニティでの扉を開き、提案を通じた資金調達につながることがあります。

1. 強力なプロジェクトを、ロードマップ、マイルストーン、予算の根拠とともに、ZecHub DAOまたはZcash Community Grantsへの提案へと発展させてください
2. フォーラム、Discord、Xでコミュニティに積極的に参加し続けてください
3. Arborist R and Dミーティングに参加し、アイデアを投稿してフィードバックを求めてください
4. 受賞できなくても作り続け、次のハッカソンに注目してください
