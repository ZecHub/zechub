# Unified Address (ZIP-316) 验证

*这是一份学习指南，并非打包好的解码器或可直接复制粘贴的支付库。它解释了 Unified Address 的结构，让你能够理解受维护的库在底层所做的工作。对于任何处理真实资金的用途，请以 [ZIP-316 规范](https://zips.z.cash/zip-0316)及下方链接的官方实现为准。*

---

## 全局概览

Unified Address (UA) 是一条包含多种接收方类型的单一地址字符串：**Transparent**、**Sapling**、**Orchard**，或其组合。付款钱包会自动选择其支持的最佳接收方池。

可以将 UA 想象成一个密封信封，里面装有数张带标签的卡片。每张卡片代表一种联系你的方式。要检查一个地址，应用程序必须：

1. **打开信封：** 解码文本字符串。
2. **还原内容顺序：** 撤销保护性混淆（**F4Jumble**）。
3. **读取每张卡片：** 提取各个接收方。
4. **执行协议规则：** 根据类型码范围忽略或拒绝条目。

---

## 为什么“只解码 Bech32m”还不够

UA 使用 Bech32m 文本编码，但仅解码 Bech32m 并不会揭示可用的接收方。

ZIP-316 在编码前故意使用 **F4Jumble** 混淆载荷。F4Jumble 可确保即使只修改地址中的一个字符，解码输出也会完全改变。这能防止地址可延展性攻击：攻击者在保持前缀和后缀看起来有效的同时，替换地址中间的字节。

> **关键规则：** 只有应用程序执行完整的解码和验证流程，可延展性保护才能生效。部分解码会移除安全性，却保留所有风险。

---

## 解码流程，逐步说明

### 第 1 步：解码 Bech32m 并检查网络
- **人类可读部分（HRP）：** `u` 表示主网；`utest` 表示测试网。*(主网 UA 以 `u1` 开头，其中 `1` 是 Bech32 分隔符。)*
- **长度限制：** 标准 Bech32m 强制执行 90 个字符的限制。UA 通常超过此限制，因此必须在解码器中禁用标准长度检查。
- 将 5 位 Bech32m 字词转换回标准的 8 位字节。

### 第 2 步：反转 F4Jumble
F4Jumble 是基于 BLAKE2b 构建的 4 轮 Feistel 网络：
- **左半部分长度：** `min(64, floor(length / 2))` 字节。64 字节的上限对应 BLAKE2b 的最大输出大小。右半部分包含剩余载荷。
- **哈希函数：** 使用固定的个性化标签（`UA_F4Jumble_G` 和 `UA_F4Jumble_H`）交替使用 G 和 H。
- **轮次顺序：** 正向编码依次执行 G(0) → H(0) → G(1) → H(1)。反转（去混淆）依次执行 H(1) → G(1) → H(0) → G(0)。
- **范围检查：** 拒绝超出 ZIP-316 载荷大小限制的输入。

### 第 3 步：移除填充并验证 HRP
在混淆前，编码器会附加 16 个包含 HRP、并以零填充的字节。
- 去混淆后移除最后 16 个字节。
- 确认嵌入的 HRP 与预期网络匹配（`u` 或 `utest`）。这可防止测试网地址被意外接受为主网地址。

### 第 4 步：提取接收方
剩余载荷由 `(typecode, length, content)` 个条目组成，其中类型码和长度以紧凑大小整数存储（较小的值使用单个字节）。已知接收方类型码：

| 类型码 | 接收方类型       | 内容长度 |
| :------- | :------------------ | :------------- |
| `0x00`   | Transparent (P2PKH) | 20 字节       |
| `0x01`   | Transparent (P2SH)  | 20 字节       |
| `0x02`   | Sapling             | 43 字节       |
| `0x03`   | Orchard             | 43 字节       |

除上述之外，ZIP-316 还为前向兼容性保留了两个范围：

- **`0xC0`–`0xDF`（非必须理解元数据）：** 使用方必须忽略此范围内其无法识别的元数据项。
- **`0xE0` 和 `0xE1`（已分配的必须理解到期元数据）：** 当前 ZIP-316 注册表将其分配给地址到期高度和时间。使用方必须理解这些项目，否则拒绝该地址。
- **`0xE2`–`0xFC`（未分配的必须理解元数据）：** 若遇到此范围内无法识别的项目，使用方必须拒绝该地址。

对于已知接收方类型，验证编码长度是否与该类型指定的内容长度匹配。对于元数据项，使用其编码的紧凑大小长度确定内容长度。拒绝截断条目或任何尾随字节。

**首选接收方顺序。** 地址成功解析后，钱包或支付工具应按以下顺序选择最佳接收方：Orchard，然后是 Sapling，最后是 transparent。

## 强制性 ZIP-316 拒绝规则

**成功解码并不代表地址有效。** 官方 Zcash 钱包会严格拒绝违反下列规则的地址。网页工具也必须拒绝它们，以防止支付失败：

- **缺少屏蔽接收方：** 地址**必须**至少包含一个 Sapling 或 Orchard 接收方。仅含 transparent 接收方的 UA 根据 ZIP-316 无效。
- **重复类型码：** 每种接收方类型最多只能出现一次。
- **未排序的类型码：** 接收方必须按严格升序的类型码顺序出现。
- **冲突的 transparent 接收方：** UA 可以包含 P2PKH 或 P2SH 其中之一，但**绝不能同时包含两者**。
- **格式错误的条目或填充：** 网络前缀不匹配、载荷截断或长度不匹配，必须立即触发拒绝。
- **无法识别的类型码：** 使用方必须忽略无法识别的项目，但必须理解元数据范围（`0xE0`–`0xFC`）内的项目除外；若无法识别，必须拒绝。在当前注册表中，`0xE0` 和 `0xE1` 是已分配的到期类型，而 `0xE2`–`0xFC` 尚未分配。此外，拒绝任何未通过上述强制有效性规则的地址，包括必须具有 Sapling 或 Orchard 接收方的要求。

## 开发者最佳实践

- **比较已解析的接收方，而不是原始字符串。** 检查相等性前，先解码地址。
- **对任何处理资金的用途使用受维护的库。** 将官方 Rust crate（如 `zcash_address`）编译为 WebAssembly，而不是部署自定义的 JavaScript 解码器。
- **谨慎对待手写解析器。** 如果为了学习而编写，请将其视为学习项目，并在将其用于任何用途前，使用下方官方测试向量进行测试。

## 术语表

| :----------------------- | :-------------------------------------------------------------------- |
| **Unified Address (UA)** | 捆绑多个接收方池的单一地址字符串。 |
| **Receiver** | 特定的支付目标类型（transparent、Sapling 或 Orchard）。 |
| **Bech32m** | 用于 UA 字符串的文本编码方案。 |

| **F4Jumble** | 确保地址完整性的可逆混淆算法。 |
| **Typecode** | 每个条目中用于定义载荷内接收方类型的数字。 |
| **Malleability** | 未经授权地修改地址字节而不被发现。 |
