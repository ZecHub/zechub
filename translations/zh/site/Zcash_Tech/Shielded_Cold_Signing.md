# 屏蔽冷签名 [Shielded Cold Signing]

> **核心理念 [Key idea]：** 伴侣钱包能够看到构建和监控一笔屏蔽交易所需的全部信息。只有硬件钱包持有授权花费的权限。这种分离正是屏蔽冷签名的全部意义。

在 Zcash 中进行屏蔽 [Shielding]，是指将资金从公开、透明的地址转入私密、屏蔽的地址，并利用 Zcash 的隐私功能隐藏交易详情。

### 当你屏蔽 ZEC 时会发生什么变化？

对于一笔透明的 Zcash 交易，以下信息：

- 发送方地址
- 接收方地址
- 转账金额

都可以在 blockchain 上被观察到。

当你屏蔽 ZEC 时，你的资金会进入一个私密 pool（例如 Ironwood）。Blockchain 可以验证一笔交易是否有效，而不会披露你的私密交易详情。自 2026 年 7 月 28 日 NU6.3 升级后，新屏蔽资金会进入 Ironwood pool，因为较早的 Orchard pool 不再接受新存款，但仍允许提款。

### 屏蔽交易的组成部分

### 1. Note（屏蔽余额记录）

Note 是一项私密的加密记录，代表用户拥有的未花费 ZEC 金额。

与余额以明文列出的公开 blockchain 不同，屏蔽 note 会加密价值和所有权详情，因此链上观察者无法看到谁拥有这些资金。

发起交易时，伴侣钱包会扫描账本，识别用户未花费的 notes，并选择要花费哪些 notes。

### 2. Nullifier（双重花费检测机制）

由于 note 的详情对公开账本隐藏，网络需要一种机制来检测双重花费，而不披露正在被花费的是哪个 note。

Nullifier 是从特定 note 派生的唯一加密标记。当一个 note 被花费时，其 nullifier 会发布到 blockchain。

网络会验证该 nullifier 是否未被记录过。如果未被记录，花费即可被接受。关键在于，外部观察者无法利用 nullifier 确定它来自哪个具体 note。

伴侣钱包会在组装交易数据时派生并构建适当的 nullifier。

## 密钥 [Keys]

密钥是控制你资金访问权限的加密信息，并使你的钱包能够执行接收、查看和花费 ZEC 等操作。

一个钱包持有多种不同的密钥，每种密钥服务于不同目的，就像一个账户可能为读取访问和写入访问分别设有凭据一样。

密钥是伴侣钱包与硬件钱包之间关系的核心，因为不同密钥具有不同用途，而且其中只有一种需要始终被锁起来。

重要的是，每个屏蔽池都将其密钥构建为一棵派生树，其中箭头从一个组件指向可由其派生的内容。希望接收屏蔽支付的用户必须拥有一个屏蔽支付地址，而该地址由花费密钥生成。

### 密钥层级

**1. 花费密钥 [Spending key]**

这是安全性最敏感的密钥。它赋予加密能力，以授权花费 ZEC。

本报告其他地方提到"硬件钱包持有密钥"时，指的就是这个密钥。

在冷签名架构中，花费密钥保存在硬件钱包内，绝不会暴露给伴侣钱包。伴侣钱包根本不应需要持有此密钥。

在 Sapling 和 Orchard 中，密钥层级都会从根花费密钥派生出两条不同分支：花费权限和查看能力：

- **Sapling：** 扩展花费密钥（𝑎𝑠𝑘、𝑛𝑠𝑘、𝑜𝑣𝑘）派生出证明授权密钥（𝑎𝑘、𝑛𝑠𝑘）和完整 viewing keys（𝑎𝑘、𝑛𝑘、𝑜𝑣𝑘），后者进一步产生传入 viewing keys（𝑖𝑣𝑘）和多样化地址。
- **Orchard：** 根花费密钥（𝑠𝑘）直接分支为花费授权密钥（𝑎𝑠𝑘）和完整 viewing key（𝑎𝑘、𝑛𝑘、𝑟𝑖𝑣𝑘）。

这种结构性分离为硬件密钥隔离提供了正式的加密基础：钱包将查看分支（UFVK）导出到主机计算机，用于余额同步和交易构建，同时将花费授权分支永久锁定在设备上。

密钥派生严格单向进行。这意味着无法逆向 viewing keys 来重建花费权限。加密上的不可逆性使导出 Unified Full Viewing Key（UFVK）是安全的，因为它授予完整的钱包可见性，却不会暴露设备上的花费秘密。

**2. Viewing keys**

Zcash 将查看屏蔽活动的能力与花费该活动的能力分开。Viewing key 允许钱包或其他获授权方查看有关屏蔽交易的信息，而不授予花费权限。

- **Full Viewing Key（FVK），封装为 Unified Full Viewing Key（UFVK）：** 它有意从花费密钥派生，使软件能够检测并解密钱包的屏蔽活动，从而识别交易。它还使软件能够计算余额，却不能授权花费。最恰当的描述是：它是花费密钥的一个隐私性较低的派生物，而不是种子的弱化副本。

Full Viewing Key（FVK）在维持严格安全隔离的同时，提供完整的只读可见性。通过解密传入和传出的 note 密文（借助其传出 viewing key 组件），仅有 FVK 的伴侣钱包能够呈现完整且带标签的交易历史，而不仅仅是一个持续更新的余额。

多个不可关联的多样化支付地址共享相同的 FVK 和传入 viewing key（IVK），从而能够无限生成地址，而不会增加 blockchain 扫描开销。

这种功能分离构成冷签名工作流程的基础。所有持续的链扫描、历史记录跟踪和地址管理均被卸载至主机软件，而花费权限仍隔离在硬件设备上。

### 关键区别：UFVK 与花费密钥

> **UFVK 可以共享。花费密钥必须留在硬件钱包中。**
>
> 伴侣钱包使用 viewing key 来监控钱包、检测传入资金、识别 notes，并协助准备交易。它并不拥有授权花费所需的私钥。

如前所述，密钥分离是冷签名架构的基础。

伴侣钱包无需控制资金，即可完成准备交易所需的大部分工作。硬件钱包只需接收准备好的交易并执行最终签名操作。

硬件钱包制造商无需自行发明这种分离。Zcash 的密钥设计已经在协议层将查看能力与花费权限分开，制造商只需在这一既有结构之上构建其签名和导出功能。该协议允许从花费密钥派生出屏蔽地址或完整 viewing key 等信息，同时花费密钥本身仍保持私密，这使得 Ledger、Keystone 和 Hito 等硬件钱包能够向伴侣软件提供其所需的查看信息，而绝不暴露可花费资金的私钥。

### 伴侣钱包实际如何使用密钥信息

通过使用 viewing key 材料，伴侣钱包可以：

- 识别你的资金和 notes
- 确定哪些 notes 可以花费
- 派生或识别相关地址
- 构建交易
- 生成或协调所需证明
- 为签名准备交易

重要的是，需要构建交易并不等于需要私密花费密钥。这种解耦是硬件钱包集成背后的核心安全理念之一。

## 屏蔽交易构建和授权

以下是创建和授权交易所涉及的流程。简单来说，这些流程就是钱包实际如何利用这些数据来转账：

### 交易构建（组装屏蔽交易）

交易构建是将用户预期支付所需的信息组装成有效 Zcash 交易的过程。

交易构建过程会将选定的 notes、接收方、金额、手续费、nullifiers 及其他必需交易数据组合成交易结构。对于屏蔽交易，它还会准备生成必要零知识证明和签名所需的信息。

伴侣钱包通常执行此阶段。它会：

- 选择要花费的 notes
- 确定交易的输入和输出
- 计算必要数值
- 准备后续将被证明和签名的交易数据。

在冷签名设置中，生成的交易数据可以打包为 PCZT，并传递给硬件钱包进行安全关键的签名步骤。

### 证明（展示协议有效性）

证明是指生成零知识证明（例如 Halo 2 或 Groth16），以表明交易遵循 Zcash 协议规则。

证明帮助网络保证：

- 花费用户有权花费这些 notes
- 这些 notes 确实存在
- 相应的 nullifiers 是唯一的
- 输入总额等于输出总额加手续费。

它在不披露任何底层私密详情的情况下完成所有这些验证。

证明生成需要大量计算资源。将这项职责卸载到伴侣设备，可防止硬件钱包卡顿或耗尽内存。

### 签名（授权花费）

签名与证明有根本区别。数字签名是由私钥持有者生成的明确授权标记。

零知识证明验证交易有效性，而数字签名证明花费权限。签名证明真正所有者认可具体的转账参数。

签名所需的计算能力极低，因此非常适合硬件钱包。

### 什么是屏蔽冷签名？

屏蔽冷签名是一种授权 Zcash 屏蔽交易的方法，同时将私密花费密钥与联网的伴侣钱包隔离。交易可以在联网计算机上构建和准备，而另一个保持离线或以其他方式隔离的硬件钱包则使用其受保护的密钥来授权交易。

## 伴侣钱包和硬件钱包

屏蔽交易可同时涉及伴侣钱包和硬件钱包，二者各自承担不同功能。

### 伴侣钱包

什么是伴侣钱包？

伴侣钱包运行在计算机或移动设备上，并执行创建交易所涉及的大多数任务，例如：

- 选择要花费的 notes
- 构建交易
- 计算必要的交易数据
- 协调生成所需的零知识证明。

### 为什么伴侣钱包有用？

伴侣钱包负责处理交易创建过程，但如果计算机感染恶意软件，攻击者可能能够：

- 查看你正在进行的操作，
- 修改未签名交易，
- 试图诱骗你批准某些内容。

伴侣钱包无需访问储存在硬件钱包中的私钥，因此它可以处理交易构建和其他计算任务，而硬件钱包则为私钥提供安全边界。

### 硬件钱包

硬件钱包是一种离线实体设备，可将你的私钥与已连接的手机或计算机隔离，如同加密资产的安全保险库。

### 为什么硬件钱包有用？

如果计算机感染恶意软件，攻击者可能能够：

- 查看你正在进行的操作，
- 修改未签名交易，
- 试图诱骗你批准某些内容。

私钥不能被直接从硬件钱包中提取，因此该设备能够充当安全边界。

伴侣钱包与硬件钱包功能对比图

这两种钱包之间的分离对于屏蔽交易尤其重要，因为屏蔽交易比透明交易更复杂，并涉及屏蔽 notes、nullifiers、commitments、零知识证明和交易签名等组件。

让硬件钱包执行每一项计算操作并不现实。相反，伴侣钱包准备交易，并向硬件钱包提供签名所需的信息，同时私密花费密钥仍保持隔离在硬件设备内。

## 密钥隔离 [Key Isolation]

> 密钥隔离意味着，能够授权花费的私钥绝不会离开硬件钱包。伴侣钱包可以准备交易；它无法对其签名。

密钥隔离是指，将授权交易所需的私钥与伴侣钱包及其运行设备分开保存。在屏蔽 [shielded] 冷签名设置中，伴侣钱包可以构建交易并协调所需的证明 [proof]，而硬件钱包则将敏感的私有花费密钥隔离保存。

如果伴侣电脑或手机遭到入侵，攻击者或许能够在交易签名之前与其交互，但理想情况下无法从硬件钱包中提取私钥。因此，密钥仍处于硬件设备的安全边界内。

这种分离使伴侣钱包能够执行交易构建和计算任务，而无需让其直接访问授权该交易所需的密钥材料。

![Key isolation](/content-images/key-isolation.webp)

需要明确的关键区别是，"viewing key" 并不意味着应用程序接收到的是种子的较弱版本。

在 Zcash 中，Full Viewing Key (FVK/UFVK) 会特意从花费密钥中派生，使持有者能够检测和解密相关的屏蔽活动，但不能授权花费。FVK 是花费密钥的秘密性较低的派生物。

**一个重要的隐私 [privacy] 注意事项：**

因此，应当明确：应用程序仅凭 UFVK 无法盗取资金，但它可以看到钱包的私密屏蔽活动。

这就是为什么，将伴侣应用程序描述为拥有 *查看权限*，比简单地说它拥有"公开信息"更准确。

概括整个理念的最简单说法是：伴侣钱包获得足以了解钱包发生情况的密钥材料，但不足以授权钱包资金发生情况的密钥材料。不过，硬件钱包会保持花费权限隔离，并且仅在用户批准交易时使用它。

这正是这些屏蔽 Zcash 硬件钱包设计背后的核心密钥隔离模型，也是即将介绍的 Ledger、Keystone 和 Hito 中逐项实现的相同模型。

## PCZT

PCZT 代表部分创建的 Zcash 交易。它是一个承载 Zcash 交易及在不同阶段之间完成该交易所需信息的包。

它是在 Zcash 交易仍在构建时使用的标准化格式。它允许不同参与者或设备执行交易创建流程的不同部分，并在它们之间传递部分完成的交易。

在零知识 [zero-knowledge] 加密货币协议（如 Zcash）中，构建交易远比签署简单的公开转账复杂。屏蔽交易需要计算密集型的零知识证明，例如使用 Halo 2 或 Groth16 生成的证明。因此，硬件钱包等低功耗设备可能缺乏处理完整交易工作流程所需的内存和处理能力。

PCZT 的引入解决了屏蔽加密架构中的几个核心挑战。PCZT 是一种标准化的中间数据格式，将交易创建拆分为模块化且独立的角色。它允许功能强大的伴侣电脑处理交易组装和证明生成，同时将离线硬件钱包严格限制为授权和签名。

### 硬件与冷存储限制

虽然硬件钱包为保护私有花费密钥提供了安全环境，但与伴侣电脑相比，它们通常拥有有限的 RAM、计算能力和数据传输能力。这些限制使其难以执行计算密集型的零知识证明生成，或维护交易构建过程中所需的完整交易状态。

因此，伴侣钱包可以处理计算需求高的任务，而硬件钱包则专注于使用其受保护花费密钥授权交易这一安全关键操作。

这不禁让人思考：如果设备限制如此严格，它如何仍能进行 *足够* 的验证以值得信赖？

简单来说，硬件钱包不能接受来自伴侣电脑的任意值并对其签名。它需要足够的信息来确认所签名的值对应于用户意图授权的交易。这形成了艰难的平衡，因为设备必须进行足够的解析和验证以保护签名流程，同时又要在内存、计算、固件大小和实现复杂性的严格限制内运行。

Ledger 的 Orchard PCZT 处理就是这项挑战的一个例子：它表明，依赖特定电路的专用解析可以让受限设备上的实现更易于管理，但在受支持的交易结构或电路演变时，也可能需要修改固件。

两个持续进行的工作展示了针对同一限制的不同应对方式。

第 423 号拨款提出了一项研究方案，探讨适合开源硬件钱包架构和普通电脑的全恒定时间证明流水线。目标是研究能够在 C 或 Rust 等环境中安全实现的加密基础设施，同时降低屏蔽 Zcash 支持的复杂性和维护负担。

不过，另一种方法是拟议的 **Zcash SeedSigner**，它是由廉价且易于获得的组件构建的开源、气隙隔离签名器。其拟议工作流程将伴侣电脑与签名设备分离，通过气隙传递 PCZT，以便在设备上进行验证和签名。

这些方法共同说明了屏蔽硬件钱包背后更广泛的工程挑战：交易构建和证明可以在安全关键设备外完成，但签名器仍必须拥有足够的信息和验证能力，以安全地授权最终交易。

### PCZT 实现分离式架构

部分创建的 Zcash 交易（PCZT）标准，是连接伴侣钱包与硬件钱包的正式数据结构。

伴侣钱包能够自行处理 note 选择、计算 nullifier，并生成零知识证明。这之所以可行，是因为这些步骤所需的信息，包括用于派生 nullifier 的密钥，来自 viewing key，而不是任何与花费权限绑定的信息。随后，伴侣钱包将这些元素打包进 PCZT 容器。

PCZT 被交给硬件钱包，硬件钱包读取交易上下文（如金额和收款人地址），使用其受保护的花费密钥应用签名，并将更新后的 PCZT 交还给伴侣设备。

这一设计建立了严格的安全边界：强大的主机硬件可以执行复杂的零知识数学运算，而无需访问花费密钥；低功耗冷存储设备则可以实施资金安全，而无需计算繁重的密码学运算。

### 证明者隐私妥协

虽然将零知识证明生成委托给伴侣钱包或其他证明者可使花费密钥保持隔离，但它仍要求证明者访问敏感交易信息，例如 note 值、收款人地址和 commitment。

PCZT 通过确保可为证明提供此类信息、同时不传输授权所需的私有花费密钥，维持了架构分离。

这确保了证明权限与花费权限分离。证明者可以执行计算密集型的证明生成，而不会获得花费用户资金的密码学权限。

### PCZT 互操作性

随着 PCZT 成为 Zcash 硬件钱包、多重签名和气隙签名工作流程的重要组成部分，不同独立实现之间的互操作性变得日益重要。

AngryDavee 于 2026 年 6 月提出的一项方案指出，PCZT 的实现已存在于包括 Ledger、Keystone、Hito、OneKey 以及 librustzcash 中的参考实现等项目中。不过，该方案发现缺少共享测试，无法确认这些实现是否以一致方式解释 PCZT。

拟议的解决方案是一套开源互操作性测试套件，其中包含规范的 PCZT 测试向量，以及覆盖完整创建 → 签名 → finalizer 工作流程的跨实现测试。它还提议测试诸如 Combiner 这样的角色边界，其中不同签名器提供的部分签名信息可在交易最终完成前被组合。

这对硬件钱包尤为相关，因为 PCZT 允许交易构建和签名分离：伴侣钱包可以构建交易并准备 PCZT，而硬件设备接收所需签名信息并执行安全关键的签名操作。

该方案未被实施，因为 Zcash Community Grants 在审查方案并考虑社区反馈后决定不推进该拨款。因此，拟议的跨实现测试套件并未通过这项拨款开发完成。因此，它是对已识别的 PCZT 互操作性挑战的拟议回应，而不是目前已存在于 Zcash 中的标准。

https://forum.zcashcommunity.com/t/pczt-interoperability-test-suite-feedback-before-at-grant-submission/55931

### PCZT 的生命周期

| # | 阶段 | 描述 |
|---|---|---|
| 1 | 创建者 | 使用全局交易元数据初始化 PCZT，包括交易版本、共识 [consensus] 分支 ID 和 pool 标志。 |
| 2 | 构造器 | 使用透明、Sapling、Orchard 或 Ironwood pool 中的预期输入和输出填充交易。 |
| 3 | IO finalizer | 声明输入和输出集合已完成，计算绑定签名密钥，并在需要时对虚拟花费签名。 |
| 4 | 更新器 | 为后续参与者附加必要的上下文数据，如完整 viewing key、锚点和 Merkle 见证。 |
| 5 | 证明者和签名器 | 执行零知识证明生成和密码学签名。在现代 PCZT 版本中，这两项任务完全独立，可以顺序或并行发生。 |
| 6 | Combiner | 如果不同设备同时处理同一交易的不同方面，则确定性地合并多个 PCZT 实例。合并规则要求严格的冲突解决机制，以防止意外数据丢失。 |
| 7 | 花费 finalizer 与提取器 | 验证所有必需的密码学元素，移除中间上下文元数据，并生成可供网络广播的最终 Zcash 交易。 |

## 现实世界的硬件钱包实现

### 一览

| 设备   | 伴侣设备接收的内容              | 保留在设备上的内容          | 传输方式      |
|----------|------------------------------------------|-----------------------------------|----------------|
| Ledger   | UFVK / Orchard FVK、地址            | 花费权限                | USB / BLE      |
| Keystone | UFVK + 统一地址                   | 种子 / 花费密钥              | QR（气隙隔离）|
| Hito     | UFVK、统一地址、种子指纹  | 种子和私有花费密钥    | QR / 本地     |

已开发多种硬件钱包实现，以探索在使敏感花费密钥与伴侣钱包隔离的同时，如何支持 Zcash 屏蔽交易。Ledger、Keystone 和 Hito 代表了将基于硬件的密钥保护集成到 Zcash 交易工作流程中的不同方法。

![Real world hardware wallet implementations](/content-images/hardware-wallet-implementations.webp)

要理解它们如何保护屏蔽资金，重要的是区分花费密钥与 viewing key。在这三种实现中，分离遵循相同模式：

| 设备 | 伴侣应用可以接收的内容 | 设备上保持受保护的内容 |
|---|---|---|
| Ledger | UFVK / Orchard FVK、地址和公开信息 | 花费权限 / 私有密钥材料 |
| Keystone | UFVK + 统一地址 | 种子 / 花费密钥 |
| Hito | UFVK、统一地址、种子指纹和网络信息 | 种子和私有花费密钥 |

### Ledger 作为硬件签名环境

Ledger 是一家硬件钱包公司。其设备围绕安全元件构建，安全元件是专门用于保存私有密钥材料并使其在物理上与设备其他部分以及与其连接的任何事物隔离的芯片。正是这个安全元件使 Ledger 设备值得用于冷存储。这意味着，即使与之连接的电脑或手机遭到入侵，安全元件内的密钥也无法被提取。

不过，Ledger 设备本身对于任何特定加密货币都是空白的。它需要在其上安装一个知道如何处理该货币特定密码学的应用程序。

Ledger 设备对于任何特定加密货币都是空白的，因此它需要一个了解该货币密码学的应用程序。对于 Zcash，已有两代产品：

- 最初由 Zondax 构建的"Zcash Shielded"应用程序，与 Zkool 等伴侣钱包配合使用，并将于 2026 年 11 月 5 日停止使用，以及
- Ledger 的新版 Zcash 应用程序（3.9.4+），由 Ledger Wallet Desktop 4.21+ 原生使用，以处理 Ironwood 屏蔽 ZEC。

下述密钥隔离模型适用于两者。

Zkool 是手机或电脑上与该应用程序通信的伴侣钱包。它构建交易，将其发送给 Ledger，设备上的 Zondax 应用程序随后对其签名并发回签名。

因此，Zondax 是运行在硬件上的软件，Zkool 是运行在硬件外部、利用 Zondax 的应用程序与设备通信的软件。

### 什么会离开 Ledger？

Ledger 的 Zcash 软件包含一项专门用于导出钱包 viewing key 的功能，该密钥允许软件查看余额和交易，但不能花费任何资金。

该功能可以返回两种内容之一：

- 统一 Full Viewing Key（UFVK），即同时覆盖 Zcash 所有屏蔽 pool 的完整 viewing key，或
- Orchard Full Viewing Key（FVK）

无论哪种方式，导出的都始终只是 viewing key。无论请求哪个版本，这项功能都无法返回唯一真正能让他人转移资金的信息，即花费密钥。

这正是其构建方式的核心：它被设计为唯一能够导出的内容，就是可安全交给伴侣应用程序的内容。

Zcash 的密钥层级结构使得每个屏蔽 pool 的花费密钥派生出两种独立内容：

- 花费授权密钥，以及
- 完整 viewing key

FVK 随后可以进一步派生其自身的查看相关能力，但该派生路径在任何时候都不会回到花费权限。一旦密钥分支进入层级结构的查看一侧，它就会停留在那里，无法用于重建其来源的花费权限密钥。

Ironwood 遵循相同模式，因为它复用了 Orchard 的底层密钥和 note 构造。不过，在共识层面它是一个独立的 pool，拥有自己的 commitment 树和 nullifier 集。这意味着，UFVK 实际上是按 pool 划分的 viewing key 束（透明、Sapling、Orchard，以及现在的 Ironwood），而不是一个单一的平面密钥。

在 Ironwood 激活前导出的 UFVK 不会包含 Ironwood viewing key，因为当时该 pool 尚不存在。这正是为什么钱包需要在 NU6.3 升级后更新，以识别并派生支持 Ironwood 的 UFVK。

### 什么保留在 Ledger 上？

花费权限仍保留在设备上。

Ledger 签名器从主机接收交易/PCZT，并根据交易从哪个 pool 花费生成花费授权签名（Ironwood pool，因为 Ledger 的当前集成仅支持 Ironwood）。签名随后在设备上生成，主机仅接收签名，而非私有花费密钥。

这也符合 Ledger 的总体安全模型。其安全元件隔离私有密钥材料，而 Ledger 的应用程序安全要求明确禁止应用程序向主机暴露这些秘密。

Ledger 的签名器可导出 FVK/UFVK，同时独立执行交易签名。这两种能力通过独立功能提供，而非捆绑在一个功能中。

### 这在实践中意味着什么？

假设你的 Ledger 包含 10 个 ZEC。

伴侣钱包可以拥有 UFVK，因此能够确定："该钱包已收到 10 个 ZEC。"它可以扫描和显示交易与余额。

但是，如果有人入侵伴侣钱包，仅有 UFVK 并不会让他们能够创建花费授权签名。

独立花费授权签名的目的，是让硬件钱包等受限设备能够授权屏蔽花费，而无需自行执行完整的 zk-SNARK 证明。

### Zondax Ledger 应用程序；硬件钱包一侧

#### 什么是 Zondax？

Zondax 是一家第三方开发公司，构建了 Ledger Zcash 应用程序。它是运行在 Ledger 硬件上的实际固件应用程序，使设备能够理解和处理 Zcash 交易。

Zondax 是外部开发者。Ledger 硬件没有处理 Zcash 交易的原生能力，而该能力完全来自 Zondax 的软件。

### 最初的 Zcash Ledger 实现

Zondax 的 Ledger Zcash 应用程序仓库包含运行在 Ledger 设备上的软件。该应用程序最初专注于 Sapling 屏蔽交易，彼时 Orchard 尚未成为 Zcash 的主要屏蔽 pool，因此，Sapling 支持就是 Ledger 设备在屏蔽 ZEC 方面所能做到的全部。

其架构展示了这种分离：主机/伴侣端准备交易信息，而 Ledger 处理敏感密钥操作和签名。

即使在最早版本的 Zcash 硬件钱包支持中，核心原则——即主机构建和证明，设备隔离签名——就已经是其设计理念。

### 向 Orchard 演进

Ledger 的工作转向 Orchard + PCZT。这是一项重大转变，而非小型更新，因为 Orchard 使用不同的证明系统（Halo 2，而非 Sapling 的 Groth16），以及不同的 note 和密钥构造。因此，扩展仅支持 Sapling 的固件以处理 Orchard 签名，需要在设备端建立新的密码学基础，而不仅仅是固件补丁。

不过，随着 Zcash 向 Ironwood 演进，Zondax 和 Ledger 将开发重点转向直接支持 Ironwood，而不是完成 Orchard 实现后又为 Ironwood 重新设计。这代表 Ledger 实现演进的又一阶段，因为 Ironwood 建立在 Orchard 密码学架构之上，同时引入了独立的屏蔽 pool 和额外的协议变化。

### 该 Ledger 应用程序内部发生什么

最终流程描述如下：

1. 主机构建 PCZT。
2. 主机将相关交易信息发送至 Ledger 设备。
3. 设备生成 Orchard 花费授权签名。
4. 主机处理之后的所有事项，包括绑定签名和最终交易组装。

运行在 Ledger 内部的应用程序，除花费授权签名本身外不会看到或生成任何内容；所有计算繁重或数据需求高的工作（证明、绑定、组装）都留在主机上，主机无需被信任来持有密钥材料。

### Ledger 的原生屏蔽集成；Ledger Wallet Desktop

Ledger 的最新 Zcash 集成提供了一个具体示例，说明如何在伴侣软件与硬件钱包之间分离屏蔽交易构建和安全关键签名。

借助 Ledger Wallet Desktop 4.21+ 与 Zcash 设备应用程序 3.9.4+，用户可以直接通过 Ledger Wallet Desktop 发送和接收 Ironwood 屏蔽 ZEC。该集成支持私密到私密转账、从透明 pool 屏蔽、解除屏蔽至透明 pool、私密收款地址和备忘录 [memo]。交易会在 Ledger 设备上验证和签名，而非仅依赖电脑呈现的信息。

该架构的关键部分是查看和花费能力的分离。在私密余额同步期间，Ledger 导出统一 Full Viewing Key（UFVK），并将其本地存储于电脑上。UFVK 允许 Ledger Wallet Desktop 检测相关屏蔽交易并确定钱包余额，但它不提供花费资金的权限。安全关键的花费权限仍保留在执行最终签名操作的 Ledger 设备上。这在管理钱包状态和构建交易的电脑，与保护授权花费所需能力的硬件设备之间建立了清晰边界。

不过，当前集成明确仅支持 Ironwood。它不会通过 Ledger Wallet Desktop 显示或管理 Orchard 或 Sapling 资金。从历史角度看，这一点很重要，因为 Ledger 早期的 Zcash 开发与 Orchard 屏蔽支持有关，之后实现才向 Ironwood 协议演进。

这一转变也凸显了密钥和账户兼容性的重要性。Ledger 有一款由 Zondax 开发的旧版"Zcash Shielded"应用程序，供 YWallet 和 zkool 等集成使用，目前正被弃用。由于这款旧应用程序对屏蔽账户采用不同的派生方案，其 Sapling 账户无法简单地由新的 Ledger 应用程序重现。

因此，该集成同时展示了屏蔽硬件钱包支持的进展和剩余限制。Ledger 现在可以提供完整的 Ironwood 体验，其中伴侣软件处理钱包同步和交易准备，而硬件设备仍是花费的安全边界。

同时，历史账户兼容性、仅支持特定屏蔽 pool、硬件交易大小限制、平台限制，以及解析和验证屏蔽交易涉及的计算与固件限制，都表明对 Zcash 的硬件钱包支持不仅取决于协议能力，也取决于每个独立实现的设计和资源。

### Zkool + Ledger — 使用官方 Zondax 应用程序

作为 Ywallet 的继任者，Zkool 继承了屏蔽冷签名的目标，但选择了不同路径。该路径直接受到一个事实影响：如果签名应用程序无法安全分发，仅有密码学并不能让集成变得可用。

https://youtu.be/eagkCIv3BlQ?si=7w5YfLlRER77bASw

### Zkool 对 Zondax 应用程序的使用

Zkool 转而使用由 Zondax 开发的官方 Ledger Zcash 应用程序，而不是 Ywallet 被放弃的专有 Ledger 应用程序。Zkool 没有维护一个 Ledger 商店不接受的自定义应用程序，而是基于已被接受并通过 Ledger 自身生态系统分发的应用程序构建。

这一转变意味着，用户不再需要依赖安装未签名的自定义 Ledger 应用程序来使用此集成，因为 Zondax 的应用程序已通过 Ledger 的生态系统正式分发。

不过，这项集成将在 2026 年 11 月 5 日面临重大变化，届时 Ledger 将逐步淘汰旧版 Zcash Shielded 应用程序，其支持预计将结束。由于 Zkool 的 Ledger 集成依赖该应用程序，这一变化引发了对现有连接未来可用性的疑问。对 Zkool 的确切影响取决于它能否在 Ledger Wallet 外继续使用旧版应用程序，或转向兼容替代方案。

### 支持的屏蔽 pool

根据 Ywallet 开发者的说法，Zkool 的 Ledger 集成使用了由 Zondax 开发的官方 Ledger 应用程序，并支持透明和屏蔽的 Zcash。不过，其屏蔽支持仅限于 Sapling，不支持 Orchard；其他集成限制还包括每种类型最多五个输入和输出，以及不兼容 Ledger Live。

这一限制反映了当时底层 Zondax Ledger 实现的范围。Zondax 早期的 Ledger 工作提供了对 Sapling 的支持，而其随后于 2024 年发布的 Zcash 屏蔽 [shielded] Ledger 应用最初排除了 Orchard 和统一地址。因此，围绕该应用构建的集成继承了其所依赖硬件钱包 [hardware wallet] 实现的功能与限制。

随着专用 Zcash 屏蔽 Ledger App 于 2024 年 11 月发布，情况随后发生了变化。Zondax 表示，该应用已通过 Ledger Live 正式发布，之后还发布了集成指南以及 Rust 和 JavaScript 软件包，以便其他钱包与其集成。然而在发布时，该应用仅与 Zecwallet Lite Desktop 通信，而更广泛的钱包集成仍在开发中。

下一阶段是开发 Ledger 更新的、基于 Rust 的 Zcash 应用。截至 2026 年 6 月，Ledger 报告称已实现 UFVK 共享和 Orchard 统一地址生成，而 Orchard 交易 [transaction] 签名 [signature] 和 ClearSign 仍在开发中。Ledger 还表示，随着协议变化，这项工作将延续至 Ironwood 路径。

Ironwood 随后要求整个 Zcash 钱包 [wallet] 生态系统进行更新。Zkool 从版本 6.24.0 开始发布了从 Orchard 到 Ironwood 迁移的支持，并在后续版本中持续完善迁移和交易流程。另一方面，Ledger 于 7 月 27 日将 PCZT v2 签名合并到其新应用中，尽管截至 8 月 20 日，该实现尚未完成 Ledger 的审核和 Ledger Live 推出；此后这一里程碑已完成，Ledger Wallet Desktop 4.21+ 现已直接提供原生 Ironwood 支持。

https://forum.zcashcommunity.com/t/a-path-forward-for-ledger-and-zcash/50951/177

因此，这一演变更适合理解为若干相关的发展，而非一次单一的 Zondax 到 Ironwood 升级：最初聚焦于 Sapling 的 Zondax 实现、2024 年的 Zcash 屏蔽 Ledger App、支持 Orchard 和 PCZT 的较新 Ledger Rust 应用、Ledger 在 Ledger Wallet Desktop 中的原生集成，以及随着生态系统过渡至 Ironwood，包括 Zkool 在内的钱包所进行的并行更新。

### Ledger 设备与平台对 Zcash 的当前支持

Zcash 在 Ledger 上的支持取决于：

- 设备型号
- 所安装的应用
- 用于管理它的平台，以及
- 交易是透明 [transparent] 的还是屏蔽的。

截至 2026 年 7 月 21 日（Ledger 的最后一次更新），Zcash Shielded app 支持 Nano S Plus、Stax 和 Flex，但尚不支持 Nano X 或 Nano Gen5。

除最初的 Nano S 外，Nano X 和其他型号仍可使用经典 Zcash app，该应用支持透明交易以及将屏蔽资金花费至透明地址（解除屏蔽），但不支持屏蔽到屏蔽的签名。最初的 Nano S 不支持任何一个应用，因为 Ledger 正逐步停止对该设备的支持，且其最新的 Zcash app 无法在该设备上使用。设备可连接至 Ledger Wallet（原名 Ledger Live），即 Ledger 的配套应用；该应用的桌面版适用于 Windows、macOS 和 Linux，移动版适用于 iOS 和 Android。

Ledger 已为基于 Ironwood pool 的 Ledger Wallet Desktop 添加原生屏蔽 Zcash，从而无需单独的配套钱包。Ledger 的 iOS 和 Android 移动应用尚不支持屏蔽 ZEC，尽管未来版本计划提供移动端支持。

在 Ledger 自身软件之外，屏蔽使用取决于兼容的配套钱包及其支持的平台。随着 Ledger 持续扩展 Ironwood 支持，兼容性取决于设备型号、固件、应用版本和操作系统，因此一般的 Zcash 支持不一定能保证兼容。

### YWallet 冷签名；一种早期方法

Ywallet 是一个配套钱包，独立于 Ledger 和 Zondax，其探索了自身实现屏蔽冷签名的路径。

从历史角度而言，Ywallet 很重要，因为它探索了对 Zcash 的冷签名，这意味着签名设备可以与在线钱包分离。

为了在 Ledger 硬件上实现该架构，Ywallet 构建了自己的 Ledger 应用，即一个专有应用，与上一节介绍的 Zondax 应用不同。这意味着 Ywallet 并不依赖 Zondax 现有的 Sapling 实现；它拥有自己的固件来运行该关系中的签名端。

### 为什么该集成很重要

拥有密码学和签名代码还不够。硬件钱包集成并不纯粹是一个密码学问题，它同样不可避免地涉及分发和平台问题。至少包括：

- 应用审核/分发——硬件制造商的官方应用商店是否会接受并分发该应用
- 固件/应用安全——该应用是否符合制造商处理密钥材料的安全要求
- 通信协议——配套钱包与设备实际如何交换交易数据
- 与钱包的兼容性——签名应用的数据格式与流程是否匹配配套钱包的预期
- 支持的屏蔽池——该应用实际可为 Sapling、Orchard（以及现在的 Ironwood）中的哪些进行签名

Ywallet 的专有 Ledger 应用满足了密码学和架构要求；它可以签署屏蔽 Zcash 交易，但未获 Ledger 官方应用商店接受。

### 逐步弃用专有 Ledger 应用

由于该应用未获官方接受，Ywallet 必须要求用户安装未签名固件才能使用它，这对用户而言是真实的安全妥协，而 Ywallet 选择不向用户提出这一要求。因此，Ywallet 最终放弃了这一特定集成，而没有采取该路径。

后续开发并未重启专有应用，而是通过 Zkool（Ywallet 的继任者）转向官方构建的 Zondax Ledger 应用，以已获 Ledger 分发生态系统接受的标准化实现，替代定制但被拒绝的实现。这一转变最终使可用的 Ledger 集成再次成为可能。

### Ywallet 的遗产

即使 Ywallet 本身已不再积极开发，其创建者 Hanh——同时也是 ZCG 成员——仍是生态系统中重要的声音，尤其是在 Ironwood 迁移引发有关资金似乎消失的报告问题时。

**ZODL：一名真实用户在 Orchard → Ironwood 迁移后经历了资金缺失**

一位用户 Jmo0615 报告称，其 ZODL 钱包中此前可见的资金在 Orchard 至 Ironwood 迁移后不再显示。他们表示，已恢复原始种子、重置并恢复钱包，并让 ZODL 版本 3.14.1 (1) 完成全量同步。他们还确认未涉及任何 Keystone 硬件钱包。

尚未确定这些资金实际已经丢失。更可能是与钱包发现或迁移有关的问题，即先前可见的资金在过渡至 Ironwood 后不再显示。未被检测或显示的资金不应自动被描述为永久丢失的资金，在理解迁移问题时，这一区别很重要。

https://forum.zcashcommunity.com/t/funds-not-showing-since-ironwood/57792

**Zkool："锁定的 notes" 可以解释表面上无法使用的资金**

屏蔽钱包的另一个重要方面是，钱包状态会如何影响用户实际可花费的资金。Hanh 解释称，用户可能会通过币种控制意外锁定一个 note；这项功能允许用户手动选择哪些 notes 用于花费。在这种情况下，一个 note 可能仍存在于钱包中，但被标记为不可用于花费。

这凸显了调查钱包问题时的重要区别。钱包中存在的 ZEC 数额并不总是等于当前可花费的数额。note 选择、同步、迁移状态、钱包恢复和币种控制设置等因素，都可能影响显示的或可花费的余额。因此，对于"资金缺失"的报告，应仔细区分未被检测或显示的资金、已检测但不可花费的资金，以及实际丢失的资金。

## 2. Keystone

**什么是 Keystone？**

Keystone 是一款隔离网络的硬件钱包。其签名设备在签名过程中不会与配套应用直接进行有线或无线连接，而是通过 QR 码通信。它在此与 Zashi（现已更名为 Zodl）搭配使用，后者是 Zcash 的原生配套钱包；这种配对使密钥隔离原则格外明确且易于追踪。

**Keystone/Zashi 流程**

Keystone 与 Zashi 的 Zcash 集成使这种分离尤为明确。当你将 Keystone 连接至 Zashi 时，统一 Full Viewing Key 会从 Keystone 传输至 Zashi。

因此，流程如下：

![Keystone and Zashi viewing flow](/content-images/keystone-zashi-viewing-flow.webp)

**Zashi 可以如何使用 UFVK？**

Zashi 可以使用它来：

- 识别传入的屏蔽交易
- 确定余额
- 获取有关屏蔽活动的信息

但仅仅因为拥有 UFVK，它无法花费这些资金。

UFVK 是一种"查看能力"，可用于了解余额和交易，但不允许花费。

### 哪些内容留在 Keystone 内？

种子/花费授权保留在 Keystone 上。Zashi 不会收到种子、花费密钥 [spending key] 或花费授权私钥。它会收到 UFVK、地址 [address] 信息，以及仅查看操作所必需的信息。

这两部分共同构成完整图景。离开设备的内容，如 UFVK、地址和仅查看信息，足以让 Zashi 监控账户，但离开设备的任何内容都不足以将资金转出。

这就是 Zashi 和 Keystone 集成能够提供屏蔽冷存储的原因。钱包应用可监控账户，但并不拥有从中花费所需的授权。该集成专门推出，以实现屏蔽 ZEC 的冷存储。

## 3. Hito

Hito 遵循与 Keystone 非常相似的密钥隔离模型，但其实现较新。Hito 并非与现有配套钱包（如 Zashi）配对，而是附带自己的 Android 钱包；硬件设备与该 Android 应用之间的引导流程记录在 Hito 的开发里程碑中。

**引导：Hito 应用收到什么**

Android 钱包在引导硬件账户时使用：

- 统一 Full Viewing Key（UFVK）
- 统一地址
- ZIP-32 种子指纹
- 网络信息

请注意，Android 应用永远不会收到硬件钱包的种子或私有花费密钥。

![Hito onboarding](/content-images/hito-onboarding.webp)

**Hito 应用获得什么？**

文档中记录的引导信息包括：

- UFVK
- 统一地址
- ZIP-32 种子指纹
- 网络

UFVK 为 Android 钱包提供了以具备查看能力的钱包身份操作账户所需的信息，而无需接收种子。种子指纹是从种子派生的固定长度标识符，用于识别各个账户；它不是种子本身，也不赋予任何花费能力，因此其存在并不与上述"永远不会收到种子"的说法矛盾。

**哪些内容留在 Hito 上？**

实际种子、私有花费密钥和签名授权仍保留在硬件设备上。随后，Hito 在离线状态下执行签名。

当前 Hito 里程碑指出，完整的创建、导出、离线签名和导入工作流程已经可用，具备 BLE 传输和已签名 PCZT 的 BBQr QR 导出功能。

这一工作流程值得明确说明，因为它是本报告前文所涵盖完整周期的具体实例：Android 钱包创建未签名的 PCZT，将其导出至 Hito，Hito 使用其隔离的密钥材料离线签名，然后将已签名的 PCZT 导入回 Android 钱包。

种子或花费密钥在任何时刻都不会向任一方向跨越该边界。

![Hito signing flow](/content-images/hito-signing-flow.webp)

## Orchard 到 Ironwood：硬件钱包 [hardware wallet] 支持的发展

Orchard 是 Zcash 协议中的一个屏蔽池 [shielded pool]，使用户能够以增强的隐私 [privacy] 存储和交易 [transaction] ZEC。它在网络升级 [Network Upgrade] 5（NU5）中推出，Orchard 使用 Halo 2 证明 [proof] 系统和重新设计的密码学架构来支持屏蔽交易，而不会泄露发送方、接收方或金额等敏感交易信息。

Ironwood 是在 Zcash 的 NU6.3 网络升级中引入的屏蔽池，作为 Orchard pool 的继任者。它采用 Orchard 密码学协议，同时引入旨在提升屏蔽资金长期安全性的变更，包括量子可恢复性以及对供应完整性更强的保障。

一开始必须澄清，Ironwood 并没有用一个全新的密码学系统替换 Orchard 协议。Ironwood 被引入为一个基于现有 Orchard 协议构建的新屏蔽池。这意味着它们具有相同的 Action 结构、相同的 Halo 2 证明系统，以及相同的 note 和密钥构造。

Ironwood 拥有自己的 note commitment tree、nullifier set、anchor 和 value pool，因此在共识 [consensus] 层面它是一个真正独立的 pool。但在密码学上，它是 Orchard 的扩展，而非重建。

它采用这种设计是为了：

1. **供应完整性。** 2026 年 5 月 29 日，安全研究员 Taylor Hornby 私下披露了 Orchard 零知识 [zero-knowledge] 证明系统中的一个关键可靠性漏洞，该漏洞本可能允许在不留下链上 [on-chain] 痕迹的情况下创建伪造的 ZEC。由于 Orchard 的交易数据是私密的，任何人都无法独立验证在修复之前是否未创建伪造的 ZEC。封存旧 pool 并从零开始建立一个新的 pool，以一种无法通过原地修补 Orchard 实现的方式解决了这个问题。
2. **确保量子可恢复性。** Ironwood 的设计使其资金在底层离散对数假设一旦被攻破时，能够参与未来的恢复机制。
3. **最小化实现变更。** 与其设计一套全新的屏蔽协议，不如复用 Orchard 已经得到验证的架构。这意味着从头编写的新交易、证明、钱包 [wallet] 和硬件钱包代码要少得多。

### 公开时间线

- 5 月 29 日：披露 Orchard 漏洞。
- 6 月：在初步修复通过 NU6.2 发布期间，Orchard 交易受到临时限制。6 月 12 日，一位核心开发者将完整升级目标定在 7 月 21 日；随后又推迟了一周。社区曾担忧 Keystone 持有者会最后迁移，随后一位核心开发者回应称，Keystone 将从第一天起支持 Ironwood，固件目标发布日期为 7 月 3 日，等待 Zcash 核心完成签名常量和 Orchard API 变更。
- 7 月初：NU6.3 进入测试网；Zebra 6.0.0 于 7 月 10 日发布。
- 7 月 27 日至 28 日：Ledger 的 Ironwood PCZT v2 签名工作合并到集成分支。Ironwood（NU6.3）于 7 月 28 日在区块 [block] 3,428,143 激活，通过一个 turnstile 封存原始 Orchard pool，该机制将可从 Orchard 离开的 ZEC 数量限制为曾合法存入其中的金额，并引入新的交易格式。

Zebra 成为必需的节点 [node]，因为 zcashd 不支持新的共识规则。地址 [address] 不会改变，因为 Ironwood 复用了 Orchard 的 receiver 结构，因此钱包会自动将现有地址路由到新 pool。不过，钱包确实需要迁移功能，因为 Orchard 资金最终必须由其所有者移入 Ironwood，而现在接收 Orchard 的新输出已被共识完全阻止。

### 技术上发生了什么变化

交易格式从版本 5 升级到版本 6，因此单笔交易可以在现有 Sapling/Orchard/透明 [transparent] 组件之外携带一个 Ironwood 组件。PCZT 也相应扩展：

- 编码从 PCZT v1 升级到 v2。
- 一个独立的 Ironwood bundle 现在与 Sapling 和 Orchard bundle 并列存在。
- 支持 v6 交易和新的 v6 sighash。
- Note 明文获得了新版本（V3）。

对于硬件钱包而言，sighash 的变更最为重要。在 v6 中，Orchard 和 Ironwood anchor 被排除在签名 [signature] 哈希之外，只会输入 authorizing data digest。这是实际的固件变更，而不只是版本号升级。设备必须正确实现新的 sighash 并自行重新计算，而不是相信配套应用声称它正在批准的内容。

隔离契约本身没有改变：设备仍然只返回花费授权签名，绝不返回 `alpha`，也绝不生成 binding signature；主机仍然负责证明及其他一切工作。

不过，v6 中有一条签名者规则发生了变化：虚拟填充花费由 IO Finalizer 签名，而不是由设备签名，因为设备无法根据真实 note 数据验证它们。设备的 Signer 角色会跳过它们，而不会被要求签署无法检查的内容。显示的手续费 [fee] 现在还会将 Orchard 和 Ironwood 的 value balance 相加，因为 v6 交易可以在同一笔交易中从任一 pool 花费。

正确处理这种 pool 记账在实践中很重要，而不只是理论问题。Brave 自己的 Zcash 钱包最近出现的一个错误就是很好的例证：其手续费计算假定所有屏蔽输入都属于旧版 Orchard pool，导致只要交易实际涉及 Ironwood，就会产生重复的 actions 和错误的手续费估算。这正是硬件钱包签名背后“自行重新计算，不要信任主机”原则所要捕捉的错误类型。一个配套钱包错误处理了 pool 记账，只有设备独立检查自己的计算，才能在签署前发现这一问题。

### 各签名者的现状

**Ledger 刚刚改变了整个局面。** 2026 年 9 月 23 日，Ledger 在 Ledger Wallet Desktop 中直接推出原生屏蔽 Zcash 支持，不再需要单独的配套应用。你的花费密钥 [spending key] 保留在设备上，电脑负责交易计算，而你会在屏幕上批准所有内容后才进行签名。它只支持 Ironwood，不支持旧的 Orchard 或 Sapling pools。缺点是，由 Zondax 构建、需要像 Zkool 这样的配套钱包才能工作的旧版“Zcash Shielded”应用将被停用。Ledger 将在 11 月 5 日下架该旧应用，因此仍在使用它的任何人都需要在此之前迁移资金。

**Keystone 状况良好。** 固件 3.0.2 早在 7 月就加入了完整的 Ironwood 支持，并且这仍是当前稳定版本的要求。不过，签署任何内容都需要该版本或更新版本。

**Hito 已经超越最初的测试网里程碑。** 它已成功在物理硬件上签署并提交第一笔真实的 Orchard 至 Ironwood 交易（最初在测试网上）。后续更新确认了生产硬件上的主网流程（Ironwood→Ironwood、Ironwood→透明以及其他流程）。稳定固件和更广泛的发布仍在进行中。

Zondax 和 Zkool 目前仍在变化中。Zondax 的应用正由 Ledger 停用。Zkool 曾依赖该应用与 Ledger 设备通信，尚未说明旧应用消失后该角色会如何发展。目前尚不清楚它是否会继续与未来的 Ledger 用户相关，还是其未来主要面向其他设备。

迁移本身是最大的连锁影响。由于跨 pool 的金额是公开的，钱包会随时间将转移分散为标准面额，而不是一次性以一个可见的大额转移余额，这意味着每次迁移需要签署许多交易，也正是为什么批量 PCZT 签名对硬件钱包如此重要。

Ledger 的固件工作也遇到了硬件限制：一次真实的 note 花费可能在单个命令中达到数万个密码学系统调用，从而触发设备看门狗。修复方案将域算术移至软件中，并需要共享的暂存状态以适应 Nano X 的堆栈限制。
