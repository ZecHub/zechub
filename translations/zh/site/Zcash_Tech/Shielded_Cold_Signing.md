# 屏蔽冷签名

> **核心理念：** 伴随钱包可以看到构建和监控屏蔽交易所需的一切信息。只有硬件钱包持有授权花费的权限。这种分离正是屏蔽冷签名的全部意义。

在 Zcash 中进行屏蔽（shielded）涉及将资金从公开、透明的地址转入私密、屏蔽的地址，并利用 Zcash 的隐私功能隐藏交易详情。

### 当你屏蔽 ZEC 时会发生什么变化？

对于透明的 Zcash 交易，以下信息：

- 发送方地址
- 接收方地址
- 转账金额

可以在 blockchain 上被观察到。

当你屏蔽 ZEC 时，你的资金会进入一个私密 pool（例如 Ironwood）。Blockchain 可以验证交易有效，而无需披露你的私密交易详情。自 2026 年 7 月 28 日 NU6.3 网络升级（network upgrade）以来，新屏蔽资金会进入 Ironwood pool，因为较旧的 Orchard pool 不再接受新的存款，但仍允许提款。

### 屏蔽交易的组成部分

### 1. Note（屏蔽余额记录）

Note 是一种私密的加密记录，代表用户拥有的未花费 ZEC 金额。

与余额以明文列出的公开 blockchain 不同，屏蔽 note 会加密价值和所有权详情，因此链上观察者无法看到谁拥有这些资金。

发起交易时，伴随钱包会扫描账本，识别用户未花费的 notes，并选择要花费哪些 notes。

### 2. Nullifier（双重花费检测机制）

由于 note 的详情对公开账本隐藏，网络需要一种机制来检测双重花费，同时不泄露正在花费的是哪个 note。

Nullifier 是从特定 note 派生的唯一加密标记。当一个 note 被花费时，其 nullifier 会发布到 blockchain。

网络会验证该 nullifier 是否此前未被记录。如果未被记录，则该笔花费可以被接受。关键在于，外部观察者无法利用 nullifier 确定它来自哪个特定 note。

伴随钱包会在组装交易数据时派生并构建适当的 nullifier。

## 密钥

密钥是控制你资金访问权限的加密信息，并允许你的钱包执行接收、查看和花费 ZEC 等操作。

钱包持有多种不同的密钥，每种密钥都有不同用途，就像一个账户可能拥有分别用于读取访问和写入访问的凭据一样。

密钥是伴随钱包与硬件钱包之间关系的核心，因为不同密钥服务于不同目的，而且只有其中一种需要保持锁定状态。

需要了解的是，每个屏蔽池都会将其密钥构建为派生树，其中箭头从一个组件指向可从其派生的内容。希望接收屏蔽支付的用户必须拥有一个屏蔽支付地址，该地址由花费密钥生成。

### 密钥层级结构

**1. 花费密钥**

这是安全性最敏感的密钥。它赋予对 ZEC 花费进行授权的加密能力。

本报告其他部分提到"硬件钱包持有密钥"时，指的就是这把密钥。

在冷签名架构中，花费密钥保存在硬件钱包内，且绝不会暴露给伴随钱包。伴随钱包根本不应需要持有此密钥。

在 Sapling 和 Orchard 中，密钥层级结构从根花费密钥派生出花费权限和查看能力这两个不同分支：

- **Sapling：** 扩展花费密钥（𝑎𝑠𝑘,𝑛𝑠𝑘,𝑜𝑣𝑘）派生出证明授权密钥（𝑎𝑘,𝑛𝑠𝑘）和完整 viewing key（𝑎𝑘,𝑛𝑘,𝑜𝑣𝑘），后者进一步产生传入 viewing key（𝑖𝑣𝑘）和多样化地址。
- **Orchard：** 根花费密钥（𝑠𝑘）直接分支为花费授权密钥（𝑎𝑠𝑘）和完整 viewing key（𝑎𝑘,𝑛𝑘,𝑟𝑖𝑣𝑘）。

这种结构性分离为硬件密钥隔离提供了正式的加密基础：钱包会将查看分支（UFVK）导出到主机计算机以进行余额同步和交易构建，同时将花费授权分支永久锁定在设备上。

密钥派生严格是单向的。这意味着无法逆向 viewing key 来重建花费权限。加密不可逆性使导出统一 Full Viewing Key（UFVK）变得安全，因为它在不暴露设备上花费秘密的情况下授予完整的钱包可见性。

**2. Viewing key**

Zcash 将查看屏蔽活动的能力与花费它的能力分开。Viewing key 允许钱包或其他获授权方查看有关屏蔽交易的信息，而不授予花费权限。

- **Full Viewing Key（FVK），封装为统一 Full Viewing Key（UFVK）：** 它经过特意从花费密钥派生，使软件能够检测并解密钱包的屏蔽活动，从而识别交易。它还允许软件计算余额，却无法授权花费。将其描述为花费密钥的隐私性较低的派生物最为恰当，而不是种子的较弱副本。

Full Viewing Key（FVK）提供完整的只读可见性，同时维持严格的安全分离。通过解密传入和传出 note 密文（通过其传出 viewing key 组件），仅有 FVK 的伴随钱包可以呈现完整、带标签的交易历史，而不仅仅是余额累计。

多个不可关联（unlinkable）的多样化支付地址共享同一个 FVK 和传入 viewing key（IVK），允许无限生成地址而不会增加 blockchain 扫描开销。

这种功能分离构成冷签名工作流的基础。所有持续链扫描、历史跟踪和地址管理都被卸载至主机软件，而花费权限仍隔离在硬件设备上。

![Key derivation diagrams](/content-images/key-derivation-diagrams.webp)

### 关键区别：UFVK 与花费密钥

> **UFVK 可以共享。花费密钥必须保留在硬件钱包上。**
>
> 伴随钱包使用 viewing key 监控钱包、检测传入资金、识别 notes，并协助准备交易。它不持有授权花费所需的私钥。

如前所述，密钥分离是冷签名架构的基础。

伴随钱包无需控制资金，便可完成准备交易所需的大部分工作。硬件钱包只需接收准备好的交易并执行最终签名操作。

硬件钱包制造商无需自行创造这种分离。Zcash 的密钥设计已在协议层面将查看能力与花费权限分开，制造商只需在这种既有结构之上构建其签名和导出功能。该协议允许从花费密钥派生出屏蔽地址或完整 viewing key 等信息，同时花费密钥本身保持私密，因此 Ledger、Keystone 和 Hito 等硬件钱包可以向伴随软件提供所需的查看信息，而绝不暴露能够花费资金的私钥。

### 伴随钱包实际如何使用密钥信息

通过 viewing key 材料，伴随钱包可以：

- 识别你的资金和 notes
- 确定哪些 notes 可以花费
- 派生或识别相关地址
- 构建交易
- 生成或协调所需的证明
- 为签名准备交易

需要了解的是，需要构建交易并不等于需要私有花费密钥。这种解耦是硬件钱包集成背后的核心安全理念之一。

## 屏蔽交易构建与授权

这些是创建和授权交易所涉及的流程。简单来说，这些流程就是钱包实际如何利用这些数据来发送资金：

### 交易构建（组装屏蔽交易）

交易构建是将用户预期支付所需的信息组装成有效 Zcash 交易的过程。

交易构建流程会将选定的 notes、接收方、金额、手续费、nullifiers 和其他所需交易数据组合成一个交易结构。对于屏蔽交易，它还会准备生成必要零知识证明和签名所需的信息。

伴随钱包通常执行此阶段。它会：

- 选择要花费的 notes
- 确定交易的输入和输出
- 计算必要的数值
- 准备稍后将被证明和签名的交易数据。

在冷签名设置中，生成的交易数据可以打包为 PCZT 并传递给硬件钱包，以执行安全关键的签名步骤。

### 证明（展示协议有效性）

证明是指生成零知识证明（例如 Halo 2 或 Groth16），以展示交易遵循 Zcash 协议规则。

该证明可帮助网络保证：

- 花费用户有权花费这些 notes
- 这些 notes 确实存在
- 相应的 nullifiers 是唯一的
- 输入总额等于输出总额加手续费。

它在不披露任何底层私密详情的情况下完成所有这些验证。

证明生成计算量很大。将这项职责卸载给伴随设备，可防止硬件钱包停滞或耗尽内存。

### 签名（授权花费）

签名与证明在根本上不同。数字签名是由私钥持有者生成的明确授权印记。

零知识证明验证交易有效性，而数字签名证明花费权限。签名证明真实所有者批准了特定的转账参数。

签名所需的计算能力很少，因此非常适合硬件钱包。

### 什么是屏蔽冷签名？

屏蔽冷签名是一种授权 Zcash 屏蔽交易的方法，同时将私有花费密钥与互联网连接的伴随钱包隔离。交易可以在联网计算机上构建和准备，而一个保持离线或以其他方式隔离的独立硬件钱包则使用其受保护的密钥来授权该交易。

## 伴随钱包和硬件钱包

屏蔽交易可以同时涉及伴随钱包和硬件钱包，每个钱包承担不同功能。

### 伴随钱包

什么是伴随钱包？

伴随钱包运行在计算机或移动设备上，并执行创建交易所涉及的大部分任务，例如：

- 选择要花费的 notes
- 构建交易
- 计算必要的交易数据
- 协调生成所需的零知识证明。

### 为什么伴随钱包有用？

伴随钱包处理交易创建流程，但如果计算机感染恶意软件，攻击者可能能够：

- 看到你的操作，
- 修改未签名的交易，
- 试图诱骗你批准某些内容。

伴随钱包无需访问存储在硬件钱包上的私钥，因此它可以处理交易构建和其他计算任务，而硬件钱包则为私钥提供安全边界。

### 硬件钱包

硬件钱包是一种离线实体设备，可将你的私钥与已连接的手机或计算机隔离，如同为你的加密资产提供一个安全保险库。

### 为什么硬件钱包有用？

如果你的计算机感染恶意软件，攻击者可能能够：

- 看到你的操作，
- 修改未签名的交易，
- 试图诱骗你批准某些内容。

私钥无法被简单地从硬件钱包中提取，因此该设备可以充当安全边界。

伴随钱包与硬件钱包能力对比图

这两种钱包之间的分离对于屏蔽交易尤其重要，因为屏蔽交易比透明交易更复杂，并涉及屏蔽 notes、nullifiers、commitments、零知识证明和交易签名等组件。

让硬件钱包执行每一项计算操作并不现实。相反，伴随钱包会准备交易并向硬件钱包提供签名所需的信息，同时私有花费密钥仍隔离在硬件设备内。

## 密钥隔离 [Key Isolation]

> 密钥隔离意味着可授权花费的私钥绝不会离开硬件钱包。配套应用可以准备交易；它无法对其签名。

密钥隔离是指，将授权一笔交易所需的私钥与配套钱包及其运行设备分开保存。在屏蔽冷签名设置中，配套钱包可以构建交易并协调所需的证明，而硬件钱包则将敏感的私有花费密钥隔离保存。

如果配套电脑或手机遭到入侵，攻击者可能能够在交易签名前与其交互，但理想情况下无法从硬件钱包中提取私钥。因此，密钥始终处于硬件设备的安全边界内。

这种分离使配套钱包能够执行交易构建和计算任务，而无需让其直接访问授权交易所需的密钥材料。

![Key isolation](/content-images/key-isolation.webp)

需要作出的关键区分是，"viewing key" 并不意味着应用会收到种子的弱化版本。

在 Zcash 中，Full Viewing Key（FVK/UFVK）是从花费密钥特意派生出来的，它使持有者能够检测和解密相关的屏蔽活动，但不能授权花费。FVK 是花费密钥的较低机密性派生物。

**一个重要的隐私注意事项：**

因此应当明确，应用仅凭 UFVK 无法窃取资金，但它可以看到钱包的私有屏蔽活动。

这也是为什么更准确的说法是，配套应用拥有 *查看权限 [viewing authority]*，而不只是说它拥有"公开信息"。

最简单的完整表述是：配套钱包获得了足够的密钥材料来了解钱包中发生的事情，但没有获得足以授权钱包资金流动的密钥材料。不过，硬件钱包会保持花费权限的隔离，并且只会在用户批准交易时使用它。

这正是这些屏蔽 Zcash 硬件钱包设计背后的核心密钥隔离模型，也是即将介绍的 Ledger、Keystone 和 Hito 中逐项实现的同一模型。

## PCZT

PCZT 表示部分创建的 Zcash 交易。它是一个用于将一笔 Zcash 交易及其完成所需的信息从一个阶段传递到另一个阶段的软件包。

它是在交易仍处于构建过程中时，用于表示 Zcash 交易的标准化格式。它允许不同参与者或设备完成交易创建过程的不同部分，并在它们之间传递部分完成的交易。

在像 Zcash 这样的零知识加密货币协议中，构建交易比为简单公开转账签名复杂得多。屏蔽交易需要计算密集型的零知识证明，例如使用 Halo 2 或 Groth16 生成的证明。因此，硬件钱包等低功耗设备可能缺乏处理完整交易工作流所需的内存和处理能力。

PCZT 的引入解决了屏蔽加密架构中的数项核心挑战。PCZT 是一种标准化的中间数据格式，将交易创建拆分为模块化、相互独立的角色。它允许性能强大的配套电脑处理交易组装和证明生成，同时将离线硬件钱包严格限制于授权和签名。

### 硬件和冷存储限制

尽管硬件钱包为保护私有花费密钥提供了安全环境，但与配套电脑相比，它们通常具有有限的 RAM、计算能力和数据传输能力。这些限制使其难以执行计算密集型零知识证明生成，或维护交易构建过程中所需的完整交易状态。

因此，配套钱包可以处理计算要求高的任务，而硬件钱包则专注于使用其受保护花费密钥授权交易这一安全关键操作。

这会让人好奇：如果设备如此受限，它如何仍能进行 *足够* 的验证以值得信赖？

简单来说，硬件钱包不能接受配套电脑提供的任意数值并对其签名。它需要足够的信息来确定所签名的数值对应于用户意图授权的交易。这造成了一个艰难的平衡：设备必须进行足够的解析和验证来保护签名过程，同时又要在内存、计算、固件大小和实现复杂性的严格限制内运行。

Ledger 的 Orchard PCZT 处理便是这一挑战的例子，它表明依赖特定电路的专用解析可以使受限设备上的实现更易管理，但当支持的交易结构或电路演进时，也可能需要更改固件。

两项正在推进的工作展示了针对同一限制的不同应对方式。

第 423 号拨款提出了一项研究建议，研究适用于开源硬件钱包架构和普通电脑的完全恒定时间证明流水线。目标是探索能够在 C 或 Rust 等环境中安全实现的密码学基础设施，同时降低屏蔽 Zcash 支持的复杂性和维护负担。

另一种方法则体现在拟议的 **Zcash SeedSigner** 中：这是一个使用廉价且易于获取组件构建的开源隔离网络签名器。其拟议工作流将配套电脑与签名设备分开，通过隔离网络传递 PCZT，以进行设备端验证和签名。

这些方法共同说明了屏蔽硬件钱包背后更广泛的工程挑战：交易构建和证明可以在安全关键设备之外进行，但签名器仍必须拥有足够的信息和验证能力，才能安全地授权最终交易。

### PCZT 实现分离架构

部分创建的 Zcash 交易（PCZT）标准是连接配套钱包与硬件钱包的正式数据结构。

配套钱包能够自行处理 note 选择、计算 nullifier 并生成零知识证明。这是可行的，因为这些步骤所需的信息，包括用于派生 nullifier 的密钥，来自 viewing key，而非任何与花费权限绑定的信息。随后，配套钱包将这些元素打包进 PCZT 容器。

PCZT 被交给硬件钱包，硬件钱包读取交易上下文（例如金额和收款人地址），使用受保护的花费密钥应用签名，然后将更新后的 PCZT 交回配套设备。

该设计建立了严格的安全边界：功能强大的主机硬件可以执行复杂的零知识计算，而无需访问花费密钥；低功耗冷存储设备则可以保障资金安全，而无需计算繁重的密码学操作。

### 证明者隐私妥协

虽然将零知识证明生成委托给配套钱包或其他证明者能够保持花费密钥隔离，但它仍要求证明者访问敏感交易信息，例如 note 金额、收款人地址和 commitment。

PCZT 通过确保可以提供这些信息以进行证明、而无需转移授权所需的私有花费密钥，维持了这种架构分离。

这确保了证明权限与花费权限相分离。证明者可以执行计算密集型证明生成，而不会获得花费用户资金的密码学权限。

### PCZT 互操作性

随着 PCZT 成为 Zcash 硬件钱包、多重签名和隔离网络签名工作流的重要组成部分，独立实现之间的互操作性变得日益重要。

AngryDavee 于 2026 年 6 月提出的一项建议指出，PCZT 的实现已经存在于多个项目中，包括 Ledger、Keystone、Hito、OneKey，以及 librustzcash 中的参考实现。然而，该建议发现缺乏共享测试来确认这些实现能一致地解释 PCZT。

拟议解决方案是一个开源互操作性测试套件，包含规范性的 PCZT 测试向量，以及覆盖完整创建 → 签名 → 最终化工作流的跨实现测试。它还提出测试诸如 Combiner 之类的角色边界，即不同签名者提供的部分签名信息可在交易最终化前合并。

这对硬件钱包尤为相关，因为 PCZT 允许交易构建与签名分离：配套钱包可以构建交易并准备 PCZT，而硬件设备接收所需签名信息并执行安全关键的签名操作。

该建议未获实施，因为 Zcash Community Grants 在审查建议并考虑社区反馈后决定不继续提供拨款。因此，拟议的跨实现测试套件没有通过该拨款得到开发。它因此是对已发现的 PCZT 互操作性挑战的拟议回应，而不是当前已存在于 Zcash 各实现中的标准。

https://forum.zcashcommunity.com/t/pczt-interoperability-test-suite-feedback-before-at-grant-submission/55931

### PCZT 的生命周期

| # | 阶段 | 描述 |
|---|---|---|
| 1 | 创建者 | 使用全局交易元数据初始化 PCZT，包括交易版本、共识分支 ID 和 pool 标记。 |
| 2 | 构建者 | 使用透明、Sapling、Orchard 或 Ironwood pool 中的预期输入和输出填充交易。 |
| 3 | IO Finalizer | 声明输入和输出集合已完成，计算绑定签名密钥，并在需要时对虚拟花费签名。 |
| 4 | 更新者 | 为后续参与者附加必要的上下文数据，例如完整 viewing key、锚点和 Merkle 见证。 |
| 5 | 证明者和签名者 | 执行零知识证明生成和密码学签名。在现代 PCZT 版本中，这两项任务完全独立，可以顺序或并行进行。 |
| 6 | 合并者 | 如果不同设备同时处理同一交易的不同方面，则确定性地合并多个 PCZT 实例。合并规则需要严格的冲突解决机制，以防止意外数据丢失。 |
| 7 | 花费最终化器和提取器 | 验证所有必需的密码学元素，移除中间上下文元数据，并生成可供网络广播的最终 Zcash 交易。 |

## 现实世界中的硬件钱包实现

### 概览

| 设备   | 配套应用接收的内容              | 留在设备上的内容          | 传输方式      |
|----------|------------------------------------------|-----------------------------------|----------------|
| Ledger   | UFVK / Orchard FVK、地址            | 花费权限                | USB / BLE      |
| Keystone | UFVK + 统一地址                   | 种子 / 花费密钥              | QR（隔离网络）|
| Hito     | UFVK、统一地址、种子指纹  | 种子和私有花费密钥    | QR / 本地     |

已经开发了数种硬件钱包实现，以探索如何在保持敏感花费密钥与配套钱包隔离的同时支持 Zcash 屏蔽交易。Ledger、Keystone 和 Hito 代表了将基于硬件的密钥保护与 Zcash 交易工作流结合的不同方式。

![Real world hardware wallet implementations](/content-images/hardware-wallet-implementations.webp)

要理解它们如何保护屏蔽资金，重要的是区分花费密钥和 viewing key。在这三种实现中，分离模式相同：

| 设备 | 配套应用可接收的内容 | 设备上保持受保护的内容 |
|---|---|---|
| Ledger | UFVK / Orchard FVK、地址和公开信息 | 花费权限 / 私有密钥材料 |
| Keystone | UFVK + 统一地址 | 种子 / 花费密钥 |
| Hito | UFVK、统一地址、种子指纹和网络信息 | 种子和私有花费密钥 |

### 作为硬件签名环境的 Ledger

Ledger 是一家硬件钱包公司。其设备以 Secure Element 为核心，这是一种专门设计的芯片，用于保存私有密钥材料，并将其与设备其他部分及连接到它的一切进行物理隔离。Secure Element 正是 Ledger 设备值得信赖用于冷存储的根本原因。这意味着即使与其连接的电脑或手机遭到入侵，Secure Element 内的密钥也无法被提取。

不过，就任何特定加密货币而言，Ledger 设备本身是空白的。它需要安装一个应用，该应用知道如何处理该货币特有的密码学机制。

Ledger 设备就任何特定加密货币而言是空白的，因此它需要一个了解该货币密码学的应用。对于 Zcash，已有两代方案：

- 最初由 Zondax 构建的"Zcash Shielded"应用，它与 Zkool 等配套钱包一起使用，并将于 2026 年 11 月 5 日停止支持；以及
- Ledger 较新的 Zcash 应用（3.9.4+），由 Ledger Wallet Desktop 4.21+ 原生使用，用于 Ironwood 屏蔽 ZEC。

以下密钥隔离模型适用于两者。

Zkool 是手机或电脑上的配套钱包，可与该应用通信。它构建交易并将其发送至 Ledger，设备上的 Zondax 应用随后对其签名并返回签名。

因此，Zondax 是运行在硬件上的软件，Zkool 是运行在硬件外部、利用 Zondax 的应用与设备通信的软件。

### 什么会离开 Ledger？

Ledger 的 Zcash 软件包含一个专门用于导出钱包 viewing key 的功能，该密钥让软件能够查看余额和交易，但不能花费任何资金。

此功能可返回两种内容之一：

- 统一 Full Viewing Key（UFVK），即同时覆盖 Zcash 全部屏蔽池的完整 viewing key；或
- 一个 Orchard Full Viewing Key（FVK）

无论哪种方式，导出的始终只是 viewing key。无论请求哪个版本，此功能都无法返回那项真正能够让人转移资金的信息，即花费密钥。

这正是其构建方式的核心：它被设计为唯一能够导出的内容，就是可安全交给配套应用的内容。

Zcash 的密钥层级结构使每个屏蔽池的花费密钥派生出两项独立内容：

- 花费授权密钥；以及
- 完整 viewing key

FVK 随后可以自行派生更多与查看相关的能力，但该派生路径绝不会回到花费权限。一旦密钥分支进入层级结构的查看侧，它就会停留在那里，不能用于重建其来源的花费权限密钥。

Ironwood 遵循相同模式，因为它复用了 Orchard 的底层密钥和 note 构造。不过，在共识层面它是一个独立的 pool，拥有自己的 commitment 树和 nullifier 集合。这意味着 UFVK 实际上是按 pool 划分的 viewing key 集合（透明、Sapling、Orchard，以及现在的 Ironwood），而不是单一的扁平密钥。

在 Ironwood 激活之前导出的 UFVK 不会包含 Ironwood viewing key，因为当时该 pool 尚不存在。这正是为什么钱包需要在 NU6.3 升级后更新，以识别和派生支持 Ironwood 的 UFVK。

### 什么留在 Ledger 上？

花费权限仍保留在设备上。

Ledger Signer 从主机接收交易/PCZT，并根据交易从哪个 pool 花费生成花费授权签名（Ironwood pool，因为 Ledger 当前的集成仅支持 Ironwood）。签名随后在设备上生成，主机仅接收签名，而不接收私有花费密钥。

这也符合 Ledger 的总体安全模型。其 Secure Element 隔离私有密钥材料，而 Ledger 的应用安全要求明确禁止应用向主机暴露这些机密。

Ledger 的签名器可以导出 FVK/UFVK，同时独立执行交易签名。这两项能力通过单独功能提供，而非捆绑在同一功能中。

### 这在实践中意味着什么？

假设你的 Ledger 中有 10 个 ZEC。

配套钱包可以持有 UFVK，因此能够确定："这个钱包已收到 10 个 ZEC。"它可以扫描并显示交易和余额。

但如果有人入侵配套钱包，仅凭 UFVK 并不能让他们创建花费授权签名。

独立花费授权签名的目的，是让硬件钱包等受限设备能够授权屏蔽花费，而无需自行执行完整的 zk-SNARK 证明。

### Zondax Ledger 应用；硬件钱包一侧

#### 什么是 Zondax？

Zondax 是一家第三方开发公司，构建了 Ledger Zcash 应用。它是运行在 Ledger 硬件上的实际固件应用，首先赋予该设备理解和处理 Zcash 交易的能力。

Zondax 是外部开发者。Ledger 硬件本身没有处理 Zcash 交易的内在能力，这项能力完全来自 Zondax 的软件。

### 最初的 Zcash Ledger 实现

Zondax 的 Ledger Zcash 应用仓库包含运行于 Ledger 设备的软件。该应用最初专注于 Sapling 屏蔽交易，而当时 Orchard 尚未成为 Zcash 的主要屏蔽池，因此 Sapling 支持就是 Ledger 设备在屏蔽 ZEC 方面所能实现的全部功能。

其架构体现了这种分离：主机/配套端准备交易信息，而 Ledger 处理敏感密钥操作和签名。

即使在这一最早版本的 Zcash 硬件钱包支持中，核心原则——主机进行构建和证明、设备进行隔离签名——已经是其设计基础。

### 向 Orchard 演进

Ledger 的工作转向了 Orchard + PCZT。这是一项实质性转变，而不是小幅更新，因为 Orchard 使用不同的证明系统（Halo 2，而非 Sapling 的 Groth16）以及不同的 note 和密钥构造。因此，将仅支持 Sapling 的固件扩展为处理 Orchard 签名，需要设备端新的密码学基础工作，而不只是一次固件修补。

然而，随着 Zcash 转向 Ironwood，Zondax 和 Ledger 将开发重心转向直接支持 Ironwood，而不是先完成一个 Orchard 实现、随后又为 Ironwood 重新设计。这代表了 Ledger 实现演进的进一步阶段，因为 Ironwood 建立在 Orchard 密码学架构之上，同时引入独立的屏蔽池和额外协议变更。

### 此 Ledger 应用内部发生了什么

最终流程如下：

1. 主机构建一个 PCZT。
2. 主机将相关交易信息发送至 Ledger 设备。
3. 设备生成 Orchard 花费授权签名。
4. 主机处理其后的全部内容，包括绑定签名和最终交易组装。

运行在 Ledger 内部的应用绝不会看到或生成超出花费授权签名本身的任何内容，而所有计算密集或数据需求高的工作（证明、绑定、组装）都留在主机上，主机无需因这些工作而被信任持有密钥材料。

### Ledger 的原生屏蔽集成；Ledger Wallet Desktop

Ledger 最新的 Zcash 集成提供了一个具体示例，展示如何在配套软件与硬件钱包之间分离屏蔽交易构建和安全关键签名。

借助 Ledger Wallet Desktop 4.21+ 和 Zcash 设备应用 3.9.4+，用户可以直接通过 Ledger Wallet Desktop 发送和接收 Ironwood 屏蔽 ZEC。该集成支持私密到私密转账、从透明 pool 屏蔽、解除屏蔽至透明 pool、私密收款地址和备忘录。交易在 Ledger 设备上验证和签名，而不是仅依赖电脑呈现的信息。

此架构的关键部分是查看能力与花费能力的分离。在私有余额同步期间，Ledger 导出统一 Full Viewing Key（UFVK），它存储在电脑本地。UFVK 允许 Ledger Wallet Desktop 检测相关屏蔽交易并确定钱包余额，但不提供花费资金的权限。安全关键的花费权限仍保留在 Ledger 设备上，由其执行最终签名操作。这在管理钱包状态和构建交易的电脑与保护花费授权能力的硬件设备之间建立了清晰边界。

不过，当前集成专门仅支持 Ironwood。它不通过 Ledger Wallet Desktop 显示或管理 Orchard 或 Sapling 资金。这在历史上意义重大，因为 Ledger 早期的 Zcash 开发在实现向 Ironwood 协议演进之前，与 Orchard 屏蔽支持相关联。

这一转变还凸显密钥和账户兼容性的重要性。Ledger 有一个由 Zondax 开发的较旧"Zcash Shielded"应用，并由 YWallet 和 zkool 等集成使用，该应用现正被淘汰。由于该旧应用为屏蔽账户使用不同的派生方案，其 Sapling 账户无法简单地由新 Ledger 应用重现。

因此，该集成既说明了屏蔽硬件钱包支持的进展，也展现了其仍存的限制。Ledger 现在可以提供完整的 Ironwood 体验：配套软件处理钱包同步和交易准备，而硬件设备仍是花费的安全边界。

与此同时，历史账户兼容性、仅支持特定屏蔽池、硬件交易大小限制、平台限制，以及解析和验证屏蔽交易所涉及的计算与固件限制，都表明对 Zcash 的硬件钱包支持不仅取决于协议能力，也取决于每个单独实现的设计和资源。

### Zkool + Ledger — 使用官方 Zondax 应用

作为 Ywallet 的继任者，Zkool 继承了屏蔽冷签名的目标，但采取了不同的实现路径。这一路径直接受到一个事实的塑造：如果签名应用无法安全分发，单靠密码学无法使集成可用。

https://youtu.be/eagkCIv3BlQ?si=7w5YfLlRER77bASw

### Zkool 对 Zondax 应用的使用

Zkool 转而使用由 Zondax 开发的官方 Ledger Zcash 应用，而不是 Ywallet 被放弃的专有 Ledger 应用。Zkool 不再维护一个无法被 Ledger 商店接受的自定义应用，而是基于已经被接受并通过 Ledger 自身生态系统分发的应用构建。

这一转变意味着用户无需再依赖安装未签名的自定义 Ledger 应用来使用该集成，因为 Zondax 的应用已通过 Ledger 的生态系统正式分发。

Ledger 将 2026 年 11 月 5 日定为停止支持此旧版 Zcash Shielded 应用的日期，并逐步淘汰该应用。Zkool 为此做了准备：[version 6.30.0](https://github.com/hhanh00/zkool2/releases/tag/zkool-v6.30.0)（2026 年 9 月 12 日）增加了对 Ledger 新官方 Zcash 应用的支持，同时保留了 Zondax 应用。创建 Ledger 账户时，Zkool 现在会询问设备运行哪个应用（官方或 Zondax）。官方应用账户覆盖透明和 Ironwood pool：Zkool 可以从设备导入其 UFVK，并使用官方应用签署 v6 交易。Zondax 应用账户则保留较旧的透明 + Sapling 设置（[zkool2#1242](https://github.com/hhanh00/zkool2/pull/1242)）。

### 支持的屏蔽池

据 Ywallet 开发者称，Zkool 的 Ledger 集成使用了由 Zondax 开发的官方 Ledger 应用，并同时支持透明和屏蔽 Zcash。不过，其屏蔽支持仅限于 Sapling，且不支持 Orchard；此外还存在其他集成限制，例如每种类型最多 5 个输入和输出，以及不兼容 Ledger Live。

这一限制反映了当时底层 Zondax Ledger 实现的范围。Zondax 较早的 Ledger 工作提供了 Sapling 支持，而其在 2024 年后续发布的 Zcash 屏蔽 Ledger 应用最初排除了 Orchard 和统一地址。因此，围绕该应用构建的集成继承了其所依赖硬件钱包实现的能力与限制。

随着专用 Zcash 屏蔽 Ledger 应用于 2024 年 11 月发布，这一情况随后发生了变化。Zondax 表示，该应用已通过 Ledger Live 正式发布，之后还发布了集成指南以及 Rust 和 JavaScript 软件包，以便其他钱包与之集成。不过，在发布时，该应用只能与 Zecwallet Lite Desktop 通信，更广泛的钱包集成仍在开发中。

下一阶段是开发 Ledger 较新的、基于 Rust 的 Zcash 应用。截至 2026 年 6 月，Ledger 报告称，UFVK 共享和 Orchard 统一地址生成已实现，而 Orchard 交易签名和 ClearSign 仍在开发中。Ledger 还表示，随着协议变化，这项工作将延续至 Ironwood 路径。

Ironwood 随后要求整个 Zcash 钱包生态系统进行更新。Zkool 从 6.24.0 版本开始发布对从 Orchard 迁移至 Ironwood 的支持，并在后续版本中持续完善迁移和交易流水线。Ledger 则于 7 月 27 日将 PCZT v2 签名合并至其新应用，尽管截至 8 月 20 日，该实现尚未完成 Ledger 的审查和 Ledger Live 的推出；这一里程碑现已完成，Ledger Wallet Desktop 4.21+ 现已直接提供原生 Ironwood 支持。

https://forum.zcashcommunity.com/t/a-path-forward-for-ledger-and-zcash/50951/177

因此，更合适的理解方式并非一次从 Zondax 到 Ironwood 的单一升级，而是若干相互关联的发展：最初聚焦于 Sapling 的 Zondax 实现、2024 年的 Zcash 屏蔽 Ledger 应用、具备 Orchard 和 PCZT 支持的较新 Ledger Rust 应用、Ledger 在 Ledger Wallet Desktop 中的原生集成，以及随着生态系统过渡至 Ironwood，Zkool 等钱包的并行更新。

### Zcash 当前的 Ledger 设备和平台支持

Ledger 上的 Zcash 支持取决于

- 设备型号
- 已安装的应用
- 用于管理它的平台，以及
- 交易是透明还是屏蔽。

截至 2026 年 7 月 21 日（Ledger 的最后更新），Zcash 屏蔽应用支持 Nano S Plus、Stax 和 Flex，但尚不支持 Nano X 或 Nano Gen5。

除原始 Nano S 外，Nano X 和其他型号仍可使用经典 Zcash 应用，该应用支持透明交易，以及将屏蔽资金花费至透明地址（解除屏蔽），但不支持屏蔽至屏蔽签名。原始 Nano S 不支持任一应用，因为 Ledger 正逐步停止对该设备的支持，且其最新的 Zcash 应用无法在该设备上使用。设备可连接至 Ledger Wallet（原称 Ledger Live），即 Ledger 的配套应用（companion application）；该应用的桌面版适用于 Windows、macOS 和 Linux，移动版则适用于 iOS 和 Android。

Ledger 已在 Ledger Wallet Desktop 中添加原生屏蔽 Zcash，其基于 Ironwood pool 构建，因此无需单独的配套钱包。Ledger 面向 iOS 和 Android 的移动应用尚不支持屏蔽 ZEC，但计划在未来版本中提供移动支持。

在 Ledger 自有软件之外，屏蔽使用取决于兼容的配套钱包及其支持的平台。随着 Ledger 持续扩展 Ironwood 支持，兼容性取决于设备型号、固件、应用版本和操作系统，因此一般性的 Zcash 支持并不一定保证兼容。

### YWallet 冷签名（cold signing）；一种较早的方法

Ywallet 是一个配套钱包，与 Ledger 和 Zondax 均相互独立，并探索了自己的屏蔽冷签名路径。

Ywallet 在历史上很重要，因为它探索了用于 Zcash 的冷签名，这意味着签名设备可以与在线钱包保持分离。

为在 Ledger 硬件上实现该架构，Ywallet 构建了自己的 Ledger 应用，即专有应用，不同于上一节介绍的 Zondax 应用。这意味着 Ywallet 并不依赖 Zondax 现有的 Sapling 实现；它拥有运行关系中签名端的自有固件。

### 该集成为何重要

拥有密码学和签名代码还不够。硬件钱包集成不仅是一个密码学问题，它同样不可避免地涉及分发和平台问题。至少包括：

- 应用审批/分发——硬件制造商的官方应用商店是否会接受并分发该应用
- 固件/应用安全——该应用是否满足制造商处理密钥材料的安全要求
- 通信协议——配套钱包和设备实际如何交换交易数据
- 与钱包的兼容性——签名应用的数据格式和流程是否符合配套钱包的预期
- 支持的屏蔽池——该应用实际上能够为 Sapling、Orchard（以及现在的 Ironwood）中的哪些进行签名

Ywallet 的专有 Ledger 应用满足密码学和架构要求；它能够对屏蔽 Zcash 交易进行签名，但未被 Ledger 的官方应用商店接受。

### 放弃专有 Ledger 应用的过渡

由于该应用未被官方接受，Ywallet 必须要求用户安装未签名固件才能使用它；这会对用户造成真实的安全妥协，因此 Ywallet 选择不向他们提出这一要求。因此，Ywallet 最终放弃了该特定集成，而非走这条路。

后续开发没有复兴专有应用，而是通过 Zkool（Ywallet 的继任者）转向由官方 Zondax 构建的 Ledger 应用，以已获 Ledger 分发生态系统接受的标准化实现，取代了定制且被拒绝的实现。这一转变最终使可行的 Ledger 集成再次成为可能。

### Ywallet 的遗产

即使在 Ywallet 本身不再积极开发后，其创建者 Hanh——同时也是 ZCG 成员——仍是生态系统中重要的声音，特别是在 Ironwood 的迁移引发了有关资金似乎消失的报告时。

**ZODL：一名真实用户在 Orchard → Ironwood 迁移后遇到资金缺失**

一名用户 Jmo0615 报告称，其先前在 ZODL 钱包中可见的资金，在从 Orchard 迁移至 Ironwood 后不再显示。其表示已恢复原始种子、重置并恢复钱包，并允许 ZODL 3.14.1（1）版本完成全部同步。其还确认没有涉及任何 Keystone 硬件钱包。

尚无法确定这些资金是否真的丢失。更可能的怀疑是钱包发现或迁移相关问题，即先前可见的资金在过渡到 Ironwood 后不再显示。未被检测或显示的资金不应自动被描述为永久丢失的资金，在理解迁移问题时，这一区别很重要。

https://forum.zcashcommunity.com/t/funds-not-showing-since-ironwood/57792

**Zkool："锁定 note" 可以解释表面上无法使用的资金**

屏蔽钱包的另一个重要方面是，钱包状态会如何影响用户实际可以花费的资金。Hanh 解释说，用户可能通过币控制意外锁定一个 note；币控制是一项允许用户手动选择用于花费的 note 的功能。在这种情况下，一个 note 可能仍存在于钱包中，但被标记为不可用于花费。

这突出了调查钱包问题时的一个重要区别。钱包中存在的 ZEC 数量并不总是等同于当前可花费的数量。诸如 note 选择、同步、迁移状态、钱包恢复和币控制设置等因素，均可能影响显示的或可花费的余额。因此，对于"资金缺失"的报告，应仔细区分未被检测或显示的资金、已被检测但无法花费的资金，以及实际丢失的资金。

## 2. Keystone

**什么是 Keystone？**

Keystone 是一款隔离网络的硬件钱包。其签名设备在签名过程本身不会与配套应用直接进行有线或无线连接，而是通过 QR 码通信。这里它与 Zashi（现更名为 Zodl）配对，后者是 Zcash 的原生配套钱包；这一配对使密钥隔离原则格外明确且易于追溯。

**Keystone/Zashi 流程**

Keystone 与 Zashi 的 Zcash 集成使这种分离尤为明确。当你将 Keystone 连接至 Zashi 时，统一 Full Viewing Key 会从 Keystone 传输至 Zashi。

因此，流程如下：

![Keystone and Zashi viewing flow](/content-images/keystone-zashi-viewing-flow.webp)

**Zashi 可以利用 UFVK 做什么？**

Zashi 可以使用它来：

- 识别传入的屏蔽交易
- 确定余额
- 获取有关屏蔽活动的信息

但仅仅因为它拥有 UFVK，它无法花费资金。

UFVK 是一种"查看能力"，可用于了解余额和交易，但不允许花费。

### 什么会保留在 Keystone 内？

种子/花费授权保留在 Keystone 上。Zashi 不会接收种子、花费密钥或花费授权私钥。它接收 UFVK、地址信息以及仅查看操作所需的信息。

这两部分共同构成完整图景。离开设备的信息，例如 UFVK、地址和仅查看信息，足以让 Zashi 监控账户，但离开设备的任何信息都不足以将资金转出设备。

这正是 Zashi 与 Keystone 的集成能够提供屏蔽冷存储的原因。钱包应用可以监控账户，而不会拥有从中花费所需的授权。该集成专门推出，以实现对屏蔽 ZEC 的冷存储。

## 3. Hito

Hito 遵循与 Keystone 非常相似的密钥隔离模型，但其实现更新。Hito 并非与 Zashi 等现有配套钱包配对，而是附带自己的 Android 钱包，硬件设备与该 Android 应用之间的引导流程已记录在 Hito 的开发里程碑中。

**引导：Hito 应用接收什么**

Android 钱包在引导硬件账户时使用：

- 统一 Full Viewing Key（UFVK）
- 统一地址
- ZIP-32 种子指纹
- 网络信息

请注意，Android 应用绝不会接收硬件钱包的种子或私有花费密钥。

![Hito onboarding](/content-images/hito-onboarding.webp)

**Hito 应用会获得什么？**

已记录的引导信息包括：

- UFVK
- 统一地址
- ZIP-32 种子指纹
- 网络

UFVK 向 Android 钱包提供其以具备查看能力的钱包身份操作账户所需的信息，而无需接收种子。种子指纹是从种子派生的固定长度标识符，用于识别各个账户；它并非种子本身，也不赋予任何花费能力，因此它的存在并不与上述"绝不会接收种子"的说法矛盾。

**什么会保留在 Hito 上？**

实际种子、私有花费密钥和签名授权仍保留在硬件设备上。随后，Hito 离线执行签名。

当前 Hito 里程碑指出，整个创建、导出、离线签名和导入工作流程均已可用，具备 BLE 传输和通过 BBQr QR 导出已签名 PCZT 的功能。

这一工作流程值得明确命名，因为它正是本报告前文所涵盖完整循环的具体实例：Android 钱包创建未签名 PCZT，将其导出至 Hito，Hito 使用其隔离的密钥材料离线签名，然后将已签名 PCZT 导入回 Android 钱包。

种子或花费密钥不会在任何时候、以任一方向跨越该边界。

![Hito signing flow](/content-images/hito-signing-flow.webp)

## Orchard 到 Ironwood：硬件钱包 [hardware wallet] 支持的演变

Orchard 是 Zcash 协议中的一个屏蔽池 [shielded pool]，使用户能够以增强的隐私 [privacy] 存储和交易 [transaction] ZEC。Orchard 在网络升级 [Network Upgrade] 5（NU5）中推出，采用 Halo 2 证明 [proving] 系统和重新设计的密码学架构，以支持不会泄露发送方、接收方或金额等敏感交易信息的屏蔽 [shielded] 交易。

Ironwood 是在 Zcash 的 NU6.3 网络升级中引入的屏蔽池，是 Orchard pool 的继任者。它采用 Orchard 密码学协议，同时引入了旨在提升屏蔽资金长期安全性的变更，包括量子可恢复性和对供应完整性的更强保证。

首先必须澄清，Ironwood 并未用全新的密码学系统取代 Orchard 协议。Ironwood 是基于现有 Orchard 协议构建的新屏蔽池。这意味着它们拥有相同的 Action 结构、相同的 Halo 2 证明系统，以及相同的 note 和密钥构造。

Ironwood 拥有自己的 note commitment tree、nullifier 集合、anchor 和 value pool，因此在共识 [consensus] 层面，它是一个真正独立的 pool。但从密码学角度看，它是 Orchard 的扩展，而非重建。

它被这样设计是为了：

1. **供应完整性。** 2026 年 5 月 29 日，安全研究员 Taylor Hornby 私下披露了 Orchard 零知识 [zero-knowledge] 证明系统中的一个关键健全性缺陷，该缺陷可能允许创建伪造的 ZEC，且不会留下链上 [on-chain] 痕迹。由于 Orchard 的交易数据是私密的，任何人都无法独立验证修复前是否创建过伪造的 ZEC。封存旧 pool 并以零余额启动新 pool，能够以原地修补 Orchard 无法做到的方式解决这个问题。
2. **确保量子可恢复性。** Ironwood 的设计使其资金能够在底层离散对数假设遭到破坏时参与未来的恢复机制。
3. **最大限度减少实现变更。** 与其设计一个完全新的屏蔽协议，不如复用 Orchard 已得到验证的架构。这意味着需要从头编写的新交易、证明、钱包 [wallet] 和硬件钱包代码会少得多。

### 公开时间线

- 5 月 29 日：披露 Orchard 漏洞。
- 6 月：Orchard 交易受到临时限制，同时通过 NU6.2 推出初步修复。6 月 12 日，一名核心开发者将完整升级目标定为 7 月 21 日；之后又推迟了一周。社区提出了一项担忧：Keystone 持有者会是最后迁移的人；随后一名核心开发者回应称，Keystone 将从第一天起支持 Ironwood，固件目标发布日期为 7 月 3 日，等待 Zcash 核心最终确定签名 [signature] 常量和 Orchard API 变更。
- 7 月初：NU6.3 进入测试网；Zebra 6.0.0 于 7 月 10 日发布。
- 7 月 27–28 日：Ledger 的 Ironwood PCZT v2 签名工作合并至集成分支。Ironwood（NU6.3）于 7 月 28 日在区块 [block] 3,428,143 激活，将原始 Orchard pool 封存在一个 turnstile 之后，该机制将能够离开 Orchard 的 ZEC 数量限制为曾合法存入其中的金额，并引入了新的交易格式。

Zebra 成为必需的节点 [node]，因为 zcashd 不支持新的共识规则。地址 [address] 不会改变，因为 Ironwood 复用了 Orchard 的 receiver 结构，因此钱包会自动将现有地址路由到新 pool。钱包确实需要的是迁移功能，因为 Orchard 资金最终必须由其所有者转移至 Ironwood，而接收 Orchard 的新输出现在已被共识完全阻止。

### 技术上发生了什么变化

交易格式从版本 5 变为版本 6，因此单笔交易可以在现有 Sapling/Orchard/透明 [transparent] 组件之外携带一个 Ironwood 组件。PCZT 也随之扩展：

- 编码从 PCZT v1 升级为 v2。
- 现在独立的 Ironwood bundle 与 Sapling 和 Orchard bundle 并列存在。
- 支持 v6 交易和新的 v6 sighash。
- Note plaintexts 新增了一个版本（V3）。

sighash 变更对硬件钱包尤为重要。在 v6 中，Orchard 和 Ironwood anchors 被排除在签名哈希之外，仅参与 authorizing data digest。这是真正的固件变更，而不只是版本升级。设备必须正确实现新的 sighash，并自行重新计算它，而不是信任配套应用声称自己正在批准的内容。

隔离契约本身没有改变：设备仍然只返回花费授权签名，绝不会返回 `alpha`，也绝不会生成 binding signature；主机仍然负责证明及其他所有工作。

不过，v6 改变了一条 signer 规则：虚拟填充花费由 IO Finalizer 签名，而非设备，因为设备无法依据真实 note 数据验证它们。设备的 Signer 角色会跳过它们，而不是被要求签署无法检查的内容。显示的手续费 [fee] 现在也会将 Orchard 和 Ironwood value balances 相加，因为一笔 v6 交易可以在同一笔交易中从任一 pool 花费。

正确处理 pool 记账在实践中至关重要，而不只是理论问题。Brave 自己的 Zcash 钱包近期出现的一个漏洞就是很好的说明：其手续费计算假设所有屏蔽输入都属于旧版 Orchard pool，导致只要交易实际涉及 Ironwood，就会出现重复的 actions 和错误的手续费估算。这正是硬件钱包签名背后"自行重新计算，不要信任主机"原则旨在捕获的错误类型。配套钱包错误处理了 pool 记账，只有独立检查自身计算的设备才能在签署前发现问题。

### 各签名器的现状

**Ledger 刚刚改变了整个局面。** 2026 年 9 月 23 日，Ledger 直接在 Ledger Wallet Desktop 内推出原生屏蔽 Zcash 支持，不再需要单独的配套应用。你的花费密钥 [spending key] 保留在设备上，计算机完成交易计算，而你会在屏幕上批准所有内容后才会签名。它仅支持 Ironwood，不支持旧版 Orchard 或 Sapling pools。缺点是，由 Zondax 构建、需要配套钱包（如 Zkool）才能运行的旧版"Zcash Shielded"应用正在停用。Ledger 将 2026 年 11 月 5 日定为从可用列表中撤下该旧应用的日期，因此仍通过它持有的资金应转移至新应用中的账户。

**Keystone 状况良好。** 固件 3.0.2 早在 7 月就新增了完整的 Ironwood 支持，而固件 3.2.2（2026 年 11 月 11 日）为 Web3 和 Cypherpunk 版本增加了 NU7 支持（[发布说明](https://github.com/KeystoneHQ/keystone3-firmware/releases/tag/3.2.2)）。由于 NU7 已在 Mainnet 激活，请在签名之前更新至 3.2.2 或更高版本。

**Hito 已超越最初的测试网里程碑。** 它已在物理硬件上成功签署并提交第一笔真实的 Orchard 至 Ironwood 交易（最初在测试网上）。后续更新确认了生产硬件上的主网流程（Ironwood→Ironwood、Ironwood→透明，以及其他流程）。稳定固件和更广泛的发布仍在推进中。

**Zkool 可与两款 Ledger 应用配合使用。** Zondax 的应用将于 Ledger 停用。Zkool 原本依赖该应用与 Ledger 设备通信，已在截止日期前完成迁移：自 [6.30.0](https://github.com/hhanh00/zkool2/releases/tag/zkool-v6.30.0)（2026 年 9 月 12 日）起，它也能与 Ledger 新的官方 Zcash 应用配合使用，从设备导入 UFVK 并签署 v6（Ironwood）交易，同时仍支持 Zondax 应用账户。之后的版本继续改进 Ledger 路径（6.32.0 通过 Zkool 的 GraphQL API 导入 Ledger 账户，6.36.0 修复了短 Ledger 回复导致的崩溃）。因此，对于希望使用配套钱包而非 Ledger Wallet Desktop 的 Ledger 用户，Zkool 仍然是一个选项。

迁移本身是最大的连锁影响。由于跨 pool 的金额是公开的，钱包会随时间将转移分散到标准面额中，而不是一次性以可见的大额余额进行转移；这意味着每次迁移需要签署许多交易，也正是批量 PCZT 签名对硬件钱包如此重要的原因。

Ledger 的固件工作还遇到了硬件限制：一次真实 note 花费可在单条命令中达到数万次密码学系统调用，触发设备 watchdog。修复方案将有限域算术移至软件，并要求共享 scratch state 以满足 Nano X 的堆栈限制。

https://forum.zcashcommunity.com/t/ironwood-is-here-updated-wallets-libraries-aug-20/56557/40
