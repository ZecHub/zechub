# 检测屏蔽支付：扫描成本

接受屏蔽 ZEC 的商家必须找到收到的支付。在透明 pool 中，这只需进行索引查询。在屏蔽池中，没有人能按地址索引支付，因此钱包或后端必须用自己的密钥检查链上的每个屏蔽输出。本页将说明这项工作的原理、成本，以及如何选择能控制成本的账户设计。

## 简要说明

* 屏蔽支付检测成本取决于你监控的 **viewing key** 数量，而不是你发放的地址数量
* 一个账户可以为每位客户或每张发票生成新的、不可关联的 **多样化地址（diversified address）**，而无需增加扫描成本
* viewing key 会显示账户的 **全部内容**。如果审计人员只能查看某一位客户，该客户就需要单独的账户，而且每个账户都会增加每个区块的扫描工作量
* 按 **满区块** 规划扫描器，而不是按平均值。主网已经出现过连续多个接近满载的区块
* 规划容量前，先在自己的硬件上测量每次试探的成本

## 为什么屏蔽支付无法索引

对于透明地址，节点可以读取每个输出中的地址，并建立地址到输出的索引。Zebra通过 `getaddressutxos` 和 `getaddresstxids` 提供此功能。

屏蔽操作不包含可读地址。它携带一个 note commitment、一个临时公钥和一条加密的 note。这些字节中没有任何信息能说明这笔支付是给谁的，因此节点和 [索引器](Lightwallet_Nodes.md)都无法建立地址索引。

因此，发现支付的过程是反过来的。钱包会逐个检查屏蔽输出，并尝试解密，询问“这是我的吗？”。这称为 **试探解密（trial decryption）**。[Viewing keys](Viewing_Keys.md) 介绍密钥能揭示哪些信息，[Zcash 钱包同步](Zcash_Wallet_Syncing.md)则介绍钱包如何安排这项工作。

## 一次试探的工作原理

对于 Orchard 协议的操作格式，Orchard 和 Ironwood pool 都使用这种格式：

1. **密钥协商：** 将操作中的临时公钥与 incoming viewing key 相乘。这是在 Pallas 曲线上进行的标量乘法，也是成本的主要部分
2. **密钥派生：** 将共享密钥哈希为对称密钥
3. **解密 note 的前 52 个字节：** 包括多样化因子、数值和 `rseed`
4. **根据解密内容重建 note commitment**
5. **将其与操作中的 `cmx` 比较。** 如果匹配，说明这条 note 属于你

只有到第 5 步才能知道这条 note 是否属于你，因此 **未命中的成本与命中基本相同**。链上的操作几乎都属于其他人，所以几乎所有工作都是未命中。

## 成本公式

```text
work per block = K × I × A × t

K  accounts you watch
I  incoming viewing keys per account (2: external and internal)
A  shielded actions in the block
t  time for one trial on one core
```

公式中没有地址这一项。钱包会同时尝试外部密钥（你发放的地址）和内部密钥（找零），这就是为什么 `I = 2`。你可以在 librustzcash 的 `zcash_client_backend/src/scanning.rs` 中看到 `for scope in [Scope::External, Scope::Internal]` 循环。

[ZIP 218](https://zips.z.cash/zip-0218) 将每个区块的屏蔽操作上限设为 **330 次**，因此 `A` 最多为 330。

## 多样化地址：多个地址，一个密钥

Orchard 协议地址由一个多样化因子 `d`（11 个字节）和一个从同一 incoming viewing key 派生的传输密钥组成。[ZIP 32](https://zips.z.cash/zip-0032) 使用 FF1 加密，从一个 88 位索引派生每个多样化因子，因此一个账户有 **2^88 个地址**，且每个地址都符合 Orchard 协议。

这为支付后端带来两个实用特性：

* **这些地址不可关联。** 没有 viewing key 时，同一账户的两个多样化地址看起来就像属于两个不同的钱包
* **支付无需查找表即可对应到发票。** 试探解密成功后，解密出的 note 中会包含 `d`。账户的多样化密钥可以将 `d` 解密回对应的索引；因此，如果索引就是你的发票编号，你就知道哪张发票收到了款项

向客户展示地址前，先将每个地址封装为 [统一地址](../Using_Zcash/Unified_Addresses.md)（[ZIP 316](https://zips.z.cash/zip-0316)）。

## 注意事项：一个 viewing key 会显示整个账户

你无法将 viewing key 限定为只能查看一个多样化地址，因为账户中的所有地址都使用同一个密钥。因此，账户也是信息披露的单位。任何拿到账户 viewing key 的人都能看到该账户中所有地址收到的每笔支付。

这意味着有 3 项内容需要一并决定：

| 设计 | 扫描成本 | 可向审计人员展示的内容 |
|:--|:--|:--|
| 一个账户，每位客户使用一个多样化地址 | 一个密钥，无论客户数量多少 | 全部内容，或什么也不展示 |
| 每位客户一个账户 | 每个区块为每位客户扫描一个密钥 | 一次展示一位客户 |
| 每位客户每个时期一个账户 | 每个区块为每位客户、每个时期扫描一个密钥 | 某个时期内的一位客户 |

提前选好账户设计。之后再拆分账户，意味着要把资金转入新账户，这会产生手续费，也会留下可见的模式。

## 实际成本

以下数据来自一台笔记本电脑的一个核心（Apple M3 Pro，发布构建），使用 `zcash_note_encryption` 0.5.1 中的 `try_compact_note_decryption`，对来自测试网的真实 Ironwood 操作进行测量：

| 测量项 | 数值 |
|:--|:--|
| 一次试探，每次处理一个密钥 | 约 82 µs |
| 一次试探，批量处理 10 或 100 个密钥 | 约 42 µs |

批处理大约能将成本减半，librustzcash 的扫描器也出于同样原因采用批处理。

在使用 `t = 42 µs` 且每个满区块包含 330 次操作时：

| 监控账户数 | 每个满区块的核心时间 | 跟上满区块所需的核心数 |
|:--|:--|:--|
| 1 | 28 ms | 0.001 |
| 1,000,000（每位客户一个账户） | 7.7 小时 | 约 1,109 |

同样是 100 万位客户，如果使用一个账户和多样化地址，每个满区块只需 28 ms。唯一的区别在于账户边界的位置。

## 按突发情况而非平均值规划

在截至高度 3,582,677 的 5,000 个主网区块中（于 2026 年 11 月 17 日采样）：

* 62% 的区块没有屏蔽输出，中位数为 0
* 每个区块平均有 12.3 个屏蔽输出
* 高度 3,579,935 至 3,580,346 之间有 153 个区块，约覆盖 3 小时的链时间；每个区块都超过 250 个输出，而且常常连续出现。这些区块包含了样本中 75% 的全部输出

按平均值配置的扫描器，遇到这样的连续高负载时会落后。请预留余量（例如，计划只使用每个区块 25 秒间隔的一半），并按上限配置。

## 紧凑区块能节省带宽，但不会减少试探次数

轻钱包会从 lightwallet 服务器扫描紧凑区块。紧凑操作为 148 字节，完整操作则为 820 字节。它只保留试探所需的数据：临时密钥、密文的前 52 个字节、nullifier 和 `cmx`。只有在客户端请求时才会发送透明数据。

紧凑区块能减少下载量。但它们不会减少试探次数，因为仍然必须用每个密钥试探每个操作。

## 支付后端检查清单

* 创建账户前，先决定将来哪些人需要查看哪些内容
* 在允许披露的情况下，尽可能从一个账户为每张发票发放一个多样化地址
* 开启批处理，在自己的硬件上测量 `t`
* 按每个区块 330 次操作并预留余量，为实时区块扫描配置容量
* 按高度范围将历史重扫任务分配给多个工作进程。历史数据固定，因此可以轻松并行处理
* 记住，每个新账户也必须从其创建高度开始扫描历史数据
