# FROST 与屏蔽 ZEC 的门限托管 [threshold custody]

> 有关 FROST 协议的完整密码学细节，请参阅 [FROST 技术页面](FROST.md)。

FROST 门限托管在 Zcash 的讨论中不断出现——它是 ZecHub Hackathon 2026 最热门的赛道——但这个概念并不总是以通俗易懂的方式解释。本页介绍它的含义、实际需要它的场景、权衡取舍，以及目前支持它的工具。

---

## 简要说明

- **FROST** 让一组密钥持有者能够共同控制一个屏蔽 Zcash 地址，而无需任何单个人持有完整私钥。
- **t-of-n** 门限表示：必须有 t 人共同签名才能花费；任意 t-1 人或更少的人都无法单独转移资金。
- 交易看起来与其他任何屏蔽交易完全相同——不会留下揭示使用过门限签名的链上痕迹。
- 这与透明多重签名根本不同（后者在链上公开，且 Zcash 长期以来一直支持它）——FROST 在屏蔽池内运行。
- 它适用于 DAO、交易所、托管服务、共同储蓄和团队金库——即任何无法接受密钥单点故障的场景。

---

## 用通俗语言来说，什么是 FROST？

想象一下，3 位商业伙伴各自持有一部分密钥。要从他们共享的钱包中花费资金，3 人中的任意 2 人必须同意并共同签名。生成的交易与普通个人转账完全相同——没有观察者能从 blockchain 看出有多人参与。

FROST（灵活轮次优化的 Schnorr 门限签名 [Flexible Round-Optimized Schnorr Threshold Signatures]）是使屏蔽 [shielded] Zcash 成为可能的密码学协议 [cryptographic protocol]。它由 Chelsea Komlo（滑铁卢大学 / Zcash Foundation）和 Ian Goldberg 创建。

核心特性：

- **门限**：只需要 t-of-n 个签名者参与（例如 2-of-3、3-of-5）
- **屏蔽**：在 Orchard 隐私 pool 内运行——金额、发送方和接收方均保持私密
- **不可区分**：最终签名看起来与任何其他 Zcash 屏蔽交易相同
- **非托管**：没有任何单一方持有完整密钥——协调者也不例外

---

## 何时应使用门限托管？

当**丢失一把密钥或失去一个人不应意味着丢失资金**时，门限托管就很有意义。

| 场景 | 门限托管为何有帮助 |
|-----------|----------------------------|
| **DAO 或团队金库** | 没有任何单一管理员可以单方面抽走资金；需要共识 |
| **交易所或托管方** | 将密钥风险分散到不同的安全区域或员工之间 |
| **个人冷存储（与信任的家人共同使用）** | 你与两位家人之间采用 2-of-3——即使死亡或失去访问权限，资金也不会丢失 |
| **托管交易** | 买方、卖方和仲裁员各自持有一份；两人同意时资金释放 |
| **高价值拨款发放** | ZCG 风格：付款前需要多名独立签名者 |
| **开发者密钥管理** | 防止内部威胁——没有任何单一工程师能抽走协议资金 |

对于你独自控制的个人钱包、小额资金，或增加的协调开销超过风险降低收益的情况，你可能**不**需要门限托管。

---

## 它与透明多重签名有何不同？

Zcash 长期以来一直支持透明多重签名——从 t 地址花费资金需要多把密钥。但透明多重签名有显著的隐私代价：**多重签名结构、所有公钥和所有签名者都在 blockchain 上可见**。

FROST 通过在屏蔽池内运行解决了这一问题：

| | 透明多重签名 | FROST 门限（屏蔽） |
|--|---------------------|--------------------------|
| Pool | 透明（公开） | Orchard（屏蔽） |
| 链上可见的签名者 | 是——所有公钥均公开 | 否——与单一签名者花费不可区分 |
| 可见金额 | 是 | 否 |
| 所需协调 | 链上脚本 | 链下通信轮次 |
| 隐私 | 无 | 完整屏蔽隐私 |

## 权衡与限制

FROST 功能强大，但在使用前应了解以下实际权衡：

### 协调开销
签名者必须同时在线（或接近同时在线）才能完成一轮签名。如果 t 位签名者分散在多个时区或网络连接不可靠，花费资金就需要单人钱包不需要的协调。

### 法定人数不可用时无法签名
如果足够多的密钥持有者不可用（生病、旅行或无响应），资金将暂时无法花费。请谨慎选择门限和份额数量——2-of-3 比 2-of-2 更具韧性。

### 密钥生成仪式
设置 FROST 需要进行分布式密钥生成（DKG）仪式，所有 n 名参与者必须同时在线。这是一次性事件，但必须谨慎完成——如果参与者在 DKG 期间遭到入侵，安全性将被削弱。

### 工具仍在成熟中
用于屏蔽 FROST 的 Zcash 相对较新。IETF 标准（draft-irtf-cfrg-frost）已较成熟，但钱包集成有限。与标准单密钥钱包相比，预计会遇到一些不够完善的地方。

### 恢复复杂性
丢失一个分片并非世界末日（这正是门限的意义），但必须提前记录恢复计划。谁持有备份？如果两个分片同时丢失会怎样？

## 签名会话如何运作（简化版）

1. **设置（一次性）：** 所有 n 名参与者运行分布式密钥生成（DKG）仪式。每人获得一个私有分片；随后派生出共享公钥。没有任何一方知道完整私钥。

2. **协调签名者：** 需要花费资金时，协调者（可以是签名者之一）会从愿意签名的 t 名参与者处收集 commitment。

3. **第 1 轮：** 每名参与的签名者生成一个 nonce 并广播一个 commitment（公开且非敏感）。

4. **第 2 轮：** 每名参与的签名者使用其私有分片计算部分签名并进行广播。

5. **聚合：** 协调者将 t 个部分签名合并为一个最终 Schnorr 签名——在链上与单方签名不可区分。

6. **广播：** 交易照常广播至 Zcash 网络。

如果任何签名者发送了错误的部分签名，协议会识别该签名者并中止（其将被排除在未来会话之外）。协调在链下进行——blockchain 只能看到最终交易。

## 选择门限参数

| 设置 | 韧性 | 风险 |
|-------|-----------|------|
| 1-of-1 | 无韧性——单点故障 | 丢失密钥 = 永久丢失 |
| 2-of-2 | 必须有两名签名者——无容错能力 | 一人不可用 = 资金冻结 |
| 2-of-3 | 可丢失或缺席一个分片 | 安全余量低于 3-of-5 |
| 3-of-5 | 可丢失两个分片；安全性强 | 协调开销更高 |
| 3-of-7 | 机构级；可容忍两次故障 | 协调成本高 |

对大多数团队而言，一个实用起点是：**2-of-3**（韧性强，协调最少）或 **3-of-5**（机构级，安全性更高）。
