# 默克尔树 [Merkle Trees]：Blockchain 如何记住每一个 note
##### 来自 [Annkkitaaa](https://github.com/Annkkitaaa) 的原创研究

![alt text](/content-images/image-19-cfbdcf8f78.webp)

### 在一个微小指纹中汇总数百万个 commitment

> **系列：** *Zcash 从第一性原理 [First Principles] 出发* 。**文章 4 . 默克尔树**
> **受众：**新手。我们以 [文章 3（哈希与 commitment）](article-3-hashing-commitments.md) 为基础。如果你知道什么是指纹和 commitment，你就准备好了。
> **你将收获：**对默克尔树的直观且正确的理解，如何在不泄露你所指项目的情况下证明成员身份，以及这究竟如何成为 Zcash 的 note commitment 树。

[文章 0](article-0-shielded-transaction.md) 描述了一个容纳所有曾被创建的 note 且只会不断增长的"公共公告板"。到现在你可以猜到钉在上面的是什么：**commitment**（文章 3），也就是密封信封。但真实的公告板会容纳*数亿个* commitment。网络如何存储它、验证它，并让你在不指向自己的信封的情况下证明它在公告板上？答案是计算机科学中最优雅的结构之一：**默克尔树。**

---

## 1. 你为什么应该关心？

当你拥有一个巨大的公开 commitment 列表时，会立即出现两个问题。

**问题一：大规模完整性 [integrity]。**如果列表有 3 亿个条目，任何人如何确认其中*没有一个*被秘密篡改？每次查看都重新检查 3 亿个项目是不可能的。

**问题二：私密成员身份。**要花费一个 note（文章 0），你必须证明你的 commitment 确实在公告板上。但如果你指向它（"它是第 4,201,337 个条目！"），你就暴露了自己的身份。你需要证明*"我的信封在这块公告板上的某个位置"*，而不揭示**是哪一个**。

默克尔树能同时解决这两个问题。它将整个列表压缩为单一指纹，并让你通过一份微小且隐藏位置的证明来证明成员身份。

---

## 2. 直觉：一场指纹锦标赛

想象一张淘汰赛对阵表，只不过晋级的不是选手，**而是被组合的指纹。**

- 在底部，每一份数据都有自己的指纹（其来自文章 3 的哈希）。这些是**叶子。**
- 将它们两两配对。每对中的两个指纹会被*一起*哈希为一个父级指纹。
- 将父级两两配对，对每一对一起哈希，以此类推。
- 持续进行，直到顶部只剩下**一个指纹。**这位冠军就是**默克尔根 [Merkle root]。**

![alt text](/content-images/image-20-f5d57e425a.webp)

最重要的特性直接来自雪崩效应（文章 3）：

> **根是其下方*所有内容*的指纹。**改变任何叶子，哪怕只改变 1 个比特，它的指纹都会改变，继而改变其父级，再改变*该*父级，一直向上。**根会改变。**因此，一个很小的根值便可认证整个列表的完整性。这解决了问题一。

---

## 3. 一棵真实的树，精确计算

让我们使用叶子 `A, B, C, D` 上实际的 SHA-256 指纹来构建上面的四叶树（为便于阅读，显示的摘要已截断）：

```
hA = 559aead08264...     hB = df7e70e50215...
hC = 6b23c0d5f35d...     hD = 3f39d5c348e5...

hAB = H(hA , hB) = 63956f0ce48e...
hCD = H(hC , hD) = 98a2fbfddbc7...

ROOT = H(hAB , hCD) = 1b3faa3fcc5e...
```

一切都只是"哈希一个事物，然后对成对的哈希再进行哈希"。没有比文章 3 更奇异的内容，只是以树形方式排列。

---

## 4. 巧妙之处：在不泄露位置的情况下证明成员身份

现在来看问题二。假设你想向一个只知道**根**的人证明叶子 `C` 在树中。你*不会*把整棵树交给他们。你只交给他们从 `C` 攀升到根所需的指纹，这被称为**认证路径 [authentication path]**（或**默克尔证明 [Merkle proof]**）：

> 要证明 `C` 在树中，请提供：
> - 它的同级节点 `hD`，以及
> - 它的叔级节点 `hAB`。

验证者只知道根，并重新计算攀升过程：

```
step 1:  H(hC , hD)        = hCD       (combine C with its sibling)
step 2:  H(hAB , hCD)      = ROOT?     (combine with the uncle)
```

实际计算结果：这会得到 `1b3faa3fcc5e...`，它**与根匹配。**叶子因此被证明在树中。

![alt text](/content-images/image-21-d9e5d6eaf6.webp)

有两点使这十分强大：

- **它非常小。**对于 4 个叶子，你提供了 2 个哈希。对于一棵有 `n` 个叶子的树，你只需提供大约 **log_2(n)** 个哈希。对于 10 亿个叶子，大约只需 **30 个哈希**，而不是 10 亿个。即使树的规模急剧膨胀，证明也几乎不会增长。
- **它是隐私的种子。**该证明显示你的叶子在树中的*某处*。当同一检查在*零知识证明 [zero-knowledge proof]*（文章 5）*内部*执行时，连路径本身也会被隐藏，因此你可以证明"我的 note 在树中"，同时既不揭示 note，也不揭示其位置。这就完全解决了问题二。

## 5. 从默克尔树到 Zcash 的 note commitment 树

现在我们可以准确说明文章 0 中的"公共公告板"究竟是什么：

> **note commitment 树**是一棵默克尔树，其**叶子是 note commitment。**每当世界任何地方创建一个 note 时，其 commitment 就会作为下一个叶子被追加，并更新根。

几个实际细节：

- **它只会增长。**叶子被追加，绝不会移除。这称为**增量默克尔树 [incremental Merkle tree]。**（这与文章 0 的"公告板永远不会拆除任何东西"相符。）
- **根被称为*锚点 [anchor]*。**当你花费时，你的交易会引用一个最近的锚点，并以零知识方式证明你的 note 的 commitment 位于具有该根的树中。
- **固定深度。**Zcash 的屏蔽树深度为 **32**，这意味着它们最多可容纳 `2^(32)`（超过 40 亿）个 note。
- **对 ZK 友好的哈希。**这棵树并非使用 SHA-256 构建。Sapling 使用 **Pedersen 哈希**对树进行哈希，而 Orchard 使用 **Sinsemilla**（两者均来自文章 3），正是为了让在电路内证明成员身份攀升过程的成本较低。

![alt text](/content-images/image-22-518354b8d5.webp)

### 树*不*处理的一件事：双重花费 [double-spends]

树证明一个 note **存在**。它本身并不能阻止你两次花费同一个 note。这项工作属于文章 0 中的**nullifier 集合 [nullifier set]**：一个独立的"作废代币"集合。当你花费时，你会发布该 note 的 nullifier，网络会拒绝此前见过的任何 nullifier。

因此，这两个公开结构发挥互补作用，而将它们分开正是切断 note 的诞生与死亡之间联系的原因：

| 结构 | 它回答的问题 | 更新时机 |
|---|---|---|
| **Note commitment 树** | "这个 note 存在吗？" | 一个 note 被**创建**时（追加 commitment） |
| **Nullifier 集合** | "这个 note 是否已被花费？" | 一个 note 被**花费**时（发布 nullifier） |

---

## 6. 一个诚实的免责声明

一如既往，这里有简化。真实的增量默克尔树会追踪"前沿"节点，从而无需重建所有内容即可更新根；网络会保留一个近期锚点窗口，而不只是最新锚点，因此钱包 [wallet] 不会因每个新区块 [block] 而失效；空叶子则使用定义好的填充值。我们还绘制了拥有整齐的 2 次幂数量叶子的二叉树。这些都不改变直觉：commitment 叶子成对哈希至一个根，并附带简短的成员身份证明。精确的记账机制会在协议文章中回归。

## 7. 总结

- **默克尔树**将数据哈希为**叶子**，然后将**成对的哈希向上处理**，直到只剩下一个**根**。
- 得益于雪崩效应，**根是整个列表的指纹**：改变一个叶子，根就会改变。一个很小的值便可认证一个巨大的数据集。
- **成员身份证明（认证路径）**只是通往根的攀升过程中的同级哈希，大约为 **log_2(n)** 个哈希，因此即使有数十亿个叶子，证明仍然很小。
- 在**零知识证明内部**执行时，该成员身份检查会隐藏你指的是*哪个*叶子，从而在不揭示 note 或其位置的情况下证明"我的 note 在树中"。
- Zcash 的 **note commitment 树**是一棵由 note commitment 构成的**增量**默克尔树，深度为 **32**，其根是**锚点**；Sapling 使用 **Pedersen** 对其进行哈希，而 Orchard 使用 **Sinsemilla**。
- 树证明**存在性**；独立的 **nullifier 集合**防止**双重花费**。将它们分开，正是将一个 note 的诞生与死亡解除关联的关键。

## 术语表

| 术语 | 通俗英语含义 |
|---|---|
| **Merkle tree** | 一棵由哈希构成的树；叶子是数据指纹，父级对其子级进行哈希 |
| **Leaf** | 一个底层节点 [node]；在 Zcash 中，是一个 note commitment |
| **Merkle root** | 汇总整棵树的唯一顶部指纹 |
| **Authentication path / Merkle proof** | 证明一个叶子位于树中所需的同级哈希 |
| **Incremental Merkle tree** | 一棵只追加的默克尔树（叶子只会被添加） |
| **Anchor** | 一笔花费所引用的默克尔根，即"我正针对其证明的树状态" |
| **Nullifier set** | 阻止双重花费的独立已花费标记集合 |

## 常见问题

**为什么使用树，而不只是一个很长的哈希列表？**
一个平面列表会迫使你为证明成员身份而揭示或处理每一个条目。一棵树为你提供对数大小的证明和一个用于完整性的单一根。

**验证者需要整棵树吗？**
不需要。验证者只需要**根**加上你的简短认证路径。这正是关键所在。

**为什么特别是深度 32？**
它将树限制在约 40 亿个 note，这提供了充足余量，同时使成员身份证明（及其电路内成本）保持为固定且可控的大小。

**如果每增加一个新 note，根都会改变，旧证明如何保持有效？**
网络会记住一个近期根（锚点）窗口，因此针对稍旧锚点生成的证明仍可验证。协议文章会对此作出精确说明。

### 测试你的直觉

在我们的四叶树中，假设攻击者秘密将叶子 `C` 替换为不同的值，却让已发布的根保持不变。对他们而言会出什么问题，为什么他们无法悄悄修复它？*（答案如下。）*

<details><summary>答案</summary>

改变 `C` 会改变 `hC`（雪崩效应），这会改变 `hCD = H(hC, hD)`，继而改变 `ROOT = H(hAB, hCD)`。因此，重新计算的根不再与已发布的根匹配，篡改会被检测到。若要"悄悄修复"，他们需要找到一个不同的 `C`，使其产生*相同的* `hC`，这就是哈希碰撞，按照文章 3 是不可行的。完整性得以保持。
</details>
