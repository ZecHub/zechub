# Zinder Индексатор

Zinder — это самостоятельно развёртываемый индексатор Zcash, написанный на Rust и опубликованный Zcash Foundation. Он однократно считывает цепочку с полного узла Zebra или Zakura, сохраняет её целостное представление и одновременно предоставляет его нескольким кошелькам, приложениям и обозревателям. Существующие лёгкие кошельки могут подключаться к нему через адаптер, совместимый с lightwalletd.

> **Zinder находится в альфа-версии.** В собственном README проекта сказано, что нативный API, интерфейс совместимости с lightwalletd, схемы хранения и топология развёртывания будут меняться, а наличие тега релиза не гарантирует стабильность. Фиксируйте точные версии и будьте готовы к несовместимым обновлениям.

## Кратко

* **Zebra** или **Zakura** проверяет цепочку. **Zinder** индексирует данные узла и предоставляет их клиентам.
* Два способа подключения: собственный API gRPC Zinder — `WalletQuery`, а также отдельный адаптер, работающий по протоколу `CompactTxStreamer` от lightwalletd. Поэтому кошельки, созданные для lightwalletd, могут подключаться к нему без изменений кода.
* Каждый запрос на чтение привязан к одному состоянию цепочки («эпохе»), поэтому пакет синхронизации никогда не смешивает данные с двух конкурирующих вершин цепочки. Ключи и сканирование защищённых данных остаются на стороне кошелька.
* Индексатор рассчитан на одного оператора, который запускает один узел и обслуживает множество потребителей. Публичные конечные точки следует защищать собственными TLS, аутентификацией и ограничением частоты запросов.
* Релизы выходят быстро (с 0.7.0 по 0.12.0 — с 10 по 14 ноября 2026 года), и несколько из них содержали несовместимые изменения. Перед каждым обновлением читайте журнал изменений.

## Где применяется Zinder

Лёгкие кошельки никогда не связываются напрямую с полным узлом. Они запрашивают у индексатора компактные блоки, состояния деревьев и данные транзакций (см. [Узлы Lightwallet](/zcash-tech/lightwallet-nodes)). Сейчас в экосистеме Zcash есть несколько индексаторов, способных это делать:

| Индексатор | Язык | Сопровождающий | Подключается к | Примечания |
|:--|:--|:--|:--|:--|
| lightwalletd | Go | сообщество ECC / Zcash | Zebra или zcashd | Исходный сервер лёгких кошельков |
| [Zaino](/zcash-tech/zaino) | Rust | Zingo Labs | Zebra или zcashd | Необязательный профиль индексатора в стеке Z3 |
| [Ztreamer](https://github.com/zcashlabs/ztreamer) | Rust | zcashlabs | Встроенный узел Zakura | См. сравнительный тест [Zaino и Ztreamer](/zcash-tech/indexer-benchmark-zaino-vs-ztreamer) |
| **Zinder** | Rust | Zcash Foundation | Zebra 7.0.0 или Zakura 1.8.6 (архивный узел) | Альфа-версия. Нативный API, адаптер lightwalletd и необязательное чтение данных обозревателем |

В документации Zinder прямо сказано, когда это подходящий вариант: индексатор особенно полезен, когда доступ к цепочке должен сохраняться независимо от процесса одного кошелька, обслуживать нескольких независимых потребителей или оставаться отдельным от кода какого-либо кошелька. Для одного тесно связанного с индексатором кошелька встроенный вариант может быть проще, а потребителю, которому нужны только данные, уже имеющиеся у узла, можно напрямую использовать RPC Zebra.

## Как он устроен

Zinder распределяет работу между отдельными процессами, каждый из которых выполняет одну задачу:

| Среда выполнения | Роль |
|:--|:--|
| `zinder-ingest` | Единственный процесс, записывающий данные в каноническое хранилище цепочки (RocksDB). Следует за узлом, обрабатывает реорганизации и поддерживает актуальное состояние мемпула |
| `zinder-projector` | Единственный процесс, записывающий данные в хранилище кошелька. Создаёт и обновляет представление цепочки, ориентированное на кошелёк |
| `zinder-query` | Предоставляет нативный API gRPC `WalletQuery` |
| `zinder-compat-lightwalletd` | Предоставляет API `CompactTxStreamer` от lightwalletd поверх тех же данных |

Необязательный слой обозревателя (`zinder-explorer` с `ExplorerQuery`) предоставляет сводки блоков, сведения о транзакциях, представления мемпула и поиск. Отдельный необязательный адаптер предоставляет REST API и API WebSocket обозревателя CipherScan. Ни один из них не входит в образы релиза.

Каждая среда выполнения предоставляет `/healthz`, `/readyz` и `/metrics`. Читающие процессы сообщают о готовности только тогда, когда их копии хранилища цепочки и хранилища кошелька указывают точно на одно и то же состояние цепочки.

## Способы подключения

* **Существующие лёгкие кошельки** сохраняют интеграцию с lightwalletd и подключаются к `zinder-compat-lightwalletd`. В документации Zinder совместимость протокола отделена от поддержки: кошелёк считается поддерживаемым только после того, как его текущий релиз прошёл сквозную сертификацию. В релизе 0.10.0 исправлено поле версии протокола `GetLightdInfo`, благодаря чему Zingo может синхронизироваться.
* **Клиенты нативного API** обращаются к `zinder-query` для запросов с привязкой к состоянию цепочки, получения компактных блоков, потоков событий цепочки и мемпула, а также результатов отправки транзакций с типизированными причинами отказа.
* **Приложения Rust** используют пакет `zinder-client` — SDK, изначально рассчитанный на удалённое подключение к `zinder-query` без включения стека хранения.
* **Обозреватели и серверные службы** объединяют чтение данных кошелька с необязательным слоем `ExplorerQuery`.

## Запуск

В кратком руководстве вышестоящего проекта сначала запускается узел со стеком [Z3](/zcash-tech/z3-stack), а затем Zinder с помощью Docker Compose из клона Zinder:

```bash
# In the Z3 checkout
Z3_NETWORK=testnet docker compose up -d

# In the Zinder checkout
docker compose --env-file deploy/.env.testnet \
  -f deploy/docker-compose.yml up -d --build
```

Рядом находятся файлы переменных среды для Mainnet и для узла Zakura (`deploy/.env.zakura-mainnet`, `deploy/.env.zakura-testnet`). Начиная с версии 0.11.0, файл Compose больше не предполагает использование Z3: в файле переменных среды нужно указать сеть узла, том с cookie-файлом и адрес RPC.

Порты по умолчанию на хосте (для Testnet к каждому добавляется 10000):

| Служба | Mainnet | Testnet |
|:--|:--|:--|
| Нативный gRPC `WalletQuery` | 9102 | 19102 |
| gRPC, совместимый с lightwalletd | 9067 | 19067 |
| Готовность: ingest / projector / query / compat | 9105 / 9110 / 9106 / 9107 | 19105 / 19110 / 19106 / 19107 |

Оба порта кошелька привязаны к loopback. Проверьте их командой:

```bash
grpcurl -plaintext -d '{}' 127.0.0.1:19102 zinder.v1.wallet.WalletQuery/ServerInfo
grpcurl -plaintext -d '{}' 127.0.0.1:19067 cash.z.wallet.sdk.rpc.CompactTxStreamer/GetLightdInfo
```

Другие способы развёртывания:

* **Образы релизов** на `ghcr.io/zcashfoundation/`: четыре среды выполнения, а также `zinder-wallet-serving` (ingest, projector и нативный query в одном контейнере — для хостов, где один том можно подключить к одному контейнеру; без адаптера lightwalletd) и `zinder-canonical-runtime` (только ingest).
* **Бинарные файлы Linux** для x86-64 (требуется процессор x86-64-v3) и AArch64 с glibc версии 2.34 или новее. Сертифицированная базовая система — Debian 12. Каждый релиз включает SBOM и подписанное подтверждение происхождения сборки SLSA.

### Что должен предоставлять узел

* **Архивный узел.** Начиная с версии 0.11.0, `zinder-ingest` отказывается запускаться с узлом, удаляющим старые данные.
* Zebra **7.0.0** или Zakura **1.8.6**. Это две версии узлов, сертифицированные для соответствующих релизов.
* Для образа `zinder-wallet-serving` нужна **конечная точка gRPC индексатора** узла (`ZINDER_NODE__INDEXER_GRPC_ADDR`, `indexer_listen_addr` у Zebra, порт 8155 в Mainnet). Для индексатора Zakura, доступного не только через loopback, требуется взаимная TLS-аутентификация; Zinder поддерживает её начиная с версии 0.11.0.

### Ресурсы для Mainnet

Из инструкции по запуску службы кошельков:

* Не менее **8 ГБ памяти**. Измеренные пиковые значения: около 2,6 ГиБ для ingest, около 2,7 ГиБ для projector во время построения и до 1,4 ГиБ для query.
* Оставьте около **130 ГБ свободного места** на томе после построения хранилища кошелька Mainnet.
* По результатам одного измерения, построение хранилища цепочки Mainnet от генезис-блока заняло около **четырёх часов** (промежуточное хранилище — около 310 ГБ), а построение хранилища кошелька — **более двух часов**. Установленные сроки построения подходят только для Testnet: для Mainnet увеличьте их как минимум до 24 ч и 12 ч соответственно, иначе построение будет перезапускаться и никогда не завершится.

## Частые ошибки

**Считать проект готовым к промышленной эксплуатации.** Проект называет себя альфа-версией. По собственному заявлению проекта, успешный локальный запуск через Compose «сам по себе не является сертификацией для промышленной эксплуатации».

**Подключать узел, удаляющий старые данные.** Ingest завершает работу при запуске. Используйте архивный узел Zebra или Zakura.

**Открывать порты gRPC напрямую в интернет.** Оба порта кошелька привязаны к loopback не без причины. Прежде чем открывать их в интернете, настройте на контролируемом вами прокси TLS, аутентификацию, ограничения частоты запросов и квоты.

**Обновлять среды выполнения по одной.** В нескольких релизах изменились ревизия нативного протокола или формат хранилища. Обновляйте службы Zinder одновременно, а нативные клиенты обновляйте в рамках того же переключения.

**Считать кошелёк поддерживаемым только потому, что поддерживается его протокол.** Адаптер lightwalletd работает по этому протоколу, но Zinder заявляет о поддержке конкретного кошелька только после сквозной сертификации его текущего релиза.
