# Определение защищённых платежей: сколько стоит сканирование

Компания, принимающая защищённые ZEC, должна находить входящие платежи. В прозрачном пуле для этого достаточно поиска по индексу. В защищённых пулах нельзя индексировать платежи по адресу, поэтому кошелёк или серверная система должна проверять каждый защищённый выход в блокчейне с помощью собственных ключей. На этой странице объясняется, как это работает, сколько стоит и как выбрать структуру аккаунтов, чтобы контролировать расходы.

## Кратко

* Стоимость поиска защищённых платежей растёт с числом отслеживаемых **ключей просмотра**, а не с числом выданных адресов
* Один аккаунт может выдавать новый, несвязываемый **диверсифицированный адрес** для каждого клиента или счёта без дополнительных затрат на сканирование
* Ключ просмотра раскрывает **весь аккаунт**. Если аудитор должен видеть платежи только одного клиента, этому клиенту нужен отдельный аккаунт, а каждый аккаунт увеличивает объём работы при сканировании каждого блока
* Рассчитывайте сканер на **полные блоки**, а не на среднее значение. В основной сети уже бывают серии почти полных блоков
* Прежде чем рассчитывать мощности, измерьте стоимость одной проверки на своём оборудовании

## Почему защищённые платежи нельзя индексировать

Для прозрачных адресов узел может прочитать адрес каждого выхода и построить индекс соответствия адресов выходам. Zebra предоставляет эту возможность через `getaddressutxos` и `getaddresstxids`.

У защищённого действия нет читаемого адреса. Оно содержит обязательство ноты, временный открытый ключ и зашифрованную ноту. Эти байты не указывают, кому предназначен платёж, поэтому ни узел, ни [индексатор](Lightwallet_Nodes.md) не могут построить индекс адресов.

Поэтому поиск работает в обратном направлении. Кошелёк берёт каждый защищённый выход и спрашивает: «Это моё?», пытаясь его расшифровать. Это называется **пробной расшифровкой**. В разделе [Ключи просмотра](Viewing_Keys.md) объясняется, что раскрывают эти ключи, а в разделе [Zcash синхронизация кошельков](Zcash_Wallet_Syncing.md) — как кошельки распределяют эту работу.

## Как работает одна проверка

Для формата действий протокола Orchard, который используют пулы Orchard и Ironwood:

1. **Согласование ключа:** умножьте временный открытый ключ действия на свой ключ просмотра входящих платежей. Это скалярное умножение на кривой Pallas, на которое приходится большая часть затрат
2. **Получение ключа:** хешируйте общий секрет, чтобы получить симметричный ключ
3. **Расшифруйте первые 52 байта** ноты: диверсификатор, значение и `rseed`
4. **Восстановите обязательство ноты** по расшифрованным данным
5. **Сравните** его с `cmx` действия. Совпадение означает, что нота ваша

Узнать, ваша ли нота, можно только на шаге 5, поэтому **неудачная проверка обходится примерно столько же, сколько успешная**. Почти каждое действие в блокчейне принадлежит кому-то другому, так что почти вся работа — это неудачные проверки.

## Формула затрат

```text
work per block = K × I × A × t

K  accounts you watch
I  incoming viewing keys per account (2: external and internal)
A  shielded actions in the block
t  time for one trial on one core
```

Число адресов в формулу не входит. Кошельки проверяют и внешний ключ (адреса, которые вы выдаёте), и внутренний ключ (сдачу), поэтому `I = 2`. Это видно в циклах `for scope in [Scope::External, Scope::Internal]` в `zcash_client_backend/src/scanning.rs` librustzcash.

[ZIP 218](https://zips.z.cash/zip-0218) ограничивает число защищённых действий **330 на блок**, поэтому `A` не превышает 330.

## Диверсифицированные адреса: много адресов, один ключ

Адрес протокола Orchard состоит из диверсификатора `d` (11 байт) и ключа передачи, производного от того же ключа просмотра входящих платежей. [ZIP 32](https://zips.z.cash/zip-0032) выводит каждый диверсификатор из 88-битного индекса с помощью шифрования FF1, поэтому у одного аккаунта есть **2^88 адресов**, и каждый из них действителен в протоколе Orchard.

Для серверной системы обработки платежей это даёт два полезных свойства:

* **Адреса нельзя связать друг с другом.** Без ключа просмотра два диверсифицированных адреса одного аккаунта выглядят так, будто принадлежат двум разным кошелькам
* **Платежи сопоставляются со счетами без таблицы поиска.** При успешной пробной расшифровке в расшифрованной ноте содержится `d`. Ключ диверсификатора аккаунта расшифровывает `d` и восстанавливает индекс. Если индекс — это номер счёта, вы знаете, какой счёт был оплачен

Прежде чем показывать адрес клиенту, оберните его в [унифицированный адрес](../Using_Zcash/Unified_Addresses.md) ([ZIP 316](https://zips.z.cash/zip-0316)).

## Важный нюанс: ключ просмотра раскрывает весь аккаунт

Нельзя ограничить ключ просмотра одним диверсифицированным адресом, потому что все адреса аккаунта используют один и тот же ключ. Поэтому единицей раскрытия информации тоже является аккаунт. Тот, кто получит ключ просмотра аккаунта, увидит все платежи на все его адреса.

Таким образом, выбор структуры аккаунтов определяет сразу три вещи:

| Структура | Затраты на сканирование | Что можно показать аудитору |
|:--|:--|:--|
| Один аккаунт, диверсифицированный адрес для каждого клиента | Один ключ при любом числе клиентов | Всё или ничего |
| Отдельный аккаунт для каждого клиента | Один ключ на клиента при сканировании каждого блока | Только одного клиента за раз |
| Отдельный аккаунт для каждого клиента и периода | Один ключ на клиента и период | Одного клиента за один период |

Выберите структуру аккаунтов заранее. Чтобы позже разделить аккаунт, придётся перевести его средства в новые аккаунты, а это требует уплаты комиссий и создаёт заметный шаблон транзакций.

## Сколько это стоит на практике

Эти данные получены на одном ядре ноутбука (Apple M3 Pro, сборка релизной версии) с помощью `try_compact_note_decryption` из `zcash_note_encryption` 0.5.1 на реальных действиях Ironwood из тестовой сети:

| Измерение | Значение |
|:--|:--|
| Одна проверка, один ключ за раз | около 82 мкс |
| Одна проверка, пакетная обработка с 10 или 100 ключами | около 42 мкс |

Пакетная обработка примерно вдвое снижает затраты. По той же причине сканер librustzcash обрабатывает ключи пакетами.

Для `t = 42 µs` и полных блоков из 330 действий:

| Отслеживаемые аккаунты | Время работы ядра на полный блок | Сколько ядер нужно для обработки полных блоков без отставания |
|:--|:--|:--|
| 1 | 28 мс | 0,001 |
| 1 000 000 (по одному на клиента) | 7,7 часа | около 1109 |

Тот же миллион клиентов, использующих диверсифицированные адреса одного аккаунта, требует 28 мс на полный блок. Разница только в том, где проходит граница аккаунта.

## Рассчитывайте мощности на пиковую нагрузку, а не на среднюю

Для 5000 блоков основной сети до высоты 3 582 677 (снимок данных от 17 ноября 2026 года):

* В 62% блоков не было защищённых выходов, медианное значение — ноль
* В среднем на блок приходилось 12,3 защищённого выхода
* В 153 блоках на высотах от 3 579 935 до 3 580 346, то есть примерно за три часа работы блокчейна, было более 250 выходов в каждом; часто такие блоки шли подряд. В них содержалось 75% всех выходов выборки

Сканер, рассчитанный на среднюю нагрузку, будет отставать во время таких серий. Оставьте запас мощности (например, планируйте использовать половину 25-секундного интервала между блоками) и рассчитывайте систему на предельное число действий.

## Компактные блоки экономят трафик, но не уменьшают число проверок

Лёгкие кошельки сканируют компактные блоки, получаемые от сервера лёгких кошельков. Компактное действие занимает 148 байт против 820 байт для полного действия. В нём остаются только данные, необходимые для проверки: временный ключ, первые 52 байта зашифрованной ноты, нуллификатор и `cmx`. Данные о прозрачных операциях передаются только по запросу клиента.

Компактные блоки уменьшают объём загрузки. Число проверок не меняется, потому что каждое действие всё равно нужно проверять каждым ключом.

## Контрольный список для серверной системы обработки платежей

* До создания аккаунтов решите, кому и какую информацию может понадобиться видеть
* Если это допускает политика раскрытия информации, выдавайте диверсифицированный адрес для каждого счёта из одного аккаунта
* Измерьте `t` на своём оборудовании с включённой пакетной обработкой
* Рассчитайте мощности сканирования новых блоков на 330 действий в блоке с запасом
* Распределите повторное сканирование по диапазонам высот между рабочими процессами. История неизменна, поэтому такую работу легко распараллелить
* Помните, что для каждого нового аккаунта также нужно просканировать блоки начиная с высоты его создания
