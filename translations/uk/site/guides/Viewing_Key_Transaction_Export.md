# Експорт історії транзакцій з Viewing Key

Більшість експортів гаманців містять мало даних. Наприклад, податковий експорт ZODL надає дати, суми та комісії за попередній календарний рік, але не ідентифікатори транзакцій, примітки чи адреси. Цього недостатньо для бухгалтерського обліку, перевірки міграції гаманця або з’ясування того, що сталося з платежем.

Щоб отримати повну картину, вам не потрібна seed-фраза. Уніфікований повний ключ перегляду (UFVK, починається з `uview1`) може бачити кожну вхідну та вихідну транзакцію в обліковому записі, а два інструменти можуть перетворити це на файл, який ви збережете: сервер Zkool GraphQL і zingo-cli. Цей посібник збирає підходи з [цього обговорення на форумі](https://forum.zcashcommunity.com/t/exporting-transaction-history-to-json-csv-from-ufvk-seed/54662) та оновлює їх для поточних випусків.

Протестовано у вересні 2026 року з Zkool 6.30.0 і zingo-cli з zingolib 6.0.0.

## Перед початком

Вам потрібні дві речі:

1. **UFVK** для облікового запису. [Ключі перегляду](/zcash-tech/viewing-keys) пояснює, що він розкриває та як його експортувати.
2. **Висота народження**, блок, з якого слід почати сканування. Використовуйте висоту до вашої першої транзакції. Якщо встановити її надто високою, старіша історія непомітно буде відсутня. Якщо встановити її надто низькою, сканування лише триватиме довше. Активація Sapling (419200) завжди безпечна, але сканування може зайняти години.

## Зберігайте конфіденційність

Ключ перегляду не дозволяє витрачати кошти, але показує всю вашу історію кожному, хто ним володіє.

- Не вставляйте його на вебсайт або в оглядач блоків. Імпортуйте його в програмне забезпечення, яке запускаєте самостійно.
- Сервер, з якого ви синхронізуєтеся, бачить вашу IP-адресу та те, які транзакції ви повністю завантажуєте. Обидва інструменти нижче отримують кожну вашу транзакцію за ідентифікатором, щоб прочитати примітки й комісії, а [ZIP 307](https://zips.z.cash/zip-0307) зазначає, що це повідомляє серверу, які транзакції належать вам. Синхронізація з власного вузла Zebra за допомогою Zaino або lightwalletd дозволяє цього уникнути. [Zingolib і Zaino Посібник](/guides/zingolib-and-zaino-tutorial) описує налаштування.
- zingo-cli 6 надсилає платежі через mixnet Nym, але синхронізація все ще підключається до сервера напряму, тож попередній пункт стосується й нього.
- Надавайте цим інструментам ключ перегляду, але ніколи не seed-фразу. Сервер Zkool GraphQL за замовчуванням не має входу, а його API поверне seed будь-якого облікового запису, створеного з неї, і може надсилати кошти.
- Тримайте сервер на власному комп’ютері. Наведена нижче команда Docker прослуховує лише `127.0.0.1`.
- Обидва інструменти зберігають ключ та вашу історію незашифрованими. Видаліть робочі дані після завершення та зберігайте експорт у зашифрованому місці.

## Варіант 1: Zkool GraphQL

`zkool_graphql` — це рушій гаманця Zkool як окремий сервер. Це окрема програма від застосунку Zkool. Найпростіший спосіб її запуску — офіційний образ Docker (amd64 і arm64). Також на сторінці випусків [Zkool](https://github.com/hhanh00/zkool2/releases) є бінарний файл Linux x86-64; йому потрібна glibc 2.38 або новіша, тож Ubuntu 24.04 підходить, а Debian 12 — ні.

### 1. Запустіть сервер

```bash
docker run -d --name zkool-export \
  -p 127.0.0.1:8000:8000 \
  -v zkool-export:/data \
  hhanh00/zkool-graphql:6.30.0 \
  --db-path /data/zkool.db
```

Він синхронізується з `https://zec.rocks`, якщо ви не додасте `--lwd-url` із власним сервером. Під час першого запуску він завантажує параметри Sapling (близько 50 МБ). Якщо це не вдасться, `docker start zkool-export` спробує ще раз.

Відкрийте `http://127.0.0.1:8000/graphiql` у браузері. Ви можете вставити туди кожен із наступних кроків і виконати його.

### 2. Імпортуйте ключ

```graphql
mutation {
  createAccount(newAccount: {
    name: "export"
    key: "uview1..."
    aindex: 0
    birth: 2500000
    useInternal: true
  })
}
```

Він повертає ідентифікатор нового облікового запису, який на новому сервері дорівнює 1.

- Завжди встановлюйте `birth`. Без нього Zkool починається з поточного блоку й нічого не знаходить.
- `useInternal: true` змушує Zkool також перевіряти прозорі адреси решти. Не вимикайте його для ключів із ZODL — це те саме налаштування, яке [Відновлення коштів](/using-zcash/recovering-funds) використовує для seed-фраз ZODL.

### 3. Синхронізація

```graphql
mutation { synchronizeAccount(idAccount: 1) }
```

Це виконується до завершення синхронізації. Не додавайте `fast: true`. Він пропускає завантаження повних транзакцій, звідки походять примітки, комісії та виходи.

Число, яке він повертає, — це висота, якої він прагнув досягти, а не доказ того, що він її досяг. Помилка мережі може завершити синхронізацію раніше без будь-якого повідомлення, тож перевірте:

```graphql
{ currentHeight accounts { id name height } }
```

Якщо `height` облікового запису відстає від `currentHeight`, запустіть синхронізацію знову. Вона продовжиться з місця зупинки.

### 4. Експорт

Збережіть це як `history.graphql`:

```graphql
{
  transactionsByAccount(idAccount: 1) {
    txid height time value fee
    notes { pool scope address value memo }
    spends { pool scope address value }
    outputs { pool vout address value memo }
  }
}
```

Не додавайте аргумент `height`, якщо не маєте цього на увазі. Він встановлює мінімальне значення, тож `height: 3000000` у прикладі з форуму відкидає все до цього блоку.

Отримайте його як JSON:

```bash
jq -n --rawfile q history.graphql '{query: $q}' |
  curl -s http://127.0.0.1:8000/graphql \
    -H 'content-type: application/json' --data-binary @- > history.json
```

Кожна транзакція повинна показувати комісію понад 0, окрім винагород за майнінг. Якщо якась показує `"fee": "0"` і не має примітки, її деталі не завантажилися. Zkool отримує повні транзакції по одній після сканування, і один збій непомітно зупиняє решту. Щоб перелічити всі уражені:

```bash
jq -r '.data.transactionsByAccount[] | select(.fee == "0") | .txid' history.json
```

Якщо щось з’явиться, синхронізуйтеся знову через кілька хвилин і знову експортуйте.

Потім перетворіть його на CSV, по одному рядку на транзакцію:

```bash
jq -r '["txid","height","time_utc","net_zec","fee_zec","memos"],
  (.data.transactionsByAccount[] |
    [.txid, .height, .time, .value, .fee,
     ([.notes[].memo, .outputs[].memo] | map(select(. != null and . != "")) | unique | join(" | "))])
  | @csv' history.json > history.csv
```

### Як читати результат

| Поле | Значення |
|---|---|
| `value` | Чиста зміна облікового запису в ZEC, включно з комісією. Від’ємна для надсилань. |
| `fee` | Комісія в ZEC. У платежах, які ви отримали, її сплатив відправник, і вона не входить до `value`. |
| `time` | Час блоку в UTC, без позначки часового поясу |
| `notes` | Що обліковий запис отримав у цій транзакції, включно з рештою. Примітки, надіслані вам, тут. Прозорі записи не мають адреси. |
| `spends` | Власні нотатки облікового запису, які використала ця транзакція |
| `outputs` | Що транзакція надіслала: кожен прозорий вихід, а також захищені платежі на інші адреси з їхніми примітками |
| `pool` | 0 прозорий, 1 Sapling, 2 Orchard, 3 Ironwood |
| `scope` | 0 зовнішній (вхідний платіж), 1 внутрішній (решта) |

Застосунок Zkool також має функції «Експорт транзакцій», «Приміток» і «Нотаток» у меню облікового запису, але це необроблені вивантаження таблиць: суми в zatoshi, часові позначки Unix і примітки в окремому файлі.

## Варіант 2: zingo-cli

zingo-cli — це гаманець із командним рядком від Zingo. Готових завантажень немає, тому його потрібно зібрати за допомогою Rust:

```bash
git clone --branch zingolib_v6.0.0 https://github.com/zingolabs/zingolib.git
cd zingolib
cargo build --release -p zingo-cli
cargo build --release --manifest-path zingo-netutils/Cargo.toml --features nym --bin nym-proxy
cp zingo-netutils/target/release/nym-proxy target/release/
```

Вам потрібен `nym-proxy` навіть лише для синхронізації. zingo-cli 6 не підключиться до жодного сервера без нього.

Перший запуск створює гаманець лише для перегляду, синхронізує його та друкує історію:

```bash
./target/release/zingo-cli --data-dir "$HOME/zingo-export" \
  --viewkey "uview1..." --birthday 2500000 \
  --server https://zec.rocks:443 \
  --waitsync transactions > transactions.txt
```

- `--data-dir` має бути абсолютним шляхом.
- `--viewkey` і `--birthday` застосовуються лише під час створення гаманця. Після цього не додавайте їх.
- zingo-cli за замовчуванням запускається офлайн. `--server` вибирає сервер і також означає вашу згоду на вихід в онлайн.
- Ключ потрапляє до історії оболонки, тож очистьте її після цього.

Наступні запуски:

```bash
Z="./target/release/zingo-cli --data-dir $HOME/zingo-export"
$Z --server https://zec.rocks:443 --waitsync transactions > transactions.txt
$Z --offline value_transfers > value_transfers.txt
$Z --offline messages > memos.json
```

`--offline` читає вже синхронізовані дані, не торкаючись мережі.

- `transactions` надає один запис на транзакцію: txid, час (UTC), висоту, тип (`received`, `sent`, `shield` або `send-to-self`), вартість, комісію та задіяні нотатки.
- `value_transfers` надає один запис на платіж, тож надсилання двом людям має два записи, кожен із адресою отримувача та примітками.
- `messages` перелічує примітки як JSON.

Кілька речей, які варто знати про результат:

- `transactions` і `value_transfers` друкують звичайний текст, який трохи нагадує JSON, але ним не є.
- Суми вказані в zatoshi (100 000 000 на 1 ZEC) і завжди додатні. `kind` вказує напрямок. Для надсилань `value` — це те, що пішло іншим людям, без комісії.
- Комісія відображається як «недоступна», коли транзакція витрачає прозорі кошти, які не належали вам. Відображаються лише текстові примітки.
- Якщо синхронізація не вдається, помилка надходить у термінал, а не у файл, і zingo-cli все одно завершується нормально. Перевірте термінал, перш ніж довіряти `transactions.txt`.

[zingoHelper](https://github.com/dismad/zingoHelper) від dismad має скрипт `exportToJSON.sh`, який перетворює `transactions` на JSON. Його написали до zingo-cli 6, він налаштований на testnet, позначає деякі вихідні записи Sapling та прозорі записи як заповнювачі й потребує GNU-інструментів, тому не працюватиме на стандартному macOS. Вважайте його результат відправною точкою та перевіряйте підсумки.

## Чого ключ перегляду не може повідомити

- **Ціни.** Жоден інструмент не записує ціну ZEC на час кожної транзакції. Додайте фіатні значення самостійно.
- **Прозора історія, якщо ключ її не містить.** Прозора частина UFVK є необов’язковою згідно з [ZIP 316](https://zips.z.cash/zip-0316). У zingo-cli `$Z --offline parse_viewkey uview1...` показує, які пули охоплює ключ.
- **Хто вам заплатив.** Захищені платежі не містять адреси відправника. Якщо тільки відправник не вказав її в примітці, її ніде немає.
- **Деякі вихідні деталі.** Адреса призначення, сума та примітка для захищених надсилань відновлюються шляхом розшифрування ключем. Проте гаманець може створити транзакцію так, щоб це було неможливо, хоча більшість цього не робить.

## Інші інструменти

| Інструмент | Що ви отримуєте |
|---|---|
| ZODL | Податковий CSV із датами, сумами, комісіями та тегом. Лише попередній календарний рік, пропускає транзакції екранування, без txid, примітки чи адреси. |
| застосунок Zkool | Необроблені табличні експорти з меню облікового запису |
| [Zenith](https://code.vergara.tech/Vergara_Tech/zenith) | Імпортує UFVK за допомогою `importvk`. `listreceived` через RPC повертає отримані нотатки з txid і приміткою, але без надсилань і комісій. |
| [Zallet](https://github.com/zcash/zallet) | `z_listtransactions` є докладним, але позначений як експериментальний, а Zallet імпортує лише ключі перегляду Sapling, а не UFVK |
| [zcash-devtool](https://github.com/zcash/zcash-devtool) | Імпортує UFVK за допомогою `wallet init-fvk`, а потім `wallet list-tx`. Його режим CSV не містить txid чи адреси, а проєкт не рекомендує використовувати його у виробничому середовищі. |
