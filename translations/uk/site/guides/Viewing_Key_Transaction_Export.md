# Експорт історії транзакцій із Viewing Key

Експорт із більшості гаманців містить мало даних. Наприклад, податковий експорт ZODL за попередній календарний рік містить дати, суми й комісії, але не містить ідентифікаторів транзакцій, приміток і адрес. Цього недостатньо для бухгалтерського обліку, перевірки міграції гаманця чи з’ясування, що сталося з платежем.

Щоб отримати повну картину, вам не потрібна початкова фраза. Об’єднаний ключ повного перегляду (UFVK, що починається з `uview1`) дає змогу переглядати всі вхідні й вихідні транзакції облікового запису, а два інструменти допоможуть зберегти їх у файл: сервер Zkool GraphQL і zingo-cli. У цьому посібнику зібрано підходи з [цієї теми на форумі](https://forum.zcashcommunity.com/t/exporting-transaction-history-to-json-csv-from-ufvk-seed/54662) та оновлено їх відповідно до поточних випусків.

Перевірено у вересні 2026 року з Zkool 6.30.0 та zingo-cli з zingolib 6.0.0. Обидва передують NU7, тож у листопаді 2026 року кроки оновлено для Zkool 6.37.0 і zingolib 8.0.0. [Zkool 6.35.0](https://github.com/hhanh00/zkool2/pull/1388) — перший випуск Zkool, зібраний із висотою активації NU7 у Mainnet, а zingolib 8.0.0 — випуск, у якому додано підтримку Mainnet для NU7.

## Перш ніж почати

Вам знадобляться дві речі:

1. **UFVK** облікового запису. У статті [Ключі перегляду](/zcash-tech/viewing-keys) пояснено, що він розкриває та як його експортувати.
2. **Початкова висота** — блок, із якого слід почати сканування. Виберіть висоту, що передує вашій першій транзакції. Якщо встановити її надто високо, старіша історія непомітно зникне. Якщо надто низько — сканування триватиме довше. Висота активації Sapling (419200) завжди безпечна, але сканування може тривати кілька годин.

## Зберігайте конфіденційність

Ключ перегляду не дає змоги витрачати кошти, але той, хто ним володіє, бачить усю вашу історію.

- Не вставляйте його на вебсайт чи в оглядач блоків. Імпортуйте його у програму, яку запускаєте самостійно.
- Сервер, з якого ви синхронізуєтеся, бачить вашу IP-адресу та всі транзакції, які ви завантажуєте повністю. Обидва наведені нижче інструменти запитують кожну вашу транзакцію за ідентифікатором, щоб отримати примітки й комісії, а в [ZIP 307](https://zips.z.cash/zip-0307) зазначено, що так сервер дізнається, які транзакції належать вам. Синхронізація з власного вузла Zebra за допомогою Zaino або lightwalletd цього уникає. У [Zingolib та Zaino Посібнику](/guides/zingolib-and-zaino-tutorial) описано налаштування.
- zingo-cli надсилає платежі через мікснет Nym, але під час синхронізації все одно підключається безпосередньо до сервера, тож попередній пункт стосується і його.
- Передавайте цим інструментам ключ перегляду, а не початкову фразу. Команда Docker нижче запускає сервер Zkool GraphQL з параметром `--allow-unauthenticated`, тож автентифікації немає. API сервера повертає початкову фразу будь-якого облікового запису, створеного з неї, і може надсилати кошти.
- Тримайте сервер на власному комп’ютері. Команда Docker нижче прослуховує лише `127.0.0.1` вашого комп’ютера. У контейнері сервер має прослуховувати всі інтерфейси (`--bind-address 0.0.0.0`), інакше Docker не зможе до нього підключитися; саме зіставлення `-p 127.0.0.1:8000:8000` залишає його локальним.
- Обидва інструменти зберігають ключ і вашу історію без шифрування. Zkool може шифрувати свою базу даних (`--db-password-file`), але наведена нижче команда спрощує приклад параметром `--allow-unencrypted-database`. Після завершення видаліть робочі дані й збережіть експорт у зашифрованому місці.

## Варіант 1: Zkool GraphQL

`zkool_graphql` — це рушій гаманця Zkool, що працює як окремий сервер. Це окрема програма, не застосунок Zkool. Найпростіший спосіб запустити її — скористатися офіційним образом Docker (amd64 та arm64). Також доступний бінарний файл Linux для x86-64 на сторінці випусків [Zkool](https://github.com/hhanh00/zkool2/releases); для нього потрібна glibc версії 2.38 або новішої, тож Ubuntu 24.04 підійде, а Debian 12 — ні.

### 1. Запустіть сервер

```bash
docker run -d --name zkool-export \
  -p 127.0.0.1:8000:8000 \
  -v zkool-export:/data \
  hhanh00/zkool-graphql:6.37.0 \
  --db-path /data/zkool.db \
  --bind-address 0.0.0.0 \
  --allow-unauthenticated \
  --allow-unencrypted-database
```

Починаючи з версії 6.32.0, сервер не запускається, доки ви явно не виберете два параметри: спосіб входу клієнтів (ключ JWT або `--allow-unauthenticated`) і спосіб шифрування бази даних (пароль або `--allow-unencrypted-database`). Тепер за замовчуванням він також прослуховує лише `127.0.0.1`, а в контейнері це означає, що ззовні до нього ніхто не підключиться, тому потрібен параметр `--bind-address 0.0.0.0`. Якщо контейнер одразу зупиняється, у `docker logs zkool-export` буде вказано, якого параметра бракує.

Синхронізація відбувається з `https://zec.rocks`, якщо не додати `--lwd-url` із власним сервером. Образ уже містить вбудовані параметри Sapling, тож нічого іншого завантажувати не потрібно.

Відкрийте `http://127.0.0.1:8000/graphiql` у браузері. Там можна вставити кожну наступну команду й запустити її.

### 2. Імпортуйте ключ

```graphql
mutation {
  createAccount(newAccount: {
    name: "export"
    key: "uview1..."
    aindex: 0
    birth: 2500000
    useInternal: true
  })
}
```

Команда поверне ідентифікатор нового облікового запису. На щойно запущеному сервері це буде 1.

- Завжди задавайте `birth`. Без нього Zkool почне сканування з поточного блока й нічого не знайде.
- Параметр `useInternal: true` змушує Zkool перевіряти також прозорі адреси для решти. Залиште його ввімкненим для ключів із ZODL; такий самий параметр використовує стаття [Відновлення коштів](/using-zcash/recovering-funds) для початкових фраз ZODL.

### 3. Синхронізуйте

```graphql
mutation { synchronizeAccount(idAccount: 1) }
```

Команда працює, поки синхронізація не завершиться. Не додавайте `fast: true`. Він пропускає завантаження повних транзакцій, з яких отримують примітки, комісії та виходи.

Повернуте число — це висота, якої програма прагнула досягти, а не підтвердження, що вона її досягла. Через помилку мережі синхронізація може завершитися раніше без повідомлення, тож перевірте:

```graphql
{ currentHeight accounts { id name height } }
```

Якщо `height` облікового запису нижчий за `currentHeight`, запустіть синхронізацію ще раз. Вона продовжиться з місця зупинки.

### 4. Експортуйте

Збережіть це як `history.graphql`:

```graphql
{
  transactionsByAccount(idAccount: 1) {
    txid height time value fee
    notes { pool scope address value memo }
    spends { pool scope address value }
    outputs { pool vout address value memo }
  }
}
```

Не додавайте аргумент `height`, якщо він вам справді не потрібен. Він задає мінімальну висоту, тож `height: 3000000` із прикладу на форумі відкидає все, що було до цього блока.

Отримайте дані у форматі JSON:

```bash
jq -n --rawfile q history.graphql '{query: $q}' |
  curl -s http://127.0.0.1:8000/graphql \
    -H 'content-type: application/json' --data-binary @- > history.json
```

У кожної транзакції має бути комісія, більша за 0, за винятком винагород за майнінг. Якщо вказано `"fee": "0"` і немає примітки, її дані не завантажилися. Zkool після сканування по черзі завантажує повні транзакції, але одна помилка непомітно зупиняє решту. Щоб побачити, які транзакції зачепило:

```bash
jq -r '.data.transactionsByAccount[] | select(.fee == "0") | .txid' history.json
```

Якщо з’являться результати, зачекайте кілька хвилин, повторіть синхронізацію й експортуйте дані знову.

Потім перетворіть їх на CSV: один рядок на транзакцію.

```bash
jq -r '["txid","height","time_utc","net_zec","fee_zec","memos"],
  (.data.transactionsByAccount[] |
    [.txid, .height, .time, .value, .fee,
     ([.notes[].memo, .outputs[].memo] | map(select(. != null and . != "")) | unique | join(" | "))])
  | @csv' history.json > history.csv
```

### Як читати результат

| Поле | Значення |
|---|---|
| `value` | Чиста зміна балансу облікового запису в ZEC, включно з комісією. Для вихідних платежів — від’ємне значення. |
| `fee` | Комісія в ZEC. За отримані вами платежі її сплатив відправник, і вона не входить до `value`. |
| `time` | Час блока за UTC, без позначення часового поясу |
| `notes` | Що обліковий запис отримав у цій транзакції, зокрема решту. Тут містяться надіслані вам примітки. Для прозорих записів адреси немає. |
| `spends` | Власні примітки облікового запису, використані цією транзакцією |
| `outputs` | Що транзакція надіслала: кожен прозорий вихід, а також захищені платежі на інші адреси з їхніми примітками |
| `pool` | 0 — прозорий, 1 — Sapling, 2 — Orchard, 3 — Ironwood |
| `scope` | 0 — зовнішній (вхідний платіж), 1 — внутрішній (решта) |

У застосунку Zkool також є функції експорту транзакцій, приміток і записів із меню облікового запису, але вони експортують необроблені таблиці: суми у zatoshi, часові позначки Unix, а примітки — в окремому файлі.

## Варіант 2: zingo-cli

zingo-cli — це гаманець Zingo для командного рядка. Готових завантажень немає, тому його потрібно зібрати за допомогою Rust. Використовуйте версію zingolib 8.0.0 або новішу: це перший випуск, у якому враховано висоту активації NU7 у Mainnet (3,543,405), згідно з [примітками до випуску](https://github.com/zingolabs/zingolib/releases/tag/zingolib_v8.0.0). Збірки зі старіших тегів, як-от 6.0.0, цього не враховують.

Для збирання потрібен [cargo-make](https://github.com/sagiegurari/cargo-make) (`cargo install cargo-make`). В Ubuntu також потрібен `sudo apt install build-essential gcc libsqlite3-dev`.

```bash
git clone --branch zingolib_v8.0.0 https://github.com/zingolabs/zingolib.git
cd zingolib
makers run-cli --build-only
```

Ця команда збирає `./target/release/zingo-cli` і розміщує поруч із ним `nym-proxy`. `nym-proxy` потрібен навіть лише для синхронізації: без нього zingo-cli не під’єднається до мережі. Починаючи з версії 8.0.0 `zingo-netutils` входить до основного робочого простору, тож давніший спосіб скопіювати `nym-proxy` із `zingo-netutils/target/release/` більше не працює.

Якщо перемістите `zingo-cli` в інше місце, перемістіть разом із ним `nym-proxy` або вкажіть zingo-cli його розташування за допомогою `--nym-proxy /path/to/nym-proxy` чи змінної середовища `ZINGO_NYM_PROXY`. Якщо цього не зробити, програма шукатиме його поряд зі своїм виконуваним файлом, а потім у вашому `PATH`. Якщо їй не вдасться запустити проксі, вона взагалі не під’єднається до мережі.

Через Nym передаються лише платежі (і запит ціни ZEC). Синхронізація під’єднується безпосередньо до сервера.

Під час першого запуску створюється гаманець лише для перегляду, він синхронізується та виводить історію:

```bash
./target/release/zingo-cli --data-dir "$HOME/zingo-export" \
  --viewkey "uview1..." --birthday 2500000 \
  --server https://zec.rocks:443 \
  --waitsync transactions > transactions.txt
```

- `--data-dir` має бути абсолютним шляхом.
- `--viewkey` і `--birthday` застосовуються лише під час створення гаманця. Потім їх можна не вказувати.
- Новий zingo-cli за замовчуванням працює офлайн, і для підключення до мережі потрібна ваша згода. Параметр `--server` вибирає сервер і водночас означає згоду. Також можна скористатися `--online` (лише для цього сеансу) або `--remember-online`; останній зберігає вибір поруч із гаманцем, тож наступні запуски під’єднуватимуться до мережі без параметра (`--forget-online` скасовує цей вибір).
- Ключ залишиться в історії командної оболонки, тож після цього очистьте її.

Наступні запуски:

```bash
Z="./target/release/zingo-cli --data-dir $HOME/zingo-export"
$Z --server https://zec.rocks:443 --waitsync transactions > transactions.txt
$Z --offline value_transfers > value_transfers.txt
$Z --offline messages > memos.json
```

`--offline` читає вже синхронізовані дані, не звертаючись до мережі.

- `transactions` повертає один запис на транзакцію: txid, час (UTC), висоту, тип (`received`, `sent`, `shield` або `send-to-self`), значення, комісію та пов’язані записи.
- `value_transfers` повертає один запис на платіж, тож надсилання двом людям дає два записи, кожен з адресою отримувача й примітками.
- `messages` виводить примітки у форматі JSON.

Про результат слід знати кілька речей:

- `transactions` і `value_transfers` виводять звичайний текст, схожий на JSON, але ним не є.
- Суми зазначено у zatoshi (100 000 000 становить 1 ZEC), і вони завжди додатні. Напрямок указує `kind`. Для вихідних платежів `value` — це сума, надіслана іншим, без комісії.
- Комісія відображається як «недоступна», якщо транзакція витрачає прозорі кошти, які вам не належали. Показуються лише текстові примітки.
- Якщо синхронізація завершується помилкою, повідомлення про неї з’явиться в терміналі, а не у файлі. Починаючи з zingolib 8.0.0 (zingo-cli 0.5.0), команда з помилкою також завершується з ненульовим кодом, але перевірте термінал, перш ніж довіряти `transactions.txt`.

У [zingoHelper](https://github.com/dismad/zingoHelper) від dismad є сценарій `exportToJSON.sh`, що перетворює `transactions` на JSON. Його написано до zingo-cli 6 і налаштовано для testnet; деякі вихідні Sapling та прозорі записи позначаються як заповнювачі. Для роботи потрібні інструменти GNU, тож на стандартній macOS він не запуститься. Сприймайте його результат як чернетку й перевірте підсумкові суми.

## Чого не показує ключ перегляду

- **Ціни.** Жоден інструмент не записує ціну ZEC на момент кожної транзакції. Додайте фіатні значення самостійно.
- **Прозора історія, якщо ключ її не містить.** Відповідно до [ZIP 316](https://zips.z.cash/zip-0316) прозора частина UFVK необов’язкова. Якщо скористатися zingo-cli, `$Z --offline parse_viewkey uview1...` покаже, які пули охоплює ключ.
- **Хто надіслав вам кошти.** Захищені платежі не містять адреси відправника. Якщо відправник не вказав її у примітці, її ніде немає.
- **Деякі подробиці вихідних платежів.** Адресу призначення, суму й примітку захищеного платежу відновлюють розшифруванням за допомогою ключа. Гаманець може сформувати транзакцію так, що це буде неможливо, хоча більшість так не робить.

## Інші інструменти

| Інструмент | Що ви отримаєте |
|---|---|
| ZODL | Податковий CSV із датами, сумами, комісіями й позначкою. Лише за попередній календарний рік; не містить транзакцій із захистом коштів, txid, приміток і адрес. |
| Застосунок Zkool | Необроблені експорти таблиць із меню облікового запису |
| [Zenith](https://code.vergara.tech/Vergara_Tech/zenith) | Імпортує UFVK за допомогою `importvk`. `listreceived` через RPC повертає отримані записи з txid і приміткою, але без вихідних платежів і комісій. |
| [Zallet](https://github.com/zcash/zallet) | `z_listtransactions` докладний, але має експериментальний статус, а Zallet імпортує лише ключі перегляду Sapling, а не UFVK |
| [zcash-devtool](https://github.com/zcash/zcash-devtool) | Імпортує UFVK за допомогою `wallet init-fvk`, а потім `wallet list-tx`. У режимі CSV немає txid і адреси, а автори проєкту не рекомендують використовувати його у виробничому середовищі. |
