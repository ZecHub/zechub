# Розсилка ZecWeekly

ZecWeekly — це розсилка, яка виходить щонеділі вранці. Вона містить усі новини, що відбулися протягом тижня в екосистемі Zcash. Новини щотижня відбираються членами спільноти, а всі відповідні посилання додаються до розсилки. Будь ласка, підпишіться на розсилку [тут](https://zechub.substack.com/).

## Зробити внесок

Найкраще працювати над внесками до розсилки, коли один учасник готує випуск за відповідний тиждень, стежить за поточним обговоренням винагороди або координації та надсилає pull request після того, як щотижневі посилання готові. Будь ласка, не надсилайте майбутній випуск до того, як ZecHub опублікує або підтвердить дату цього випуску. Ранні pull request часто не містять оновлень наприкінці тижня, конфліктують із призначеним куратором або мають неправильний дедлайн.

### 1. Підтвердіть поточний випуск

Перш ніж почати писати:

- Перевірте [ZEC Bounties ](https://bounties.zechub.wiki/) щодо поточного завдання для розсилки.
- Дочекайтеся призначення

![ss](/content-images/149a802c-b64f-4969-ad89-e83ffecf568e-d5d8387145.webp)



### 2. Зробіть форк репозиторію

Якщо ви новачок у GitHub, використовуйте цей робочий процес:

1. Відкрийте [репозиторій ZecHub](https://github.com/ZecHub/zechub).
2. Натисніть **Fork** і створіть форк у своєму обліковому записі GitHub.
3. У своєму форку створіть нову гілку для випуску. Зрозуміла назва гілки буде корисною, наприклад `digest-may-30-2026`.
4. Переконайтеся, що ваш pull request буде спрямований на `ZecHub/zechub` як базовий репозиторій і на `main` як базову гілку.

Якщо ви використовуєте командний рядок, той самий робочий процес виглядає так:

```bash
git clone https://github.com/YOUR-USERNAME/zechub.git
cd zechub
git checkout -b digest-month-day-year
```

Замініть `YOUR-USERNAME` на власне ім’я користувача GitHub. URL-адреса вище є заповнювачем і в такому вигляді не працюватиме.

### 3. Створіть файл розсилки

Використовуйте [шаблон розсилки](https://github.com/ZecHub/zechub/blob/main/newsletter/newslettertemplate.md) як відправну точку. Випуски розсилки мають зберігатися в папці [`newsletter`](https://github.com/ZecHub/zechub/tree/main/newsletter).

Створюючи файл:

- Дотримуйтеся формату назви файлу, зазначеного в issue або використаного в нещодавно прийнятих випусках.
- Зберігайте той самий порядок розділів, що й у шаблоні, якщо завдання не вимагає іншого формату.
- Додавайте посилання лише за відповідний тиждень.
- Пишіть короткий і зрозумілий опис для кожного посилання, щоб читачі розуміли його важливість.
- За потреби перекладайте або узагальнюйте неангломовні джерела англійською.
- Перевірте кожне посилання перед відкриттям pull request.

### 4. Збирайте посилання у відповідний час

ZecWeekly зазвичай охоплює активність екосистеми Zcash за поточний тиждень і публікується наприкінці тижня. Найбезпечніший графік:

- Починайте збирати посилання після публікації поточного випуску або завдання розсилки.
- Ведіть чернетку, поки тиждень ще триває.
- Надсилайте pull request близько до запитуваної дати подання, після перевірки оновлень наприкінці тижня.
- Не надсилайте розсилку за майбутній тиждень до появи завдання на цю дату або до підтвердження ZecHub, що вам слід її підготувати.

Якщо в issue зазначено, що потрібно подати матеріал до певної дати, дотримуйтеся цієї дати. Якщо між цією сторінкою та поточним issue є суперечність, дотримуйтеся поточного issue.

### 5. Відкрийте pull request

Коли файл вашої розсилки готовий:

1. Зробіть commit своїх змін у форку.
2. Відкрийте pull request до `ZecHub/zechub` у гілку `main`.
3. Використайте назву, що відповідає випуску, наприклад `Zcash Ecosystem Digest | May 30th`.
4. Додайте посилання на issue в тілі pull request, щоб рецензенти могли пов’язати роботу із завданням.

Приклад тіла pull request:

```md
Closes #ISSUE_NUMBER

Summary:
- Adds the Zcash Ecosystem Digest for Month Day.
- Uses the newsletter template and the current issue deadline.
- Checks links and descriptions for the requested week.
```

Після відкриття pull request стежте за коментарями рецензентів. Якщо ZecHub попросить внести зміни, оновіть ту саму гілку замість відкриття другого pull request для того самого випуску.

### Поширені помилки, яких слід уникати

- Відкриття pull request до підтвердження дати випуску або завдання.
- Робота над issue, який уже має пов’язаний pull request.
- Надсилання pull request до власного форку замість `ZecHub/zechub`.
- Використання неправильної назви файлу або розміщення файлу поза папкою `newsletter`.
- Копіювання старого випуску без оновлення кожної дати, посилання й опису.
- Додавання посилань за неправильний тиждень.
- Залишення непрацюючих чи дубльованих посилань або тексту-заповнювача із шаблону.
- Відкриття нового pull request після коментарів рецензентів замість оновлення початкової гілки.

### Фінальний контрольний список

Перш ніж запитувати рецензію, переконайтеся, що:

- Дата issue або завдання відповідає файлу вашої розсилки.
- Жоден інший відкритий pull request уже не охоплює той самий issue або випуск.
- Файл міститься в папці `newsletter`.
- Розділи шаблону заповнені.
- Кожне посилання працює та має корисний опис.
- Тіло pull request містить посилання на правильний issue.
- Ви готові внести зміни, якщо рецензенти їх запросять.
