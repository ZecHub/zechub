# Інформаційний бюлетень ZecWeekly

ZecWeekly — це інформаційний бюлетень, який виходить щонеділі вранці. Він містить усі новини, що сталися протягом тижня в екосистемі Zcash. Новини щотижня відбираються учасниками спільноти, і до бюлетеня додаються всі релевантні посилання. Будь ласка, підпишіться на бюлетень [тут](https://zechub.substack.com/).

## Долучитися

Найкраще надсилати внески до бюлетеня тоді, коли один учасник готує випуск для правильного тижня, стежить за поточним тредом bounty або координації та надсилає pull request після того, як щотижневі посилання будуть готові. Будь ласка, не надсилайте майбутній випуск до того, як ZecHub опублікує або підтвердить дату цього випуску. Передчасні pull request часто пропускають оновлення наприкінці тижня, конфліктують із призначеним куратором або використовують неправильний дедлайн.

### 1. Підтвердьте поточний випуск

Перш ніж почати писати:

- Перевірте [ZEC Bounties ](https://bounties.zechub.wiki/) для поточного завдання бюлетеня.
- Дочекайтеся призначення

![ss](/content-images/149a802c-b64f-4969-ad89-e83ffecf568e-d5d8387145.webp)



### 2. Зробіть форк репозиторію

Якщо ви новачок у GitHub, скористайтеся таким робочим процесом:

1. Відкрийте [репозиторій ZecHub](https://github.com/ZecHub/zechub).
2. Натисніть **Fork** і створіть форк у своєму акаунті GitHub.
3. У своєму форку створіть нову гілку для випуску. Корисно використовувати зрозумілу назву гілки, наприклад `digest-may-30-2026`.
4. Переконайтеся, що ваш pull request буде спрямований на `ZecHub/zechub` як базовий репозиторій і `main` як базову гілку.

Якщо ви використовуєте командний рядок, той самий робочий процес виглядає так:

```bash
git clone https://github.com/YOUR-USERNAME/zechub.git
cd zechub
git checkout -b digest-month-day-year
```

Замініть `YOUR-USERNAME` на своє ім'я користувача GitHub. URL вище є заповнювачем і не буде працювати в наведеному вигляді.

### 3. Створіть файл бюлетеня

Використовуйте [шаблон бюлетеня](https://github.com/ZecHub/zechub/blob/main/newsletter/newslettertemplate.md) як відправну точку. Випуски бюлетеня мають розміщуватися в папці [`newsletter`](https://github.com/ZecHub/zechub/tree/main/newsletter).

Під час створення файлу:

- Дотримуйтесь формату назви файлу, зазначеного в issue або використаного в нещодавно прийнятих випусках.
- Зберігайте той самий порядок розділів, що й у шаблоні, якщо тільки завдання не вимагає іншого формату.
- Додавайте посилання лише з відповідного тижня.
- Пишіть короткий і зрозумілий опис для кожного посилання, щоб читачі розуміли, чому це важливо.
- За потреби перекладайте або стисло викладайте неангломовні джерела англійською.
- Перевірте кожне посилання перед відкриттям pull request.

### 4. Збирайте посилання в правильний час

ZecWeekly зазвичай охоплює активність екосистеми Zcash за поточний тиждень і публікується ближче до кінця тижня. Найбезпечніший час для цього:

- Починайте збирати посилання після того, як буде опубліковано поточний випуск бюлетеня або завдання.
- Підтримуйте чернетку, поки тиждень ще триває.
- Надсилайте pull request ближче до запитуваної дати подання, після того як перевірите оновлення наприкінці тижня.
- Не надсилайте бюлетень на майбутній тиждень до того, як з'явиться завдання на цю дату або поки ZecHub не підтвердить, що саме ви маєте його підготувати.

Якщо в issue вказано, що потрібно подати до конкретної дати, дотримуйтесь цієї дати. Якщо між цією сторінкою та поточним issue є суперечність, дотримуйтесь поточного issue.

### 5. Відкрийте pull request

Коли ваш файл бюлетеня готовий:

1. Закомітьте свої зміни у свій форк.
2. Відкрийте pull request до `ZecHub/zechub` у гілку `main`.
3. Використайте заголовок, що відповідає випуску, наприклад `Zcash Ecosystem Digest | May 30th`.
4. Додайте посилання на issue в тілі pull request, щоб рев'юери могли пов'язати роботу із завданням.

Приклад тіла pull request:

```md
Closes #ISSUE_NUMBER

Summary:
- Adds the Zcash Ecosystem Digest for Month Day.
- Uses the newsletter template and the current issue deadline.
- Checks links and descriptions for the requested week.
```

Після відкриття pull request стежте за коментарями рев'ю. Якщо ZecHub попросить внести зміни, оновіть ту саму гілку замість відкриття другого pull request для того самого випуску.

### Поширені помилки, яких слід уникати

- Відкриття pull request до підтвердження дати випуску або завдання.
- Робота над issue, до якого вже прив'язано pull request.
- Надсилання pull request до власного форку замість `ZecHub/zechub`.
- Використання неправильної назви файлу або розміщення файлу поза папкою `newsletter`.
- Копіювання старого випуску без оновлення кожної дати, посилання й опису.
- Додавання посилань не з того тижня.
- Залишення неробочих посилань, дублікатів посилань або тексту-заповнювача з шаблону.
- Відкриття нового pull request після коментарів рев'ю замість оновлення початкової гілки.

### Фінальний контрольний список

Перш ніж запитувати рев'ю, переконайтеся, що:

- Дата issue або завдання відповідає вашому файлу бюлетеня.
- Жоден інший відкритий pull request ще не охоплює те саме issue або випуск.
- Файл розміщено в папці `newsletter`.
- Усі розділи шаблону заповнені.
- Кожне посилання працює та має корисний опис.
- Тіло pull request містить посилання на правильне issue.
- Ви готові внести зміни, якщо рев'юери їх попросять.
