# Zinder індексатор

Zinder — це індексатор Zcash із самостійним розгортанням, написаний мовою Rust і опублікований Zcash Foundation. Він один раз зчитує блокчейн із Zebra або Zakura повного вузла, зберігає єдине узгоджене представлення блокчейна та одночасно надає його кільком гаманцям, застосункам і оглядачам. Наявні легкі гаманці можуть підключатися до нього через адаптер, сумісний із lightwalletd.

> **Zinder — альфа-версія.** У власному README проєкту сказано, що нативний API, поверхня сумісності з lightwalletd, структури сховищ і топологія розгортання змінюватимуться, а позначений тегом випуск не є обіцянкою стабільності. Фіксуйте точні версії та очікуйте несумісних змін під час оновлень.

## Коротко

* **Zebra** або **Zakura** перевіряє блокчейн. **Zinder** індексує дані вузла та надає їх клієнтам.
* Два способи підключення: власний `WalletQuery` gRPC API від Zinder і окремий адаптер, що використовує протокол `CompactTxStreamer` від lightwalletd. Тож гаманці, створені для lightwalletd, можуть підключатися до нього без змін коду.
* Кожне читання прив’язане до одного стану блокчейна («епохи»), тож пакет синхронізації ніколи не змішує дані з двох конкуруючих вершин ланцюга. Ключі та сканування захищених даних залишаються на боці гаманця.
* Рішення розраховане на одного оператора, який запускає один вузол і обслуговує багатьох споживачів. Публічні кінцеві точки слід розміщувати за власними засобами TLS, автентифікації та обмеження частоти запитів.
* Випуски виходять швидко (з 0.7.0 до 0.12.0 між 10 і 14 листопада 2026 року), і кілька з них містили несумісні зміни. Перед кожним оновленням читайте журнал змін.

## Де тут Zinder

Легкі гаманці ніколи не взаємодіють із повним вузлом безпосередньо. Вони запитують в індексатора компактні блоки, стани дерев і дані транзакцій (див. [Вузли Lightwallet](/zcash-tech/lightwallet-nodes)). В екосистемі Zcash тепер є кілька індексаторів, які можуть це робити:

| Індексатор | Мова | Супроводжувач | Підключається до | Примітки |
|:--|:--|:--|:--|:--|
| lightwalletd | Go | Спільнота ECC / Zcash | Zebra або zcashd | Оригінальний сервер легких гаманців |
| [Zaino](/zcash-tech/zaino) | Rust | Zingo Labs | Zebra або zcashd | Необов’язковий профіль індексатора у стеку Z3 |
| [Ztreamer](https://github.com/zcashlabs/ztreamer) | Rust | zcashlabs | Вбудований вузол Zakura | Див. порівняння [Zaino та Ztreamer](/zcash-tech/indexer-benchmark-zaino-vs-ztreamer) |
| **Zinder** | Rust | Zcash Foundation | Zebra 7.0.0 або Zakura 1.8.6 (архівний вузол) | Альфа-версія. Нативний API, адаптер lightwalletd та необов’язкові запити оглядача |

У документації Zinder прямо сказано, коли це правильний вибір: він найкраще підходить, коли доступ до блокчейна має працювати незалежно від окремого процесу гаманця, обслуговувати кількох незалежних споживачів або залишатися відокремленим від коду будь-якого гаманця. Для одного тісно пов’язаного з індексатором гаманця вбудоване рішення може бути простішим, а споживач, якому потрібні лише дані, уже наявні у вузла, може напряму використовувати RPC від Zebra.

## Як це влаштовано

Zinder розподіляє роботу між окремими процесами, кожен із яких виконує одне завдання:

| Середовище виконання | Роль |
|:--|:--|
| `zinder-ingest` | Єдиний процес, що записує дані до канонічного сховища блокчейна (RocksDB). Стежить за вузлом, обробляє реорганізації, підтримує актуальний стан мемпулу |
| `zinder-projector` | Єдиний процес, що записує дані до сховища гаманця. Створює та оновлює представлення блокчейна у форматі, потрібному гаманцю |
| `zinder-query` | Надає нативний gRPC API `WalletQuery` |
| `zinder-compat-lightwalletd` | Надає API `CompactTxStreamer` від lightwalletd на основі тих самих даних |

Необов’язковий рівень оглядача (`zinder-explorer` разом із `ExplorerQuery`) надає зведення блоків, подробиці транзакцій, перегляд мемпулу та пошук. Окремий необов’язковий адаптер надає REST API та API WebSocket для оглядача CipherScan. Жоден із них не входить до образів випуску.

Кожне середовище виконання надає `/healthz`, `/readyz` і `/metrics`. Читачі повідомляють про готовність лише тоді, коли їхні копії сховища блокчейна та сховища гаманця вказують на той самий стан блокчейна.

## Способи підключення

* **Наявні легкі гаманці** зберігають свою інтеграцію з lightwalletd і підключають її до `zinder-compat-lightwalletd`. У документації Zinder розрізняються сумісність протоколу та підтримка: гаманець вважається підтримуваним лише після того, як його поточний випуск пройде наскрізну сертифікацію. У випуску 0.10.0 виправлено поле версії протоколу `GetLightdInfo`, тож Zingo може синхронізуватися.
* **Нативні клієнти** звертаються до `zinder-query` по прив’язані до стану блокчейна дані, компактні блоки, потоки подій блокчейна й мемпулу, а також результати надсилання транзакцій із типізованими причинами відхилення.
* **Застосунки Rust** використовують крейт `zinder-client` — SDK, орієнтований на віддалене підключення, який з’єднується з `zinder-query` без підключення до стека сховища.
* **Оглядачі та серверні системи** поєднують дані гаманця з необов’язковим рівнем `ExplorerQuery`.

## Запуск

У короткому посібнику upstream спершу запускають вузол зі стеком [Z3](/zcash-tech/z3-stack), а потім Zinder за допомогою Docker Compose з копії репозиторію Zinder:

```bash
# In the Z3 checkout
Z3_NETWORK=testnet docker compose up -d

# In the Zinder checkout
docker compose --env-file deploy/.env.testnet \
  -f deploy/docker-compose.yml up -d --build
```

Поруч розміщені файли змінних середовища для Mainnet і вузла Zakura (`deploy/.env.zakura-mainnet`, `deploy/.env.zakura-testnet`). Починаючи з 0.11.0 файл Compose більше не передбачає використання Z3: у файлі змінних середовища потрібно вказати мережу вузла, том із файлом cookie та адресу RPC.

Типові порти на хості (для Testnet до кожного додається 10000):

| Служба | Mainnet | Testnet |
|:--|:--|:--|
| Нативний gRPC `WalletQuery` | 9102 | 19102 |
| gRPC, сумісний із lightwalletd | 9067 | 19067 |
| Готовність: ingest / projector / query / compat | 9105 / 9110 / 9106 / 9107 | 19105 / 19110 / 19106 / 19107 |

Обидва порти гаманця прив’язані до loopback. Перевірте їх так:

```bash
grpcurl -plaintext -d '{}' 127.0.0.1:19102 zinder.v1.wallet.WalletQuery/ServerInfo
grpcurl -plaintext -d '{}' 127.0.0.1:19067 cash.z.wallet.sdk.rpc.CompactTxStreamer/GetLightdInfo
```

Інші способи розгортання:

* **Образи випуску** на `ghcr.io/zcashfoundation/`: чотири середовища виконання, а також `zinder-wallet-serving` (ingest, projector і native query в одному контейнері для хостів, які можуть під’єднати один том до одного контейнера; без адаптера lightwalletd) і `zinder-canonical-runtime` (лише ingest).
* **Бінарні файли Linux** для x86-64 (потрібен процесор x86-64-v3) та AArch64, із glibc версії 2.34 або новішої. Сертифікований мінімальний рівень — Debian 12. Кожен випуск містить SBOM та підписані відомості про походження SLSA.

### Що має надавати вузол

* **Архівний вузол.** Починаючи з 0.11.0, `zinder-ingest` відмовляється запускатися з вузлом зі скороченою історією.
* Zebra **7.0.0** або Zakura **1.8.6**. Це дві версії вузлів, сертифіковані для відповідних гілок випусків.
* Для образу `zinder-wallet-serving` потрібна **кінцева точка gRPC індексатора** вузла (`ZINDER_NODE__INDEXER_GRPC_ADDR`, Zebra `indexer_listen_addr`, порт 8155 у Mainnet). Для індексатора Zakura, доступного не через loopback-адресу, потрібен взаємний TLS, який підтримується в Zinder починаючи з 0.11.0.

### Ресурси для Mainnet

Згідно з інструкцією для обслуговування гаманців:

* Щонайменше **8 ГБ пам’яті**. Виміряні пікові значення: ingest — близько 2,6 ГіБ, projector — близько 2,7 ГіБ під час побудови, query — до приблизно 1,4 ГіБ.
* Під час побудови сховища гаманця Mainnet на томі має залишатися близько **130 ГБ вільного місця**.
* Один виміряний випадок побудови Mainnet від генезису тривав близько **чотирьох годин** для сховища блокчейна (проміжні дані займали майже 310 ГБ) і **понад дві години** для сховища гаманця. Встановлених строків побудови вистачає лише для Testnet: збільште їх щонайменше до 24 годин і 12 годин для Mainnet, інакше побудова перезапускатиметься й ніколи не завершиться.

## Поширені помилки

**Сприймати його як готове до промислового використання програмне забезпечення.** Проєкт називає себе альфа-версією. За словами самого проєкту, успішне локальне розгортання Compose «саме по собі не є сертифікацією для промислового використання».

**Підключати його до вузла зі скороченою історією.** Ingest завершує роботу під час запуску. Використовуйте архівний вузол Zebra або Zakura.

**Відкривати порти gRPC безпосередньо в інтернет.** Обидва порти гаманця прив’язані до loopback не просто так. Перш ніж відкривати їх в інтернет, додайте TLS, автентифікацію, обмеження частоти запитів і квоти на контрольованому вами проксі.

**Оновлювати середовища виконання по одному.** У кількох випусках змінюється редакція нативного протоколу або формат сховища. Оновлюйте всі служби Zinder разом і в тому самому вікні перемикання оновлюйте нативні клієнти.

**Вважати гаманець підтримуваним лише через сумісність протоколу.** Адаптер lightwalletd працює з протоколом, але Zinder заявляє про підтримку конкретного гаманця лише після наскрізної сертифікації його поточного випуску.
