# 거래정보 보호 프로토콜의 처음부터 끝까지
##### [Annkkitaaa](https://github.com/Annkkitaaa)의 원문 연구

![alt text](/content-images/image-27-4094293ec0.webp)

### 모든 요소를 하나의 프라이빗 Zcash 거래로 조립하기

> **시리즈:** *Zcash 기초부터* . **제6편 . 거래정보 보호 프로토콜** (마지막 편)
> **대상:** 0편부터 5편까지 읽은 입문자. 이 글에서는 모든 내용이 하나로 연결됩니다.
> **이 글을 읽고 나면:** 시리즈에서 다룬 모든 개념이 제자리를 찾고 0편에서 제기된 모든 의문이 풀리는, 거래정보 보호 Zcash 거래에 대한 완전하고 정확한 이해를 갖추게 됩니다.

[0편](article-0-shielded-transaction.md)에서는 공개 게시판에 놓인 봉인된 봉투에 관한 이야기와 역설로 시작했습니다. 그런 다음 5편에 걸쳐 유한체, 타원곡선, 커밋먼트, Merkle 트리, 영지식 증명 등 여러 요소를 하나씩 살펴봤습니다. 이제 이 모든 것을 결합해 실제 프라이빗 결제가 처음부터 끝까지 어떻게 이루어지는지 살펴보겠습니다.

---

## 1. 왜 관심을 가져야 할까요?

각각의 요소만 보면 지금까지 배운 내용은 꽤 영리합니다. 하지만 Zcash의 *마법*은 이 요소들이 어떻게 맞물리는지에 있습니다. Nullifier 하나만으로는 프라이버시를 보장하지 못합니다. 커밋먼트 하나만으로는 위조를 막지 못합니다. 증명 하나만으로는 유용한 사실을 증명하지 못합니다. 5가지 구성 요소를 프라이빗하면서도 신뢰할 수 있는 돈으로 바꾸는 것은 바로 **조립**입니다.

이 글에서는 그 조립 과정을 살펴봅니다. 다 읽고 나면 *“네트워크는 볼 수 없는 거래를 검증한다”*라는 문장이 역설이 아니라, 이미 이해한 여러 요소에서 자연스럽게 따라 나오는 결론으로 느껴질 것입니다.

---

## 2. 다시 조립해 보는 구성 요소

0편의 이야기 속 요소를 실제 작동 방식에 대응시켜, 시리즈 전체를 한 페이지에 정리했습니다.

| 0편 이야기 속 요소 | 실제 구성 요소 | 구성 방식 |
|---|---|---|
| 봉투 안의 돈 | **노트** (금액, 수신자, 무작위 값) | 필드 요소로 인코딩 (1편) |
| 불투명하게 봉인된 봉투 | **노트 커밋먼트** | Pedersen / Sinsemilla 커밋먼트 (2편, 3편) |
| 공개 게시판 | **노트 커밋먼트 트리** (앵커 = 루트) | 증분형 Merkle 트리 (4편) |
| 무효 토큰 | **Nullifier** | 노트와 비밀 키를 입력으로 하는 ZK 친화적 해시 (2편, 3편) |
| “들어온 돈과 나간 돈은 같다” | **가치 커밋먼트 + 잔액 확인** | 동형사상적 Pedersen 커밋먼트 (2편, 3편) |
| 장막 뒤의 마법 | **영지식 증명** | 산술 회로에 대한 zk-SNARK (5편) |
| “봉투는 본인만 읽을 수 있다” | **암호화된 노트 + viewing key** | 암호화 + 키 계층 구조 (이 글) |

## 3. 키는 어디서 만들어질까요?

사용자가 할 수 있는 모든 일은 단 하나의 비밀인 **spending key**에서 시작해 단방향 계층 구조를 따라 이어집니다. (각 화살표는 되돌릴 수 없는 파생을 나타내며, 이는 2편과 3편에서 살펴본 트랩도어 덕분입니다.)

![alt text](/content-images/image-32-f443f9bb72.webp)

앞서 살펴본 내용에서 비롯되는 중요한 점이 2가지 있습니다.

- 키를 분리하면 **viewing key**를 다른 사람에게 넘겨줄 수 있습니다. 예를 들어 감사인에게 이를 제공하면 자금을 쓸 권한은 주지 않고 거래만 공개할 수 있습니다. 프라이버시는 전부 아니면 전무가 아니라 선택적으로 제공할 수 있습니다.
- 각 파생은 **단방향**입니다. viewing key를 갖고 있어도 spending key를 알아낼 수 없습니다. 2편에서 살펴본 타원곡선 트랩도어가 바로 이렇게 작동합니다.

---

## 4. 노트 사용하기: 4가지 주장

노트를 프라이빗하게 사용하려면 노트, 금액, 위치, 신원을 공개하지 **않고도** 네트워크가 4가지 사실을 동시에 받아들이도록 해야 합니다. 각 주장은 이미 살펴본 구성 요소로 성립합니다.

![alt text](/content-images/image-31-86309af194.webp)

증명은 바탕이 되는 사실, 즉 어떤 노트인지, 누구의 키인지, 금액이 얼마인지 **전혀** 공개하지 않습니다. *4가지 주장이 모두 성립한다는 점만* 보여줍니다. 이것이 하나의 다이어그램으로 정리한 거래정보 보호 Zcash의 핵심입니다.

## 5. 가치 잔액 확인의 비결 (마지막을 위해 남겨 둔 핵심)

2편과 3편에서는 Pedersen 커밋먼트가 **서로 더해진다**고 설명했습니다. `v_1`에 대한 커밋먼트와 `v_2`에 대한 커밋먼트를 더하면 `v_1 + v_2`에 대한 커밋먼트가 됩니다. 이 속성이 여기서 쓰입니다.

모든 입력 노트와 출력 노트에는 **가치 커밋먼트**가 들어갑니다. 이는 금액 `v`을 숨기는 Pedersen 커밋먼트 `v.G + r.H`입니다. 이 커밋먼트들을 더할 수 있으므로 네트워크는 다음을 계산할 수 있습니다.

```
(sum of input value commitments) − (sum of output value commitments)
```

거래의 잔액이 맞으면, 즉 돈이 새로 생기거나 사라지지 않으면 `v` 부분은 정확히 상쇄되어, 남은 무작위 값으로 가려진 **0의 가치**에 대한 커밋먼트만 남습니다. 송신자는 잔여 무작위 값을 알고 있음을 **바인딩 서명**이라는 짧은 서명을 만들어 증명합니다. 유효한 바인딩 서명은 금액의 잔액이 실제로 맞을 때만 만들 수 있지만, **어떤 금액도 공개되지 않습니다.**

> 동형사상적 곡선 기반 커밋먼트가 *왜* 필요한지 시리즈 전체에서 가장 명확하게 보여주는 사례입니다. “들어온 돈과 나간 돈은 같다”는 규칙은 **봉인된 봉투를 서로 더한 뒤** 그 결과가 0으로 봉인되는지 확인하는 방식으로 강제됩니다.

## 6. 실제 거래를 처음부터 끝까지 살펴보기

Alice가 Bob에게 결제하는 과정을 조립해 보겠습니다. 학습을 위해 명확하게 구분된 “사용 측 / 출력 측” 구조를 가진 Sapling를 모델로 사용하겠습니다.

**거래정보 보호 거래에는 2가지 설명이 포함됩니다.**

| 사용 설명 (노트를 소비함) | 출력 설명 (노트를 생성함) |
|---|---|
| 입력의 가치 커밋먼트 | 출력의 가치 커밋먼트 |
| 증명의 기준이 되는 **앵커** (트리 루트) | 새 **노트 커밋먼트** (새 리프) |
| 사용한 노트의 **nullifier** | 암호화에 사용할 **임시 키** |
| 재무작위화된 공개 키 + 사용 권한 서명 | **암호화된 노트** (수신자가 받을 암호문) |
| 4가지 주장을 증명하는 **zk-SNARK** | 출력이 올바른 형식임을 증명하는 **zk-SNARK** |

여기에 번들 전체의 가치 잔액을 강제하는 **바인딩 서명** 하나가 더해집니다 (5절).

![alt text](/content-images/image-30-98511eb2d0.webp)

프라이버시가 어떻게 지켜지는지 살펴보겠습니다. 네트워크는 앵커를 확인하고 nullifier가 새것인지 확인한 다음, 증명을 검증하고 잔액을 확인했습니다. 그 결과 금액도 주소도 어떤 노트를 사용했는지도 알지 못한 채 유효한 결제를 승인했습니다. 한편 사용된 노트의 **nullifier** (그 노트의 죽음)와 Bob의 새 **커밋먼트** (그의 노트의 탄생)는 서로 다른 2개의 공개 구조에 기록되고, 둘 사이의 연결은 드러나지 않습니다. 이것이 0편에서 끊어 놓은 연결입니다.

## 7. 0편에서 시작된 모든 의문 풀기

0편에서는 일부러 질문을 던졌습니다. 이제 그 질문에 모두 답해 보겠습니다.

| 0편에서 제기한 의문 | 답 |
|---|---|
| 봉인되어 있지만 위조할 수 없는 봉투는 어떻게 가능할까요? | 커밋먼트: 무작위 값으로 내용을 숨기고, 충돌 저항성 / 곡선 트랩도어로 내용을 고정합니다 (3편). |
| 키와 비밀 레시피는 어디서 만들어질까요? | 필드 산술과 타원곡선 스칼라 곱셈입니다 (1편, 2편). |
| “게시판”은 정확히 무엇인가요? | 노트 커밋먼트를 담는 증분형 Merkle 트리이며, 루트가 앵커입니다 (4편). |
| 무효 토큰을 봉투와 연결할 수 없는 이유는 무엇인가요? | Nullifier는 커밋먼트와 별도의 집합에 보관되는 키 기반 해시입니다 (2편, 3편, 4편). |
| 아무것도 공개하지 않고 유효성을 어떻게 증명할까요? | 4가지 주장을 모두 인코딩한 산술 회로에 대한 zk-SNARK입니다 (5편). |
| 수신자는 결제를 받았다는 사실을 어떻게 알까요? | 노트는 수신자의 주소를 대상으로 암호화되며, 수신자는 viewing key로 시험 복호화를 합니다 (이 글). |
| “들어온 돈 = 나간 돈”을 프라이빗하게 어떻게 강제할까요? | 동형사상적 가치 커밋먼트와 바인딩 서명을 사용합니다 (5절). |

첫 페이지에서 제시한 역설, *볼 수 없는 것을 검증하라*는 이제 완전히 풀렸습니다. 네트워크는 **숨겨진 데이터에 관한 주장**을 검증할 뿐, 데이터 자체는 들여다보지 않습니다.

## 8. Sapling와 Orchard, 한눈에 비교하기

구조가 가장 명확하게 나뉘는 Sapling를 학습 모델로 사용했습니다. 현재 설계인 **Orchard**은 이러한 개념을 대체하지 않고 개선합니다.

| | **Sapling** | **Orchard** |
|---|---|---|
| 거래 단위 | 별도의 **사용** 및 **출력** 설명 | 하나의 **액션** (각 액션은 노트 하나를 사용하고 노트 하나를 출력함) |
| 증명 시스템 | **Groth16** (트러스트 셋업 사용) | **Halo 2** (트러스트 셋업 불필요) |
| 곡선 | BLS12-381 + Jubjub | Pallas / Vesta (Pasta) |
| 커밋먼트 해시 | Pedersen | Sinsemilla |

이 글의 모든 개념은 그대로 적용됩니다. Orchard는 주로 사용과 출력을 하나로 묶고, 별도의 의식이 필요 없는 증명 시스템을 도입합니다. 5가지 핵심 원리는 변하지 않습니다.

## 9. 솔직한 면책 고지

이 글은 시리즈에서 가장 완전한 그림을 보여주지만, 여전히 하나의 모델입니다. 노트의 정확한 필드 인코딩, 정밀한 키 파생 공식, 사용 키의 재무작위화, 다각화 주소, 메모 필드, 수수료 처리, 가치 커밋먼트와 노트 커밋먼트의 차이에 관한 세부 사항, 각 서명의 정확한 역할을 간략히 다뤘습니다. 또한 대표적인 하나의 흐름만 소개했습니다. 실제 거래에는 여러 사용과 출력이 동시에 포함될 수 있으며, 투명한 부분과 거래정보 보호 부분이 함께 들어갈 수도 있습니다. 권위 있는 자료는 Zcash 프로토콜 명세서입니다. 이제 기본 구조를 이해하셨으며, 명세서에서 세부 사항을 모두 확인할 수 있습니다.

## 10. 요약

- 거래정보 보호 거래는 5가지 구성 요소를 하나로 엮습니다. **노트** (가치), **노트 커밋먼트 트리**에 저장되는 노트의 **커밋먼트**, 이중 사용을 막는 **nullifier**, 잔액을 맞추는 **가치 커밋먼트**, 그리고 이 모든 요소를 결합하는 **zk-SNARK**입니다.
- 노트를 사용할 때는 4가지 주장, 즉 노트가 존재하고, 사용 권한이 있으며, nullifier가 올바르고, 가치 잔액이 맞다는 점을 **영지식**으로 한꺼번에 증명합니다. 바탕이 되는 사실은 전혀 공개하지 않습니다.
- **가치 잔액**은 **동형사상적 커밋먼트를 더해** 결과가 0으로 봉인되는지 확인하고, 이를 **바인딩 서명**으로 증명하는 방식으로 강제됩니다. 금액은 공개되지 않습니다.
- 사용자의 권한은 하나의 **spending key**에서 **단방향 계층 구조**를 따라 파생되므로, 사용 권한을 주지 않고 정보를 공개하는 **viewing key**를 만들 수 있습니다.
- 네트워크는 **숨겨진 데이터에 관한 주장을 검증**하므로 0편에서 제시한 검증과 프라이버시의 역설이 해소됩니다. 0편에서 시작된 모든 의문이 이제 풀렸습니다.
- **Orchard**은 **Sapling**을 개선합니다. 액션을 하나로 통합하고, 트러스트 셋업이 필요 없는 Halo 2, Pasta 곡선, Sinsemilla를 사용하지만 5가지 핵심 원리는 바뀌지 않습니다.

## 용어집

| 용어 | 쉬운 설명 |
|---|---|
| **Spending key** | 사용자의 모든 키가 파생되는 단일 루트 비밀 값 |
| **Viewing Key** | 보유자에게 거래를 공개하지만 자금을 사용할 권한은 주지 않는 키 |
| **Spend description** | 노트를 소비하는 거래 부분 (nullifier, 앵커, 증명) |
| **Output description** | 노트를 생성하는 거래 부분 (커밋먼트, 암호문, 증명) |
| **Action (Orchard)** | 노트 하나를 사용하고 노트 하나를 함께 출력하는 통합 단위 |
| **Value commitment** | 금액에 대한 동형사상적 Pedersen 커밋먼트 |
| **Binding signature** | 금액을 공개하지 않고도 가치의 잔액이 맞음을 증명하는 서명 |
| **Anchor** | 사용한 노트가 트리에 포함되어 있음을 증명할 때 기준으로 삼는 트리 루트 |
| **Trial decryption** | 수신자가 자신에게 온 노트를 찾기 위해 새 커밋먼트를 시험해 복호화하는 과정 |

## 자주 묻는 질문

**네트워크는 금액이나 누가 누구에게 결제했는지 알 수 있나요?**
아니요. 네트워크는 증명, nullifier의 최신 여부, 앵커, 바인딩 서명을 검증합니다. 모든 비공개 값은 숨겨집니다.

**노트를 두 번 사용하는 것을 어떻게 막나요?**
Nullifier가 막습니다. 노트를 사용하면 nullifier가 공개되고, 네트워크는 nullifier 집합에 이미 있는 nullifier를 거부합니다. 같은 노트에서는 언제나 같은 nullifier가 나옵니다.

**금액이 숨겨져 있는데 잔액을 어떻게 확인할 수 있나요?**
가치 커밋먼트는 동형사상적으로 더해집니다. 잔액이 맞는 거래에서는 커밋먼트가 상쇄되어 0에 대한 커밋먼트가 되고, 바인딩 서명이 이를 증명합니다.

**통제권을 넘기지 않고 감사인에게 거래 내역을 증명할 수 있나요?**
네. viewing key를 건네주시면 됩니다. 단방향 키 계층 구조 덕분에 거래정보 보호 활동은 공개되지만, 해당 키로 자금을 사용할 수는 없습니다.

**Orchard가 생긴 지금 Sapling은 더 이상 쓰이지 않나요?**
둘 다 네트워크에서 사용되어 왔으며, Orchard가 현재 설계입니다. 두 방식의 개념은 공통되므로 하나를 이해하면 다른 하나도 이해할 수 있습니다.
