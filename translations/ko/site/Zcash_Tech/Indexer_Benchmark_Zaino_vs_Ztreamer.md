# 인덱서 벤치마크: Zaino vs Ztreamer

Zaino와 Ztreamer는 라이트월렛 gRPC 프로토콜을 제공하는 두 인덱서입니다. 이 프로토콜은 Zcash 라이트 지갑이 동기화할 때 사용합니다. 이 페이지에서는 두 인덱서를 독립적이고 재현 가능한 방식으로 비교한 결과를 요약합니다. 동일한 응답을 반환하는지, 인덱스를 구축하는 데 얼마나 걸리는지, 지갑에 응답하는 속도는 어떤지 살펴봅니다.

## 요약

* 두 인덱서 모두 정확한 체인 데이터를 반환합니다. Zebra와 대조해 확인할 수 있었던 모든 응답이 일치했으므로, 지갑은 둘 중 어느 인덱서든 사용할 수 있습니다.
* 확인된 차이는 관례와 예외 사례에 해당합니다. 오류 코드, 해시 1개의 바이트 순서, 중복 주소의 집계 방식, 몇 가지 JSON-RPC 응답 형식이 다릅니다.
* Ztreamer는 같은 CPU에서 인덱스를 약 6배 더 빠르게 구축합니다. 구축 중에는 요청을 Zebra로 전달해 Zaino가 6초 만에 응답을 시작합니다.
* 측정한 모든 시나리오에서 Ztreamer가 더 빠르게 응답합니다. 전체 지갑 다운로드 시 초당 블록 수가 13~17배 많습니다.
* Zaino의 지연 시간 중 상당 부분은 소켓 설정 하나(`TCP_NODELAY`)가 누락되어 발생하며, 이로 인해 여러 요청에 약 40ms가 추가됩니다. 한 줄만 수정하면 해결할 수 있습니다.

## 비교 대상

| 빌드 | 기반 노드 | 이유 |
|:--|:--|:--|
| Zaino 0.10.1 | Zebra 6.4.2 (`direct` 백엔드) | 최신 안정 Zaino 릴리스 |
| Zaino 0.9.0 | Zebra 6.4.2 (`direct` 백엔드) | Ztreamer가 자체 공개 비교에서 측정한 버전 |
| Ztreamer v0.1.0 | 내장 Zakura 노드 | 최신 Ztreamer 태그 |
| Ztreamer master | 내장 Zakura 1.5.1 | Ztreamer의 설치 안내에 따라 빌드되는 버전 |

두 인덱서는 서로 다른 설계를 사용합니다.

* **Zaino**는 [Zebra](Zebra_Full_Node.md) 풀 노드 옆에서 별도 프로세스로 실행되고, Zebra의 상태를 읽어 자체 인덱스를 유지합니다. [Z3 스택](Z3_Stack.md)의 인덱서입니다. 자세한 내용은 [Zaino](Zaino.md)를 참조하세요.
* **Ztreamer**는 같은 프로세스에 Zebra 포크인 [Zakura](Zakura_Node.md) 노드를 내장하고, 컴팩트 블록 인덱스를 유지합니다.

## 측정 방법

* **모두 같은 데이터를 사용했습니다.** 모든 빌드는 높이 4,382,897에서 고정한 동일한 Zcash Foundation 테스트넷 스냅샷으로 시작했으므로, 모두 정확히 같은 체인을 인덱싱했습니다.
* **누구나 재현할 수 있습니다.** 모든 작업은 무료 GitHub 호스팅 러너에서 실행됩니다. 저장소를 포크하고 워크플로 하나를 실행하면 됩니다.
* **각 빌드별로 3회 실행**했으며, 매번 빈 인덱스에서 시작했습니다. 서버와 부하 생성기는 서로 다른 CPU 코어에서 실행했습니다.
* **호환성:** 라이트월렛 프로토콜의 gRPC 메서드 20개(테스트 사례 274개)를 바이트 단위로 비교하고, Zebra의 JSON-RPC와 대조했습니다. Zaino가 제공하는 JSON-RPC 메서드 28개도 확인했습니다.
* **성능:** 인덱스 구축 시간과 리소스, 요청별 지연 시간, 블록 범위 처리량, 동시 클라이언트 1~128개, Sapling 활성화 시점부터 최신 블록까지의 전체 지갑 다운로드를 측정했습니다.

## 결과

### 인덱스 구축

3회 실행의 중앙값입니다.

| 빌드 | 인덱스 완료 | 첫 응답 | 디스크상의 인덱스 크기 |
|:--|--:|--:|--:|
| Zaino 0.10.1 | 1,395초 | 6초 | 22.06GiB |
| Zaino 0.9.0 | 1,211초 | 6초 | 22.06GiB |
| Ztreamer v0.1.0 | 216초 | 210초 | 1.44GiB |
| Ztreamer master | 159초 | 158초 | 1.44GiB |

Zaino는 인덱스를 구축하는 동안 요청을 Zebra로 전달하므로 거의 즉시 사용할 수 있습니다. Ztreamer는 인덱스 구축이 완료되기 전까지 아무 응답도 제공하지 않습니다. 같은 CPU 모델에서 Zaino 0.10.1은 Ztreamer v0.1.0보다 6~6.5배 더 오래 걸렸고, CPU 시간도 7.5~8배 더 사용했습니다(Zebra 포함).

### 응답 성능

3회 실행의 중앙값입니다. 별도 표기가 없는 경우 초당 블록 수입니다.

| 시나리오 | Zaino 0.10.1 | Ztreamer v0.1.0 |
|:--|--:|--:|
| 블록 1,000개 범위 조회 | 11,414 | 179,486 |
| 전체 지갑 다운로드 (280,000 → 최신 블록) | 11,124 | 189,041 |
| 클라이언트 128개로 블록 1,000개 범위 조회 | 110,093 | 229,527 |
| 클라이언트 128개로 단일 블록 조회 (초당 요청 수) | 6,843 | 11,044 |

클라이언트가 128개일 때는 두 서버 모두 CPU 코어 2개만 사용할 수 있어 차이가 약 2배로 줄어듭니다.

### 40ms 지연 시간 하한

Zaino에서는 RPC 12개 중 6개의 중앙값 지연 시간이 약 40ms이며, 모든 RPC의 99번째 백분위 지연 시간은 약 41ms입니다. 원인은 Zaino가 gRPC 리스너를 설정하는 방식입니다. `TCP_NODELAY` 소켓 옵션이 활성화되지 않아 운영체제가 작은 응답을 최대 40ms 동안 보류합니다.

Zaino 바이너리를 변경하지 않고 외부에서 해당 옵션을 활성화하자 지연 시간 하한이 사라졌습니다. 예를 들어 `GetTreeState`는 40.3ms에서 0.75ms로 줄었습니다(Ztreamer: 0.63ms). 대량 블록 스트리밍은 달라지지 않았으므로, 위에서 확인한 처리량 차이는 실제 성능 차이입니다.

### 호환성 차이

* **Zaino 0.9.0**은 기본적으로 `GetBlock`에 투명 데이터를 포함합니다. 하지만 프로토콜에서 지정한 기본값은 거래정보 보호 데이터만 포함하는 것입니다. 이 문제는 0.10.1에서 수정되었습니다.
* **`GetSubtreeRoots`:** `completingBlockHash` 필드의 바이트 순서가 두 인덱서에서 서로 반대입니다. 현재 지갑은 이 필드를 읽지 않습니다.
* **오류 코드:** Zaino는 잘못된 입력에 `INTERNAL`를 반환하고, Ztreamer는 `INVALID_ARGUMENT` 또는 `NOT_FOUND`를 반환합니다.
* **중복 주소:** `GetTaddressBalanceStream`에서는 중복 주소를 2회 집계하지만, Ztreamer master에서는 그렇지 않습니다.
* **JSON-RPC:** Zaino의 `getrawtransaction`은 verbosity 0일 때 16진수 문자열이 아닌 객체를 반환합니다. Zebra 및 zcashd와 다릅니다.

## 제한 사항

* **테스트넷만 사용했습니다.** 테스트넷 블록은 메인넷 블록보다 작으므로, 절대 시간과 크기는 메인넷의 수치가 아닙니다. 동일한 입력을 사용해 상대적인 성능을 비교했습니다.
* **여러 CPU 모델을 사용하는 공유 CI 머신**에서 실행했습니다. 주요 수치에 대한 동일 CPU 비교는 전체 보고서에 나와 있습니다.
* **측정하지 않은 항목:** 리오그, 라이브 체인의 최신 블록 따라잡기, 메모리풀 부하, TLS입니다.
