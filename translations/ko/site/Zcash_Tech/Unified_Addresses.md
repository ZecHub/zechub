# 통합 주소(ZIP-316) 검증

*이 문서는 학습 안내서이며, 패키지로 제공되는 디코더나 복사해 붙여 넣어 사용할 수 있는 결제 라이브러리가 아닙니다. 통합 주소의 구조를 설명하여 관리되는 라이브러리가 내부에서 어떻게 작동하는지 이해할 수 있도록 돕습니다. 실제 자금을 다루는 경우에는 아래에 링크된 [ZIP-316 사양](https://zips.z.cash/zip-0316)과 공식 구현을 따르십시오.*

---

## 전체 개요

통합 주소(UA)는 여러 수신자 유형인 **투명**, **Sapling**, **Orchard** 또는 이들의 조합을 담는 단일 주소 문자열입니다. 결제하는 지갑은 지원하는 수신자 풀 중 가장 적합한 것을 자동으로 선택합니다.

통합 주소를 여러 장의 이름표가 붙은 카드가 들어 있는 봉인된 봉투라고 생각해 보십시오. 각 카드는 사용자에게 도달하는 서로 다른 방법을 나타냅니다. 주소를 확인하려면 애플리케이션이 다음을 수행해야 합니다.

1. **봉투 열기:** 텍스트 문자열을 디코딩합니다.
2. **내용물 풀기:** 보호를 위해 뒤섞인 내용(**F4Jumble**)을 원래대로 되돌립니다.
3. **각 카드 읽기:** 개별 수신자를 추출합니다.
4. **프로토콜 규칙 적용:** 유형 코드 범위에 따라 항목을 무시하거나 거부합니다.

---

## “”Bech32m만 디코딩하면”” 충분하지 않은 이유

통합 주소는 Bech32m 텍스트 인코딩을 사용하지만, Bech32m만 디코딩해서는 사용할 수 있는 수신자를 확인할 수 없습니다.

ZIP-316은 인코딩하기 전에 **F4Jumble**을 사용해 페이로드를 의도적으로 뒤섞습니다. F4Jumble은 주소에서 문자 하나만 바뀌어도 디코딩 결과 전체가 달라지도록 합니다. 따라서 공격자가 주소의 접두부와 접미부는 유효해 보이도록 유지하면서 중간의 바이트를 바꾸는 주소 변조 공격을 방지합니다.

> **핵심 규칙:** 주소 변조 방지는 애플리케이션이 전체 디코딩 및 검증 절차를 실행해야만 작동합니다. 일부만 디코딩하면 위험은 그대로 둔 채 안전성만 사라집니다.

---

## 단계별 디코딩 절차

### 1단계: Bech32m을 디코딩하고 네트워크 확인
- **사람이 읽을 수 있는 부분(HRP):** `u`은 메인넷을 나타내고, `utest`은 테스트넷을 나타냅니다. *(메인넷 통합 주소는 `u1`로 시작하며, 여기서 `1`은 Bech32 구분자입니다.)*
- **길이 제한:** 표준 Bech32m은 90자 길이 제한을 적용합니다. 통합 주소는 대개 이 제한을 초과하므로 디코더에서 표준 길이 검사를 비활성화해야 합니다.
- Bech32m의 5비트 단어를 표준 8비트 바이트로 다시 변환합니다.

### 2단계: F4Jumble 되돌리기
F4Jumble은 BLAKE2b를 기반으로 하는 4라운드 Feistel 네트워크입니다.
- **왼쪽 절반 길이:** `min(64, floor(length / 2))`바이트입니다. 64바이트 상한은 BLAKE2b의 최대 출력 크기에 해당합니다. 오른쪽 절반에는 나머지 페이로드가 들어 있습니다.
- **해시 함수:** 고정 개인화 레이블(`UA_F4Jumble_G` 및 `UA_F4Jumble_H`)을 사용하여 G와 H를 번갈아 적용합니다.
- **라운드 순서:** 정방향 인코딩은 G(0) → H(0) → G(1) → H(1) 순으로 실행합니다. 역방향(뒤섞인 내용 복원)은 H(1) → G(1) → H(0) → G(0) 순으로 실행합니다.
- **범위 확인:** ZIP-316 페이로드 크기 제한을 벗어난 입력은 거부합니다.

### 3단계: 패딩을 제거하고 HRP 확인
뒤섞기 전에 인코더는 HRP를 담고 0으로 패딩한 16바이트를 덧붙입니다.
- 뒤섞인 내용을 복원한 후 마지막 16바이트를 제거합니다.
- 포함된 HRP가 예상 네트워크(`u` 또는 `utest`)와 일치하는지 확인합니다. 이를 통해 테스트넷 주소가 실수로 메인넷에서 허용되는 것을 방지합니다.

### 4단계: 수신자 추출
나머지 페이로드는 `(typecode, length, content)` 항목으로 구성되며, 유형 코드와 길이는 컴팩트 크기 정수(작은 값은 1바이트)로 저장됩니다. 알려진 수신자 유형 코드는 다음과 같습니다.

| 유형 코드 | 수신자 유형        | 콘텐츠 길이 |
| :------- | :------------------ | :------------- |
| `0x00`   | 투명(P2PKH) | 20바이트       |
| `0x01`   | 투명(P2SH)  | 20바이트       |
| `0x02`   | Sapling             | 43바이트       |
| `0x03`   | Orchard             | 43바이트       |

이 외에도 ZIP-316은 향후 호환성을 위해 2개의 범위를 추가로 예약합니다.

- **`0xC0`–`0xDF`(반드시 이해하지 않아도 되는 메타데이터):** 소비자는 이 범위에 있는 항목 중 인식하지 못하는 메타데이터를 무시해야 합니다.
- **`0xE0` 및 `0xE1`(할당된 필수 이해 만료 메타데이터):** 현재 ZIP-316 레지스트리는 이 유형 코드를 주소 만료 높이와 시간에 할당합니다. 소비자는 이 항목을 이해해야 하며, 그렇지 않으면 주소를 거부해야 합니다.
- **`0xE2`–`0xFC`(할당되지 않은 필수 이해 메타데이터):** 소비자는 이 범위에서 인식할 수 없는 항목을 발견하면 주소를 거부해야 합니다.

알려진 수신자 유형의 경우, 인코딩된 길이가 해당 유형에 지정된 콘텐츠 길이와 일치하는지 확인합니다. 메타데이터 항목의 경우, 인코딩된 컴팩트 크기 길이를 사용해 콘텐츠 길이를 확인합니다. 잘린 항목이나 뒤에 남는 바이트가 있으면 거부합니다.

**선호하는 수신자 순서.** 주소를 성공적으로 파싱한 후 지갑이나 결제 도구는 다음 순서에 따라 가장 적합한 수신자를 선택해야 합니다. Orchard, 그다음 Sapling, 마지막으로 투명 수신자입니다.

## 필수 ZIP-316 거부 규칙

**성공적으로 디코딩했다고 해서 주소가 유효한 것은 아닙니다.** 공식 Zcash 지갑은 다음 규칙을 위반하는 주소를 엄격하게 거부합니다. 결제 실패를 방지하려면 웹 도구도 해당 주소를 거부해야 합니다.

- **거래정보 보호 수신자 누락:** 주소에는 Sapling 또는 Orchard 수신자가 적어도 1개 있어야 합니다. 투명 수신자만 포함된 통합 주소는 ZIP-316에 따라 유효하지 않습니다.
- **유형 코드 중복:** 각 수신자 유형은 최대 1회만 나타날 수 있습니다.
- **정렬되지 않은 유형 코드:** 수신자는 유형 코드가 엄격하게 오름차순이 되도록 나타나야 합니다.
- **충돌하는 투명 수신자:** 통합 주소에는 P2PKH 또는 P2SH 중 하나만 포함할 수 있으며, **둘 다 포함할 수는 없습니다.**
- **잘못된 항목 또는 패딩:** 네트워크 접두부가 서로 다르거나, 페이로드가 잘렸거나, 길이가 일치하지 않으면 즉시 거부해야 합니다.
- **인식할 수 없는 유형 코드:** 소비자는 필수 이해 메타데이터 범위(`0xE0`–`0xFC`)에 있는 항목을 제외한 미인식 항목은 무시해야 합니다. 해당 범위의 미인식 항목은 거부해야 합니다. 현재 레지스트리에서 `0xE0` 및 `0xE1`는 만료 유형으로 할당되어 있고, `0xE2`–`0xFC`는 할당되지 않았습니다. 이와 별개로 Sapling 또는 Orchard 수신자가 있어야 한다는 요건을 비롯해 위의 필수 유효성 규칙을 충족하지 않는 주소는 모두 거부해야 합니다.

## 개발자를 위한 모범 사례

- **원시 문자열이 아니라 파싱한 수신자를 비교합니다.** 주소를 비교하기 전에 먼저 디코딩합니다.
- **자금을 다루는 경우에는 관리되는 라이브러리를 사용합니다.** 공식 Rust 크레이트(예: `zcash_address`)를 컴파일하여 WebAssembly로 사용하고, 맞춤형 JavaScript 디코더를 배포하지 마십시오.
- **직접 작성한 파서는 신중하게 다룹니다.** 학습을 위해 직접 작성했다면 이를 학습 프로젝트로 취급하고, 실제 작업에 사용하기 전에 아래의 공식 테스트 벡터로 검증합니다.

## 용어집

| 용어 | 의미 |
| :----------------------- | :-------------------------------------------------------------------- |
| **Unified Address (UA)** | 여러 수신자 풀을 하나로 묶은 단일 주소 문자열입니다. |
| **Receiver** | 구체적인 결제 목적지 유형입니다(투명, Sapling 또는 Orchard). |
| **Bech32m** | 통합 주소 문자열에 사용되는 텍스트 인코딩 방식입니다. |
| **HRP** | 사람이 읽을 수 있는 부분 또는 네트워크 접두부입니다(`u` 또는 `utest`). |
| **F4Jumble** | 주소 무결성을 보장하는 가역적 난독화 알고리즘입니다. |
| **Typecode** | 페이로드의 각 항목에서 수신자 유형을 정의하는 숫자입니다. |
| **Malleability** | 감지되지 않은 채 주소 바이트를 무단으로 수정할 수 있는 성질입니다. |
